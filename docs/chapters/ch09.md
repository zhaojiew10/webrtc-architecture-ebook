# 第 9 章 HTTP

超文本传输协议（HTTP，Hypertext Transfer Protocol）是浏览器获取网页和资源的基础。理解 HTTP，既要掌握客户端、服务器、请求与响应这些基本语义，也要看清不同版本如何逐步解决重复建连、请求串行等待和传输层队头阻塞等问题。

## 请求—响应语义

Web 采用客户端—服务器架构。服务器等待传入连接，通常处于被动状态；客户端主动建立连接并发送 HTTP 请求，服务器再在同一连接上返回 HTTP 响应。传统 HTTP 通信都围绕这一次次请求与响应展开，客户端是请求的发起方，服务器负责作答。

早期 HTTP 使用 TCP，原因与其传输需求直接相关：

- **可靠性**：客户端要确认请求被服务器收到，也要确保响应能够回到客户端，不能随意丢失数据。
- **面向连接**：客户端与服务器之间先建立一条可持续传递消息的连接。
- **拥塞控制**：Web 和浏览器中的 HTTP 流量很大，不能让单个用户或应用无节制地占用网络。TCP 内置拥塞控制，HTTP 因而也获得这一能力。

HTTP 使用多种方法（或称动词）表达请求意图：

- `GET` 用于获取网页或其他数据，按语义不应改变服务器上的数据；
- `POST` 用于改变服务器状态；
- 其他方法还包括 `HEAD`、`OPTIONS`、`PUT`、`DELETE` 等，其中 `GET` 和 `POST` 最常见。

早期 HTTP 是基于文本的协议，后续版本是在这一基础上逐步修补和演进而来的。一次 HTTP/1.1 的 `GET` 请求可以带有编码、语言、连接类型、目标主机和 `User-Agent` 等请求头；`User-Agent` 可说明正在使用哪种浏览器。响应则用状态码表达结果，例如 `200 OK` 表示成功，`301 Moved Permanently` 表示永久移动。课程访问博客的示例返回了 301，并经由该博客使用的 Cloudflare CDN 发生重定向。

## HTTP/1.0：每次请求都重新建连

HTTP/1.0 的协议栈可以理解为：IP 之上运行 TCP，TLS 是可选层，最上面是 HTTP/1.0 的请求—响应语义。因此，连接上的数据可以加密，也可以不加密。

它获取资源的基本步骤是：

1. 客户端打开一条到服务器的 TCP 连接；
2. 客户端发送一个请求；
3. 服务器返回响应；
4. 连接关闭；
5. 下一个资源再重复上述过程。

即使最简的 HTML 页面，通常也不只有 HTML 文件本身，还会包含一个 CSS 样式文件和一个 JavaScript 文件，实际页面往往更多。若每个文件都重新建连，TCP 三次握手会反复增加等待时间，服务器也要不断消耗 CPU 来打开和关闭连接。

## HTTP/1.1：复用连接，但请求仍要排队

HTTP/1.1 对网络行为、格式和语义做了多方面修改，其中最关键的是连接复用。客户端建立连接、发送请求并收到响应后，不再立即关闭连接，而是通过保持连接（keep-alive）在同一连接上发送后续请求。这样省去了每个资源都重新建连的成本。

但复用并不等于任意并行。在课程讨论的典型 HTTP/1.1 过程中，客户端发出一个请求后，仍需等待响应，才能继续处理下一个请求。为了获得一些并行度，浏览器可以另外打开客户端到服务器的 TCP 连接，并在各连接上分别发送请求；早期浏览器和服务器对同一服务器允许的并行连接数还很少，课程提到过去常见的是不超过两个。

这一限制在现代页面中变得突出。课程引用的 2016 年数据是：平均一个网页需要 101 个 HTTP 文件请求，分布在 18 个域名上。这意味着至少要连接 18 台不同服务器，再在各连接上处理大量请求。若每个连接都按“请求—等待响应—下一个请求”线性推进，等待时间会不断累积，页面加载随之变慢。

## HTTP/2：在一条连接上并行处理流

HTTP/2 起源于 Google 开发的 SPDY。SPDY 的目标是改进 HTTP/1.1，随后通过 IETF 的标准化工作演进为 HTTP/2。

HTTP/2 引入了流，使同一连接上可以同时处理多个会话，并加入优先级、流量控制和服务器推送。服务器推送意味着服务器可以在预计客户端随后需要某项数据时主动发送它，而不必一直等到客户端明确请求。

其请求—响应过程与 HTTP/1.1 的关键差别是：

1. 客户端建立一条连接并发送第一个请求；
2. 如果已经知道还需要其他资源，可以立即发送第二个及后续请求，不必等第一个响应；
3. 服务器并行处理这些请求，并可按实际完成情况返回响应。

例如，第二个请求对应的文件较小或已经缓存，而第一个请求还需要访问另一台服务器获取信息，服务器就可以先返回第二个响应。客户端不必因为第一个请求尚未完成，而让所有后续请求都停在本地等待。课程中的页面加载对比正是要说明这一点：HTTP/1.1 中存在大量等待空隙，HTTP/2 则能让多个资源请求并行推进，从而缩短页面内容获取时间。

在协议规范层面，HTTP/2 与 HTTP/1.0、HTTP/1.1 一样，把 TLS 视为可选；但课程指出，实现 HTTP/2 的浏览器都把 TLS 作为必需条件。实际浏览器实现因此以加密为默认设计，形成了“HTTPS 无处不在”的方向，也与 WebRTC 对安全的要求一致。

## HTTP/3：以 QUIC 取代 TCP 传输

HTTP/2 改善了应用层的并行性，却仍建立在 TCP 之上。TCP 是有序流：发生丢包后必须等待重传，并按既定顺序补齐数据。在同一条 TCP 连接承载多个 HTTP 请求时，这些请求在逻辑上未必相关，但某个请求的数据包丢失，仍可能让连接上的其他数据一起等待。这就是课程要解决的传输层阻塞问题。

HTTP/3 将 TCP 换成 UDP，并在 UDP 之上运行 QUIC。QUIC 与 SPDY 一样来自 Google，可视为 SPDY 的兄弟协议；它把 TLS 集成在协议内部，因此 HTTP/3 不提供完全不加密的工作方式。

各层职责也随协议栈重新划分：

- HTTP/3 自身包含优先级和服务器推送等语义；
- QUIC 层改进流和流量控制；
- UDP 提供底层数据报传输；
- 加密由 QUIC 内部集成的 TLS 完成，不再是在 TCP 上单独叠加一个可选 TLS 层。

课程对光纤、ADSL、4G 和 3G 等网络条件下的建连时间作了比较。传统方式需要依次承担 TCP、TLS 和 HTTP 部分的成本；QUIC 的相应成本更低，其目标是获得连接保密性，而不再付出原先独立的 TLS 与 TCP 建连开销。课程还对比了小型网站、内容网站和单页应用（SPA）的加载时间：总体趋势是 HTTP/2 快于 HTTP/1.1，HTTP/3 又进一步缩短加载时间，但也存在个别例外。

## 协议栈与版本关系

| 版本 | 主要下层协议 | TLS 的位置 | 核心改进或限制 |
|---|---|---|---|
| HTTP/1.0 | IP + TCP | 可选 | 每次请求后关闭连接，重复建连成本高 |
| HTTP/1.1 | IP + TCP | 可选 | 复用连接，但典型请求仍串行等待 |
| HTTP/2 | IP + TCP | 规范可选；课程所述浏览器实现要求使用 | 多流并行、优先级、流量控制、服务器推送 |
| HTTP/3 | IP + UDP + QUIC | 集成在 QUIC 内，通信加密 | 重新划分流与流量控制等职责，避免 TCP 有序流带来的共同阻塞 |

从演进关系看，SPDY 通向 HTTP/2，QUIC 则支撑 HTTP/3。它们不是简单修改 HTTP 请求格式，而是在调整 HTTP 语义、传输层以及安全层之间的组合关系。

## 课程给出的时间线

| 时间 | 协议或事件 |
|---|---|
| 1974 年 | TCP 出现，属于互联网传输协议 |
| 1980 年 | UDP 出现；可靠的 TCP 早于不可靠的 UDP |
| 1996 年 | HTTP/1.0 出现，作为浏览器中的应用层协议运行在用户空间 |
| 1999 年 | HTTP/1.1 出现，继续使用 TCP |
| 2010 年 | Google 推出 SPDY，并在 Chrome 和其网站中试验、优化 |
| 2012 年 | Google 推出使用 UDP 的 QUIC |
| 2015 年 | IETF 将 HTTP/2 标准化，随后进入浏览器 |
| 2019 年 | 课程时间线将 HTTP/3 列于这一阶段 |

课程录制时，HTTP/1.0 已不再使用，HTTP/1.1 仍非常普遍，HTTP/2 和 HTTP/3 则相对较新；当时 Can I Use 所列的 HTTP/3 浏览器支持情况是除 Safari 外均可用。这些普及程度和支持状态都属于课程录制时的观察。

## 小结

HTTP 的核心语义是客户端发起请求、服务器返回响应。HTTP/1.0 的主要问题是逐请求建连；HTTP/1.1 通过保持连接减少建连成本，却仍有串行等待；HTTP/2 通过流让多个请求和响应在一条连接上并行推进；HTTP/3 再以 UDP 上的 QUIC 取代 TCP，并把 TLS 集成进 QUIC。理解这条演进路线，有助于区分 HTTP 自身的语义、下层传输和安全机制各自解决的问题。
