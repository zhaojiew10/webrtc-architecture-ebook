# 第 54 章 多方会议

多方会议是 WebRTC 最常见的应用场景之一，但不同会议产品的需求差异很大。参会人数、活跃发言者、设备、布局、角色权限和外部连接都会改变架构；当单台媒体服务器无法承载会议时，MCU 或 SFU 的级联方式又会进一步改变媒体流和布局灵活性。设计应从需求清单出发，而不是直接套用某种会议拓扑。

## 先收集决定架构的需求

### 会议规模与活跃参与者

首先要明确会议规模：是最多三至四人，还是需要支持 10、100、1,000，乃至一百万用户？不同规模需要不同的技术和界面方案。

四人会议通常可以让每个人在大部分时间里看到彼此，不必频繁切换画面。千人会议则完全不同：大多数人不会被展示，也无法随时发言，需要举手或其他机制从听众转为积极参与者。

因此，除了总参会人数，还要分别确定：

- 同时有多少人可以积极参与；
- 同时有多少人可以发言；
- 同时有多少人能够被看到。

“能说话”和“能被看到”是两个独立条件，不能用同一个“在线人数”指标替代。

### 设备与外部系统连接

需要明确支持的设备：仅限 PC 浏览器，还是也包括使用原生应用的移动设备、电视、平板及其他移动设备？设备类型会影响需要提供的布局，也会影响后端技术方案。

还要列出所有外部连接需求：

- 是否接入电话系统，让普通电话号码以语音加入；
- 是否连接不支持 WebRTC、但具有视频通信能力的传统会议室；
- 是否需要从其他来源接收视频；
- 是否要把会议视频发送或广播到其他目的地，例如 YouTube Live。

这些连接决定会议边界之外还需要哪些组件，不能只设计浏览器之间的媒体路径。

### 会中控制、协作与集成

产品需要定义用户加入后能做什么，例如聊天、自我静音或静音他人。协作能力也包括屏幕共享、白板、在他人的屏幕内容上涂鸦，以及围绕 Mural 等在线白板共同工作。

同时要考虑 API 与集成方式：是否允许第三方把自己的服务集成进会议应用，是否使用第三方已有能力，以及是否提供 Zapier 集成，让用户连接他们需要的其他服务。这些功能会改变会中控制面，而不仅是页面上的按钮数量。

### 地理覆盖、分辨率与个性化视图

用户位于哪里、服务在哪些数据中心托管，会直接影响质量；部署位置越靠近用户，通常越有利于质量。还要明确需要 VGA、QVGA、HD 还是 4K，并把分辨率目标与规模、设备等其他需求放在一起权衡。

视图是否一致也是架构需求。例如，四人会议如果不显示本地画面，每个人就只接收并看到另外三人的视图，而不是所有人共享完全相同的四宫格。产品必须明确是否需要为不同参与者生成不同视图，以及应用为此要增加什么处理。

人工智能与机器学习功能同样应提前列入需求，例如转录、翻译、噪声抑制和背景移除，而不是完成会议架构后再默认它们可以无副作用地加入。

### 确定最重要的优化对象

需求收集最后要回答：“这场会议中最重要的内容是什么？”

- 如果重点是视频质量，目标可能是看清对方面部细节，例如疲惫状态或剃须细节。
- 如果重点是声音，那么即使视频清晰，听不清对方也会使会议失去价值。
- 如果重点是共享内容，最重要的视觉信息就不是人物视频，而是共享屏幕和共同协作的数据。

不同答案会导向不同的优化投入。团队应把最多的理解和设计精力放在对该业务最关键的内容上。

## 布局选择及其处理代价

布局决定参与者如何出现在他人的屏幕上，也会影响录制合成和级联后的画面组织。

### 常见人物布局

| 布局 | 展示方式与设计取舍 |
| --- | --- |
| 全屏或切换模式 | 每次全屏显示一人，通常是当前发言者。可以依据音量或其他方法在发言者之间切换。某些会议录制方案即使让现场用户使用其他布局，录制时也只保留当前发言者的视频，同时混合所有人的音频，以减少生成录制文件所需的 CPU。 |
| 画中画 | 在同一画面中显示两人，一人占主画面，另一人位于小窗口。常见用法是小窗口显示本地视图，大窗口显示远程参与者。 |
| 并排视图 | 将两位讨论者并列显示，也可以再叠加本地画中画。画面顶部、底部或两侧可能出现空白；可通过调整视频尺寸并裁剪接收画面来填满区域。 |
| 方阵布局 | 将参与者放入 2×2、3×3、4×4 等方格。课程提到，7×7 在疫情期间较流行，录制时已不如当时普遍。方格不必等大，可以让某位参与者占据更大区域，其余人围绕排列。 |
| 轮播布局 | 一位参与者占主视图，其余通常以较小窗口排列在底部、侧边或顶部，适合一位主展示者、其他人多数时间倾听的场景。 |

移动端通常需要不同于 PC 的布局。虽然设备性能和电池寿命也需要考虑，但课程强调的主要限制是屏幕更小，无法放下与桌面端同样多的人物画面。

### 内容优先的视图

有些会议的重点不是人物，而是共同查看的内容。例如，屏幕共享占据主要区域，发言者视频只以小圆形窗口出现。Loom 的录制方式可以说明这种内容优先原则，尽管它本身并不是多方视频会议。另一种形式是内容占全屏主要区域，两位参与者像轮播一样排在内容旁边。

选择这类布局时，优化对象是共享内容和协作材料，人物视频退居辅助位置。它与“必须让每个人看到所有参与者”的会议不是同一种设计目标。

### 方形与圆形视频窗口

把视频放入圆形窗口会裁掉部分已经传输的画面，也就是发送了内容却不展示。从媒体利用角度看，这可能浪费资源，但圆形窗口仍可能符合产品的氛围或隐私目标。

课程以 Rabbit 中人们围绕同一内容协作，以及祖父母和孙辈远程聊天、共同游戏的应用为例：这类产品强调“远程一起做点什么”，人物画面用于增强陪伴感，圆形窗口可能更合适。Around.co 则把圆形窗口用于减少周围环境的可见范围，并结合头部跟踪，使用户头部保持在圆形中央，把它作为隐私体验的一部分。

## 布局设计需要回答的问题

在确定布局清单前，还应逐项回答以下问题：

1. **哪个视图占主导？** 哪种布局最重要，其中哪一路接收视频最关键？如果某一路更重要，就需要为它分配更多屏幕像素。
2. **如何处理本地视图？** 用户是否必须看到自己，能否选择显示或隐藏自己？
3. **所有人是否看到相同视图？** 例如 30 人教室中，教师可能希望看到所有学生，而学生主要需要看到教师；教师是学生端的主导画面，双方视图不必一致。
4. **布局由谁控制？** 用户能否自行配置和切换，还是完全由系统自动决定？
5. **移动端与桌面端有何差异？** 二者是否服务同一目的，是否鼓励用户从手机承担主持人角色？
6. **如何呈现纯语音参与者？** 怎样标识他们正在发言，当他们成为主导视图时又如何展示？
7. **人数超过页面容量后怎么办？** 当参与者超过 20、40 或 100 人时，是否用轮播或分页浏览，页面切换是否自动化，观众是否还需要在这些页面中看到自己？

这些问题既影响用户体验，也影响需要接收、展示或合成的媒体视图。

## 参与角色与权限模型

### 对称会议与非对称会议

对称会议中，所有参与者拥有相同权限，每个人都能执行相同操作。非对称会议则按角色区分能力。

- **主持人与参与者**：网络研讨会中，主持人可以展示视频和发言，普通参与者默认主要是听众；主持人可以允许某人提问、加入对话或打开麦克风。
- **主持人、参与者与嘉宾**：企业内部人员与外部人员可以拥有不同权限。例如，允许参与者发起会议，却不允许嘉宾发起；嘉宾也可能必须等主持人或参与者入场并接纳后，才能加入。
- **主持人、参与者、嘉宾与观众**：观众甚至可能完全不使用 WebRTC，而是以不同延迟和体验接收内容。

课程给出的一个角色组合示例是：1 名主持人、最多 4 名参与者、最多 200 名实时参与的嘉宾，以及另一批观众。观众收到的内容可以延迟 10 秒或 1 分钟。这里的数字用于说明不同角色可以对应完全不同的实时性与媒体路径，而不是所有会议都应采用的固定配额。

## 入会流程也是架构的一部分

用户如何进入会议，可以与角色权限组合设计：

- 生成随机或临时 URL，并发送给受邀者；
- 在日历邀请中放入入会链接；
- 使用个人化的固定链接，例如 `blog.geek.me/meeting/tzachy`；
- 要求用户先认证，再查看受邀会议列表，或在点击链接后完成认证；
- 通过短信或电子邮件发送邀请；
- 在网站中嵌入小组件，让用户直接通过组件加入；
- 在网络研讨会等场景收集入会者资料；
- 在正式入会前把用户放入等候室。

这些机制可以串联使用。医疗场景的一种完整流程是：为会诊生成临时链接，通过短信发给患者；患者点击后在设备上打开会诊，先完成身份验证，再进入等候室，直到医生批准其加入实际诊疗。入会设计因此不仅是分发链接，还包含认证、资料收集和准入控制。

## 本地控制与远程管理

本地控制是用户对自己的操作，常见能力包括：

- 静音或恢复自己的音频，关闭或恢复自己的视频；
- 调整布局；
- 开始或停止共享整个屏幕或部分屏幕；
- 使用聊天、上传文件等功能。

远程控制则决定主持人或管理者能对他人执行什么操作，例如：

- 静音他人的音频或视频；
- 将已经获准加入的人重新送入等候室；
- 批准入会或将人移出会议；
- 授权内容共享、授予发言台，或允许举手者实际提问。

主持人静音他人可以用于处理设备回声或大型会议中的无关发言，但权限不应无限扩大。课程特别强调：**可以远程静音，不代表应该能够远程取消静音**。即使主持人拥有管理权，也仍要保留参与者的边界。

## 大型会议中的级联与媒体流

当会议参与者很多时，单台媒体服务器可能不足以处理整通呼叫，需要多台媒体服务器级联。MCU 与 SFU 的级联方式具有不同的媒体流形态和布局限制。

### MCU 级联：逐台生成合成画面

MCU 是混合器，把接入它的用户音频和视频合成为统一视图。假设不同地点的用户分别连接不同 MCU：

1. 每台 MCU 混合由自己服务的参与者媒体，生成一路合成视频。
2. MCU 之间互相发送视频。两台 MCU 时，跨机器看到的主要是两路视频源，每一路都包含对应机器上所有参与者的合成内容。
3. 新用户加入某台 MCU 时，会被加入该机器已有的合成视频，而不是独立增加一路跨机器视频。
4. 增加第三台 MCU 后，系统需要处理来自三台机器的三个合成视图，每个视图仍承载该机器上全部参与者。

继续增加用户和 MCU 后，系统既要处理每台机器内部的布局，又要把这些合成结果拼接成更大的布局。虽然这种方式理论上可以把一千名参与者组织到屏幕布局中，但课程认为结果往往不够美观、灵活性有限，因为各层的布局决策会相互约束。

### SFU 级联：在服务器之间路由媒体

通常更倾向采用路由器，即 SFU。其媒体路径是：

1. 每位参与者把视频发送给自己所连接的 SFU。
2. 该 SFU 根据对端位置，把媒体路由给其他参与者，或路由到服务其他参与者的 SFU。
3. 多台 SFU 由此形成级联，而不是先把每台服务器上的所有人混合成单一视频再交换。

大部分媒体可通过 SFU 之间的直接连接传输。相比终端用户接入路径，运营者对这些服务器间连接拥有完整或至少部分控制力，也更容易据此组织媒体分发。这里的关键差异不是服务器数量，而是 MCU 在级联边界传递合成视图，SFU 在级联边界继续路由媒体。

## 小结

多方会议架构需要同时确定规模、活跃发言与可见人数、设备、外部连接、协作功能、地理部署、分辨率、角色和入会控制。布局也不是纯粹的界面装饰：它会改变录制时的 CPU 投入、各参与者收到的视图，以及多级混合时的灵活性。

扩展阶段尤其要分清媒体在服务器之间以什么形式流动。MCU 级联交换每台机器的合成画面，新增层级会带来布局组合限制；SFU 级联继续路由媒体，并利用相对可控的服务器间连接。最终方案应让布局、权限和媒体拓扑共同服务于该产品最重要的内容，而不是追求一种适用于所有会议的固定结构。
