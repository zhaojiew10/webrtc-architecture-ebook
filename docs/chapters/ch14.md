# 第 14 章 WebTransport

WebTransport 为浏览器提供了一种面向客户端—服务器通信的多流传输方式。它既能使用可靠传输，也能按应用需要选择不可靠传输，因此位于 WebSocket 与 WebRTC 所覆盖场景之间。本章从浏览器网络技术的演进出发，比较 WebTransport 在信令、数据和实时媒体中的能力，并说明它带来的基础设施简化与开发成本。

> 本章关于规范状态、浏览器支持和产品成熟度的描述，均指课程录制时的情况：WebTransport 当时仍较新，W3C 规范处于草案阶段，浏览器支持也有限。

## 在浏览器网络技术中的定位

可以从可靠性和通信灵活性两个维度理解相关技术。

- **HTTP/1.1** 强调可靠性，采用客户端—服务器模型，通常由客户端发出请求、服务器作出响应。
- **WebSocket** 同样提供可靠传输，但客户端建立连接后，通信就是双向的。服务器无须等待一个待处理的客户端请求，也可以主动向客户端发送消息。
- **HTTP/2** 仍是可靠传输，并允许同时发出多个请求，因此比单一请求—响应模式更灵活。
- **WebRTC** 面向低延迟通信，允许媒体采用不可靠传输，以减少可靠交付引入的等待；它既可用于客户端—服务器，也可用于客户端—客户端，具有点对点特征。
- **HTTP/3** 在课程的比较中被描述为具备可靠与不可靠能力的技术，但 HTTP/3 自身在这一上下文中按可靠方式使用。

WebTransport 保留了 WebSocket 式的客户端—服务器、双向通信模型，同时把可靠性选择交给 API 使用者。客户端连接服务器后，双方可以通信；应用则可针对要发送的内容选择可靠或不可靠方式，以不可靠传输换取更低的等待时间。

## 核心能力与协议架构

按照课程所引用的 W3C 草案，WebTransport 用于向服务器发送数据并接收服务器数据。它的 API 使用方式与 WebSocket 有相似之处：建立连接、发送数据、接收数据，最后关闭连接。但它并不只有一条数据流，而是具备以下能力：

- 支持**多流**，可在同一连接中打开多个不同的流；
- 每个流可以是**双向流或单向流**；
- 支持**乱序交付**；
- 同时提供**可靠与不可靠传输**；
- 不同流可采用不同可靠性，因此可靠流和不可靠流可以并存。

从架构看，WebTransport 是一组建立在 HTTP/3 之上的 API，并提供 HTTP/2 回退。不可靠传输等能力来自 QUIC；应用通过 HTTP/3 访问这些能力。

之所以在 HTTP/1.1、HTTP/2、HTTP/3、WebSocket 和 WebRTC 之外还需要它，主要有两个原因：WebSocket 对日益复杂的通信需求不够灵活，而 WebRTC 虽然功能强大，却并非所有客户端—服务器数据场景都需要它的完整连接模型与实时媒体能力。

## 用于信令和数据：与 WebSocket 比较

WebSocket 经常用于信令。评估 WebTransport 能否替代它，需要比较传输、安全、多路复用、可靠性和队头阻塞等方面。

| 比较项 | WebSocket | WebTransport |
| --- | --- | --- |
| 底层传输 | 使用 TCP | 可使用 UDP 和 TCP，优先使用 UDP |
| 加密 | 可选；可使用普通 WebSocket，也可通过 TLS 使用安全 WebSocket | 必须加密，不能发送未加密内容 |
| 多路复用 | 单个连接虽然双向，但只有一条数据流 | 同一连接中可建立多个特性不同的流 |
| 可靠性 | 必须可靠 | 可按流选择可靠或不可靠，并可混合使用 |
| 队头阻塞 | 单流模型下问题未解决，可能只能另开到同一服务器的 WebSocket | 可通过多个流处理课程所讨论的队头阻塞问题 |

因此，在信令与数据场景中，WebTransport 的主要价值是更灵活的流与可靠性选择。真正需要判断的不是它是否“更新”，而是应用是否确实需要这些额外能力。如果只需要一条可靠的双向信令通道，额外灵活性未必能转化为实际收益。

## 用于实时媒体：与 WebRTC 比较

实时媒体不只需要把字节送到服务器，还需要数据包化、播放时序、拥塞控制、音视频同步和音频处理。WebRTC 已集成这些能力，WebTransport 则把其中许多工作留给开发者。

| 能力 | WebRTC | WebTransport |
| --- | --- | --- |
| UDP 与 TCP | 两者都支持 | 两者都支持 |
| NAT 穿越 | 使用 STUN、TURN 和 ICE | 客户端只连接服务器，通常不需要额外的 NAT 穿越服务器 |
| RTP 数据包化 | 内置时间戳、序列号等实时媒体所需机制 | 由开发者处理 |
| 抖动缓冲 | 内置自适应抖动缓冲区，决定缓存、等待和播放时机 | 由开发者处理 |
| 拥塞控制 | 内置面向实时媒体的机制 | 某些层面已有能力，但使用不可靠通道时仍需开发者负责，难以直接达到 WebRTC 的实时媒体控制方式 |
| 音视频同步 | 内置音视频唇同步能力 | 由开发者实现，而且并不容易 |
| 音频算法 | 内置回声消除、自动增益控制等算法 | 留给开发者实现，部分能力甚至无法直接获得 |

### 为什么不需要 STUN/TURN，仍有网络注意事项

WebTransport 是客户端—服务器架构，客户端直接连接服务器，因此不存在 WebRTC 点对点连接中的同类 NAT 穿越问题，也不需要为此额外部署 STUN、TURN 和 ICE 流程。

但这不等于网络部署毫无限制。课程特别提醒，UDP 与 TCP 之间的回退，以及防火墙对 WebTransport 的认识程度，都可能影响连接。如果防火墙执行数据包检查并丢弃无法识别的新协议流量，WebTransport 仍可能受阻；课程录制时，这类新协议尚未被所有网络设备熟悉。

### 抖动缓冲和拥塞控制不能省略

接收媒体包后，系统需要决定缓存哪些包、何时立即播放、等待多久以接收后续包。WebRTC 的自适应抖动缓冲区已经承担这项工作；在 WebTransport 上重建实时媒体系统时，这部分需要自行解决。

拥塞控制尤其影响发送方向。课程认为，如果由流媒体服务器向客户端发送媒体，WebTransport 可以是一种合理选择；如果由客户端向服务器发送视频，现有拥塞控制方式则不够合适，难以满足实时媒体的要求。

## 用 WebAssembly 补齐媒体能力

WebTransport 简化的是连接与服务器基础设施，不是实时媒体算法本身。课程提到的常见补齐方式，是从 `libwebrtc` 代码库中挑选所需组件，例如抖动缓冲、拥塞控制和 RTP 数据包化，再把相应的 C/C++ 代码交叉编译为 WebAssembly，运行在 WebTransport 之上。

这说明 WebTransport 与 WebRTC 并非简单的竞争关系。开发者可以复用 WebRTC 的实现成果，同时获得更底层的控制权；代价是需要自行选择、集成和维护这些组件。

从系统结构看，WebTransport 有一些直接优势：

- 不需要 STUN 和 TURN 服务器，活动部件更少；
- 需要管理的服务器类型更少；
- 媒体和信令可以放在同一组服务器上。

但它不支持点对点连接，也缺少多项实时媒体能力。这些缺口究竟是劣势还是创新机会，取决于团队是否理解底层机制、是否愿意自行构建，以及希望获得多大控制权。

## 什么时候考虑 WebTransport

课程给出的场景都以明确需求为前提，而不是为了采用新技术而采用新技术。

### 专用 WebSocket 替代方案

多人游戏协议往往希望使用 UDP，并接受不可靠传输以换取低延迟。若还要在浏览器中运行，WebTransport 是可选方案。低延迟协作也类似：应用明确接受数据不一定可靠交付，从而获得 WebSocket 的可靠 TCP 通道无法提供的时序选择。

### WebRTC 数据通道的替代方案

上述游戏与协作功能也能用 WebRTC 数据通道实现。WebTransport 更适合以下情况：

- 应用没有、也不希望建立完整的 WebRTC 连接；
- 连接对象本来就是服务器；
- 希望减少建立 WebRTC 数据通道所需的时间和精力；
- 相比 WebRTC，目标服务器更可能直接支持 WebTransport。

### 特定流媒体场景中的 PeerConnection 替代方案

这类用途通常出现在流媒体应用，而不是双向对话式产品。前提是 HLS、MPEG 等方案不能满足需求，WebRTC 又不适合或过于复杂，同时应用确实需要专门处理。选择者必须清楚其他方案为什么不适合，以及自行补齐媒体能力的成本。

课程录制时，WebTransport 主要在 Chrome 中可用，成熟度介于“有吸引力的新工具”和“不够稳定的技术”之间。它适合愿意实验、可能借此形成独特能力的团队，但不稳定性和自行探索的成本也必须计入方案。

## 小结

WebTransport 的核心价值，是在客户端—服务器的双向连接中提供多流、乱序交付以及可选可靠性。它比 WebSocket 更灵活，却不自动具备 WebRTC 的实时媒体能力。

用于普通信令时，应先判断多流和不可靠传输是否确有必要；用于实时媒体时，则必须考虑 RTP 数据包化、抖动缓冲、拥塞控制、音视频同步和音频算法的实现成本。它可以减少 STUN/TURN 等基础设施，却把更多底层责任交给开发者。合适的应用通常是需求明确的客户端—服务器游戏、低延迟协作和专用流媒体场景，而不是所有 WebRTC 或 WebSocket 用途的通用替代品。
