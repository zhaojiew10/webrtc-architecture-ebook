# 第 18 章 WebRTC 中的信令协议

WebRTC 并没有替应用规定一套完整的信令协议。传输机制只解决“怎样把消息送到对方”，应用还必须决定“发送什么消息、按什么顺序发送，以及对方如何理解这些消息”。本章比较 SIP、XMPP、专有协议和第三方服务，并说明如何围绕实际业务作出选择。

## 信令协议要解决什么

两个用户要建立 WebRTC 会话，首先需要有底层传输路径，让一方能够把数据发送给另一方。但仅有传输路径还不够，信令至少还要承担以下任务：

- **发现与定位目的地**：找到希望通信的用户或房间。
- **协商会话参数**：交换会话描述协议（SDP）所表达的媒体能力和会话配置。
- **传递应用需要的其他信息**：例如加入会议、对方已到达、错误状态等。

因此，信令协议定义的不只是消息格式，还包括消息的语义、交互顺序以及响应方式。SDP offer、SDP answer 和 ICE 候选都需要借助这套机制在对端之间传递，而具体的网络发送过程位于 WebRTC 本身之外。

## SIP：面向 VoIP 的成熟协议

### 基本特征与典型消息

会话发起协议（SIP，Session Initiation Protocol）是 IETF 标准。它采用文本消息，结构类似 HTTP，并使用 SDP 描述会话。SIP 在 VoIP 中非常普遍：在 WebRTC 出现以前，许多语音通信方案已经采用 SIP；直到今天，连接传统电话服务仍是它在 WebRTC 架构中的重要用途。

SIP 包含多种请求和通知消息，课程中提到的包括：

| 消息 | 在课程语境中的作用 |
| --- | --- |
| `INVITE` | 发起会话邀请 |
| `ACK` | 确认 |
| `CANCEL` | 取消请求 |
| `BYE` | 结束会话 |
| `REGISTER`、`SUBSCRIBE` | 注册或订阅，以某种方式表达可用性 |
| `PUBLISH`、`NOTIFY` | 发布信息和发送通知 |

这些消息只是 SIP 能力的一部分。丰富的电话功能使 SIP 能覆盖转接、呼叫保持等场景，但也带来了明显的复杂度。对于只需要建立简单浏览器会话的应用，整套 SIP 往往显得过重。

### 传输方式与浏览器支持

SIP 最初标准化在 UDP 之上，随后加入 TCP 和 TLS。WebRTC 出现以前，应用主要通过这些方式传送 SIP 消息。为了能在浏览器中配合 WebRTC 使用，SIP over WebSocket 后来也得到标准化。课程提到的浏览器客户端实现包括 SIP.js 和 JsSIP。

课程录制时，WebTransport 尚不能直接视为 SIP 的现成传输方式。IETF 中虽有 SIP over QUIC 草案，而 QUIC 又是 WebTransport 的底层技术之一，但讲师对此持保留态度：WebSocket 已经提供浏览器运行 SIP 所需的能力，WebTransport 是否还能为这类信令带来足够收益，并不明确。

### 移动电话语义与推送通知

SIP 的设想起步远早于现代智能手机，其原始模型没有推送通知的概念。这一点会直接影响移动 VoIP 应用。

课程以 iOS 10 时期的变化为例：应用进入后台后，长期打开的套接字可能被关闭，因而无法继续接收即时消息或来电信令，应用需要借助 PushKit 或推送通知完成唤醒。类似做法后来也成为 Android 移动应用的常见模式。与其让套接字始终保持连接、消耗电量和网络资源，不如在需要时使用推送通知。

这并不意味着 SIP 的电话能力没有价值，而是说明这些能力必须与移动平台的生命周期模型结合。是否需要转接、保持等完整电话功能，以及如何处理后台唤醒，都应由具体应用决定，不能仅因为“语音通信用 SIP”就照搬全部架构。

## XMPP：联邦、在线状态与即时消息

可扩展消息与在线状态协议（XMPP，Extensible Messaging and Presence Protocol）同样是 IETF 标准。它也基于文本，但消息使用 XML，而不是 SIP 那种类 HTTP 的消息结构。

XMPP 的重点是：

- 联邦式网络；
- 在线状态（presence）；
- 即时消息；
- 通过扩展增加新的协议能力。

语音和视频通话并不是它最初的核心，不过已有扩展能够支持这些功能。讨论 XMPP 时需要特别注意：某项能力不属于基础协议，并不代表整个 XMPP 生态没有相应扩展。

在浏览器环境中，XMPP 可以通过 BOSH 使用 HTTP 长轮询。典型实现需要两个 HTTP(S) 通道：一个承载客户端发往服务器的请求，另一个保持等待，以便服务器有消息时及时返回。XMPP over WebSocket 则提供了另一种浏览器传输方式。XMPP 的消息较为冗长，因此更适合确实需要在线状态、消息和联邦能力的应用。课程以使用 XMPP 做信令的开源群组视频服务 Jitsi Meet 为例，说明它也能进入实时音视频架构。

## 为什么使用专有线令协议

选择专有协议并不一定是毫无理由地“重复造轮子”。常见原因有三类。

### 只实现真正需要的消息

应用开发者最清楚自身需要哪些信令。简单的 WebRTC 服务可能不需要完整的电话功能，也不需要在线状态和联邦机制。此时，SIP 或 XMPP 的通用能力会变成协议与运维负担。

### 复用应用已有的消息系统

设想一个已经上线的交友应用：用户有个人资料，可以搜索其他用户、互发消息、更新页面内容，并约定线下见面。后来，产品希望增加浏览器语音或视频通话。

这个应用原本就有用户身份、消息传输和业务交互。如果另起一套 SIP 或 XMPP，只会增加重复概念和系统集成工作。更自然的做法往往是沿用已有传输和消息协议，只补充 WebRTC 所需的 offer、answer、ICE 候选及房间控制消息。

### 让消息格式适合客户端和后端

自建协议可以选择符合技术栈的编码和解析方式。例如，客户端与服务器都主要使用 JavaScript 时，JSON 通常比用 JavaScript 解析 SIP 文本更直接。这里的优势不是某种格式绝对更好，而是它与现有实现更加匹配。

## 自建信令时的传输与设计清单

专有协议可以使用多种承载方式：

- REST 与 XML，以及长轮询、XHR 等 HTTP 方案；
- WebSocket，上层传 JSON、文本或二进制消息；
- HTTP/2 或 HTTP/3；
- 在课程所述阶段，也可把 WebTransport 作为实验性选择。

真正困难的部分通常不是选定传输，而是把协议行为定义完整。

### 1. 消息类型与内容

需要明确每类消息要达成什么目标、为什么需要它、包含哪些字段、由谁发送以及发送时机。还要定义正常响应、错误响应和所有边界情况，不能只描述成功路径。

### 2. 实现语言与解析方式

应用可能同时包含 Web、移动端和多个后端组件，后端又可能使用 Node.js、C、Java 等不同语言。消息格式应适合各端生成、校验和解析，不能只考虑浏览器一端。

### 3. 移动端与推送通知

要提前确定应用进入后台后的行为，以及推送通知如何与信令衔接。是否需要推送、推送中承载什么、收到推送后怎样恢复信令，都属于应用协议设计的一部分。

### 4. 安全性与端到端加密

如果群组通话采用端到端加密，需要明确服务器是否能看见客户端消息，以及哪些信令必须由服务器处理、哪些内容应保持不可见。已有协议可以提供参考，但应用仍需明确自己是否要支持这种模式。

### 5. 可扩展性与可维护性

成功应用的信令几乎一定会随功能增加而扩展。课程以 WatchRTC 为例：该产品通过 WebSocket 在客户端与服务器之间传递 WebRTC 指标。随着功能增加，原有协议被多次扩展，同时还要修补边界情况。即使是采集指标这种不直接建立 WebRTC 通话的系统，也无法避免协议演进。

### 6. 扩容与地理负载均衡

当一台信令服务器无法承担负载，或需要按地理位置分配流量时，协议和服务如何协同工作？多服务器状态、负载分担和地理负载均衡越晚考虑，补入现有系统的成本通常越高。

## 一个简化的专有线令流程

课程引用了一个刻意保持简单的会议示例，参与者包括主叫方、被叫方和信令服务器：

1. 主叫方向服务器发送 `join`。
2. 被叫方也发送 `join`，随后发送 `callee arrived`，表示被叫方已经到达。
3. 主叫方发送新的描述，即 SDP offer。
4. 被叫方返回新的描述，即 SDP answer。
5. 双方继续发送新的 ICE 候选，以支持 Trickle ICE。

这个例子有两个值得注意的地方。

第一，第二位用户为何会来到同一个房间，并没有由上述消息解释。现实中的会议邀请可能只是一段放在日历中的 URL，用户点击链接后进入会议。邀请本身可以位于 WebRTC 信令协议之外。

第二，用户如何知道自己是主叫还是被叫，同样可能由应用上下文决定，而不是由 offer/answer 消息决定。被叫方发送 `callee arrived`，只是这个示例选择的一种房间状态表达。

可见，一个能运行的 WebRTC 信令协议不必很复杂，但必须把会议建立、SDP offer/answer 和 ICE 候选交换串成明确的流程。会议邀请、角色判定等逻辑则要有意识地决定放在协议内还是协议外。

## Matrix.org 与第三方方案

课程还提到 Matrix.org。它在某些方面与 SIP、XMPP 类似，但课程特别强调其背后的推动者主要是 Matrix.org，而不是另一个独立标准化组织。它采用去中心化设计，出现时间晚于 WebRTC，包含客户端、保存用户数据的 home server，以及 application service、桥接器和机器人等概念。

如果不准备自行维护完整信令栈，还可以使用第三方项目或托管服务：

- SimpleWebRTC、EasyRTC、SaltyRTC 等 WebRTC 相关方案；
- Matrix.org；
- PubNub、Pusher、Scaledrone 等提供传输机制、并内置部分信令能力的托管服务。

这类服务通常已经考虑扩容问题，可以减少底层协议和基础设施工作，但仍需判断其消息模型是否满足业务要求。

## 如何选择

可以按下面的顺序审视需求：

| 需求或约束 | 课程给出的选择思路 |
| --- | --- |
| 必须连接电话或现有 VoIP 网络 | 后端很可能需要 SIP；客户端是否也使用 SIP，可另行决定 |
| 大量在线状态与即时消息 | 可考虑 XMPP，尤其是团队已经熟悉它时 |
| 接入已有服务 | 除非有充分理由，否则沿用该服务正在使用的协议 |
| 不需要连接外部网络，也不需要完整 VoIP 功能 | 优先考虑简单的专有协议，避免引入 SIP/XMPP 的额外负担 |
| 团队缺乏 VoIP 经验，只需实现 WebRTC 应用 | 不必为了简单通话先掌握整套 SIP |
| 不希望自建和维护信令基础设施 | 评估第三方项目或托管服务 |

“连接电话网络需要 SIP”并不等于“浏览器端必须原样使用 SIP”。一种架构可以让浏览器运行轻量专有协议，再由后端与 SIP 网络衔接；另一种架构则让客户端直接使用 SIP。课程中两种做法都存在，关键在于系统边界和团队能力。

## 小结

信令负责发现对端、交换会话参数和表达应用状态，传输协议只负责承载这些消息。SIP 适合电话与 VoIP 互通，但功能丰富、复杂度较高，并且要与移动推送机制配合；XMPP 擅长联邦、在线状态和消息，可通过扩展支持更多能力；专有协议则能贴合已有业务和简化实现。

选择时不应只比较协议名称，而应检查消息语义、错误与边界情况、移动后台行为、安全、演进和扩容。对无需外部网络互通的 WebRTC 服务，一套定义清楚的轻量协议往往比完整电话协议更合适；需要标准化互通时，再让 SIP、XMPP 或其他既有体系承担相应职责。
