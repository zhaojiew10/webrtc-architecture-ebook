# 第 17 章 WebRTC 中的传输协议

WebRTC 产品需要把“希望建立通话”等信令信息送到通信对端，但浏览器、移动应用、嵌入式设备和 PC 原生应用可用的传输机制并不相同。本章先区分信令传输与信令协议，再介绍浏览器中的 HTTP、WebSocket 和 WebTransport，最后比较原生应用的三种选择及移动推送通知带来的影响。

## 区分信令传输与信令协议

课程引用 Justin Uberti 的观点，把信令相关设计分为两个独立层次：

- **传输层**：负责实际发送信令数据，是信息传递的基础机制。
- **信令层**：决定如何表达和传递这些信息，也就是采用什么信令协议。

可以把现实中的对话作为类比：讲话的内容和表达方式，与声音借助空气传播，是两个不同问题。数字通信同样需要一种传输介质或机制，把“我想和你通话”之类的信息从一端送到另一端。本章关注的是底层传输，而不是具体的信令协议本身。

这一区分很重要，因为“使用 WebSocket”并没有说明上面运行什么信令；同样，“选择 SIP”也不意味着所有平台都必须采用完全相同的底层连接方式。

## 浏览器中的传输选择

### HTTP：请求、轮询与服务器事件

浏览器可以使用 HTTP，但通常不是直接把 HTTP 当作完整的双向信令机制，而是与其他方法组合。

一种方式是通过 REST 和 XMLHttpRequest（XHR）发送客户端请求并接收响应。客户端可以采用长轮询或短轮询访问服务器，以获取服务器需要返回的信息。

如果希望服务器在有数据时主动发送事件，可以使用服务器发送事件（Server-Sent Events，SSE）。SSE 会让请求保持打开，服务器有数据时即可推送，不必由客户端为每一条事件重新发起请求。

采用 HTTP 做信令传输时，可以按应用需要组合上述方法。课程还以 BOSH 说明长轮询的一种具体应用：BOSH 是 XMPP 在 HTTP 上的绑定，通常由一条 HTTP 请求向服务器发送数据，另一条保持等待的请求接收服务器数据。它利用的是 HTTP 长轮询，而不是把 SSE 当作 BOSH 的接收协议。

### WebSocket：建立后的双向连接

WebSocket 是课程录制时非常流行的选择。连接从 HTTP 请求开始，服务器确认支持 WebSocket 后，双方改用 WebSocket 通信。此后，浏览器与服务器之间形成一条双向连接，任何一方都可以通过这条连接发送数据，不再局限于客户端请求、服务器响应的交替模式。

这种模型很适合持续信令交换。课程给出的常见实践，是把 WebSocket 作为传输，再在其上运行应用选定的信令协议。

### WebTransport：能力强，但可能过于复杂

WebTransport 在课程录制时并未得到所有浏览器支持，主要用于探索和实验。它提供的选项应当比 WebSocket 更灵活，但对于当时要完成的信令任务，课程认为它可能属于过度设计，反而增加不必要的复杂性。因此，是否采用它应取决于实际需求，而不能只依据功能多少判断。

### 浏览器环境中的加密要求

浏览器中的 WebRTC 传输始终处于加密环境，页面和信令连接也必须把这一点纳入设计。

例如，网页希望调用 WebRTC API 并访问摄像头时，页面本身应通过 HTTPS 而不是普通 HTTP 提供。网页虽然不直接等同于 WebRTC，但浏览器会通过安全上下文要求间接影响它。使用 WebSocket 时，同样应采用安全 WebSocket 连接，而不是普通 WebSocket。换言之，浏览器内的 WebRTC 方案应按 HTTPS 与安全连接来构建。

### 先确定信令，再匹配传输

课程观察到的最佳实践通常是 WebSocket 加上其上的某种信令，但这不是固定规则。更稳妥的选择顺序是：

1. 先确定产品需要采用的信令协议；
2. 查看该协议能够使用哪些传输方式；
3. 再选择与信令及应用环境相匹配的传输。

因此，WebSocket 是常见答案，却不是脱离信令需求就必然正确的答案。

## 移动、嵌入式与 PC 原生应用

原生应用受到的限制比浏览器少，不必依赖 HTTP、WebSocket 或 WebTransport，可以直接使用其他传输机制。课程给出三种主要选择。

### 方案一：沿用浏览器可行的方案

原生应用可以继续使用 HTTP、WebSocket，未来也可能使用 WebTransport。这样做的主要目标是跨平台一致性。

例如，一个移动原生应用可能还需要在网页中提供另一部分功能，或者未来计划增加浏览器版本。如果所有设备和浏览器能够共用同一种传输协议，就可以减少平台之间的差异。因此，许多供应商会让移动原生应用与 Web 浏览器使用相同传输，最终在应用侧采用 HTTPS 或 WebSocket。移动端已经有成熟的库支持这些协议，采用它们通常不会成为障碍。

### 方案二：直接使用 TCP、UDP 或其他协议

原生应用也可以直接使用 TCP、UDP 或所需的其他协议，而不必照搬浏览器方案。

以 SIP 为例，如果选择 SIP 作为信令协议，原生应用很可能直接使用 UDP 和 TCP，因为这些方式在原生环境中可用，也便于直接实现；有些团队还已经拥有可运行的实现。进入浏览器后，由于不能直接使用这些原始 TCP、UDP 能力，同一 SIP 信令可以改为通过 WebSocket 承载。

这个例子再次说明，信令协议可以保持为 SIP，而不同平台采用不同传输方式。

### 方案三：让信令协议决定传输

课程最推荐的方式仍然是让信令需求主导选择：先确定信令协议，再检查可用的传输协议，最后挑选适合当前产品的组合。

这种方法既不会为了跨平台一致性而勉强保留不合适的机制，也不会因为原生平台能够直接使用 TCP 或 UDP，就忽略信令协议本身的要求。

## 不要忘记移动推送通知

无论采用上述哪种方案，移动原生应用都应检查移动推送通知如何参与整体流程。推送通知可能给信令协议的工作方式带来额外复杂性。

需要提前明确的问题包括：推送通知到达后应用应当做什么，以及应用是否需要重新与服务器通信，以获取通知中没有包含的详细信息。传输和信令设计若忽略这一过程，可能只覆盖了应用已经保持连接的情况，却无法完整处理由推送唤醒后的信令交互。

## 小结

信令传输与信令协议是两个层次：前者负责数据如何发送，后者负责信息如何表达和交换。浏览器常用 HTTP 组合机制或 WebSocket，WebTransport 在课程录制时仍属于探索性选择；浏览器中的 WebRTC 方案还必须遵循 HTTPS 与安全连接要求。

原生应用可以与浏览器共用传输，也可以直接使用 TCP、UDP 等协议。课程更推荐先选信令协议，再匹配传输方式，而不是把 WebSocket 当作所有场景的固定答案。移动端还需把推送通知到达后的服务器通信纳入完整设计。
