# 第 53 章 会议录制器

会议录制没有适用于所有场景的单一方案。录制发生在客户端还是服务器、媒体是否实时混合、文件何时生成以及如何回放，都会改变系统的媒体路径、部署组件和处理成本。本章分别分析短视频、一对一会议和多方会议，并说明这些选择背后的条件。

## 三类录制路径

### 服务器端录制

服务器端录制要求在整个会话期间把媒体发送到服务器，由服务器保存数据并负责录制。服务器因此成为会话的一部分，而不只是会话结束后的文件存放位置。这条路径适合参与者无法等待本地上传，或产品必须持续掌握录制过程的场景。

### 客户端录制

客户端录制使用 `MediaRecorder` API。其基本过程是通过 `getUserMedia()` 取得实际媒体数据，将其交给 `MediaRecorder`，生成媒体 `Blob` 或文件，再按产品需要上传，通常上传到服务器。容器与编码由浏览器实现及所选 `mimeType` 决定，常见为 WebM 或 MP4；可以使用 `MediaRecorder.isTypeSupported()` 检查目标格式，并按回放要求决定是否重新封装或转码。`MediaRecorder` 是否被归入 WebRTC 并不影响这里的架构判断；关键在于媒体先在本地形成文件，而不是在整个会话中持续发送到录制服务器。

### 转发

课程还提到转发这一少见选择，但讲师只见过一两次实际使用，因此不对其展开。真正选型时，仍应在具体场景和要求下比较客户端与服务器端路径，而不是预设某一种永远最好。

## 场景一：短视频录制

短视频录制可以用于意见调查、异步访谈或快速屏幕录制，Loom 是课程给出的服务示例。在这类场景中，浏览器内直接完成屏幕录制，可能比在浏览器外使用本地录制工具更简单。

### 工作流程与媒体路径

典型流程是：

1. 用户打开网站，允许访问摄像头、麦克风或二者。
2. 在客户端完成录制。
3. 录制结束后上传文件。
4. 用户检查并批准上传内容或已有录制。

课程在这里选择客户端录制，原因有三点：

- **部署更简单**：不需要媒体服务器，只需要存储服务器，减少了系统中的活动部件。
- **工作流程允许等待**：录制后本来就有上传、检查和批准环节；只要能让用户等待上传完成，就无需把实时媒体服务器引入路径。
- **更容易保留录制质量**：媒体不是在会话中通过 SRTP 实时发往服务器，因此录制结果不受这一实时传输过程中的丢包影响。录制完成后，整个媒体文件再像普通文件一样上传。

### 回放时效与编码选择

如果产品要求录制内容在线提供、可在各种浏览器中播放，并且在几分钟内可用，就不能依赖第二天才完成的离线批处理。这样的时效要求与本地 `MediaRecorder` 录制、随后上传的流程相匹配。

接下来还要选择录制编码，例如 VP8、VP9、H.264 或其他编码。选择取决于目标播放环境。课程观察到许多场景倾向 H.264，但如果需要支持旧款 Android 设备，并通过其中的浏览器完成录制或播放，就必须实际验证可用性，不能仅凭编码名称作决定。

## 场景二：一对一会议录制

医疗、教育和金融科技等领域可能需要保存一对一会议：参会者可能需要留存实际沟通结果，组织也可能因治理或政策要求必须录制。

这类场景与短视频有两个关键差异：

1. **无法控制用户行为和工作流程**。用户可能在会议中途或结束时离开，不会检查结果，也不会等待本地上传，而会立刻进入下一场会议。
2. **回放要求差异很大**。不同业务需要不同文件形式、保存方式和访问路径。

因此，不能依赖用户留在浏览器中完成上传，服务器端录制成为更合适的选择。

### 经 SFU 路由并分别保存两路媒体

一种基本结构是使用选择性转发单元（SFU）路由双方媒体：A 把媒体发送到 SFU，由 SFU 转发给 B；B 的媒体也沿相反方向经 SFU 发给 A。SFU 已经接收双方媒体流，因此可以在服务器本地把接收到的流保存为两个独立文件，一个属于 A，另一个属于 B。

这条路径把录制嵌入现有媒体路由过程，不需要用户在上传阶段配合。分别保存的 A、B 两路文件也可继续用于后续处理。

### 将两路输入送入混合器

如果希望直接得到单一画面，可以让 SFU 把 A、B 两路媒体同时送入混合器，例如多点控制单元（MCU）。混合器把参与者的音频和视频合成为一个视图，再保存到数据库或存储系统。

这种方法会在录制时完成音视频混合，但混合器需要消耗大量 CPU。是否在会议期间立即混合，应与后处理方案比较，而不能把“最终需要一个文件”理解为“必须实时混合”。

## 录制档位、存储与回放

### 延迟生成不同录制档位

SFU 保存的两路媒体流可以移到另一处远程存储，再由 Cron 等调度方式在预定时间生成目标文件。这样可以提供不同录制档位：

- 不混合视频，保留各路文件原貌；
- 只混合音频，生成纯音频文件，满足只需要收听会议的人；
- 需要视频但降低分辨率，例如会议以较高清的 HD 进行，录制文件却采用 VGA，以减少处理 CPU 或文件存储空间。

文件生成后，还可以放入检索耗时更长、但存储成本更低的存储层。这里需要在检索速度和长期保存费用之间取舍。

### 回放方式影响处理时机

录制文件可以通过多种方式回放：

- 使用 WebRTC，虽然可行，但课程认为成本较高；
- 直接下载文件，在本机播放器中播放，不必经过浏览器；
- 使用 MPEG-DASH 或 HLS 提供回放。

选择取决于实际访问需求及文件被回放的频率。如果录制的文件远多于真正会被回放的文件，只有极少数录制会被访问，就没有必要为所有录制提前完成混合。可以保留分路文件，等有人请求回放时再混合，并采用文件下载等较简单的方式，避免为无人观看的内容投入处理资源。

### CPaaS 中的职责分界

通信平台即服务（CPaaS）供应商可以通过 API 提供录制能力，生成文件并保存在自己的存储或客户指定位置。此时，平台负责录制与交付 MP4、WebM 等文件，构建在平台上的应用开发者则决定如何播放这些文件。另一种业务模式是只负责保存并提供文件，把后续回放处理完全交给使用文件的一方。

## 场景三：多方会议录制

多方会议是一对一录制的扩展，但参与者增多后，“何时决定布局”成为核心选择。以 A、B、C 三人会议为例，可以走两条不同路径。

### 立即混合后存储

把 A、B、C 的输入混合成一个文件，再发送到存储。这种方法必须在录制时决定每路视频的大小和整体布局。为了把参与者放进同一画面，可能需要降低部分视频的分辨率，或者由系统直接选定一种布局。录制完成后，早期作出的布局决定也随之固定在文件中。

### 保存多路独立媒体流

另一种方法是分别处理 A、B、C，把每一路保存为独立媒体文件，由应用决定以后是否混合、如何混合。其优势包括：

- 把布局决策推迟到回放或后处理阶段；
- 在整个会议期间，尽量按每路可获得的最高分辨率和码率保存媒体；
- 回放时可以单独观看某一路，也可以根据当时希望关注的内容采用不同布局。

多流录制并没有消除合成工作，而是改变了合成发生的时间与位置。设计时还要决定回放是否混合、在哪里混合，以及是否同步文本消息、表情符号和会话中发生的其他元数据。这些处理可以离线进行，也可以在线在浏览器侧完成；相应的同步位置也需要明确。

## 用虚拟机中的无头浏览器实时合成

课程介绍的一种常用实时方案，是在虚拟机中运行无头浏览器，让这个浏览器充当混合器。

其部署和媒体处理流程如下：

1. 无头浏览器作为一个不显露的额外参与者加入会议。原本只有 A、B、C 的会议中，实际还会存在参与者 D，即运行在虚拟机中的录制容器。
2. 浏览器像普通会议用户一样接收会议内容，并在自己的页面上呈现录制所需的布局。
3. 应用通过 HTML 和 JavaScript 调整布局、增加界面叠加元素，从而精确控制最终画面。
4. 对浏览器画面进行屏幕抓取并编码、封装，生成 MP4 文件并按需发送或保存。如需推送到 YouTube Live，应将合成结果交给流媒体服务器，通过其支持的接入方式（课程时点可采用 RTMP/RTMPS）推送；若输出 RTP，则发送给支持 RTP 的接收端或网关，而不是直接把裸 RTP 交给 YouTube Live。

这种方式在线、实时完成合成，适合需要制作具体播出画面的场景。例如，播客或直播可以把两名或更多发言者放在同一布局中，再叠加姓名横幅等元素，最后输出录制文件或推送到在线服务。与分别保存原始流相比，它把布局、叠加和合成工作放进了实时会议路径。

## 小结

录制架构应从用户流程和回放需求反推：短视频如果能等待上传并检查，客户端录制可以减少服务器组件并避免实时丢包影响；一对一会议通常无法依赖用户等待，适合由 SFU 接收媒体并在服务器保存；多方会议则要在实时混合与多流保存之间选择布局决策的时机。

文件生成、混合、存储和回放是不同决策。低回放率可以支持按需混合，低成本存储意味着较慢检索，无头浏览器则提供了可编程的实时画面制作与媒体输出路径。只有把这些环节分别分析，才能避免为所有录制支付并不需要的实时处理成本。
