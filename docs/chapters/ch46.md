# 第 46 章 媒体服务器替代方案

媒体服务器的选型不能只比较品牌或功能清单，还要区分 SFU 路由、MCU 混音、通用网关和流媒体广播等架构，并评估安装、扩展、维护与技术支持的成本。本章按课程录制时的观察，整理开源媒体服务器、商业媒体服务器和“媒体即服务”三类路径。产品的维护状态、能力和讲师评价均保留课程时点，不作后续更新。

## 开源媒体服务器概览

WebRTC 周围有大量开源项目，其中不少面向信令，真正形成较高采用度的媒体服务器项目相对集中。课程首先概括了几类代表：

- **Kurento**：过去采用度和流行度很高，但课程认为其维护已经减弱，不建议继续选用。
- **Janus**：历史较长的通用 WebRTC 网关，适合其他框架不够贴合的特定项目。
- **Jitsi**：面向会议的完整解决方案，适合用户界面和交互接近 Jitsi Meet 默认形态的项目。
- **mediasoup**：课程认为其采用度正在上升，常用于可扩展会议和流媒体方案。
- **Pion**：Go 语言 WebRTC 实现，在其之上还构建了其他媒体服务器，适合 Go 技术栈或特殊集成需求。

这些项目不是可以互相直接替换的同构产品。网关、完整会议应用、SFU 构建库和底层 WebRTC 实现，处于不同的抽象层。

## Janus：轻量级通用 WebRTC 网关

Janus 由意大利的 Meetecho 团队开发和维护，团队也围绕 Janus 提供自由职业和外包工作。课程将 Janus 描述为通用、轻量的 WebRTC 网关，采用 C 编写，许可证为 GPLv3。

它的基本思路是：一侧连接 WebRTC，另一侧可以通过插件接入不同系统。课程见到的用途包括：

- SIP 或物联网场景的网关；
- 群组通话；
- SFU；
- 录制服务器。

Janus 自带一些开箱插件，也允许开发者编写满足自身需求的插件。课程以无人机接入为例：可以为 Janus 编写插件，借助 GStreamer 连接第三方媒体源，再把媒体送往 WebRTC 一侧；该例提到了 VP8、RTP 和 MJPEG 等环节。

因此，Janus 的优势是通用性和插件边界，限制也同样明显：项目需要理解网关与插件的工作方式。它更适合需要特定协议或设备集成的场景，而不是不加判断地作为所有会议系统的默认选择。

## Jitsi：面向会议的一整套方案

Jitsi 最初来自 BlueJimp，后经 Atlassian，课程录制时由 8×8 维护。其上还有 Jitsi Meet 应用。课程建议，在所需 UI 或 UX 与 Jitsi Meet 默认提供的形态非常接近时优先考虑 Jitsi，因为它本来就是一套面向会议目的构建的方案，而不只是孤立的媒体转发模块。

### Jitsi Videobridge 与系统组件

Jitsi Videobridge 建立在 SFU 架构上，采用 Java 编写，使用较宽松的 Apache 许可证。课程将其称为当时很流行的开源 SFU，尤其面向群组通话。疫情期间，许多公司自行安装服务器，或围绕它构建自己的服务。

一套 Jitsi 系统涉及多个部分：

- **Jitsi Videobridge**：SFU 实现；
- **Jicofo**：提供会议桥接相关功能；
- **Jitsi Meet**：位于其上的应用；
- **IdP**：身份识别服务；
- 其他支持录制或 SIP 连接的服务器。

课程对它的运维评价是“设置简单，但扩展和维护有些困难”，原因就在于系统存在多个活动部件。选择 Jitsi 时，不能把初次安装顺利等同于长期扩展和维护成本很低。

8×8 当时还提供名为 **Jitsi as a Service** 的 CPaaS 方案，可以让 Jitsi 的部分组件或整个系统在云端运行。这为不想完全自行运营的团队提供了另一种部署路径。

## mediasoup：嵌入 Node.js 应用的媒体路由构建块

课程将 mediasoup 描述为主要由两人维护的项目，两位维护者都在远程工作服务公司 Around 工作。项目在录制时维护良好，近年来人气上升。

mediasoup 由 C++ 与 Node.js 部分组成，采用 ISC 许可证，课程认为它与 BSD、MIT 类似。使用 mediasoup 时，开发者实际上是在编写一个 Node.js 应用，并把 mediasoup 作为该 Node 服务的一部分集成进去。课程也对其代码架构给予较高评价。

### 媒体路由方式

mediasoup 内部通过 Router 在自身内外路由媒体：

1. Producer 通过 WebRTC 或其他 RTP 传输收集媒体。
2. 媒体被发送给 Consumer。
3. 输出可以通过 SRTP 或 RTP 流向外部，也可以流向 mediasoup 自己的其他 Node.js 服务器。

这种结构为扩展提供了空间。不过，它要求团队以构建媒体应用的方式使用 mediasoup，而不是期待得到一个无需开发的完整会议产品。

## Pion：Go 语言实现与特殊集成

Pion 是 Go 语言的 WebRTC 实现，由 Sean DuBois 发起并持续维护，也有其他贡献者参与。课程指出，其各部分和组件按独立模块组织，周围还存在 Ion、LiveKit 等基于它构建的媒体服务或库。

课程认为 Pion 特别适合两类情况：

- 团队偏好 Go，或需要与 Go 技术栈紧密结合；
- 需要特殊集成，例如嵌入式方案或云游戏。云游戏中，一侧可能需要在 WebRTC 之外实时渲染视频，再把 WebRTC 接入这一过程。

Pion 首先是模块化 WebRTC 实现。选用它时，需要区分底层实现、媒体服务库与完整应用之间的责任边界。

## Kurento 与 OpenVidu

### Kurento

Kurento 曾被 Twilio 收购。课程称收购后原工程团队被大幅裁撤，项目由西班牙一所大学维护。它是通用媒体引擎，课程描述其为 C++ 实现、采用 Apache 许可证，过去流行且功能多样，主要用例包括媒体录制、混音和路由。

Kurento Media Server（KMS）负责媒体处理，内部的媒体管道允许干预处理过程；应用服务器则通过 Kurento 协议向媒体服务器发出指令并影响其行为。

尽管架构通用，课程基于当时的维护状况明确建议不要使用。这个例子说明，历史流行度和功能丰富度不能弥补维护不足带来的长期风险。

### OpenVidu

OpenVidu 是位于 Kurento 和 mediasoup 之上的一层。它最初是 Kurento 的封装，用于构建媒体会议服务器，后来增加或转向对 mediasoup 的支持。

OpenVidu 包含服务器组件和浏览器组件，两者共同提供较接近成品的方案，减少采用方需要的开发工作。它还有企业版，可以付费获得服务和额外能力。

因此，OpenVidu 与直接使用底层媒体服务器的区别，在于它提供了更多现成组件；相应地，选型也要接受这一层已经确定的结构和能力边界。

## 其他开源项目

### Intel Open WebRTC Toolkit

Intel Open WebRTC Toolkit 包含客户端和服务器方案。课程观察到它在亚洲的流行程度明显高于世界其他地区，并指出其开发和维护主要在中国，这可能使欧洲或美国用户获得支持更困难。这里的限制主要是支持可达性，而不是单纯的功能比较。

### Licode

Licode 由西班牙的 Lynckia 开发和维护，围绕 MCU 概念构建，采用混音而非路由方式，使用 C++ 编写并采用 MIT 许可证。

课程认为它在纸面上很有趣，但讲师实际看到的采用有限，也没有从身边的使用者那里得到满意反馈。这属于课程经验判断。架构上需要明确的是：它与本章多数以 SFU 为主的项目并不走同一条媒体处理路线。

### Medooze

Medooze 由 eFace2Face 团队构建，后由 Cosmo Software 维护；课程称这两个团队当时都已停止运营。Millicast 将其用于广播服务，而 Millicast 后来被 Dolby 收购。

课程描述 Medooze 最初采用 MCU，随后迁移到 SFU 架构，使用 Java 编写并采用 GPLv2 许可证。它更像技术构建块，而不只是开箱媒体服务器；课程还指出，当时主要使用者似乎就是其构建者。采用这类项目时，维护主体和使用社区都是需要审慎评估的限制。

## 商业媒体服务器

商业方案的核心是带支持的专有产品。课程指出，其中许多技术早于 WebRTC，市场份额也不如开源方案。商业产品主要集中在两个方向：MCU／混音，以及视频流媒体。

### 低延迟流媒体方向

| 产品 | 课程描述的 WebRTC 能力与定位 | 限制或注意点 |
| --- | --- | --- |
| Wowza | 支持 WebRTC 输入，并在观看侧提供部分能力；主要用于低延迟直播 | 课程认为其 WebRTC 部分当时采用度较低 |
| Red5 Pro | 为输入和输出都加入 WebRTC 支持，可回退到 Flash、HLS、MPEG-DASH 等流媒体方案 | 重点仍是低延迟广播，而非通用会议 SFU |
| Ant Media | 同样面向视频流媒体，加入 WebRTC，并可回退到 Flash、HLS、MPEG-DASH | 重点是低延迟广播 |
| Flashphoner | 面向流媒体用例，提供录制、屏幕共享、WebRTC 到 HLS 等能力 | 应按流媒体工作流评估，而不是只看是否支持 WebRTC |

这些方案都把 WebRTC 放进更广泛的流媒体链路中。若需求是低延迟广播，这种定位可能正合适；若需求是多方会议，就不能据此推断其一定提供所需架构。

### MCU、互通与企业媒体处理

Compunetix 是课程列举的商业 MCU 厂商，提供与 SIP、H.323 的互通，并具备 WebRTC 能力，同时提供托管和本地部署选项。这与其原有的企业会议和互通背景相符。

课程还讨论了 Dialogic PowerMedia XMS。讲师认为它是可靠的产品，但不确定其在录制时的流行程度。它源自移动通信领域，按 IMS MRF 设计，后来才加入 WebRTC，包含多数相关功能。

如果需要的是 SFU，课程认为 Dialogic PowerMedia XMS 并不合适，因为它主要是混音器。这再次说明，“具有 WebRTC 功能”并不等于“具有目标媒体架构”。

课程最后还简要提到 SURF HMP：这是一种基于 GPU 的转码方案，课程时点尚不支持 Opus。课程未进一步展开其架构细节；实际选型时需要另行核实其协议与编解码支持。

## 媒体即服务

“媒体即服务”希望进一步取消媒体服务器的安装和维护：用户不部署媒体服务，而是直接消费托管能力。课程指出，这种独立形态在录制时并不常见，更像是通往完整 CPaaS 的一级台阶。

课程提到过一个名为 MC1.com 的方案，但录制时它已经不存在。讲师认为未来可能还会出现类似服务，但没有据此断言具体产品或市场结果。

媒体即服务与完整 CPaaS 的区别在于范围：前者聚焦媒体服务器这一层，后者通常还提供定义明确的 API、更多通信构建块和配套支持。采用前需要确认，自己究竟只想省去媒体服务器运维，还是希望托管整个通信基础设施。

## 成本与选型的实际边界

本章没有给出统一的价格比较，而是给出了更直接的成本来源：

- **部署成本**：完整方案可能安装较快，但多个组件会增加后续管理复杂度。
- **扩展与维护成本**：Jitsi 等方案被课程明确评价为易于设置、较难扩展和维护。
- **开发与集成成本**：Janus 插件、mediasoup Node.js 应用和 Pion 特殊集成都需要实际开发。
- **支持成本与可获得性**：商业产品提供支持；开源项目则要考虑维护活跃度、社区和地域支持条件。
- **架构不匹配的代价**：MCU 混音、SFU 路由、通用网关和广播链路服务于不同需求，不能只因某项产品支持 WebRTC 就互相替换。
- **托管范围**：云服务或媒体即服务可以减少自行运营工作，但需要确认托管的是单个组件还是完整系统。

因此，合理的选型顺序是先确定用例和媒体架构，再核对现成组件、维护状态、支持方式和长期运营责任。

## 小结

开源媒体服务器覆盖从底层实现到完整会议应用的不同层次：Pion 是 Go 语言 WebRTC 实现，mediasoup 是可嵌入 Node.js 服务的媒体路由构建块，Janus 是插件化通用网关，Jitsi 则更接近完整会议系统。OpenVidu 又在底层媒体服务器之上提供服务器和浏览器组件。

商业产品主要集中于低延迟流媒体、MCU 和企业互通。它们的支持方式与开源项目不同，但同样要检查架构是否匹配。最终成本不仅是获得软件的成本，还包括开发、部署、扩展、维护、支持和迁移的成本；最重要的限制，则往往来自项目维护状态与既有架构边界。
