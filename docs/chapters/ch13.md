# 第 13 章 媒体质量指标

评估实时媒体质量，不能只看某一张截图或一次主观体验。比特率、丢包、延迟、往返时间和抖动描述了媒体传输的不同侧面，而且这些指标会随时间变化。本章逐项说明它们的含义、常见成因、参考量级和应对方式，并解释为什么长时间会话还需要按较短时间段分析。

## 比特率：实际用于媒体的数据量

比特率表示某个媒体通道随时间发送或接收的数据速率。它回答的问题是：在可用带宽中，有多少真正用于媒体？例如，网络路径可以承载 3 Mbps，实际媒体编码可能只使用其中一部分。

通常，较高比特率有机会带来更好的媒体质量，但这不是绝对关系；与此同时，服务方和用户都要承担更高的带宽与处理成本。因此，目标不是无条件把比特率推到最高，而是在内容需求、质量、网络能力和成本之间取得平衡。

### 比特率为什么会动态变化

会话中的比特率会受到多类因素影响：

- **网络拥塞**：发送端试图传输的数据超过路径承载能力，或者本地网络及互联网路径上有其他流量占用资源，就需要降低比特率。
- **应用或媒体服务器决策**：媒体服务器或应用程序可能依据自身逻辑主动提高或降低比特率。
- **本地资源竞争**：同一设备上的其他进程，或同一局域网中的其他设备，都可能争用网络和处理资源。
- **无线链路条件与干扰**：设备离 Wi-Fi 接入点或蜂窝基站过远，干扰增大时，可用比特率可能下降。
- **网络策略**：网络可能限制用户能够使用的带宽。
- **物理故障**：故障网线等硬件问题也会降低比特率并引发其他网络错误。
- **编码器与内容行为**：内容变化越少，通常需要传输的信息越少。例如，静态演示文稿只有在切换页面时才明显变化，页面停留期间不需要持续使用很高比特率。

### 语音和视频需要多少比特率

课程以 G.711、Opus、H.264 和 VP8 为例给出了以下参考量级。这些数值用于建立直观认识，实际需求还会随编解码器、内容和配置变化。

| 媒体与格式 | 课程给出的参考比特率 |
| --- | --- |
| G.711 语音 | 固定为 64 kbps |
| Opus 语音 | 约 16 kbps 已可获得较好音质；16～40 kbps 区间可提供质量较好的宽带音频，应用还可配置最大比特率 |
| QVGA 视频，H.264 或 VP8 | 约 200～400 kbps 通常足够，也可能达到约 500 kbps |
| VGA 视频，H.264 或 VP8 | 约 450～800 kbps |
| 720p 及以上视频，H.264 或 VP8 | 从约 800 kbps 起步，更高需求会继续增加 |
| 4K、60 fps 视频 | 很容易需要 20～30 Mbps |

换用 VP9、AV1 等编码格式时，不能直接沿用上述数字。课程给出的预期是，VP9 所需比特率可比前述参考值低约 50%，但这仍应作为估计，而不是所有场景下的固定比例。

WebRTC 会依据网络和设备状况动态调整比特率、分辨率与帧率。课程描述的顺序是先确定可用比特率，再调整分辨率、帧率等其他参数。

### 可用带宽不等于必须全部用完

发送端需要估计可用的出站比特率，再让编码输出低于这一上限。课程示例中，网络估计值约为 4.5 Mbps，而实际只发送约 2.5～2.7 Mbps，因为当前内容不需要更多数据。

因此，带宽估计给出的是可用上限，不是必须达到的目标。发送端会在内容所需比特率与估计的最大出站比特率之间取合适值，而不是机械地占满全部可用带宽。

## 丢包：数据没有到达另一端

假设发送端依次发送编号为 1、2、3、4、5 的数据包，而接收端没有收到 2 号包，这就是丢包。发送流和接收流都可能出现丢包，其数量也会随时间变化。

丢包可能来自**拥塞**，也可能来自**数据损坏**。二者需要区分：拥塞意味着网络中的发送量过大，降低比特率可能缓解问题；数据损坏则意味着无论是否降速，部分数据包仍可能损坏或丢失。实际观察指标时，原因未必直接可见，需要据此作出判断。

### 应对丢包的几种方式

**重传。** 接收端指出某个包没有到达，发送端再次发送该包。重传在信令中很常见，在实时媒体中则受到时间约束：等待请求和重传会消耗时间，数据到达时可能已经错过播放时机。因此，实时媒体不能简单照搬普通可靠传输的处理方式。

**丢包隐藏。** 接收端不等待重传，而是尽量掩盖缺失。例如，重复播放前一帧；根据先前数据包估计缺失内容并合成输出；视频中跳过一帧并请求刷新。不同方式的共同点，是不把数据缺失直接暴露为播放中断。

**前向纠错。** 发送端在未被请求的情况下主动发送额外或重复数据，以便部分包丢失后仍有恢复机会。这会占用比特率预算，降低用于原始媒体的有效比特率。它在 Opus 音频中有一定效果，但对视频通常更困难，因为额外数据量更大，可能迫使系统同时降低视频质量。

**降低比特率。** 如果判断丢包由拥塞造成，降低发送速率可以减少路径压力，是常见的处理措施。

### 不同媒体对丢包的耐受能力

课程给出的参考量级体现了明显的格式差异：

- **G.711**：自身抗丢包能力很弱，几乎不能依靠编解码器容忍丢包。
- **Opus**：更稳健；课程给出的经验说法是，即使丢包率达到约 20% 或更高，仍有可能听清并理解对方讲话。
- **普通视频方案**：通常可容忍约 1%～2% 的丢包而继续正常使用。
- **采用时间可扩展性、可伸缩视频编码等方案**：课程给出的参考是可应对约 10% 或更高的丢包水平。

这些数字用于比较相对韧性，不应脱离具体实现和内容，理解为统一的质量保证。

## 延迟与往返时间

**单向延迟**是数据包从发送到接收所经历的时间。两个方向的网络路径和处理情况可能不同，因此 A 到 B 的延迟与 B 到 A 的延迟可能相差很大。

**往返时间（RTT）**是发出数据包后，到收到对方响应所经历的时间。它把两个方向合并为一个可观测指标，也是 WebRTC 统计中常用的网络延迟估计。

### 测量边界并不简单

完整的媒体体验还包含网络之外的时间：从摄像头采集图像到数据进入设备需要时间，编码需要时间；音频也涉及麦克风和扬声器；接收端从尝试播放到显示器真正呈现画面，同样存在延迟。

因此，需要明确指标究竟覆盖端到端设备链路，还是只覆盖网络、网络接口和应用处理响应的部分。实践中通常主要观察网络相关部分，并用 RTT 作为足够好的估计，而不是把每一次设备采集和显示延迟都单独纳入。

在 WebRTC 统计中，可以在远程入站 RTP 流统计，即 `RTCRemoteInboundRtpStreamStats` 相关的数据中查看这一估计。它根据对端返回的 RTCP 接收报告（RTCP Receiver Report）数据计算：当本端发送媒体时，可从远程入站 RTP 流统计中看到相应的往返时间。它仍是估计值，但通常具有实用价值。

### 实时通信的参考延迟

课程给出的经验范围是：RTT 在 **100～150 ms** 左右属于很好的实时通信延迟；达到 **600 ms 或更高**时，对实时交互而言已经相当差。这里的重点是交互体验，而不只是数据最终能否送达。

## 抖动：到达间隔的不稳定

假设发送端大约每 20 ms 发出一个媒体包，数据包在发送时间轴上等间隔排列；经过网络后，接收端的包间隔可能不再一致。抖动就是对这种延迟或响应时间变化的度量，单位为毫秒。

造成抖动的常见因素包括：

- 网络拥塞；
- 数据包丢失；
- 设备性能问题。

如果 CPU 需要编码、解码过多数据或发送过多数据包，使用率达到约 80%～90% 以上，就可能出现更明显的抖动和节流。稳定网络和稳定播放是媒体处理的目标；课程给出的参考是，抖动超过 **30 ms** 就表明质量可能正在下降，需要进一步检查。

在质量排查的优先级上，课程通常把抖动放在比特率、丢包和延迟之后。这不代表抖动不重要，而是应先排除更直接限制媒体质量的因素。

## 用时间窗口识别突发质量问题

所有指标都有时间维度，质量问题也往往会集中爆发。在某些短暂区间内，可能同时出现高丢包、比特率突升或突降、抖动增加、帧率变化和延迟变化。

如果会话持续 5 分钟或更久，只看整场会议的平均值，可能掩盖这些短时故障。要接近真实体验，除了会话整体数据，还应把丢包、抖动及其他指标切分到更短的时间段中分析，找出问题发生的时刻和持续范围。

## 小结

比特率描述媒体实际占用的数据速率，丢包描述数据是否到达，单向延迟和 RTT 描述传输耗时，抖动描述到达时序的稳定程度。它们相互关联，却不能互相替代。

分析媒体质量时，应先理解编解码器、内容和网络条件对指标的影响，再选择合适的恢复或降速策略。参考数值有助于发现异常，但最终判断还应结合指标随时间的变化，尤其要检查被整场平均值掩盖的短时质量下降。
