# 第 31 章 VP9 与 HEVC

VP8 与 H.264 之后，视频编解码器沿两条路线继续演进：一条是以 VP9 为代表的免版税路线，另一条是以 HEVC（H.265）为代表的需支付版税路线。选择新一代编解码器并不只是比较压缩率，还要同时考虑 CPU、硬件加速、浏览器支持、可伸缩视频编码（SVC）生态以及专利许可。

## 视频编解码器的代际演进

课程将视频编解码器大致划分为几个阶段：

- 早期主要有 H.261、带有许多附录的 H.263，随后 H.264 开始受到关注。
- WebRTC 正在走出的阶段以 VP8 和 H.264 为主。二者都是 WebRTC 必须实现的编解码器，广泛存在于各浏览器中，但技术已经相当成熟、历史也较长。
- 课程所称的当前一代主要是 VP9 和 HEVC。HEVC 也称 H.265。
- 再往后则是 AV1 和 VVC（H.266），其中 AV1 是下一章的重点。

H.261、H.263、H.264 和 HEVC 属于需要处理专利许可与版税的技术路线；VP8、VP9 和 AV1 则以免版税为目标。随着计算能力提升和编码研究深入，新一代编解码器能够更好地压缩视频，但“更新”并不意味着在所有设备、所有场景下都应该立即替换旧方案。

## 为什么产业会转向免版税编解码器

### 用户生成内容改变了成本结构

过去的视频大多由工作室制作一次，再在电视等终端上多次播放。内容制作者能够直接从作品中获得收入，因此围绕编码环节收取一定许可费用，在商业上相对容易解释。

用户生成内容改变了这一前提。手机让每个人都能持续拍摄、直播并发布视频，编码行为不再集中于少数专业制作机构，而是分布在海量用户和海量内容中。若每次编码都附带复杂或许可成本，整个内容生产模式都会受到影响。

### 不对称商业模式需要低摩擦的基础能力

许多互联网服务向用户免费提供搜索、社交分享、语音或视频通话，再通过广告等其他业务获利。这种“不对称”的商业模式要求基础功能可以低成本甚至免费提供给用户。如果视频编码本身需要逐项付费，免费服务就可能难以成立，或者被迫承担过高成本。

互联网公司也熟悉开源、自由软件和开放标准，因此免版税音视频编解码器自然更符合其工程与商业习惯。

### HEVC 的许可碎片化

HEVC 的问题不只是“要付费”，还在于很难确定究竟应向谁付费。课程列举了其录制时所涉及的专利组织与公司：

- HEVC Advanced：课程旧资料中列有至少一万项相关专利。
- MPEG LA：拥有另一组专利，同时有些公司也参加了其他专利池。
- Velos Media：拥有独立的 HEVC 相关专利组合。
- 未加入上述组织的公司：仍可能单独主张许可费用。
- Via LA：课程后来又提到的一个专利许可组织。

因此，即使使用者愿意付款，也可能在取得一个专利池的许可后，仍无法确认是否覆盖全部必要专利。后续还可能遇到其他权利人的收费或诉讼主张。

VP9 和 AV1 也并非从未面对专利争议。课程提到 Sisvel 曾试图围绕它们收费，而当时业界的反应大体是忽略这些主张。讲师特别说明，这部分资料已有数年历史，不能把它当作持续更新的法律结论。

## VP9：在码率与质量之间重新取舍

从 VP8 迁移到 VP9，可以从两个方向理解收益：

1. **保持相近质量，降低码率。** 这可以减少云带宽费用，也可能让原本带宽不足的手机或网络获得可用的视频质量。
2. **保持相同码率，提高质量。** 对同一段视频，在码率不变的情况下获得更好的画面，或者支持更高分辨率与帧率。

因此，VP9 既适合追求 1080p、4K 或 60 fps 等更高规格的场景，也适合只有约 100～200 kbit/s 可用带宽、希望尽量改善画质的场景。前者关注“从同一码率中挤出更多质量”，后者关注“让低码率链路仍然可用”。

不过，VP9 通常比 VP8 消耗更多 CPU。高码率、高分辨率下，编码端是否承担得起这份计算开销，需要单独评估。不能只看压缩收益而忽略设备发热、能耗和服务端计算成本。

## VP9 的实际采用与工程限制

Google 在 VP9 推出时积极展示其压缩能力，YouTube 曾用它以相近码率提供更高分辨率，尤其改善低带宽地区的观看体验；YouTube 后来也使用 AV1。但点播平台的使用情况不能直接代表 WebRTC。

课程引用的一组较早统计中，Chrome 的 WebRTC 使用约有 90% 为 VP8、约 10% 为 H.264，VP9 只占很小部分。这组数据产生于 Google Meet 采用 VP9 之前。按课程录制时的情况，VP9 已成为 Google Meet 的主要编解码器，Jitsi Meet 也在使用，Agora 于 2023 年加入支持，因此旧比例已不能代表当时的市场结构。

在工程上仍需注意以下限制：

- **浏览器与设备能力并不完全一致。** VP9 在现代浏览器中大体可用，解码器分布很广，编码器则要看设备 CPU 是否能承受；Safari 的支持在课程中被描述为“存在但并不完全可用”。
- **SVC 生态不透明。** VP9 支持可伸缩视频编码，但课程指出，当时缺少充分的公开文档和配套生态。开发者可能需要自行研究，甚至逆向分析 Google Meet 的实现方式。
- **硬件支持有限。** 硬件解码比硬件编码更常见，针对 SVC 的硬件支持尤其有限。
- **实际收益需要测量。** 课程提到的初步反馈是质量确有改善，但幅度可能很小。不要直接套用宣传中的百分比，应在自己的内容、码率、分辨率和设备上测试。

## HEVC：更强编码工具与硬件依赖

HEVC 是 H.264 的后继技术，编码时可使用的工具更多。课程以 H.264 的 8×8、16×16 宏块为对比，强调 HEVC 的块划分更灵活，因而更适合大尺寸图像。在 4K、8K 乃至 16K 等分辨率下，继续使用 H.264 很难保持同样效率。

HEVC 在 WebRTC 中的关键问题不是压缩能力，而是可用性。按课程录制时的观察：

- Apple 是主要推动者，在 iOS 和 macOS 设备中提供硬件编码器与解码器，并长期用于 FaceTime。
- Intel 也表达了在芯片组中支持 WebRTC HEVC 的兴趣。课程认为，这可能是在硬件能力已经存在后，进一步向软件与 WebRTC 开放。
- Chrome、Edge 和 Safari 已出现支持迹象；当时尚未看到 Firefox 跟进的明确信号。

浏览器中的 HEVC 实现主要依赖硬件加速，而不是通用的软件编解码器。原因仍与许可有关：若由浏览器提供软件实现，版税责任更可能落到浏览器厂商身上；若能力来自芯片组和硬件，相关费用通常已在硬件供应链的其他环节处理。

这意味着 HEVC 可能只在经过适配的 iOS、Mac，以及部分较新的 Android 和 PC 设备上可用。应用必须识别实际设备能力，并准备不支持时的替代方案，不能把“浏览器出现支持”理解成“所有设备都能使用”。

## 如何选择 VP9 或 HEVC

| 场景 | 课程建议与理由 |
| --- | --- |
| 群组通话，尤其大型、低分辨率通话 | 可优先考虑 VP9。一次编码、多次解码，而编码通常比解码更耗 CPU；大型通话中往往也不会以高分辨率观看每个人。 |
| 有可用的 VP9 硬件编码器 | 更适合采用 VP9，可降低软件编码带来的 CPU 压力。 |
| 低码率云游戏 | 可考虑 VP9，甚至 AV1。低码率下编码负载相对可控，压缩效率更有价值。 |
| 设备统一且可控，例如全部为 Apple 设备 | 可考虑 HEVC。设备能力明确，边缘情况和兼容风险较少。 |
| 点对点通话 | 可机会主义地选择 HEVC：确认本次通话两端均支持后再启用；若随后切换到媒体服务器进行群组通话，则重新决策。 |
| 需要最广泛兼容、没有能力探测与回退机制 | VP8 和 H.264 仍是最稳妥的基线，因为它们是 WebRTC 必须实现的编解码器。 |

## 小结

VP9 的核心价值是在同等质量下降低码率，或在同等码率下提升质量，但代价通常是更高 CPU 消耗，以及硬件编码和 SVC 生态方面的不确定性。HEVC 提供适合高分辨率的高效编码工具，却受到专利池碎片化和硬件依赖的制约。

按课程录制时的概括，VP8 与 H.264 几乎无处不在；VP9 接近普遍可用，但 Safari、硬件加速和 SVC 仍需特别验证；HEVC 在 Chrome、Edge、Safari 上逐渐出现，主要限于硬件实现，而当时 Firefox 尚未提供支持。最终选择应基于真实终端、具体码率与通话架构，而不是只依据编解码器的代际名称。
