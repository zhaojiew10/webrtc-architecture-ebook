# 第 2 章 什么是 WebRTC

理解 WebRTC，既要说明它能做什么，也要划清它的边界。本章从媒体引擎、浏览器标准和开源实现三个角度建立定义，再拆解一个 WebRTC 应用所需的客户端、服务器与会话协商过程，最后回顾其从实验技术走向实时通信基础设施的历程。

## WebRTC 的定义与边界

如果用一句话概括，**WebRTC 让浏览器原生提供实时通信能力**。在支持它的现代浏览器中，这项能力已经内置；对于直接在浏览器里使用的应用，用户不必另外安装插件或下载媒体引擎。

更具体地说，WebRTC 是一个带有 JavaScript API 的媒体引擎。媒体引擎并不是 WebRTC 发明的新事物：它负责处理媒体，并通过网络发送和接收媒体；在实时互动场景中，这些处理必须以足够低的时延完成。WebRTC 的关键变化在于，它把这类能力做进浏览器，并通过标准化的 JavaScript API 向 Web 开发者开放。

必须同时记住另一点：**WebRTC 是一项技术、一个基础构件，而不是完整解决方案。**因此，“WebRTC 与 Zoom 或 Skype 相比怎么样”并不是同一层次的比较。Zoom 和 Skype 是完整应用，可能使用 WebRTC，也可能使用其他技术；合理的比较对象是两个应用或解决方案，例如基于 WebRTC 的 Google Meet 与其他会议产品。对开发者而言，更有意义的问题是：能否用 WebRTC 构建出满足特定需求的产品。

## 标准规范与开源软件栈

“WebRTC”在日常讨论中常有两个相互关联的含义。

### 作为浏览器技术的 WebRTC 1.0

WebRTC 1.0 是浏览器技术的标准规范，于 2021 年完成，整个标准化过程约历时十年。在此之前，开发者、产品和供应商已经将 WebRTC 用于生产环境，并未等到正式规范完成后才采用它。

标准化工作主要由两个组织承担：

- **IETF** 负责网络上传输的协议及相关规范。
- **W3C** 负责 Web 侧的 API 等工作，包括基于 JavaScript 的 WebRTC API；其工作范围也包括 HTML、CSS 等 Web 技术。

### 作为开源项目的 libwebrtc

webrtc.org 所代表的开源项目由 Google 维护和开发，其中的 **libwebrtc** 是 WebRTC 规范的软件实现。课程所描述的浏览器支持正是建立在这一实现及其生态之上。开发者可以下载源代码，将它移植到自己的操作系统，也可以按需要选取其中一部分并做定制。

因此，讨论 WebRTC 时需要分辨自己指的是标准规范，还是 libwebrtc 这套软件栈。实际交流中两者经常交替使用，但在分析兼容性、实现缺陷或移植工作时，这个区别十分重要。

## 一个完整应用需要哪些组成部分

浏览器已经提供客户端媒体引擎，并不意味着一个 WebRTC 应用只需要浏览器。完整系统通常包含以下部分：

| 组成部分 | 职责与注意事项 |
| --- | --- |
| 浏览器客户端 | 浏览器内置 WebRTC，可直接通过 JavaScript API 构建应用。 |
| 移动端或其他原生客户端 | 可将开源的 WebRTC 实现移植到目标系统，再按产品需求修改和定制。许多供应商采用这种方式。 |
| 应用服务器 | 承载应用逻辑，与其他 Web 应用的应用服务器承担类似职责。 |
| 信令服务器 | 在 WebRTC 客户端之间传递建立会话所需的消息，包括携带 SDP 的消息，以便发现并联系其他用户。它可以与应用服务器合并，也可以独立部署，取决于应用设计。 |
| STUN/TURN 服务器 | 帮助媒体穿越防火墙和网络地址转换（NAT），建立可用的网络路径。 |
| 媒体服务器 | 常用于录制或多人通话等场景。它在 WebRTC 中并非绝对必需，但许多实际应用都需要。 |

“WebRTC 已在浏览器里”只解决了其中一层。应用逻辑、信令、网络穿越和媒体处理仍然需要架构设计与部署决策。

## 会话如何建立

设想两个参与者：一端使用 Chrome，另一端使用移动设备上的原生应用，中间是应用的信令服务器。最基本的呼叫过程如下：

1. 发起方希望与接收方通信，先产生一个**提议（offer）**，通过信令服务器发送给接收方。
2. 信令服务器可以原样转发消息，也可以按应用需要修改消息内容。
3. 接收方得知有传入会话，选择接受后生成**应答（answer）**，再经信令服务器返回发起方。
4. 提议与应答交换完成后，双方进入后续连接过程，媒体可以在两个对等端之间传输，而不必把所有媒体都交给应用服务器中转。

这一提议—应答过程称为 **JSEP**，其中使用**会话描述协议（SDP）**描述会话。SDP 中承载的信息包括音频或视频会话的需求、希望使用的编解码器及其他能力描述。

这里有一个常见误区：**WebRTC 并没有规定应用必须用哪一种信令协议来传输这些消息。**SDP 等内容有相应规范，但消息怎样经过网络、由什么应用协议封装，需要由应用自行决定。也就是说，“不指定信令”不等于“不需要信令”。

媒体能够在浏览器或原生对等端之间直接流动，是 WebRTC 与许多传统浏览器通信方式的重要差别。常规 Web 数据交换主要发生在客户端和服务器之间，而 WebRTC 还能在对等端之间传送媒体或任意数据。对等通信在 VoIP 领域早已存在，WebRTC 则把这套能力带进了浏览器。所谓“直接”仍受网络条件约束，后文提到的 STUN/TURN 正是连接建立的重要组成部分。

## 三组主要 API

本章先用三组 API 建立整体认识，后续章节再展开接口细节。

### 媒体采集

媒体采集中的 `getUserMedia` 可让应用获得摄像头和麦克风等输入。它严格来说并不专属于 WebRTC，但语音、视频通话通常需要它。应用也可以单独使用采集能力，例如拍摄用户头像或获取屏幕相关内容，而不建立 WebRTC 通话。

### 对等连接

`RTCPeerConnection` 是 WebRTC 的核心对象。会话协商、媒体编码与解码、网络发送以及 NAT 穿越等工作都围绕它展开，也是实时、低时延通信的主要承载对象。

### 数据通道

数据通道用于在对等端之间发送任意数据，而不仅是音频和视频。它适合需要低时延的数据交互；在采用直接对等路径时，业务数据无需经过应用服务器转发，这也可能有助于某些隐私设计。但路径是否真正直连取决于网络环境，不能把这一点理解为无条件承诺。

## WebRTC 为什么重要

媒体引擎早已存在，WebRTC 的影响主要来自开放程度、Web 开发方式以及它降低的采用门槛。

### 自由使用的高质量媒体引擎

WebRTC 提供可自由使用的开源实现，采用宽松的 BSD 许可证。开发者可以使用、修改和移植源代码，并将修改后的版本部署到自己的产品中，而无须把这些修改贡献回 WebRTC 库。高性能、高质量的媒体引擎因此不再只是少数专业厂商才能负担的构件。

课程同时提到，当时行业通常不把 WebRTC 视为存在突出专利许可障碍的技术，但也曾出现少量相关诉讼。因此，这一历史背景不应被解读成对未来法律风险的绝对保证。

### 面向更广泛的开发者

传统 VoIP 开发往往要求工程师掌握专门的呼叫与媒体知识。WebRTC 通过 JavaScript API 和浏览器中的现成实现，让 Web 开发者也能从简单示例开始构建实时通信应用。它减少了底层媒体工程的重复工作，在许多应用中降低了组建专门媒体工程团队的必要性。

这并不表示实时媒体从此没有技术难度，而是说更多开发者可以参与应用和使用场景的创新，不必每个人都先实现一套媒体引擎。

### 降低最终用户的操作阻力

对于浏览器应用，用户打开网址即可尝试发起通话，不需要安装插件、下载单独应用或先进入应用商店。步骤减少带来两方面收益：

1. 下载和安装环节更少，因设备、语言环境或安装步骤不兼容而失败的机会也随之减少。
2. 每个额外操作都是用户可能放弃的关键点，减少操作能提高用户真正完成通信的概率。

例如，电商网站希望访客尽快联系客服。如果访客在通话前必须先安装软件，就需要额外判断这次通话是否值得付出安装成本；浏览器内直接通信可以消除这道门槛。这里的优势针对浏览器使用方式，并不表示原生应用本身没有价值。

### 降低新供应商的进入门槛

开源许可、浏览器内置实现和减少底层媒体工程投入，共同降低了新供应商进入市场的成本。课程把这看作促进竞争、创新和用户选择的重要因素。

**不强制指定信令协议**也是这种开放性的一部分。开发者可以选择基于标准的方案，例如 SIP over WebSocket、XMPP 或 MQTT，也可以使用适合特定场景的专有信令。假设一个交友网站已有用户消息系统，现在需要加入语音或视频通话，就可以让 WebRTC 所需的会话消息复用原有信令通道，而不必另外建设一套并协调两套系统。

## WebRTC 位于 VoIP 与 Web 的交叉点

WebRTC 一端连接传统 VoIP 的语音、视频通信技术，另一端连接浏览器中的 HTML、JavaScript，以及 Web 应用的开发、测试、扩展和维护方式。

只具备其中一个背景，容易忽略另一侧的问题：

- 来自传统 VoIP 的开发者需要理解 Web 应用的工程方式与用户环境。
- 来自 Web 的开发者则需要补上实时媒体、呼叫和网络传输等知识。

这种交叉也解释了为什么 WebRTC 架构设计不能只考虑 API 调用。开发者通常并不控制应用运行的全部条件：

- **网络不受控制**：需要面对质量良好或恶劣的网络，以及蜂窝、有线和 Wi-Fi 等不同环境。
- **用户设备和外设不受控制**：设备可能新旧不一，包括不同尺寸的移动设备和桌面设备，外设行为也会带来额外问题。
- **浏览器实现不受控制**：不同浏览器的行为存在差异，浏览器变化也可能打破应用原先依赖的假设。

应用逻辑只是主角之一，架构必须把这些不可控因素纳入设计。

## WebRTC 的发展历程

### 技术来源：On2 与 GIPS

Google 在 2010 年收购 On2。On2 拥有 VPx 视频编解码技术，当时的 VP6、VP7 是专有编解码器，并曾用于 Adobe Flash。Google 随后围绕开放、免版税编解码器目标建设 WebM 项目。

同年 5 月，Google 收购 GIPS。GIPS 的资产包括语音引擎、视频引擎以及 iLBC、iSAC 编解码器。iLBC 当时因 Skype 的使用而广为人知；课程强调这类编解码器具有抗误码设计，iLBC 内部包含前向纠错能力，iSAC 则面向宽带音频。GIPS 的客户还包括 Google、Yahoo、Avaya 等厂商。Google 最终利用其语音、视频引擎等基础设施构建 WebRTC。

2013 年 3 月，Google 又与 MPEG LA 就 VP8 相关专利许可达成协议，使 VP8 能以免版税方案的形式用于 WebRTC。至此，视频编解码技术、语音引擎和视频引擎被组合为 WebRTC 的技术基础。

### 从源代码发布到跨浏览器、跨平台

| 时间 | 课程列举的进展 |
| --- | --- |
| 2011 年 5 月 | WebRTC 对外发布，源代码首次以宽松的 BSD 许可证开放。此时它仍很粗糙，尚未形成可用的浏览器生态。 |
| 2012 年 11 月（课程幻灯片误标为 2011 年） | Chrome 23 默认加入 WebRTC 支持。当时能力不完善，不支持数据通道，也没有其他浏览器支持，回声消除等效果仍有问题。 |
| 2012 年 | 课程将其概括为相对平静的一年。 |
| 2013 年 1 月 | Firefox 20 加入早期支持，主要是 `getUserMedia`，可访问摄像头等能力。 |
| 2013 年 2 月 | Firefox 与 Chrome 实现视频通话互通，首次清楚展示跨浏览器实时通信的方向。 |
| 2013 年 6 月 | Firefox 22 加入数据通道 API，在浏览器实现中早于 Chrome 提供这一能力。 |
| 2013 年 7—9 月 | Chrome for Android 先以测试版支持 WebRTC，8 月转为正式发布；9 月 Firefox for Android 也加入支持。WebRTC 由此进入移动浏览器。 |
| 2013 年底 | 课程估计已有约 100 家公司、应用或初创团队使用或试验 WebRTC。 |

2014 年，Opera 18 测试版通过 libwebrtc 引入 WebRTC，随后 Opera for Android 也加入支持。Microsoft 曾承诺让 Internet Explorer 支持 `getUserMedia`，但课程指出这一目标并未真正实现。Microsoft 同年宣布支持对象实时通信（ORTC），它一度被视为 WebRTC 标准化的竞争路线，甚至有人称之为“WebRTC 1.1”；后来独立的 ORTC 路线被放弃，其概念转而被吸收到 WebRTC 中。

### 2015 年前后的生态扩张

2015 年是课程重点回顾的繁忙年份，多个事件表明 WebRTC 已不只是浏览器实验：

- AT&T 在 CPaaS 平台中推出增强 WebRTC API，虽然后来放弃该项目，但它比正式标准完成早了约六年。
- Cisco 发布 Spark，即后来 Cisco Webex 所对应的产品，提供类似 Slack 并包含语音、视频能力的协作方案。
- Google 将 WebRTC 演示移到 GitHub，让开发者更容易获取和使用示例。
- Facebook Messenger 首次加入 WebRTC 支持；Atlassian 收购开源媒体服务器项目 Jitsi。
- Chrome 移除 NPAPI 插件支持，Microsoft 的新 Edge 也采取相同方向，浏览器通信进一步摆脱插件模式。
- Twilio Video 进入非公开测试；Cisco 收购当时支持 WebRTC 的 Tropo，后来又将其关闭。
- 开放媒体联盟（Alliance for Open Media）在课程所述的 2015 年下半年形成，浏览器厂商及其他供应商共同推动 AV1 视频编解码器，AV1 此后逐步进入 WebRTC。
- Microsoft Edge 一度加入 ORTC 支持，后来放弃独立路线并转向 Chromium 基础；Cisco 收购使用 WebRTC 提供高端浏览器视频会议的 Acano。
- 课程还提到 Spotlight 广播功能的出现，用它说明 CPaaS 平台开始把广播能力纳入产品；Chrome 同时转向以 HTTPS 为重点，与 WebRTC 对安全上下文的要求方向一致。

2016 年被课程概括为缺少标志性进展的一年，Internet Explorer 和 Apple 的平台支持仍然明显缺席。到 2017 年，Microsoft Edge 开始支持 WebRTC，Safari 也开始加入支持。2017—2018 年围绕 WebRTC 1.0 “即将完成”的讨论很多，但正式完成最终是在 2021 年。

### 事实标准、疫情与差异化竞争

到 2019 年，WebRTC 已成为实时媒体通信的**事实标准**。Google、Microsoft、Facebook、Cisco、Amazon 等公司都在使用 WebRTC。这里的“事实标准”描述行业采用程度，不应与 2021 年完成的 WebRTC 1.0 正式规范混为一谈。

同一时期 Zoom 快速成长。课程特别指出，在当时观察到的大规模视频通话中，Zoom 并未直接采用 WebRTC，也没有当时加入 WebRTC 的计划，这与行业广泛采用形成了有趣对照。2019—2020 年，Microsoft 则完成了从自有技术基础的旧 Edge 到基于 Chromium 的新 Edge 的迁移，新 Edge 与 Chrome 使用相同的浏览器基础。

2020 年疫情显著提高了实时通信需求：通话分钟数、用户量和所需服务器数量都随之增长。课程以 Chrome Status 中 `addStream` 相关 API 的页面流量为例，指出疫情期间出现四倍或更高的增长；到课程所说的后疫情阶段，相关使用量仍约为疫情前的四倍。这里反映的是采用程度的跃升，而不是某一项 API 本身构成了全部增长原因。

课程把整个历程归纳为三个阶段：

| 阶段 | 核心问题 | 主要特征 |
| --- | --- | --- |
| 2011—2014：探索期 | “我应该使用 WebRTC 吗？它适合我吗？” | 浏览器支持不完整，开发者需要权衡缺少 Internet Explorer 等环境时怎么办。 |
| 2015—2019：增长期 | “我应该怎样使用它？” | 重点转向在应用中落地；Edge、Safari 陆续加入，现代浏览器支持逐步完整。 |
| 2020 年以后：差异化期 | “既然使用 WebRTC 已成共识，我如何竞争？” | 正式标准消除了部分不确定性；Zoom 塑造了用户对质量、按钮和整体体验的预期；疫情又改变了使用场景和需求规模。 |

差异化并不意味着所有产品都在与 Zoom 直接竞争，而是用户会自然地把熟悉的会议产品质量和体验当作参照。

## 行业采用情况

课程以录制时 Gartner 通信领域的若干魔力象限为参照，归纳了 WebRTC 的行业渗透情况：

- **会议解决方案**：几乎所有领先厂商都在某种程度上使用 WebRTC，包括 Cisco 和 Microsoft。Zoom 当时虽未在视频通话中直接使用 WebRTC，但其原生应用使用了 WebRTC 的一些组件。
- **统一通信即服务（UCaaS）**：几乎所有领先厂商都使用 WebRTC，至少用于浏览器访客接入，即使它不是应用的主要接入方式。课程列举了 RingCentral、Google、LogMeIn，以及通过 Jitsi 等布局 WebRTC 的 8x8。
- **联络中心即服务（CCaaS）**：课程观察到的领先厂商也都在使用 WebRTC。疫情后的居家办公让坐席无需安装软件、直接通过浏览器工作变得尤其重要，浏览器接入因此快速普及。

这些例子说明，WebRTC 未必总是产品唯一或主要的媒体路径，却经常承担浏览器访问、访客接入等关键角色。

## 小结

WebRTC 是浏览器原生实时通信能力、WebRTC 1.0 标准和 libwebrtc 开源实现共同构成的技术体系，而不是开箱即用的完整产品。它通过提议—应答和 SDP 描述会话，由应用自行选择信令，并结合 STUN/TURN 等组件建立连接。

它的核心价值在于把高质量媒体引擎以开放方式提供给更广泛的开发者，同时减少浏览器用户的操作步骤和新供应商的进入成本。要真正设计可靠的 WebRTC 应用，仍须处理网络、设备、浏览器差异以及应用服务器、信令和媒体服务等完整系统问题。
