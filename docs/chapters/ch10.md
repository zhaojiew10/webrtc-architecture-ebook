# 第 10 章 WebSocket

传统 HTTP 擅长“客户端请求、服务器响应”，却不擅长服务器在有事件时立即通知浏览器，也不适合类似对话的持续双向通信。为弥补这一差距，Web 先后使用了 XHR 轮询、长轮询和服务器发送事件（SSE）等办法，WebSocket 则通过协议切换建立了真正的双向消息通道。

## 问题：服务器如何主动通知客户端

早期 Web 主要消费静态页面：浏览器请求页面或资源，服务器返回响应。除响应请求外，服务器通常不主动做什么。

交互式网站改变了这一需求。Gmail 收到新邮件、Facebook 出现新状态，或者 WebRTC 应用收到来电时，状态可能在用户没有操作的情况下因外部事件而变化，服务器需要及时通知浏览器。在课程所讨论的传统 HTTP 请求—响应模式中，服务器不能任意向客户端发起一条消息，只能借助已有的请求和连接想办法把事件送出去。

可选路线分为两类：一类继续利用 HTTP，通过轮询、长轮询或流式响应变通；另一类是在 HTTP 建立连接后切换到 WebSocket。

## XHR 轮询

XHR 指 `XMLHttpRequest`。用 XHR 做普通轮询时，浏览器周期性询问服务器“有没有新事件”，其过程如下：

1. 浏览器向服务器发送请求；
2. 若没有事件，服务器立即返回“没有内容”；
3. 客户端等待一个轮询间隔，再发送下一次请求；
4. 若服务器已经收集到事件，就在某次响应中把事件返回；
5. 浏览器处理响应，并继续安排下一轮请求。

课程示例用 `checkUpdates` 创建并发送 `XMLHttpRequest`，在 `onload` 中处理服务器响应，再用 `setInterval` 每 60 秒调用一次 `checkUpdates`。

这种方法有两个相互牵制的问题：

- **网络请求过多**：即使消息一天或一小时才出现一次，客户端仍可能每分钟都发请求。缩短间隔会增加无用流量，增大间隔又会降低及时性。
- **事件延迟**：事件发生后，要等到下一次轮询才能取回。60 秒的间隔意味着事件可能最多延迟约一分钟；对需要接听或拒绝的来电，这通常不可接受。

此外，服务器需要缓冲区或队列暂存事件，因为事件到达时未必正好有一个客户端请求可供响应。

## 长轮询与 Comet

长轮询（long polling，也称 Comet）让服务器暂时不完成响应，以减少等待下一次轮询造成的延迟：

1. 浏览器发送一个挂起的 `GET` 请求，含义相当于“有事情发生时再回复”；
2. 服务器保持该请求，不立即作答；
3. 事件发生，或者等待定时器到期时，服务器返回响应；
4. 客户端在 `onload` 中处理事件；
5. 客户端立即再次调用 `checkUpdates`，发出下一个挂起请求。

长轮询同样需要服务器配合：浏览器仍然只是创建并发送 `XMLHttpRequest`，真正让请求“挂起”的是服务器延迟响应的策略。

与固定间隔轮询相比，事件可以更快送回客户端，但它并没有消除所有成本：

- 大量请求会在服务器上保持打开，占用连接资源；
- 在 HTTP/1.0 和 HTTP/1.1 的典型限制下，挂起请求所占的连接不能同时用于其他请求；
- 从服务器发出事件响应，到客户端下一个挂起请求到达之间仍有间隙，因此服务器仍需缓冲这一间隙内的新事件；
- 服务器还要持续管理大量待处理请求和超时。

## SSE：让响应保持为事件流

服务器发送事件（SSE，Server-Sent Events）采用另一种方式：不是反复留下未完成请求，而是让一次响应长期不结束。

其步骤是：

1. 客户端发出一个请求，建立事件源（`EventSource`）；
2. 服务器有事件时，把它作为响应的一部分发送，而不是完成整个响应；
3. 客户端通过 `onmessage` 处理收到的事件；
4. 后续事件继续沿同一个响应流发送；
5. 直到事件源或会话需要关闭，才结束这一过程。

因此，不需要为每个事件再发一个新请求。其思路与某些基于 HTTP 的流式传输相近：打开单一请求，把连续内容作为流交付。SSE 很适合服务器连续产生许多事件的场景，但它仍是在 HTTP 请求—响应模型上的变通，而不是任意的双向对话。

## WebSocket 的协议切换

轮询、长轮询和 SSE 都试图在 HTTP 内解决服务器事件通知问题。WebSocket 的目标则更直接：提供持续、双向、可携带二进制数据的消息通道，同时又能与现有 HTTP/HTTPS 环境并行工作，不必完全抛开浏览器和 Web 基础设施重新设计一套入口。

建立 WebSocket 的过程分为两个阶段：

1. **通过 HTTP/HTTPS 检查并建立连接。**客户端先发送 HTTP 请求，询问服务器是否支持 WebSocket；服务器再通过 HTTP 响应确认支持。
2. **切换到 WebSocket。**双方确认支持后，连接从 HTTP 切换为 WebSocket，随后客户端和服务器直接通过 WebSocket 双向传递消息，不再把每次通信组织成一次 HTTP 请求和响应。

在 WebRTC 场景中，课程要求使用 HTTPS 完成这一阶段，因为安全性是必需的。WebSocket 得到现代浏览器和大多数 Web 代理支持，课程将其视为浏览器中完成这类通信的高效方式。

## 浏览器中的消息接口

浏览器端通过 URL 创建 `WebSocket` 对象，创建对象就会开始建立连接。随后主要使用四类事件回调和一个发送方法：

| 接口 | 作用 |
|---|---|
| `onopen` | 连接已经打开，可以开始使用 |
| `onmessage` | 收到对端发来的消息 |
| `onerror` | 处理错误等异常情况 |
| `onclose` | 处理 WebSocket 连接关闭 |
| `send` | 向对端发送自己的消息 |

`send` 可以发送文本、数据块（Blob）或所需的二进制数据。连接建立后，任何一端都可以发送消息；每条消息是单向地从一端到另一端，但通信双方的角色不再被固定为“只能请求的客户端”和“只能响应的服务器”。

## XHR、SSE 与 WebSocket 对照

课程从消息流、封装、二进制和压缩等方面比较了三种方案：

| 对比项 | XHR | SSE | WebSocket |
|---|---|---|---|
| 请求方向的流式能力 | 不支持，一次发送一个请求 | 不支持任意请求流 | 建立后不再受请求—响应模型约束，可连续发送消息 |
| 响应方向的流式能力 | 受限 | 支持持续事件流 | 支持持续消息流 |
| 封装机制 | HTTP | 事件流 | WebSocket 协议自带的二进制帧 |
| 二进制数据 | 支持 | 不直接支持，课程以 Base64 编码作为限制说明 | 支持 |
| 压缩 | 原生支持 | 原生支持 | 课程所述支持较有限，需要应用自行处理时不能指望协议自动完成 |
| 应用传输协议 | HTTP | HTTP | 建立后使用 WebSocket 自身 |
| 主要网络传输 | TCP 为主 | TCP 为主 | TCP 为主 |

按课程对 SSE 的说明，用 Base64 承载二进制时，每个编码字符只承载 6 位数据，因而不能像直接传输二进制那样让每 8 位都用于原始数据。WebSocket 的优势也不只是“服务器可以响应”，而是双方可以在同一已建立连接上随时发消息，不受请求和响应必须配对的限制。

课程表格以 TCP 为三者的主要网络传输，同时提示实际下层协议还取决于浏览器、服务器和所采用的 HTTP 协议栈；课程录制时仍以 TCP 为主，后续可能随这些实现的支持而演变。

## Socket.IO 的定位

Socket.IO 可看作对 WebSocket 可用性的一种尽力而为封装：在不能按理想方式工作时，它会自动回退到 HTTP，课程还提到可回退到 Flash 或其他机制；录制时也已出现关注 WebTransport 支持的实现。其目标是尽可能在各种环境中工作，利用当时实际可用的能力。

这是否意味着应当用 Socket.IO 替代 WebSocket，课程没有给出确定答案。需要区分的是，WebSocket 是一种协议和浏览器接口，而 Socket.IO 的重点是兼容与自动回退。

## 小结

XHR 轮询实现简单，却要在无用请求与通知延迟之间取舍；长轮询通过挂起请求降低延迟，但占用连接并仍需缓冲；SSE 用一个不结束的响应持续发送服务器事件。WebSocket 先经 HTTP/HTTPS 建立连接，再切换为独立的双向消息协议，支持文本和二进制数据，更接近 WebRTC 信令所需要的持续对话模型。
