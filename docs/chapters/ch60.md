# 第 60 章 WebRTC 标准化

开发 WebRTC 应用时，面对的不只是“是否符合标准”这一个问题，还要同时考虑浏览器已经实现的接口和产品自身的交付要求。课程讨论这一主题时，WebRTC 1.0 仍处于制定过程中，因此开发者必须在规范草案、浏览器实现和项目进度之间作出取舍。

## 两种开发依据：规范与浏览器实现

课程区分了两种需要同时关注的 WebRTC：

- **WebRTC 1.0 规范**：由 W3C 和 IETF 负责制定。在课程所述时间点，它尚不可用，存在的主要是规范草案。
- **浏览器中的实际实现**：应用真正调用的接口和行为。课程尤其关注当时市场份额较大的 Chrome，但不同浏览器的实现并不完全一致。

因此，“按照 WebRTC 开发”还需要进一步说明：是对齐 WebRTC 1.0 规范，还是对齐某个浏览器的现有实现？答案取决于标准制定方式、浏览器迁移策略以及产品需求。

## 规范、产品需求与实现的三角关系

实现者需要处理三个彼此关联、但并不总是重合的方面：

1. **标准规范**：接口和行为在理论上应当怎样定义。
2. **产品需求**：正在构建的产品必须实现什么，以及何时需要。
3. **实际实现**：把规范或需求转化为可以运行的产品。

在规范尚未稳定、浏览器实现又各不相同的阶段，有限的项目时间往往只允许优先兼顾其中两项：

- 可以让实现贴近规范，却未必能及时满足全部产品需求；
- 可以让实现满足产品需求，却可能暂时偏离规范；
- 也可以让需求完全符合规范，但当下未必存在可直接采用的实现。

随着规范成熟、实现逐步迁移，三者才有机会逐渐靠拢。课程所说的“三者不能同时得到”，描述的是这一发展阶段的时间约束，而不是三者永远互斥。

## 标准制定为何需要时间

标准由委员会共同制定。参与者来自不同国家和公司，各自带着需要保护的利益、技术观点和议程。参与者都希望推动技术进步，但“共同作出决定”本身就需要协调。

标准制定者与工程实现者面对的约束也不相同。工程师为了交付产品，经常需要在现实条件下作取舍；标准制定者更倾向于追求理论上完整、合理的设计，不能随意绕过仍待明确的问题。课程讲师以自身参与标准制定的经验说明，这种差异是标准工作的一般特点，并非对 WebRTC 标准内部过程的直接披露。

课程回顾的时间线也体现了这种不确定性：WebRTC 1.0 最初曾计划在 2015 年发布，而到课程讲述时的 2017 年仍未正式发布，因此无法据此断言最终发布日期。同时，ORTC（Object RTC）中的一些重要内容已经找到归宿，或进入 WebRTC 本身，或先体现在浏览器实现中。WebRTC 1.0 试图一次解决大量问题，但仍有事项会留给后续版本；即使 1.0 发布，标准化也仍是持续推进的工作。

## 课程所述时期的浏览器差异

不同浏览器并非以同样的速度、朝同一个方向变化。课程描述的是当时的状态，不应直接当作后来的产品现状：

- **Firefox**：变化速度较快，重点不只是增加功能，也在于提高实现与规范草案的一致程度。
- **Chrome**：拥有庞大的现有用户和应用基础，更关注平稳迁移。如果过快废弃已有 API、立即改用仍在制定的接口，可能破坏已有应用，因此其实现不会在所有情况下都与规范草案使用完全相同的 API。
- **Microsoft Edge**：为使浏览器之间能够互操作，努力在行为上与 Chrome 对齐；Chrome 中的一些能力也会出现在 Edge 中。

这些差异说明，“浏览器支持 WebRTC”并不等于各浏览器提供完全一致的开发接口。

## 根据交付时间选择对齐策略

审视产品需求时，需要回答两个问题：

1. 产品需要完成什么？
2. 产品什么时候需要它？

如果可以等待半年或一年，就有更多空间向规范靠拢；如果功能已经迫在眉睫，则更应依据浏览器现有实现。课程给出的一般建议是：**实现对齐当前浏览器，同时为未来标准做好规划。**

具体做法包括：

- 持续了解规范的内容和方向，避免只熟悉某一个浏览器当前的接口；
- 使用 WebRTC 项目在 GitHub 上提供的 **adapter.js**；
- 在 adapter.js 提供的适配层之上开发，而不是直接依赖各浏览器原生的 WebRTC API 差异。

adapter.js 的作用是弥合浏览器之间、以及浏览器与规范之间的不一致。课程把它类比为当年 Web 开发中的 jQuery：未来也许不再需要，但在课程所述环境中，它仍是处理兼容差异的重要工具。

## 小结

WebRTC 标准化不是一份规范取代所有实现差异的瞬间事件，而是规范、产品需求和浏览器实现逐步收敛的过程。规范尚未稳定时，开发者应明确自己优先满足哪两项目标，并根据交付时间选择对齐对象。课程建议以实际浏览器实现支撑当前交付，以标准方向指导后续演进，并通过 adapter.js 降低跨浏览器和跨规范差异带来的影响。
