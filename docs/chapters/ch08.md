# 第 8 章 TCP 与 UDP

TCP 与 UDP 是后续理解 WebRTC 信令和媒体传输的基础。二者都位于传输层，却提供了几乎互补的服务：TCP 通过连接、确认和重传等机制提供可靠、有序的数据流；UDP 只承担轻量的数据报传输，把可靠性、顺序和拥塞处理等问题留给上层。

## OSI 模型与传输层

OSI 模型把网络分为七层，从物理层、数据链路层、网络层，一直到传输层、会话层、表示层和应用层。物理层和数据链路层可视为硬件及底层设备驱动的基础；会话层、表示层和应用层则靠近应用运行的用户空间。TCP 和 UDP 位于中间的传输层，现代操作系统的网络协议栈都包含对它们的支持。

两台设备各自具有 IPv4 或 IPv6 地址。以 IPv4 为例，地址由四个八位组构成。传输层不仅让一台机器能够向另一台机器发送消息，还允许同一对机器之间同时存在多个连接。区分这些连接需要端口：

- 数据从源机器的源端口发出；
- 数据发往目的机器的目的端口；
- 因而一次传输可由“源 IP、源端口、目的 IP、目的端口”这一组信息来标识。

TCP 与 UDP 都使用这样的源、目的地址和端口，但它们在此之上提供的能力不同。

## UDP：轻量、无连接的数据报传输

用户数据报协议（UDP，User Datagram Protocol）只做把消息从一端送往另一端所需的最基本工作。UDP 首部开销为 8 字节，其余主要是待发送的数据。发送时指定源 IP 与端口、目的 IP 与端口即可，不需要先建立和维护连接。

UDP 是面向消息的，但其交付没有任何保证。应用发出数据报后，既不知道它是否到达，也不能依赖协议获得以下能力。

### 不保证交付

连续发送内容为 `abcd` 和 `efgh` 的两个数据报，接收端可能只收到其中一个。发送端不会仅凭 UDP 得知另一个数据报已经丢失，更不会由 UDP 自动重传。

### 不保证顺序

多个数据报可能按不同于发送顺序的次序到达。上述两个数据报即使都送达，也可能变成先 `efgh`、后 `abcd`。UDP 不会在为应用交付前负责重排。

### 没有内置拥塞控制

应用可以持续以很快速度发送 UDP 数据报，而路径中的交换机和路由器需要接收、缓冲并转发这些数据包。发送量超过网络承受能力时，设备的缓冲区会带来排队延迟，设备也可能直接丢包。对实时通信而言，延迟尤其有害；UDP 本身既不会主动降低发送速率，也不会替应用解决这些问题。

因此，使用 UDP 并不意味着这些问题消失了，而是意味着是否需要交付保证、排序、重传和拥塞控制，以及如何实现它们，要由上层方案决定。

## TCP：面向连接的可靠字节流

传输控制协议（TCP，Transmission Control Protocol）采取相反的设计方向。它是面向连接的：发送数据前，先连接目的 IP 和端口，通过三次握手完成“发送消息—接收响应—再发送一条消息”的建立过程。连接建立后，双方可以在同一连接上双向发送数据。这一初始过程有建立成本，但为后续的可靠性和顺序保证提供了基础。

### 确认与重传

TCP 使用序列号标识数据，并通过交付确认让发送端知道对方已经收到数据。如果数据没有成功送达，TCP 会重传，再等待相应确认。序列号因此同时支撑确认、重传和有序交付。

### 有序交付

如果编号为 2 的数据先到，而编号为 1 的数据尚未到达，接收端的传输层不会直接把乱序结果交给应用。它会等待 1，或者指出 1 缺失并触发重传；待 1 到达后，再按 1、2 的正确顺序向应用交付，随后继续处理后续数据。

这也说明 TCP 是面向流的：应用看到的是连续、有序的数据流，而不是像 UDP 那样逐个独立保留的消息。

### 拥塞控制

TCP 内置拥塞控制。课程用一个简化过程说明其窗口变化：发送端有一个限制可发送数据段的窗口；一轮传输正常并得到确认时，窗口按倍数增长；出现丢包时，窗口显著缩小，课程示例中为减半；随后再逐步增加。

这种策略在状况良好时逐步利用可用带宽，一旦察觉到拥塞或丢包，就积极减少注入网络的数据量，再相对谨慎地恢复。它与 UDP 让应用自行决定发送速率的方式形成鲜明对比。若需进一步研究细节，课程推荐了《High Performance Browser Networking》。

## 传输安全的目标与协议

网络通信常用 Alice、Bob 和窃听者 Eve 来说明安全问题。Alice 与 Bob 希望交换消息，却不希望 Eve 读懂内容，因此需要加密。随之而来的关键问题是：双方如何在没有预先共享密钥的情况下，通过同一个可能被窃听的通道确定加密所需的信息？公钥与私钥机制用于解决这一类问题，本课不展开其细节。

课程将通信安全目标归纳为三项：

1. **完整性（integrity）**：接收到的数据没有被篡改或替换。
2. **身份验证（authentication）**：借助证书等机制识别服务器、发送者或接收者，确认其确为所声称的身份。
3. **保密性（confidentiality）**：对信息加密，使其他各方无法查看和读取通信内容。

在 TCP 与 UDP 之上，对应的安全协议分别是：

- **传输层安全（TLS，Transport Layer Security）**：可概括为“TCP 加安全保护”。
- **数据报传输层安全（DTLS，Datagram TLS）**：基于 TLS 的技术，可概括为“UDP 加安全保护”。

SSL 是 TLS 的前身。课程录制时以 TLS 1.3 作为当前版本的参照；部署应禁用 SSL 以及已弃用或配置不当的旧协议和弱密码套件，但不能据此认定 TLS 1.2 一概不安全。版本、密码套件和配置需要一起评估。

## TCP 与 UDP 对照

| 对比项 | UDP | TCP |
|---|---|---|
| 数据形态 | 面向消息的数据报 | 面向流的连续数据 |
| 交付 | 不可靠，不保证到达 | 可靠，通过确认与重传保证交付 |
| 顺序 | 不保证 | 按序交付给应用 |
| 连接 | 无连接，直接向目标 IP 和端口发送 | 面向连接，先经三次握手建立连接 |
| 协议机制 | 不内置排序、确认、重传和拥塞控制 | 提供分段排序、确认、重传和拥塞控制 |
| 基本首部开销 | 8 字节 | 20 字节或更多，另有确认和重传的成本 |
| 对应安全机制 | DTLS | TLS |

## 在 WebRTC 中的位置

WebRTC 并不是简单地“只用 UDP”或“只用 TCP”。信令几乎总是使用 TCP，但也存在使用 UDP 的情况；媒体通常使用 UDP，在特定网络条件下也可能需要 TCP。具体采用哪一种，要由后续介绍的连接协商、候选地址和回退机制共同决定。

## 小结

UDP 提供低开销、无连接的数据报服务，不保证交付、顺序，也不内置拥塞控制；TCP 通过连接、序列号、确认、重传和拥塞控制提供可靠有序的数据流。TLS 与 DTLS 分别承担 TCP 和 UDP 场景下的安全保护。理解这些差异，才能进一步理解 WebRTC 为何通常以 UDP 传输实时媒体，又为何仍需要 TCP 及其他回退路径。
