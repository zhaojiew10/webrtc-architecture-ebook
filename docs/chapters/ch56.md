# 第 56 章 PSTN 连接

把 WebRTC 应用接入公共交换电话网（PSTN），并不只是选择一台 SIP 服务器。首先要判断 SIP 在整个产品中的位置：它是现有业务的核心，还是只为少量电话接入提供边缘能力？这个判断会决定信令是否端到端使用 SIP、网关放在哪里，以及多方通话中的音频在哪里混合。

## 先判断 SIP 是否处于核心位置

PSTN 不等于 SIP。课程之所以把二者联系起来，是因为电话网后端和 PSTN 互联大量采用 SIP：应用通过 IP 网络和 SIP 语音能力，连接到手机号或固定电话号码。因此，真正需要先回答的不是“要不要 SIP”，而是“业务对 SIP 的依赖有多深”。

典型情况有两种：

- **SIP 是主体，WebRTC 是补充**：现有系统本来就是 VoIP 或电话系统，只是需要让浏览器用户接入。
- **WebRTC 是主体，SIP 位于边缘**：产品本来就是基于 WebRTC 的通信应用，只是偶尔需要让电话用户加入。

同样叫“PSTN 连接”，这两种情况不应照搬同一套架构。

## WebRTC 为核心：把 SIP 限制在边缘

当 SIP 只承担次要的电话接入能力时，课程建议不要不加区分地端到端使用 SIP。原因主要有三类。

### 只需要电话能力的一小部分

应用可能只需要把一个人连接到另一个人，并不需要保持通话、电话振铃、传统会议、呼叫转接或呼叫前转，更不需要大型专用交换机（PBX）的全部功能。此时引入完整 SIP 体系，往往超出实际需求。

SIP 面向传统电话业务，而现代应用中的“通话”可能只是一个功能。例如，在即时通信应用中发起群聊，通常只需建立一个群组并点击呼叫，不会要求用户先呼叫一人、保持该通话、再拨另一人并合并通话。若交互本身不是传统电话模型，强行让 SIP 适配所有业务逻辑，反而会增加实现难度。

### 应用已经有自己的信令通道

许多应用已有消息系统、业务逻辑和设备之间的信令通道，再增加一条平行运行的 SIP 通道，会形成重复建设。

课程以约会应用增加语音和视频通话为例：用户原本已经能在应用内互相联系和发送消息，因此可以直接利用现有协议传递 WebRTC 所需的 SDP，而不是另外引入 SIP over WebSocket。熟悉 VoIP 的开发者容易从既有经验出发选择 SIP，但架构上应先盘点已经存在的通道。

### 不必继承全部历史机制

SIP 的设计背景早于现代智能手机、推送通知等能力，后来逐步增加了相应机制。对于没有 SIP 既有系统和技术积累的新应用，这些附加机制未必都是必需的。如果主要业务是通过网站和浏览器连接用户，只有少数人从 PSTN 加入，更合理的做法通常是只在电话互联边界使用 SIP。

### 边缘网关的媒体与信令路径

这种网关可以用下面的逻辑路径表示：

**WebRTC 应用：专有信令 + WebRTC 媒体 → 网关 → SIP 信令 + RTP 媒体 → SIP 中继或电话基础设施 → PSTN。**

网关左侧继续使用应用自己的业务信令，右侧才转换为电话系统需要的 SIP 和 RTP。SIP 因而停留在边缘，而不是扩散到整个应用核心。

### 可选组件与实现方式

FreeSWITCH 和 Asterisk 等开源项目同时支持 SIP 与 WebRTC，可用于构建这种连接。它们也支持 SIP over WebSocket，使浏览器能够运行 WebRTC 并使用 SIP over WebSocket；FreeSWITCH 还提供名为 Verto 的专有信令方案。选择哪一种取决于应用，但在“WebRTC 为核心”的场景中，重点是让 FreeSWITCH 或 Asterisk 位于边缘，而不是把它们变成整个应用的核心基础设施。

大型应用也可以基于已经在使用的媒体服务器构建 PSTN 网关，例如 Janus、mediasoup 或 Jitsi。课程讲师观察到的常见选择是使用 Janus 承担 SIP 网关，让一侧连接 WebRTC，另一侧连接 SIP 和 RTP。

现有媒体框架还可能提供 SIP 互联组件：

- Jitsi 体系有 Jigasi，用于连接 SIP。
- 课程提到 Kurento 的 SIP 网关能力，但明确不建议在课程录制时继续采用它。
- Jitsi as a Service 可以提供 PSTN 连接；即使会议仍运行在自建的 Jitsi 部署上，也可以利用这项服务完成电话接入。

这些选项解决的是同一类边界转换问题，选择时应服从现有媒体架构，而不是先引入一套与核心系统平行的电话体系。

## SIP 为核心：让 WebRTC 接入现有电话系统

相反，如果现有系统本来就围绕 SIP 建设，就应从另一侧设计“进入 WebRTC 的网关”。呼叫中心是典型例子，尤其是较早建设、绝大多数呼叫本来就来自 PSTN 的系统。新需求通常只是：客户希望使用网页浏览器，怎样把浏览器接入现有 SIP 部署？

此时，呼叫由 PSTN 一侧还是 Web 一侧发起并不是架构判断的关键；关键在于既有部署在哪里、主要业务是什么。

可以采用两类路径：

1. **直接连接 PBX**：继续使用 FreeSWITCH 或 Asterisk，但不再只是把它们当作边缘网关，而是让 WebRTC 直接接入这套核心系统。具体可以通过 SIP over WebSocket 或其支持的其他方式完成。
2. **引入支持 WebRTC 的 SBC**：会话边界控制器（Session Border Controller，SBC）承担 WebRTC 与既有 SIP 网络之间的连接。课程提到 AudioCodes，以及其他具备 WebRTC 能力的 SBC。

采用这条路径时，需要确保支持 Opus 音频编解码器。课程把 Opus 支持列为明确要求，其媒体层面的原因对应前面的编解码器课程内容。

## 混合多方通话：SFU 与电话会议桥的差异

前面的网关路径主要解决一对一互联，多方通话还会遇到媒体模型差异。

在五人 SFU 视频通话中，每个用户把自己的媒体发送到 SFU，并接收其他四人的四路媒体，因此每人有一条上行和四条下行。SFU 选择并转发独立媒体流，不预先把所有人混成一路。

电话会议桥通常采用另一种方式：先把音频混合，再把一路适合电话终端的音频送回去。将 PSTN 用户加入 SFU 会议时，必须明确这两种模型在哪里衔接。

假设会议中有三位 Web 视频参与者和两位电话参与者。三位 Web 用户连接 SFU，各自发送媒体，并接收另外两位 Web 用户的媒体。第一位电话用户加入后：

1. 电话音频先进入网关，再由网关送入 SFU。
2. SFU 把这位电话用户当作一个新的音频来源，将其转发给其他参与者。
3. 返回电话的方向，可以由 SFU 先提供混合音频，也可以把三位 Web 用户的三路音频分别交给网关，再由网关混成电话所需的一路音频。

第二位电话用户加入后，网关与 SFU 之间如何处理两位电话用户，就成为关键架构选择。

## 在网关上混音，或向 SFU 分别路由

### 方案一：在网关上混音

网关可以把来自 SFU 的音频与电话侧音频一起处理，向每部电话发送适合的混合流，并把两位电话用户的媒体组合后，通过一条上行媒体路径送入 SFU。SFU 再将这路音频转发给其他参与者。

若完整地在网关执行混音，网关需要处理的不只是“所有人混在一起”这一件事。假设两位电话用户分别称为红色电话和蓝色电话：

- 发给红色电话的混音包含其他所有参与者的音频，但排除红色电话自己的声音。
- 发给蓝色电话的混音同样包含其他所有参与者，但排除蓝色电话自己的声音。
- 另有一路混音把两位电话用户的音频组合起来，发送给 SFU，由 SFU 作为单一流转发给 Web 用户。

因此，这个例子在网关上形成了三个混音任务：两个分别面向电话用户的混音，以及一个面向 SFU 的电话音频混音。

这一方案减少了 SFU 需要看到的电话媒体通道数，但 SFU 收到的一路混合音频中包含多个人，电话用户在 Web 会议侧不再天然具有独立媒体身份。

### 方案二：每部电话分别路由到 SFU

另一种做法是让第二位电话用户成为网关进入 SFU 会议的另一条独立呼叫。这样，SFU 看到的是两路电话媒体，而不是来自网关的一路混合媒体。

独立路由带来更细的控制能力：

- **说话者区分与转写**：若网关上来的单一流中包含多位说话者，带说话者分离的转写会更难判断谁说了什么；独立流保留了更清楚的来源边界。
- **独立静音**：要静音其中一位电话用户而不影响另一位时，不必在一条混合流上额外设计复杂的 SFU—网关信令来恢复身份信息。

代价是 SFU 必须处理更多媒体通道。需要根据使用场景以及 Web 侧、电话侧各自希望支持的参与者数量做权衡，而不能只追求流数量最少。

## 混音位置与控制边界

混音器可以放在网关、SFU 或其他组件中，没有适用于所有系统的唯一答案。设计时至少要回答以下问题：

- 每一侧出现多路需要混合的音频时，由哪里处理？
- 一侧如何理解另一侧发来的媒体：它是一条包含多个用户的流，还是多个可独立控制的用户？
- 系统能否识别和控制流中的电话用户，还是只能控制整条混合流？
- Web 会议能否像处理独立 SFU 流一样，灵活地处理电话参与者的媒体？
- Web 侧是否也统一混音？

有些系统最终采用“视频始终使用 SFU，音频始终使用混音器”的方式，原因就是让电话支持更简单。从 SIP 和电话系统迁移到 WebRTC 的团队尤其可能选择这种方式，因为在其业务中，PSTN 或 SIP 仍比 WebRTC 更居核心位置。

这说明混音并非单纯的媒体性能选择，它还会决定用户身份、控制粒度和后续功能能否方便地实现。

## 不同场景下的选型

| 主要场景 | 建议的核心与边缘关系 | 架构重点 |
| --- | --- | --- |
| 运营既有 VoIP 网络，只需支持浏览器 | SIP 为核心，WebRTC 位于边缘 | 通过进入 WebRTC 的接入路径扩展现有网络 |
| 已有 WebRTC 应用，只需少量电话用户加入 | WebRTC 为核心，SIP 位于边缘 | 用网关完成 SIP/RTP 互联，不必让整个应用改用 SIP |
| 以传统多方语音会议为主 | 通常以 SIP 和混音体系为核心 | 电话会议桥擅长混音，但仍需检查实际需求 |
| 以视频为主 | WebRTC 为核心，SIP 位于边缘 | SIP 虽支持视频，课程仍建议以 WebRTC 为主 |
| 大多数呼叫本来就是 PSTN 与 WebRTC 之间的互联 | SIP 为核心，WebRTC 位于边缘 | 既然需要 FreeSWITCH 或 Asterisk 等电话基础设施，可将其放在核心位置考虑 |

多方语音并非绝对只能以 SIP 为中心。课程特别以 Clubhouse 为例，说明它实际上把 WebRTC 作为主要部分，而且不少需要多方语音的服务也在向 WebRTC 迁移。因此，表格中的传统选择不能代替需求分析。

最后，团队经验也是现实因素。如果团队熟悉 SIP，现有需求又没有证明必须把 WebRTC 放到中心，继续使用 SIP 同样合理。能用熟悉的技术更快交付可用系统，本身就是重要的工程标准。

## 小结

PSTN 连接首先是一个架构重心问题。WebRTC 为主时，应复用已有应用信令，把 SIP/RTP 限制在电话互联边缘；SIP 为主时，则可通过 PBX 或支持 WebRTC 的 SBC 接入浏览器，并确保 Opus 支持。

进入多方场景后，还要决定电话音频是混成一路还是分别路由到 SFU。前者减少通道，后者保留说话者身份与控制粒度。混音位置、用户数量、转写和静音需求，以及团队已有技术积累，共同决定最终方案。
