# 第 67 章 连接 WebRTC 会话为何困难

WebRTC 应用在开发机上能够通话，并不代表它能在真实用户的网络中可靠连接。很多连接问题直到切换网络、扩大使用范围或进入企业环境后才暴露出来。本章从一个典型故障入手，说明为什么“示例已经跑通”与“生产环境可以稳定连接”之间仍有很大距离。

## 一个典型的跨网络连接故障

Discuss WebRTC 论坛中出现过这样一类问题：两个系统位于同一网络时，视频通话完全正常；把其中任意一个系统切换到另一网络后，就看不到视频，通话也无法使用。例如，一端在 Wi-Fi 网络、另一端在蜂窝网络，或者两位用户分别位于不同房屋中，连接就会失败。

提问者给出的配置只有 Google 的公共 STUN 服务器，没有配置 TURN 服务器。这一现象并不是某个用户的偶发问题，而是 WebRTC 初学者经常遇到的情况。它可以归纳为四个相互关联的原因：

1. **没有进行充分测试。** 应用跑通后便进入实际使用环境，直到跨网络通话时才暴露问题。
2. **依赖免费的公共 STUN 服务。** 服务不由应用运营者控制，其可用性和持续性无法得到保障。
3. **完全没有配置 TURN。** 这是该案例中最关键的问题。某些网络之间无法建立直接连接，需要中继路径，而仅有 STUN 配置不能覆盖这些场景。
4. **服务器配置不当。** 即使部署了相关服务器，错误的主机、端口、传输方式或网络开放策略仍可能使连接失败。

因此，“换了一个网络就不能通话”不应只被当作某段代码的缺陷来排查，还应检查连接架构、服务器配置和测试方法。

## 连接问题有哪些表现

连接失败并不总是表现为所有通话都无法建立。实际投诉可能包括：

- 偶发断线，某些通话开始时正常，一段时间后断开；
- 连接失败率偏高，部分会话始终无法建立；
- 连接时好时坏，重试有时能够成功；
- 与会人数变化后，连接成功率或稳定性随之变化；
- 在普通网络中正常，进入限制性网络或企业网络后无法连接。

如果实际测量会话连接结果，失败率可能达到 20%、30%、50%，甚至 70%。这些数字说明问题已经不是个别用户的偶然现象，而是需要系统处理的连接性缺陷。

另一个值得关注的信号是 TURN 中继比例。如果超过 50% 的通话经过 TURN，就必须追问原因；课程讲师甚至建议，在超过 20% 时就开始调查。这里的关键不是把某个比例机械地当成故障阈值，而是理解为什么如此多的会话无法使用预期路径，以及配置、网络覆盖或部署方式是否存在问题。

## 为什么入门示例容易误导

WebRTC 官方 GitHub 示例中的基础点对点演示，通常在同一个浏览器标签页内创建两个对等连接。点击开始或呼叫按钮后，媒体从一个显示区域传到另一个区域，但整个演示仍局限于本机和同一页面。

这种示例便于说明 API 的基本用法，却省略了生产环境的关键条件：

- 信令虽然存在，但不需要真正经过网络；
- 两端不处于不同的 NAT、防火墙和网络环境中；
- 不需要独立的 STUN 服务器；
- 不需要 TURN 服务器。

如果开发者直接从这类“Hello World”示例扩展应用，就可能根本没有意识到还需要认真设计 STUN、TURN 及其配置。

类似问题也存在于网上的第三方示例。课程中分析过一个使用 React.js 和 WebRTC 构建的类 Zoom 视频会议项目：代码配置了 Google 公共 STUN 服务器，却没有 TURN 服务器。这与论坛中的故障配置本质相同。项目能够在作者演示的条件下运行，并不意味着它具备生产环境所需的跨网络连接能力。

## 从“能运行”转向“可连接”

认真对待 WebRTC 应用，就必须把连接性当作独立的设计和运营问题，而不是对等连接 API 的附属配置。首先要建立一个可量化的问题：**应用中究竟有多少通话或会话能够成功连接？**

在继续修复之前，至少应开始记录成功连接数、尝试连接总数和连接成功率，并区分同网络测试与真实跨网络会话。只有先获得这一基线，后续的架构调整和配置修改才有可验证的效果。

下一章将延续这一思路：在动手更换服务器或修改配置之前，先理解本地测试为什么掩盖问题，以及公共 STUN、TURN 服务为什么不适合作为生产连接方案的基础。

## 小结

同一网络中的成功演示无法证明 WebRTC 应用具备生产连接能力。缺少真实网络测试、依赖公共 STUN、没有 TURN 以及配置不当，是跨网络会话失败的常见根源。偶发断线、高失败率、异常偏高的 TURN 中继比例和企业网络无法连接，都应成为系统排查的入口。第一步不是随意修补，而是测量并理解实际连接成功率。
