# 第 22 章 屏幕共享

屏幕共享并不只是把摄像头视频换成桌面画面。它涉及不同的捕获 API、浏览器强制权限、分辨率和码率特征，以及多人会话中的共享权限和连接架构。本章先说明捕获方式与媒体特征，再讨论如何组织共享连接和典型应用。

## 捕获 API 与浏览器约束

屏幕共享的主要 API 是 `getDisplayMedia`。如果需要同时共享电脑音频，可以像使用 `getUserMedia` 请求音频那样，加入约束 `{ audio: true }`。课程指出，当时的 Chrome 对电脑音频共享支持较好，Firefox 只能部分工作，实际结果还取决于共享的是标签页、屏幕还是浏览器音频。因此，应用不能假定所有浏览器和共享来源都会得到相同音轨。

调用后，浏览器会提供模态选择界面，让用户选择共享：

- 整个屏幕；
- 设备上正在运行的某个应用窗口；
- 某个浏览器标签页。

这个界面由浏览器提供，网页不能更改其外观，也不能因为应用“只需要整个屏幕”就跳过用户选择。用户必须主动发起共享并完成额外点击，浏览器也不会把一次授权变成以后自动共享的永久许可。在 Electron 或原生应用等受控环境中，开发者可以接管这部分交互，减少或覆盖浏览器弹窗；普通网页则不能绕过这一安全模型。课程提到 RingCentral 在 Cranky Geek 的分享中讨论了改善 Chrome 屏幕共享体验的实践。

除主要 API 外，课程还比较了几种相关方式：

| 方式 | 用途与限制 |
| --- | --- |
| `getUserMedia` 捕获屏幕 | 早期方案，需要浏览器扩展，已不再推荐，不应继续作为新应用的主要方案。 |
| `getDisplayMedia`（GDM） | 当前课程采用的主要方式，可共享整个屏幕、特定应用或浏览器标签页。 |
| `getViewportMedia` | 课程录制时仍在讨论的建议接口，目标是只共享浏览器标签页，并可围绕当前标签页简化选择流程；不能把它当作已经普遍可用的能力。 |
| `captureStream` | 从当前标签页中的特定画布取得流，适合共享画布生成的内容，也常用于背景替换等处理；它有效，但并非最高效的方式。 |

WebRTC GitHub 示例中有可实际运行的 `getDisplayMedia` 示例，可用于观察捕获和共享行为。

## 屏幕画面与摄像头视频的差异

摄像头和屏幕都能产生视频轨，但其内容特征明显不同，不能沿用完全相同的质量和码率预期。

| 特征 | 摄像头视频 | 屏幕共享 |
| --- | --- | --- |
| 常见分辨率 | VGA、720p、1080p 等适合人像通话的规格 | 很多场景下达到 4K 或 5K，原始画面尺寸很高 |
| 常见帧率 | 通常为 30 fps，动作较少时可降至 15 fps；需要更强运动感时也可能追求 60 fps | 可在约 1～60 fps 之间变化，取决于共享内容 |
| 内容特点 | 以说话人物为主，通常持续存在一定程度的变化 | 既可能是长期静止的幻灯片，也可能是电影等高度动态内容 |
| 常见码率方式 | 通常采用恒定比特率（CBR） | 通常采用可变比特率（VBR），随画面变化量波动 |

共享一份很少翻页的演示文稿时，每秒一帧可能已经足够；播放电影则需要约 30 fps 或适合其内容的更高帧率。即使仍使用幻灯片，快速翻页时也要求变化尽快传到接收端，因此“静态内容”并不等于可以忽略瞬时更新。

如果应用知道共享内容的类型，可以把提示传给 WebRTC，帮助编码器选择合适的处理方式。屏幕共享编码不应只根据分辨率判断负载，还要考虑内容变化频率。

课程用 TestRTC 的测量结果比较了这两种码率行为：摄像头流目标约为 800 kbit/s，实际码率在该数值附近小幅波动；屏幕共享采用 VBR，码率随时间明显起伏，峰值往往对应翻页等画面突变。这个差异也会影响质量指标的解读。不能看到屏幕共享码率下降就认定连接变差，也不能拿摄像头 CBR 的平稳程度作为屏幕流必须达到的标准。

## 摄像头与屏幕共享的连接组织

应用可以只发送摄像头视频、只发送屏幕，也可以同时发送两者。同时发送时有两种基本组织方式：

1. 打开两个独立的对等连接，一个用于摄像头，另一个用于屏幕共享。
2. 在同一个对等连接上使用多个轨道，同时传输摄像头和屏幕画面。

采用独立连接时，还需要决定何时建立屏幕共享连接：

- **提前建立**：把建连及部分协商工作提前，减少开始共享时的等待。是否仍需重新协商，取决于屏幕轨道和相应媒体描述是否已经预留。课程提到 Jitsi 曾长期采用这种方式，但不应据此推断其录制后的实现仍然如此。
- **按需建立**：用户真正开始共享时，才打开单独的 `RTCPeerConnection` 并进行协商。
- **加入现有连接**：使用 Unified Plan，在已有摄像头或语音连接上增加屏幕共享轨道。这样一个对等连接可以同时向外发送两路视频。

这个选择会改变信令时机和整体架构，而不只是改变几行捕获代码。

## 多人会话中的共享权限与分发

一对一场景很直接：一名参与者共享，另一名观看。多人会议则首先产生应用策略问题：

- 是否允许多人同时共享？一个人共享时，其他人能否再发起共享？
- 多个共享画面是否都显示给观看者？主焦点放在哪一路？
- 是否只有主持人可以共享，或共享前必须取得权限、申请权限或传递某种令牌？

这些规则位于应用逻辑中，与浏览器是否允许捕获屏幕是两个不同层面。浏览器授权只说明用户允许本次捕获，并不表示会议中的其他参与者或主持人已经同意其发布画面。

共享流还需要按照会议拓扑分发。应用可以通过 SFU 或 MCU 将画面发送给所有参与者，也可以在网状（mesh）网络中把共享流逐一发送给其他端。多人同时共享、观看布局与焦点策略会进一步影响实际传输需求。

## 典型应用场景

### 会议与纯语音协作

最常见的是多人在线会议：一人共享，其他人观看。另一种常见形式是纯语音通话加屏幕共享。参与者甚至可能通过 PSTN 开电话会议，只在独立显示器上使用屏幕共享；也可以通过 VoIP 或 WebRTC 传输语音和视频，再额外叠加共享画面。

### 远程访问与控制

VNC、TeamViewer 一类远程接入场景也可以利用屏幕流。被访问机器运行 WebRTC 并共享自身画面，另一端的浏览器接收该流，从而形成远程桌面体验。这里的捕获端不一定是普通用户主动在会议里演示，而可能是受控的远端设备。

### 浏览器录制与教学视频

Loom 一类服务允许用户从浏览器录制摄像头和屏幕，再把数据上传到服务器处理并保存为文件。用户可以迅速制作一段教学或说明视频，并分享给其他人。这里屏幕共享不仅用于实时观看，也成为录制管线的输入。

### 云游戏与三维渲染

云游戏的媒体方向与普通演示相反：云端服务器实际运行并渲染游戏，取得游戏图像帧，生成 WebRTC 流后发送给玩家。它不完全是桌面共享，但媒体处理思路相近。课程提到，相关实现可以使用 `libwebrtc`、GStreamer 或 Pion 等开源组件，把渲染结果接入实时流。

### 呼叫中心坐席监控

呼叫中心可能需要在通话同时录制坐席屏幕，用途包括监管留痕、质量检查、培训和改进工作流程。在这种受控业务中，每次录制都要求坐席重新同意会妨碍既定服务流程，因此通常需要由受控应用接管普通浏览器中的逐次确认交互。它仍然是一项涉及隐私和权限的设计，不能被理解为网页可以静默绕过浏览器授权。

## 小结

屏幕共享的首选捕获方式是 `getDisplayMedia`，但浏览器保留来源选择和用户授权，应用必须尊重这一约束。屏幕流通常分辨率更高、帧率跨度更大，并采用随内容变化的 VBR，因而需要不同于摄像头的编码预期和质量分析。多人场景还要单独设计共享权限、画面焦点、分发拓扑，以及提前建连、按需建连或向 Unified Plan 连接增加轨道的策略。
