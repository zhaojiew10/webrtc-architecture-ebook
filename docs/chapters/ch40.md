# 第 40 章 录制

WebRTC 录制的目标通常不是单纯保存网络数据，而是让一场两人或多人对话在此后能够回放。不同方案的根本差异，在于媒体是否改变原有路径、在哪里解码和混合、由谁承担上传与存储，以及最终需要怎样的回放形式。本章比较服务器端录制、客户端录制、并行转发和无头浏览器录制，并继续讨论元数据、后期处理、安全与播放要求。

## 先确定录制结果与回放频率

录制的最终产物通常位于数据中心或云存储中，但从会议媒体到存储文件并没有唯一路径。设计前首先要明确：

- 需要保存单一合成节目，还是所有原始媒体流？
- 录制会被频繁观看，还是只有极少数会话会被回放？
- 会议结束后必须立即可用，还是允许等待后期处理？
- 回放需要普通播放器即可，还是允许开发专用播放器？

回放频率会直接影响成本分配。如果大量录制永远不会播放，提前为所有会议解码、混合和编码可能浪费计算资源；如果内容需要立即、广泛分发，预先形成通用单流又可能更合适。

## 服务器端录制

### 媒体必须经过可处理它的媒体服务器

服务器端录制要求把媒体路由到媒体服务器，再由服务器直接写入本地存储，或通过网络写入其他存储。群呼本来就可能经过 MCU 或 SFU，可以在这一路径上增加录制；一对一通话若原本点对点传输，为了服务器录制就必须额外引入媒体服务器。

不能因为媒体经过 TURN，就认为 TURN 能完成录制。TURN 服务器只是中继媒体，无法访问解密媒体所需的密钥，因此不能仅靠它得到可回放的音视频内容。服务器端录制需要真正能够处理媒体的媒体服务器，并让相应媒体经过它。

这一区别也决定了一对一录制的成本：原本可以直接点对点或采用 Mesh 的媒体，现在要增加服务器入口、出口和处理资源，带宽成本会随之上升。

### 单流录制：先混合，再存储

若服务器要生成一个合成媒体流，典型处理链是：

1. 接收两名或更多参与者的媒体；
2. 解码所有需要参与合成的输入流；
3. 混合音频、合成视频布局；
4. 重新编码输出；
5. 写入存储。

普通 SFU 路由主要接收并转发数据，而上述过程新增了解码、混合和编码，CPU 消耗显著增加。因此，在 SFU 架构中直接要求“顺便录成单流”，实际上给服务器加入了一部分类似 MCU 的工作，不能把它当作零成本附加功能。

### 多流录制：推迟混合，但增加存储与回放复杂度

服务器也可以分别保存多路原始编码流，从而跳过录制时的解码、混合和重新编码。代价主要有两个：

- 多路流需要更多存储空间；
- 回放时必须同步处理这些流，要么开发能够播放多流及布局的专用播放器，要么在播放前或播放时再进行混合。

如果实际只会回放少数录制，按需混合往往比提前处理所有流更合理。还可以采用折中方案，例如只混合音频，视频则选择当前发言者的一路输出，而不是合成所有人的画面。课程以 Google Meet 通常突出主要发言者、而不是把所有人混成一个画面为例，说明单流录制不一定意味着完整网格合成。

无论选择哪种方式，只要不预先混合，就必须回答“多个流如何同步回放”这一问题；仅把文件分别保存下来并没有完成回放产品设计。

### 容器、转码与存储瓶颈

服务器录制还需要明确文件容器和编码格式：

- 容器可以是 WebM、MP4、AVI 或其他格式，系统既要能把媒体写入容器，也要保证目标播放器能够读取；
- 通话中可能使用 VP8 或 VP9，但为了目标回放环境，可能希望输出 H.264，这就需要转码；
- 音频同样可能存在格式转换需求，不能只考虑视频；
- 存储可以位于本机 SSD，也可以通过网络写入其他设备。较慢的非 SSD 存储或网络 I/O 可能拖慢写入，使系统从 CPU 受限转为存储受限。

容器选择、编解码转换和存储写入不是彼此独立的细节。它们共同决定录制管道能否实时跟上输入，以及最终文件能否在目标介质上播放。

### 优势与代价

服务器端录制不要求客户端改变原有行为，也不依赖客户端具备额外存储、上传或持续在线能力。服务器可以按目标介质调整录制质量，例如降低视频分辨率以节省空间、只录音频，或只记录发言者。

其代价是基础设施中增加媒体、录制或存储服务器，并由服务端承担大量带宽和计算。一对一通话还会因为媒体改道而增加原本不存在的媒体服务器流量。

## 客户端录制

### 本地录制后再上传

WebRTC 可以通过 MediaRecorder API 在客户端本地录制媒体。基本流程是先录制并保存在本地，再把结果上传到服务器进行后期处理或长期存储。上传通常使用 WebSocket 或 HTTPS，而不是继续沿用通话中的 WebRTC 媒体通道。

录制责任可以有不同分配：每个参与者分别录制并上传自己的内容，或者由一名参与者录制双方乃至整个群组所需的内容。必须在设计时明确由谁录制，否则容易遗漏远端流或产生不必要的重复。

### 本地空间和用户行为不可控

客户端方案首先受到本地存储约束。应用通常无法准确知道设备还能提供多少空间，也无法用同一假设覆盖一分钟、五分钟、半小时、两小时乃至八小时的会话。移动设备的可用空间往往比桌面设备更紧张。

上传阶段还依赖用户行为。假设会议结束后需要上传 50～100 MB 数据，在某些网络上需要数分钟；用户是否愿意一直保持标签页打开？如果用户直接关闭页面，录制可能永远无法完整到达服务器。

课程因此给出了非常保守的经验提醒：不要简单依赖客户端本地录制来承载超过约五分钟的会话。这里应理解为对长时间积累、上传和退出风险的架构建议，而不是把该数字当作所有场景通用的硬限制。

### 持续上传可以缓解等待，却会争用通话资源

一种优化是不等到会议结束，而是按短片段持续上传，例如每 5 秒或每 1 分钟上传一次，甚至边录制边立即上传。这样可以减少结束后的等待和本地数据积累，但会在实时通话期间同时消耗 CPU 和上行带宽。

尤其在上行本来就紧张时，录制上传会与真实会议媒体争用同一资源。它并没有消除上传成本，只是把成本从会后移动到会议进行中。

客户端录制的优点是不必为了录制在原媒体路径中增加媒体服务器，基础设施可能更简单；缺点是应用逻辑更复杂，并高度依赖场景、设备、网络和用户行为。课程建议只有在能够充分控制录制客户端的网络、CPU 和应用程序时，才优先依赖这种方式。

## 并行转发到录制服务器

并行转发与“本地保存后上传”不同。发送端建立两条独立的 WebRTC 对等连接：

- 一条连接真正的通话对端，维持原会话；
- 另一条连接媒体服务器，把媒体并行发送给录制服务。

原通话媒体不需要先经过录制服务器，录制服务器也不负责路由或管理整个会议，只接收需要录制的部分。可以把它理解为在点对点通话上增加第三条 Mesh 支路，只是第三个端点不是普通参与者，而是录制服务器。

这种方法避免把媒体服务器插入原有通话路径，却会让发送端承担约两份上行媒体。课程还提出，可以借鉴 Simulcast，在通往录制服务器的支路上使用较低码率，但同时指出这种做法几乎没有人采用。它更适合作为需要谨慎验证的设计可能性，而不是成熟默认方案。

## 无头浏览器录制

### 把录制器作为云端浏览器参与者

无头浏览器录制把“浏览器里显示的会议”本身作为录制对象。系统在云端启动 Chrome 浏览器，让它作为一个不发言的参与者加入会议。它不向真实用户渲染画面，而是把浏览器实际渲染出的帧取出，编码后写入存储。

媒体路径因此变成：各参与者正常加入群呼，云端浏览器也接收会议内容；录制发生在云端浏览器的渲染与捕获阶段，而不是简单保存某一路 RTP 流。

### 布局和非媒体内容的灵活性

这种方案的突出优势是可以使用 HTML 和 CSS 决定录制布局。相比用 GStreamer 或 FFmpeg 并行混合、编码多路媒体，网页布局更容易按产品需求调整，也能在会议中途动态改变。

录制对象也不再局限于音频和视频。只要是浏览器会话中能够呈现的内容，例如随会议出现的文本、共同浏览内容或其他界面元素，都可以进入录制结果。对于“用户实际看到的会议是什么样子”这一目标，无头浏览器比逐路媒体混合更直接。

按课程录制时的观察，无头浏览器已经成为常见最佳实践之一。不过，这仍是一种架构选择，而不是所有录制需求下的唯一答案。

### CPU、内存与系统组件成本

无头浏览器并不意味着省去媒体处理成本。若服务器端混合录制本来就需要解码、合成和编码，无头浏览器完成渲染、捕获与编码也需要相近量级的 CPU，课程估计可能再高出几个百分点；同时，浏览器通常消耗明显更多内存。

因此，它与完整服务器混合录制相比，成本差距未必像直觉上那么大。还需要维护云端浏览器这一额外活动组件，并处理其生命周期和运行环境。

## 四种录制路径对比

| 方式 | 媒体路径与处理位置 | 主要优势 | 主要限制 |
| --- | --- | --- | --- |
| 服务器端录制 | 媒体经过媒体服务器，服务器存原始流或混合后存储 | 客户端无改动，质量和输出可控 | 服务器带宽、CPU、存储成本；一对一需媒体改道 |
| 客户端录制 | 原通话路径不变，本地录制后经 WebSocket 或 HTTPS 上传 | 不必在媒体路径中增加服务器 | 本地空间、上行争用、关闭页面和长时间会话风险 |
| 并行转发 | 原 WebRTC 通话之外，再建一条到录制服务器的 PeerConnection | 录制服务器不管会议路由，原路径不被插入 | 发送端约双倍上行，额外连接与发送处理 |
| 无头浏览器 | 云端浏览器作为参与者接收并渲染，再捕获、编码、存储 | HTML/CSS 布局灵活，可录非音视频界面内容 | CPU 与内存开销较高，增加云端浏览器组件 |

## 元数据不能只靠媒体文件自然保存

一场会议除了音频和视频，还可能包含幻灯片及其切换、共同浏览、文字聊天、上传文件等资料。是否保存以及如何回放这些内容，需要单独设计。

首先要决定用户真正需要哪些元数据，其次要明确：

- 在客户端还是服务器端记录？
- 会议结束后统一上传，还是会议中持续记录？
- 是否以事件日志形式与媒体录制并排放置？
- 是否需要专用播放器，按时间同步恢复这些事件？
- 元数据需要单独检索和访问，还是只需出现在最终画面中？

无头浏览器可以把文字、幻灯片等直接录进视频，但此时它们主要成为画面像素，不再天然具备结构化访问和搜索能力。相反，独立事件日志更利于检索，却需要额外同步与回放机制。保存之后是否、以及如何回放元数据，也必须在录制前考虑。

## 后期处理与回放要求

### 编解码器和容器取决于播放环境

“已经录制”不等于“目标设备可以播放”。课程以 VP8 通话为例：如果存储内容仍为 VP8，而用户尝试通过 iPhone 浏览器回放，是否需要转码为 H.264，取决于当时具体播放环境的支持情况。课程对此保留了不确定性，因此不能假定任意浏览器和应用都能直接播放原始会议格式。

目标介质会反向决定容器和编码格式。需要面向非 WebRTC 浏览器、没有 WebRTC 能力的应用或特定 iOS 环境播放时，应把这些要求纳入转码和封装流程，而不是只考虑会议双方当前支持的格式。

### 从会议结束到录制可用需要多久

混音、转码和文件转换都可能引入延迟。产品需要明确录制必须在会议结束瞬间可用，还是允许异步处理。课程举例称，StreamYard 可以在结束后约两秒提供结果，而 Google Meet 的录制可能需要几分钟到几小时才出现在文件夹中。这些是课程当时的产品体验示例，不是固定服务承诺。

还有一种需求是边录制边播放，例如把群呼输出到 YouTube Live，让外部观众实时观看。这同时具有录制和直播性质，处理链必须按实时输出设计，不能等会议结束后再开始所有转换。

### 快进、倒退和定位需要合适的 I 帧结构

如果播放器需要频繁快进、倒退或跳转到不同位置，码流需要足够的 I 帧。WebRTC 为实时传输生成的默认码流未必提供适合文件定位的 I 帧密度。

解决方法之一是在后期重新解码、编码，生成不同于实时通话默认输出的录制码流；另一种方法是在会话期间通过媒体服务器请求更多 I 帧。后一种方法会影响正在进行的会议，因此不能只为了录像检索体验而忽略实时媒体质量与传输压力。

### 录制质量不一定等于实时通话质量

需要明确保存内容应保持原质量、降低质量以节省空间，还是采用更高质量。课程以视频播客为例：服务器可以承担实时输出，同时在受控客户端并行录制更高质量素材，会后上传，用于点播或发布到 YouTube。播客制作者通常更能控制设备和客户端行为，因此比开放、随意的会议场景更适合这种混合方案。

还应决定最终保存一个合并文件、全部原始流，还是只跟随活跃发言者在不同视频流之间切换。若只有极少数录制会被单人观看，按需混合可能比提前为所有会议生成合成文件更经济。

## 安全与访问控制

录制安全不仅是“文件是否需要密码”，还包括内容与时间的细粒度权限：

- 录制是否需要端到端加密？
- 内容应对公司开放，还是仅向实际参与会议的用户开放？
- 如果某人只在会议部分时段参加，是否只能访问其参会期间对应的录制片段？
- 如何验证访问者身份？
- 如何保护录制不被篡改？

这些问题在应用引入端到端加密时尤其需要与录制架构一起设计。不能先假设服务器始终能够读取所有媒体，再在完成后补充权限要求。

## 小结

录制架构首先由媒体路径决定，再由回放目标校正。服务器端录制对客户端透明，却增加媒体改道、计算和存储成本；客户端录制减少服务器介入，但依赖本地资源、上行和用户行为；并行转发保留原通话路径，却增加一条媒体支路和上行负担；无头浏览器以最接近用户界面的方式获得布局和元数据呈现灵活性，同时承担浏览器 CPU 与内存成本。

最终方案还要同时回答单流还是多流、何时混合、使用何种容器与编解码器、多久可用、如何定位播放、保存哪些元数据，以及谁可以访问哪些录制片段。只有把这些要求与回放频率一起考虑，才能在实时会议成本与后期处理成本之间作出合理选择。
