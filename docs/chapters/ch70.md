# 第 70 章 WebRTC 1.0

WebRTC 1.0 不只是一次 API 改名，而是对象模型、SDP 协商方式、统计接口和浏览器实现逐步收敛的过程。本章从开发者的角度梳理课程录制时点的标准状态、Chrome/Firefox/Edge/Safari 的实现差异，以及旧应用迁移时需要验证的实际问题。文中的版本号、采用率和发布预测均属于当时的课程语境，不代表后续或当前标准状态。

## 标准化状态与演进背景

### 候选推荐标准意味着什么

在课程录制当年早些时候，WebRTC 成为 W3C 候选推荐标准（Candidate Recommendation）。这是 W3C 流程中的正式状态，大致表示：

- 工作组不再预期发生重大变化；
- 规范已基本达到可以实现的程度；
- 主要问题已经解决，没有再出现无法预料的根本性障碍；
- 仍有不少开放问题，但工作组知道如何处理，并已有相应计划。

因此，“候选推荐”并不等于所有细节都已结束，也不等于所有浏览器已经一致实现。它更像是一个信号：规范的主体足以供浏览器实现和应用开发使用，剩余工作转向问题收尾、实现一致性和实际验证。

### ORTC 对 WebRTC 1.0 对象模型的影响

WebRTC 1.0 与早期设想相比已经发生了很大变化。其中一个重要变化，是吸收了许多来自 ORTC 的对象模型。ORTC 在 2014 年由微软和 Google 推动，起初被视作 WebRTC 的另一种路线，后来其部分设计被并入 WebRTC。

`RTCRtpSender` 和 `RTCRtpReceiver` 就是典型例子。它们与 ORTC 中的对象仍然非常相似，但在 WebRTC 1.0 中以只读方式使用。课程录制时，这些对象已在 Chrome、Firefox、Safari 以及 Edge 的 WebRTC 兼容层中实现，但 Edge 的原生模型并不相同。

这一演进说明，WebRTC 1.0 并非简单冻结早期 `RTCPeerConnection` 的用法，而是在保留对等连接入口的同时，逐步把媒体发送、接收和协商过程表达为更明确的对象。

### 从 Stream 到 Track，再到 Transceiver

早期开发者通常把 SDP 交给 `RTCPeerConnection`，剩下的过程仿佛由浏览器“自动完成”。随着应用变复杂，这种模型难以准确描述实现行为，于是 API 经历了两次重要转向：

1. **Stream 模型转向 Track 模型。** 不再只通过 `addStream` 添加整个流，而是可以通过 `addTrack` 添加单个音频或视频轨道。流逐渐被视为轨道的容器，并向浏览器说明这些轨道应如何同步。
2. **Track 模型进一步转向 Transceiver 模型。** `addTransceiver` 和收发器模型更明确地描述媒体发送、接收及 SDP 协商之间的关系，比单纯添加轨道更适合表达底层实现。

Mozilla 的 Jan-Ivar 曾撰文讨论这一从 Streams 到 Tracks、再到 Transceivers 的演变。课程嘉宾也经历过 Edge 的 ORTC 兼容层：它在 ORTC API 之上模拟 WebRTC 1.0 的 `RTCPeerConnection`，随后又向收发器模型迁移。新模型并不等于旧代码会自然保持一致，但它让规范与真实实现更加吻合。

规范能否成功，还取决于浏览器是否及时跟上。课程反复强调，API 出现在规范中，与 API 在各浏览器里稳定工作，是两个不同阶段。

### 标准制定与应用开发之间的差距

当时的工作组主要由浏览器厂商推动，包括 Google、Microsoft、Ericsson 等公司的参与者。他们投入大量工作，使规范既可由浏览器实现，也可供应用开发者使用。

课程嘉宾同时指出，真正运营服务或开发应用的人参与不足，容易在规范制定者与实际代码编写者之间形成脱节。应用开发者若希望参与，审查规范、提出基于真实场景的问题，始终是受欢迎的贡献方式。

即使 WebRTC 1.0 当时尚未完全结束，工作组中已经出现关于后续方向的讨论，包括是否以其他方案替换整个媒体栈以及 STUN/TURN 栈。这些讨论只代表当时对未来的探索，并不是已经确定的后续标准。

## 课程时点的四种主要浏览器实现

### Chrome：旧接口仍常见，新接口逐步落地

Chrome 在 WebRTC 市场占据最大份额，但表面 API 仍与 2012—2013 年的用法很接近：

- `addStream` 仍然存在并被广泛使用；
- 原生 `addTrack` 直到 Chrome 64 才发布；此前 Adapter.js 可在 Stream API 之上模拟 `addTrack`；
- Chrome 团队当时正在把 `addStream` 的内部实现重写为 Track API 之上的兼容层；
- 浏览器尚未实现完整收发器模型，也不支持 `addTransceiver`，但底层 WebRTC.org 原生库刚加入相关支持；
- `getSenders` 已加入，可返回负责通过对等连接发送轨道的对象列表；
- `replaceTrack` 在 Chrome 65 落地，允许用一个轨道替换正在发送的另一个轨道。

SDP 方面，Chrome 自 2012 年以来默认使用 Plan B。符合规范的 Unified Plan 当时才逐步开始实现，并受约束和标志控制，迫切需要真实应用参与测试。

统计方面，Chrome 已支持符合规范的 `getStats` 约一年，接口本身已经相当可用；但 `chrome://webrtc-internals` 等开发工具仍使用旧版统计数据，讲师估计许多开发者也同样如此。

### Firefox：更积极跟随规范，但切换仍会带来行为变化

Firefox 很早就支持 `addTrack`，并推动开发者从 Stream 模型转向 Track 模型。它也较早支持符合规范的 `getStats`、`RTCRtpSender` 和 `replaceTrack`。例如，Firefox Hello 曾利用 `replaceTrack` 在手机前后摄像头之间切换。

当时 Firefox 的统计项反而比 Chrome 少一些。两者虽然都使用 WebRTC.org 底层引擎，但 Firefox 没有以同样方式接入全部统计信息。这说明“使用同一引擎”并不自动意味着上层 API 暴露完全一致。

Firefox 59 在课程录制前两周切换到收发器模型，整体迁移比讲师预期顺利，只发现少量问题，但仍有两个值得注意的变化：

- 如果应用把 SDP 中的轨道 ID 通过信令传到另一端，并期望它原样出现，这一假设不再成立；
- `getLocalStreams` 在某个边界场景中的行为发生变化。

这类变化提醒我们，即使浏览器是在向规范靠拢，应用若依赖未明确保证的行为，也可能在升级中受到影响。

### Microsoft Edge：原生接口与 ORTC 兼容层各有取舍

Edge 最初只提供 ORTC，希望开发者在 ORTC 可用时使用它，不可用时再使用 WebRTC 1.0。这个设想没有达到预期，因此 Edge 后来又加入原生 `RTCPeerConnection` API。

课程当时将两条实现路径作了如下区分：

| 实现路径 | 能力与限制 |
| --- | --- |
| Edge 原生 WebRTC 1.0 | 并不完整符合标准；每个连接限一个音频轨道和一个视频轨道，但可能覆盖约 90% 的使用场景；支持实际应用中很重要的 ICE 重启 |
| ORTC 之上的 JavaScript 兼容层 | 少于 1000 行 JavaScript；可自行修改，能实现 `addTrack`、`getSenders`、`replaceTrack`，支持多个流，行为可非常接近其他浏览器；但不支持 ICE 重启 |

Edge 当时的一个重大缺口是不支持数据通道，因为完整的 SCTP 栈尚未就绪。屏幕共享则刚加入 Windows Insider 版本；讲师希望它在当年 4 月或 5 月正式发布，但这只是当时预期。

### Safari：开始提供 WebRTC，但兼容边界很多

Safari 选择基于 WebRTC.org 库实现 WebRTC。团队起初不希望加入旧式 `addStream` API，这本可促使开发者至少迁移到 `addTrack`。但旧 API 最终被放在“WebRTC 遗留 API”标志之后，而且 Safari 发布时默认启用了该标志。课程认为这错失了一次推动迁移的机会，并提醒开发者不要因此继续依赖旧接口。

当时 Safari 还存在以下差异：

- 由于使用 WebRTC.org，多流场景采用 Plan B SDP；
- 提供了规范中新版的 Transceiver API，但底层 SDP 模型并不真正支持收发器语义，因此该 API 尚不能保证按规范工作；
- 只支持 H.264，尽管 VP8 属于规范要求实现的编解码器，后续发展仍待观察；
- WebKit WebView 没有接入 `getUserMedia`；
- 因而 iOS 上的 Chrome 也不支持 `getUserMedia`，但可使用 `RTCPeerConnection`。只需要数据通道的应用仍可受益，需要摄像头或麦克风的应用则仍需原生应用等方案；
- 旧式 `createOffer` 中用于请求接收音频或视频的约束没有原生实现，Adapter.js 中由社区贡献了相应兼容层；
- iOS 对自动播放限制严格，视频元素至少需要添加 `playsinline`，这是开发者经常踩到的兼容问题。

这些差异共同说明，仅仅检测“浏览器是否支持 WebRTC”远远不够，还必须核对应用实际调用的每一项能力。

## 跨浏览器兼容的现实基线

### 基本通话与复杂应用应区别对待

课程讲师估计，当时 Chrome 及 Opera、Brave、Electron 等类 Chrome 环境合计占 WebRTC 市场至少 80%。但跨浏览器基本能力已经相当不错：如果应用只有单个流、不需要重新协商，类似 Google AppRTC 示例的流程通常可以正常工作。

Adapter.js 能减少浏览器版本之间的命名差异和偶发破损，让开发者少处理一部分兼容细节。不过，它不能替代应用测试，更不能让复杂 SDP 协商、设备切换和多流场景自动获得一致行为。

只面向 Chrome 开发也不应成为默认选择。课程举出的反例是 YouTube 当时的 WebRTC 摄像头上传功能：它只支持 Chrome，并组合使用了旧式、带前缀的 `webkitRTCPeerConnection`。这类实现对 WebRTC 的跨浏览器目标没有帮助。

### 新旧 API 的采用需要时间

Chrome Status 可以查看某项 API 在页面加载中的使用比例。课程当时引用的数据为：

- `addStream` 出现在约 0.045% 的 Chrome 页面加载中；
- `addTrack` 约为 0.0025%，折算相对采用率约为 5%；考虑到它在 Chrome 稳定版只发布了三四个月，这一增长已经不错；
- `getSenders` 的相对采用率约为 2.7%；
- `replaceTrack` 几乎没有被使用；
- Promise 风格调用约占 0.02% 的页面加载，略高于回调风格。

这些数字的历史价值不在于今天仍然适用，而在于说明：**规范发布、浏览器实现和开发者采用之间存在很长的时间差。** 旧 API 能继续运行很多年，也是迁移缺乏直接业务动力的原因之一。

Adapter.js 本身也可能改变兼容边界。课程提到，在为 Chrome 加入 `addTrack` 模拟支持时，Cisco Spark 的代码曾发生破损，所幸在影响用户前被测试发现。这再次说明，兼容层减少差异的同时，也必须纳入端到端验证。

### 媒体元素应使用 `srcObject`

早期代码常通过 `URL.createObjectURL` 为媒体流创建 URL，再把它赋给视频元素的 `src`。如果开发者没有撤销这些 URL，就容易造成内存泄漏。

后来的做法是把 `getUserMedia`、`onaddstream` 或 `ontrack` 提供的流直接赋给视频元素的 `srcObject`。Chrome 当时已弃用对 MediaStream 使用 `URL.createObjectURL()` 的路径；Firefox 57 则移除了带前缀的 `HTMLMediaElement.mozSrcObject`，并曾因此导致 Facebook Messenger 的 messenger.com 出现问题，随后该网站迅速修复。

### 配置字段与异步模型也在变化

`RTCIceServer` 配置曾把单个服务器字段从 `url` 改为可容纳多个地址的 `urls`。课程当时的 Chrome Status 数据显示，旧写法的使用量仍约为新写法的 20%，下降速度很慢。即使只是一个字段改名，让大量既有代码完成更新也十分困难。

另一个重要转变是从回调模型迁移到 Promise 模型。Promise 能写出更清晰的异步代码，避免深层回调嵌套，但采用过程同样渐进而非瞬间完成。

## 混用不同代 API 的风险

`RTCPeerConnection` 上同时存在多代接口时，开发者很容易把它们随意组合。例如，先调用 `addTrack`，并传入轨道及一组流，随后又调用已经从规范中移除的 `getLocalStreams`。此时行为可能没有被规范定义，不同浏览器也可能给出不同结果，测试覆盖通常很少。

类似问题还包括：

- 通过 Stream API 添加媒体后，再移除一个轨道，流本身是否也应被移除？
- 如果移除的是流中的最后一个轨道，空流应如何处理？
- 调用 `addStream` 后，`getSenders` 会为流中的每个轨道返回发送器，应用是否正确理解了这种映射？
- 新接口与旧有功能组合后，原能力是否仍然正常？

最后一项并非理论风险。`addTrack` 在 Chrome 64 发布时无法与 DTMF 正常配合，到 Chrome 66 才修复。由此得到的实践原则是：不要因为两个 API 分别都能工作，就假定它们的组合也受到明确支持；应尽量使用同一代模型，并对不可避免的过渡组合做针对性测试。

为辅助 JavaScript 代码迁移，课程嘉宾还编写过 codemod：解析源代码，把 `addStream` 等实例替换为相应的 Track 或 Promise 写法。自动转换能减少重复劳动，但不能替代行为测试。

## 是否应该迁移现有应用

### 先回答“为什么迁移”

如果现有应用运行稳定，仅为了追逐新 API 而重写，直接业务价值可能很低。产品经理完全可能更希望团队把同样时间用于开发用户可感知的功能。因此，迁移前需要明确收益，例如：

- 新应用希望直接建立在较新的对象模型上；
- 需要使用 `replaceTrack` 等新能力；
- 希望减少对未规范行为的依赖；
- 需要让长期维护与浏览器演进方向一致。

对于新应用，课程建议直接使用新 API，并优先参考 WebRTC GitHub Pages 上尽量采用新接口的示例，而不是只依赖描述旧 API 的早期书籍。

暂时不迁移也并非没有代价。Chrome 当时正在把 Stream 的内部实现重写到 Track API 之上，即使表面接口不变，底层行为仍可能因缺陷而变化。另一方面，旧 `addStream` 已被使用多年，讲师当时判断它在 2020 年前被移除的可能性不大。这是课程时点对迁移窗口的判断，而不是确定的标准时间表。

### appear.in 的迁移经验

课程嘉宾所在的 appear.in 用两年多时间推进应用更新，其中实际迁移持续了一年以上，目标是借助兼容层在各浏览器使用基于 Track 的 API。工作包括为当时尚无原生 `addTrack` 的 Chrome 添加模拟支持、完善兼容层，并验证规范是否仍能表达应用所需功能；单个任务可能耗时数周，累积成本很高。

appear.in 既有点对点模式，也有由选择性转发单元（SFU）支持的群组模式。每条流程都要测试，组合复杂度迅速增加。因此，课程建议把**良好的端到端测试套件**作为迁移起点，而不是迁移完成后的补充。

Chrome 64 Beta 首次带来 `addTrack` 时，视频会在几秒后冻结，原因涉及内存泄漏和对象被错误解除引用。Beta 发布当天，整个持续集成面板全部变红，嘉宾花了六个小时调试。这一案例说明，测试不仅能证明迁移后的代码正确，也能在浏览器问题进入稳定版前帮助定位它。

## `replaceTrack` 的价值与应用

`replaceTrack` 允许通过 `RTCRtpSender` 替换正在发送的轨道。课程把它视为当时最重要的新能力之一，并通过 appear.in 的实际用法说明其价值。

### 在摄像头与屏幕共享之间切换

在屏幕共享场景中，可以用屏幕画面替换摄像头画面。Firefox 和 Edge 的实现基于 `replaceTrack`；Chrome 早期则依赖 SDP 修改：创建 offer 后操作 SDP。旧办法虽然有效，但更复杂、没有文档，也不属于 Google 正式支持的稳定路径，随时可能失效。

应用通过检测 `window.RTCRtpSender` 及其原型上的 `replaceTrack` 来决定是否启用新路径。Chrome 一旦发布原生支持，代码便可自动采用受支持的方法。能力检测比单纯按浏览器名称和版本分支更有前瞻性，但仍需配套测试。

### 停止发送视频并关闭摄像头指示灯

视频静音按钮在某些实现中不只是暂停画面，而是真正停止视频轨道，从而关闭摄像头指示灯。Chrome 65 之后，可以停止旧轨道，再通过新的 `getUserMedia` 流接回视频，并利用 `replaceTrack` 避免重新协商。

Firefox 中相同做法当时效果不佳，但 Firefox 60 的计划行为是：轨道没有发送实际摄像头图像时就关闭摄像头指示灯，因此把轨道的 `enabled` 属性设为 `false` 即可达到目的，不必照搬 Chrome 的实现。

迁移过程中还遇到了自动播放策略变化。当时原定在 Chrome 65 推出的调整被推迟到 Chrome 66，而 WebRTC 会受到何种影响仍缺少文档。嘉宾认为，在用户已经授权摄像头和麦克风后，再限制相关视频自动播放并不合理，但当时只能继续观察并处理实际问题。

### 通话中切换设备与调整采集参数

`replaceTrack` 还可用于不重新加载页面就切换通话中的设备，但平台限制会影响体验：

- Firefox 当时只允许同时打开一个麦克风，切换前必须停止旧麦克风；用户是否接受设置期间声音中断，是产品设计必须回答的问题；
- Android 可能只允许同时打开一个摄像头，使平滑切换更困难；
- 调整摄像头分辨率时，宽高比可能被锁定，导致预览与实际输出图像的分辨率或宽高比不同。

没有 `replaceTrack` 时，课程团队很难在短期内实现这些流程；新 API 让实现成为可能，但并未消除操作系统、设备和用户体验方面的限制。

## SDP 能力协商：Plan B 与 Unified Plan

### 两种多流表达方式

在同一 SDP 中如何表达多路音频和视频，长期存在两种方案：

- **Plan B**：音频使用一条 m 行，视频也使用一条 m 行，再把多个流复用到对应媒体行中。Chrome 最初提出并长期默认采用该方案。
- **Unified Plan**：更符合 SDP 原有语义，在每个媒体段中放置一个流或轨道。Firefox 支持这一方向。

Unified Plan 早在 2012 年柏林会议上就被提出，而 Chrome 到课程录制时才刚开始实现。这一时间跨度说明，协议协商模型的变化比增加一个 JavaScript 方法更缓慢，因为它还会影响媒体服务器和整个生态系统。

### SFU 与 Simulcast 让迁移更复杂

Chrome 对 Simulcast 的支持有特定实现方式，许多厂商已经据此调优自己的 SFU。当时尚不清楚这种行为将如何与 Unified Plan 配合。

如果 SFU 同时支持 Chrome 和 Firefox，厂商很可能本来就需要同时处理 Plan B 与 Unified Plan，并继续维持两套路径，观察浏览器实现如何收敛。不能只修改 SDP 中的一处标记，就假定整个 SFU 已完成迁移。

### 点对点场景并非都必须立即切换

对不使用 SFU、只做点对点通信的应用，真正必须依赖 Unified Plan 的场景并不多。appear.in 曾在同一个点对点连接中同时分享摄像头和屏幕，浏览器端并未直接依靠 Unified Plan 完成，而是进行了大量 SDP 修改：线上使用 Chrome 的 Plan B，再转换为 Firefox 和 Edge 所需的 Unified Plan。

团队希望尽早删除这类转换代码，但愿意至少再等待一年，直到实现稳定。测试时，Unified Plan 被放在功能标志之后。简单示例能够运行，复杂应用却暴露了大量问题；嘉宾曾向 Google 提交一批崩溃 ID，涉及 `getSenders`、`getStats` 等接口未正确接入。Chrome 中相关问题修复后，又会碰到 Firefox 的缺陷。原定交付时间已经推迟，何时稳定只能继续观察。

这里得到的经验是：SDP 方案迁移必须结合真实应用、SFU、Simulcast 和统计接口一起测试，不能以基础点对点示例作为充分验证。

## `getStats` 的标准化与高效使用

### 从旧统计对象到标准化 Map

`getStats` 用于查询连接及连接质量数据。2015 年底前后，WebRTC 1.0 把统计结果从 JavaScript 对象改为 JavaScript `Map`。原先通过对象属性或索引读取某项统计的代码，需要改为 `get(id)` 形式。

这是破坏性变化，却仍随 WebRTC 1.0 发布，因为当时规范尚处于形成 1.0 的阶段。WebRTC 1.0 的这一版本号不应被理解为遵循 JavaScript/NPM 生态常见的语义化版本承诺。

Chrome 在 2016 年年中以前还使用自己的统计变体，其名称和处理方式与规范差异很大。Adapter.js 做了大量转换，使结果更接近标准 API，但并未、也无法掩盖所有差异：

- 部分统计名称保持相同，许多名称已经改变；
- 统计项在大型统计对象中的位置可能不同；
- 旧 Chrome 统计中仍可能包含尚未进入规范的信息；
- 新模型与 ORTC 及其他 WebRTC 对象更加一致。

因此，旧统计字段文档仍有迁移参考价值，但应用需要逐项核对映射，不能只更换 `getStats` 的调用形式。

### 针对单个发送器查询统计

Chrome 当时准备提供 `RTCRtpSender.getStats`，让应用只查询某个轨道或发送器的统计。例如，可以向音频发送器请求所发送音频的电平等信息，而不是遍历整个对等连接的统计结果。

这一接口本质上是对全量统计的过滤和优化。一次全量查询可能返回约一百项数据，而单轨道查询可能只需九到十项。对于希望减少统计开销的应用，优先查询更具体的对象比反复遍历完整报告更高效。课程团队当时也在讨论如何为旧版本提供兼容模拟。

### 用计数器差值计算时间段指标

WebRTC 1.0 统计的一项设计原则，是通常提供累计计数，而不是直接给出应用所需的全部瞬时速率。例如：

- 帧数；
- 已发送或已接收的字节数；
- 已发送或已接收的 NACK 数；
- 图像丢失指示（PLI）的数量。

应用应在两次调用之间计算计数差，再除以时间差，得到该时间段的平均值或速率。这种设计让调用者能够自行决定统计窗口。课程建议参考规范中的示例实现这一计算。

## 如何评估网上的 WebRTC 代码

### 星标数不能代表可维护性

GitHub 星标只能说明关注度，不能回答项目是否仍适合当前应用。真正需要评估的是谁在开发、谁在维护，以及维护者能否持续投入。

WebRTC 虽然不要求为 API 本身付费，但完整服务并不便宜。成本可能包括：

- 信令服务器；
- STUN/TURN 服务器，其中 TURN 带宽成本尤其明显；
- 成本更高的媒体服务器；
- 测试、质量保障和持续集成基础设施；
- 跨浏览器端到端测试及浏览器问题跟进。

如果团队不愿长期承担这些工作，选择平台提供商并支付费用可能是一项合理投资，而不是单纯增加开支。

### 检查项目生命力和维护网络

评估开源项目时，首先应查看最后一次提交时间。课程当时以 PeerJS 为例：它很早出现，但近几年提交不多，而规范与 API 已大幅演进，因此仍主要依赖旧接口。如果它恰好满足应用需要，可以继续使用；一旦出现问题，应用可能缺乏维护支持。

还应检查：

1. 有多少贡献者，是否有持续维护者；
2. 哪些真实产品在使用它；
3. issue 是否得到处理，处理质量如何；
4. 项目或维护者是否出现在 WebRTC bug tracker 中；
5. 维护者是否会向浏览器厂商报告问题并合作解决；
6. 是否有跨浏览器、跨版本自动化测试；
7. 是否使用 `addTrack`、`getSenders` 等较新 API，还是长期停留在维护模式。

SimpleWebRTC 当时约有 3000 个星标，但原维护者离开原团队约两年后仍无人接手。这说明星标和持续维护完全是两回事，也反映出开源项目需要可持续的商业与投入基础。

### 在浏览器稳定版发布前发现问题

浏览器每次版本更新都可能破坏一两项既有行为。进入稳定版后，再想要求浏览器迅速修复会困难得多，因此至少应在 Beta 阶段发现问题。

课程以 Feross 的 simple-peer 为例：该库使用 `getStats` 判断连接是否正常运行，而 Chrome 66 一度不再为仅包含数据通道的连接返回相关统计，可能使库失效。有人报告后，该问题成为 Chrome 66 的发布阻断项并得到修复。这个案例体现了维护者参与浏览器缺陷跟踪的实际价值。

Adapter.js 则展示了测试基础设施的做法：通过 Travis 持续集成，在每个拉取请求上运行多个浏览器版本，包括四个 Firefox 版本、三个 Chrome 版本以及 Electron。这样的矩阵能够尽早暴露大量细小差异。对准备长期运营 WebRTC 服务的团队而言，这类测试不是额外装饰，而是控制升级风险的基础能力。

## 面向迁移与选型的实践清单

综合全章，可以把 WebRTC 1.0 相关工作的检查顺序整理为：

1. 明确应用使用的是 Stream、Track 还是 Transceiver 模型，避免无依据地混用不同代 API；
2. 用能力检测和 Adapter.js 处理差异，但不要以兼容层代替真实浏览器测试；
3. 把 `srcObject`、`urls`、Promise、`getStats` 的 Map 读取方式等基础变化纳入代码审查；
4. 新应用优先采用新 API，旧应用则根据功能收益、维护成本和业务价值决定迁移节奏；
5. 使用 `replaceTrack` 时，同时验证重新协商需求、设备占用、自动播放和摄像头指示灯行为；
6. 涉及 Plan B、Unified Plan、Simulcast 或 SFU 时，使用复杂真实流程验证，而不只运行简单示例；
7. 在浏览器 Beta 阶段运行端到端测试，并跟踪浏览器缺陷；
8. 选择第三方库时，以维护活动、测试、贡献者和浏览器厂商协作情况为核心，而不是只看星标。

## 小结

WebRTC 1.0 在课程时点已经成为 W3C 候选推荐标准，但规范稳定、浏览器实现和应用采用仍处在不同阶段。ORTC 对象、Track/Transceiver 模型、Plan B 与 Unified Plan、标准化 `getStats` 共同构成了这次演进的核心。`replaceTrack` 等新 API 能显著简化设备与媒体轨道切换，却也暴露自动播放、设备限制和跨浏览器差异。

迁移的关键不是把旧方法名全部替换成新方法名，而是用真实业务和端到端测试验证整个媒体协商链路。无论是升级自己的应用，还是选用 GitHub 上的第三方项目，持续维护、跨版本测试和对浏览器缺陷的跟进能力，都比“目前能跑”或“星标很多”更可靠。
