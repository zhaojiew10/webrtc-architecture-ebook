# 第 47 章 WebRTC PaaS

WebRTC PaaS 通常以通信平台即服务（Communication Platform as a Service，CPaaS）的形式出现：平台托管或管理以 WebRTC 为重要组成部分的通信基础设施，并通过定义明确的 API 提供给开发者。本章整理 CPaaS 的选择标准、供应商类型、能力分层、市场变化和主要趋势。所有产品能力、市场状态和课程判断均按录制时表述，不作后续更新。

## 什么构成 WebRTC CPaaS

课程认为，一个支持 WebRTC 的 CPaaS 平台应包含以下要素：

1. **托管或管理的 WebRTC 基础设施**：客户不必自行搭建整套通信基础设施。
2. **定义明确、文档完善的 API**：不仅要有平台能力，还要让开发者清楚如何访问这些能力。
3. **以开发者为主要受众**：开发者是平台的客户，并在平台之上构建应用。
4. **配套支持服务**：平台不仅交付 API，还要提供与使用平台相关的支持。

因此，CPaaS 不只是把媒体服务器放到云上，也不只是提供若干 SDK。它把基础设施、开发接口、目标用户和支持组合成一种平台服务。

## 商业层面的选择标准

选择 CPaaS 意味着选择一个准备长期合作的供应商，首先要核对业务本身。

### 业务性质与供应商匹配

不同业务对供应商的要求不同。例如，医疗保健业务可能需要寻找符合 HIPAA 要求或具备相应合规能力的公司；大型服务提供商也会根据自身规模考察 CPaaS 供应商。

这里的关键不是简单追求“大”或“小”，而是确认供应商能否满足行业、合规、规模和支持要求。

### 通信是附加功能还是核心能力

如果大型应用只需要少量视频通话，而主要价值都在与 WebRTC 无关的领域，团队对通信平台的选择方式会不同于以实时通信为核心的产品。

附加功能更强调快速接入和减少开发工作；核心能力则需要更深入地检查架构限制、路线图、控制力和长期依赖。相同供应商未必同时适合这两种定位。

### 供应商锁定

每家供应商都有自己的 API。选定平台后，需要回答：

- 自己被锁定到什么程度？
- 能否转向另一家供应商？
- 迁移会有多困难？

锁定不只发生在媒体服务器接口，也可能发生在消息、身份验证、业务流程和用户交互等更高层能力中。

### 收费模式与自身商业模式

CPaaS 供应商如何向应用方收费，最终会影响应用方如何向自己的客户收费。课程特别指出，免费增值（Freemium）模式通常与 CPaaS 不太匹配；社交网络和免费增值类应用经常会选择自行构建基础设施，而不是采用 CPaaS。

这并不表示所有此类产品都必然自建，而是提醒选型者把单位通信成本、免费用户成本和自身收入模式放在一起评估。课程没有给出统一价格公式，核心依据是供应商计费方式必须与应用商业模式相容。

## 技术层面的选择标准

### 封闭服务还是外部互通

首先要判断服务是否是一座“孤岛”。如果必须与外部网络连接，就要确认供应商能否支持相应互通，例如：

- 连接 PSTN 电话网络；
- 通过 SIP 中继连接 SIP；
- 支持 SIP 视频。

还需要明确服务是开放还是封闭，以及是否需要本地部署方案。支持实时视频并不等于自动支持所有这些网络和协议边界。

### 地理分布与基础设施覆盖

应用的地理分布会影响平台选择。需要确认供应商是否能在特定国家或地区提供基础设施，是否足够接近用户，以及其服务覆盖是否符合应用目标。

不同供应商在全球不同地点运营基础设施，提供的服务类型也不同，因此不能只根据“全球服务”这一笼统描述作判断。

### 服务等级协议

应用若有服务等级协议（SLA）要求，就应向 CPaaS 供应商明确询问可以获得什么保障。不同供应商提供的 SLA 不同，其部署位置和服务能力也不同。SLA 应与业务承诺一起核对，而不是默认所有平台提供相同等级的保障。

## 横向与纵向供应商

课程把 CPaaS 供应商概括为横向和纵向两类。

### 横向供应商：覆盖广泛通信渠道

Twilio 是课程用于说明横向供应商的例子。它当时提供多种 CPaaS API，包括可编程短信、电子邮件、视频、语音、聊天、传真，以及 WhatsApp 和 Facebook Messenger 等渠道 API。

横向厂商需要覆盖开发者的广泛通信需求。课程据此认为，其 WebRTC 视频或语音支持通常不如更专注的平台深入或功能丰富。这是一项课程中的类型判断，具体项目仍需逐项核对能力。

Twilio 还展示了横向厂商向更高层业务扩展的路径：

- 收购 SendGrid，扩展电子邮件能力；
- 构建 Twilio Flex，进入可编程呼叫中心方向；
- 收购客户数据平台（CDP）公司 Segment，管理企业客户信息；
- 将 CDP、电子邮件和呼叫中心能力结合，向客户互动平台拓展。

课程认为，横向 CPaaS 厂商当时普遍在建立自己的呼叫中心方案，并尝试与 CDP 厂商合作或自行构建相应能力。CPaaS 仍然存在，但供应商的关注点可能扩展到更大的客户互动业务。

### 纵向供应商：深入特定通信能力

纵向供应商会在特定通信 API 领域继续深入，提供课程所谓的“最佳单项”方案。课程以 Agora 为例：

- 从视频通话服务起步；
- 增加实时互动视频流；
- 将音频纳入其中；
- 提供视频通话相关的录制功能；
- 当时又加入实时消息能力。

它也在增长，但主要沿着人与人之间的 IP 通信纵向扩展，而不是横向覆盖所有业务渠道。

横向与纵向的区别不是简单的功能多少，而是平台把开发和支持资源投向更广泛的渠道，还是更深入的实时通信场景。

## CPaaS 的能力分层

### 底层基础设施与通信构建块

课程从底向上描述 CPaaS 的能力图：

1. **基础设施层**：电话号码、VoIP，以及可能连接的社交网络等。
2. **通信构建块**：应用实际消费的 API，如短信、语音、视频、传真和 IP 消息等。

在这一层，视频主要采用 WebRTC；语音有时包含 WebRTC，但主要还是电话通信。因而，不能因为平台同时列出“语音”和“视频”，就假定两者都使用同一种 WebRTC 架构。

### 更高抽象层

CPaaS 供应商还会向上提供双因素认证、通知、代理和全渠道消息等服务。其直接价值是让应用以更少代码获得更多能力，减少开发工作。

但更高抽象也会增强供应商锁定。例如，通过不同 CPaaS 供应商发送一条短信，差异可能不大；双因素认证却可能改变最终用户看到的界面、体验和操作步骤，甚至改变服务流程。

因此，高抽象层同时带来两种结果：

- 减少开发量；
- 增加迁移难度和对供应商的依赖。

这是一项需要主动接受的取舍，而不是只有收益的能力升级。

### Serverless、Studio 与机器学习

课程指出，Twilio 曾定义的一些能力后来成为 CPaaS 的常见配置：

- **Serverless**：函数可以直接运行在 CPaaS 平台上，简化运行环境。
- **Studio／Flow**：通过拖放方式构建流程，不同公司可能使用不同名称。

这些能力几乎总是服务于短信和传统语音流程，在 WebRTC 所在的语音、视频场景中则不那么常见。选型时应核实目标场景，而不能把某一渠道已有的能力推广到所有渠道。

机器学习也被放入 CPaaS 能力图中，但不同供应商的支持程度不一致：有些提供，有些没有，有些提供得较少。

## 按实时场景核对能力

WebRTC 和 VoIP 相关覆盖可以涉及语音、视频、录制、IP 消息、PSTN 与 SIP 网关，但课程强调重点仍是语音和视频。实时场景还可以进一步分为：

- 一对一或点对点通信；
- 群组通话；
- 广播与直播。

因此，供应商写明“支持视频”远远不够。若需求是千名参与者的直播，或是 40 人的群组通话，就必须按这个具体规模和场景检查平台支持，而不是用一个笼统的“视频”标签替代需求。

## 市场时间线：动态性本身就是风险

课程讲师自 2013—2014 年开始跟踪这一市场，并持续更新相关报告。时间线的价值不在于记住所有公司名称，而在于观察供应商如何频繁进入、退出、更名、转型和被收购。

### 2014—2016 年

- 2014 年初的报告已包含 Apidaze、Temasys、Voximplant 等厂商。
- 2014 年末，AddLive 被 Snap 收购并退出开放 API 市场，其客户不得不迁移；Requestec 被 Blackboard 收购并转向电子学习；vLine 放弃 API 项目。
- Crocodile 被 Acision 收购并更名为 Forge，同时也有 Respoke 等新进入者。
- 2015 年，AT&T 的开发者项目和 Circuit 等进入市场；TokBox 被 Telefónica 收购，Tropo 被 Cisco 收购，Forge 又随 Acision 的并购发生变化。
- 2016 年，QuickBlox 等继续进入，已有厂商则继续更名和调整。

这些变化表明，供应商被收购后可能继续发展，也可能改变服务对象，或要求客户迁移。

### 2017—2019 年

- 2017 年，AT&T 和 ooVoo 在约两年后停止 API 项目，Respoke 等厂商改变重点，SightCall 转向远程视觉辅助，Sinch 与 CLX 之间发生收购和品牌变化。
- 同年末，已被 Cisco 收购的 Tropo 停止 API 项目并关闭，Forge 也取消 API 项目；Apidaze 被 VoIP Innovations 收购。
- NTT Data 的 SkyWay、Phenix 等新服务进入市场。
- 2019 年，Vonage 收购 Nexmo 和 TokBox，并把 TokBox 纳入 Nexmo 体系；Kandy 随 Genband 的公司更名与合并转向 Ribbon。
- SignalWire 进入市场。课程特别指出，它来自构建 FreeSWITCH 的团队，而许多相关供应商当时使用 FreeSWITCH 作为开源 PBX，承担媒体服务器和 PSTN 连接功能。

有些厂商在并购后继续存在，有些则停止服务。仅看收购新闻，无法判断 API 是否会长期保留。

### 2020—2021 年

- Phenix 转向广播，不再把 API 作为通信工具的重点；Bit6 被课程从列表移除，CafeX 等厂商结束 API 项目。
- ApiRTC、Vidyo 等经历品牌或归属变化，Dolby 通过收购进入这一领域。
- Azure 和 AWS 推出自己的 CPaaS 平台；8×8 提供结合 Jitsi、API 与托管服务的方案。
- Bandwidth、Daily.co、EnableX、LiveSwitch 等进入课程视野。LiveSwitch 最初以 Frozen Mountain 命名，先提供本地媒体服务器方案，后来转向云服务。
- 2021 年，100ms 进入市场，Apidaze 则调整重点并退出相关市场。

课程另外提到 Dyte、MessageBird、Sendbird 等未在时间线中展开的厂商，其中许多也提供 WebRTC 方案并被客户或其他供应商采用。

### 时间线对选型的意义

公司更名、改变重点、被收购后退出市场，或被收购后继续运营，都在反复发生。课程认为这种动态性会持续存在，因此选择供应商时必须问：这家公司是否会长期留在市场？如果它退出或改变方向，应用如何迁移？

供应商稳定性不是附加问题，而是平台选型本身的一项技术兼商业风险。

## 课程观察到的趋势

### IaaS 厂商进入 CPaaS

课程把“IaaS 也成为 CPaaS”视为重要趋势，主要指 Microsoft 和 Amazon：

- Microsoft 提供 Azure Communication Services（ACS）；
- Amazon 提供 Chime SDK 和 Amazon Connect。

对大型 IaaS 厂商而言，CPaaS 只是众多服务中的一项，可以与整体 IaaS 方案一起销售。初创企业获得的 Amazon 或 Microsoft 免费额度，有一部分还可用于其 CPaaS API，这会形成使用大型平台的现实激励。

课程还以 ACS 与 Microsoft Teams 的连接为例，说明 IaaS 厂商能够提供其他独立平台无法提供的独特组合。讲师因此认为，IaaS 平台是独立 CPaaS 供应商的重要竞争威胁，同时也是应用方应当考察的选项。

### 重点转向直播

课程列举了几种不同实现路线：

- Twilio 推出 Twilio Live，当时不使用 WebRTC；
- Dolby 收购 Millicast，获得支持 WebRTC 或基于 WebRTC 构建的直播方案；
- Agora 有自己的 WebRTC 方案，同时结合专有组件，在平台上扩展直播能力。

这些例子说明，行业关注可以向直播转移，但“直播”并不自动意味着使用 WebRTC。技术路线仍需按具体产品核对。

### 无代码与低代码

CPaaS 在提供 API 的同时，也开始提供减少甚至绕过直接 API 开发的快捷方式：

- **Daily**：提供完整 iframe，包含通信服务所需能力，应用可以嵌入并进行个性化定制。
- **100ms**：提供低代码方案，让 API 承担比其他平台更多的工作。
- **Agora**：提供应用构建工具，通过向导式表单生成代码。
- **EnableX**：提供类似 Daily 的方案。
- **Vonage 与 Twilio**：通过 API 集和参考应用，向低代码、无代码 WebRTC 会话方案靠近。

无代码和低代码减少代码量，却没有消除平台边界。嵌入的界面、生成代码所依赖的 API，以及可定制范围，仍然会影响迁移和长期维护。

## 谨慎看待分析师市场图

课程引用一份 IDC CPaaS MarketScape，指出其中存在“领导者”和“主要参与者”，却没有“竞争者”和“参与者”。讲师对此提出质疑，因为 CPaaS 市场中供应商一直在进入和退出。

课程还指出，该图没有体现 Agora、Amazon 和 Zoom：Agora 是值得关注的供应商，Amazon 已有 Chime SDK，Zoom 则提供可构建通信应用的 API，虽然课程强调其 API 不完全等同于 WebRTC。

讲师因此通常不依赖分析师对 CPaaS 的判断，认为其视角可能偏向短信和语音。这里的教训是，市场图可以作为参考，但不能替代对具体 WebRTC 场景、产品路线图和架构能力的调查。

## Zoom 作为间接竞争基准

课程把 Zoom 称为“房间里的大象”。按录制时的判断，没有供应商能凭其规模完全复制 Zoom 所做的事情；Zoom 使用 WebRTC 并不多，而且主要视频通话产品并不以 WebRTC 为核心。

即便如此，构建通信服务仍会与 Zoom 形成竞争，因为用户会拿自己的体验与 Zoom 比较，并提出“没有 Zoom 好用”的反馈。课程因此把 Zoom 视为即时竞争者，即使它不是直接竞争同一 API 产品。

对 CPaaS 选型而言，这意味着平台和最终应用都要面对用户已经形成的质量与体验预期，不能只证明技术上能够建立通话。

## 选型复核清单

在作出最终决定时，课程要求再次检查以下项目：

1. **市场动态与并购**：供应商是在增长、转型，还是可能退出市场？
2. **功能列表与路线图**：现有功能是否满足需求，路线图是否包含后续必需能力？
3. **功能覆盖**：平台对所需一对一、群组、直播、消息或互通场景具体支持到什么程度？
4. **数据中心覆盖**：基础设施位于哪里，是否足够接近用户？
5. **多供应商采购**：使用一家还是多家供应商？短信和语音是否来自一家，直播视频来自另一家，视频通话再来自其他供应商？

课程表示，实际中见过上述多种组合。关键不是追求供应商数量最少或最多，而是把真实需求映射到应用如何使用各平台，并明确跨平台集成责任。

## CPaaS 与 IaaS、SaaS 的责任边界

CPaaS 不是唯一选择。课程用服务分层比较三条路径。

| 路径 | 第三方提供 | 应用团队负责 | 主要代价或限制 |
| --- | --- | --- | --- |
| IaaS | 网络、存储、服务器和虚拟化 | 从操作系统到应用的全部内容，WebRTC 位于自建部分 | 需要构建和运营更多基础设施 |
| CPaaS／PaaS | 在 IaaS 内容之外，还提供操作系统、中间件、运行时和 WebRTC 基础设施 | 主要构建和管理应用及其数据 | 接受平台 API、能力边界、计费和锁定 |
| SaaS | 第三方提供完整服务，可提供可嵌入的应用或逻辑 | 将其嵌入网站并做一定品牌与外观定制 | 开发工作少，但直接控制和定制空间更受现成服务限制 |

过去常见的本地部署方式，需要团队从网络一直构建到应用；课程认为这种全自建在当时已经很少见。更常见的选择，是在 IaaS、PaaS／CPaaS 或 SaaS 之间确定责任分界。

成本也应沿这条边界理解：自行管理层次越多，建设和运营责任越重；交给平台的层次越多，开发工作通常减少，但平台计费、能力限制和供应商锁定会更加重要。

## 小结

WebRTC CPaaS 以托管通信基础设施、明确 API、开发者导向和支持服务为核心。选择平台时，需要同时考虑行业与商业模式、通信在业务中的地位、互通需求、SLA、地理覆盖、供应商锁定和长期稳定性。

横向供应商强调渠道广度，纵向供应商强调实时通信深度；更高抽象、无代码和低代码能够减少开发，却可能增强依赖。市场并购和退出频繁，产品路线图与迁移可行性必须纳入选型。

最终，没有脱离场景的“最佳 CPaaS”。合理决策应从一对一、群组或直播等具体需求出发，核对现有功能与路线图，并明确 IaaS、CPaaS、SaaS 各自把哪些成本、控制权和运营责任留给应用团队。
