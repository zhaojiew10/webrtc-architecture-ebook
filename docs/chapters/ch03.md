# 第 3 章 浏览器与设备支持

WebRTC 已能覆盖现代浏览器、移动应用和多种嵌入式设备，但“支持”并不等于各环境行为完全一致。本章按课程录制时的情况，梳理桌面浏览器、原生桌面应用、移动端和嵌入式设备的接入方式，以及每种选择带来的测试与控制成本。

## 桌面浏览器的支持现状

WebRTC 的浏览器支持经历了从只有 Chrome，到 Chrome 与 Firefox，再到 Edge、Safari 陆续加入的过程。课程所描述的阶段中，所有现代浏览器都已能开箱即用地支持 WebRTC，但实现行为仍略有差异，也各有不同的缺陷。

| 浏览器或环境 | 课程说明的支持情况 |
| --- | --- |
| Chrome、Firefox | 已在 Windows、macOS、Linux 和 Android 上支持多年；iOS 支持出现较晚，并受 Apple 的 WebKit 能力约束。 |
| Edge | 先在 Windows 上提供支持，随后扩展到其他操作系统；课程录制时主要在 Windows 上流行。 |
| Safari | 在 Safari 所在的 macOS 和 iOS 上提供 WebRTC。支持形成较晚，虽然可以使用，但课程认为它并不总是最省心的选择。 |
| Internet Explorer | 从未真正支持 WebRTC，课程也不再把等待其支持视为可行路线。 |

Apple 后来为 iOS WebKit 加入 WebRTC 支持，才使 Chrome、Firefox 等其他浏览器能够在 iOS 上提供相应能力。原因不在于这些产品名称，而在于 iOS 浏览器的底层约束：开发自己的浏览器必须基于 Apple 提供的 WebKit WebView，而 WebKit 也是 Safari 的基础。因此，在 Apple 的 WebView 支持 WebRTC 之前，iOS 版 Chrome 无法仅凭自身加入完整支持。

原生应用则是另一条路径。由于 WebRTC 具有开源实现，开发者可以把 libwebrtc 移植到目标操作系统并直接使用。许多供应商多年前就这样做了，所以“某个浏览器尚未支持”并不意味着“同一设备上的原生应用也无法支持”。

## 理解浏览器架构

浏览器支持为何会逐渐趋同，可以从浏览器的分层结构理解。以 Chrome 为例：

- **浏览器本身**是用户看到的产品。
- **浏览器引擎**驱动网页运行，处理页面并执行其中的 JavaScript。Chrome 对应的开源基础是 Chromium，Edge、Brave 等浏览器也建立在 Chromium 之上。
- **渲染器**处理 HTML、CSS 并将页面呈现给用户。Chromium 使用的渲染引擎是 Blink。
- **运行时**负责 JavaScript，也涉及 WebAssembly。
- 在更大范围内，Chrome OS 可以被看作一种以浏览器概念为基础构建的操作系统。

早期 Internet Explorer、Chrome、Safari 和 Firefox 并存时，Chrome 与 Safari 曾共同使用 WebKit，Firefox 和 Internet Explorer 则使用各自的引擎。Google 后来认为 WebKit 的多平台协调拖慢了 Chrome 的开发，于是派生出自己的 Blink 代码库，先删除 Chrome 不需要的代码，再加快新功能开发。此后 Blink 与 WebKit 成为两条独立路线，Apple 也会按需要将 Blink 的部分代码移植回 WebKit。

Microsoft 先以 Edge 取代 Internet Explorer，之后又让新版 Edge 转向 Chromium。于是 Chrome 与新 Edge 在浏览器实现和行为上具有高度共同基础，这也解释了为什么桌面支持策略中常把 Edge 与 Chrome 放在一起考虑。

按课程录制时的工程经验，Chrome 通常最容易支持：使用者多，WebRTC 调试和开发工具也最完善。Safari 往往最难支持，主要原因是持续出现的缺陷，尤其是 iOS 设备上的音频处理。这里的“容易”与“困难”是相对测试和调试成本而言，并非说其他浏览器没有问题。

## 原生桌面应用与 Electron

有些产品希望用户不必打开浏览器，并通过常驻桌面的应用提高使用黏性。Electron 是课程重点介绍的方案：它把开源的 Chromium 与 Node.js 打包，并整合不同操作系统所需的服务。可以将其简化为 **Node.js + Chromium + 桌面系统集成**。

开发者可以把已有的 Chrome Web 应用连同浏览器基础一起封装成原生应用，在 Windows、macOS 和 Linux 上运行。同一套 Web 代码既可以运行于浏览器，也可以运行于 Electron。与完全依赖用户浏览器相比，Electron 还有三个特点：

1. 应用可以控制内置浏览器的升级过程。
2. 开发者可以重新编译并替换浏览器的某些部分，加入自有实现；课程提到一些 WebRTC 供应商确实这样定制。
3. 可以加入操作系统特定能力或直接访问设备的功能，实现普通浏览器环境无法提供的集成。

## 桌面端支持策略

课程列出了几种实际策略，它们没有脱离产品需求的统一优劣：

- **只支持 Chrome**：实现和测试范围最小。课程录制时 Chrome 的市场份额超过 60%，因此部分 Web 应用只保证在 Chrome 上运行。
- **支持 Chrome 与 Safari**：覆盖课程所说的两种最受欢迎浏览器，同时照顾 Safari，尤其是移动端用户。
- **支持 Chrome 与 Firefox**：课程认为这两者在当时较容易兼容。这里没有单列 Edge，是因为新版 Edge 与 Chrome 基础接近，支持 Chrome 后通常也具备支持 Edge 的良好条件。
- **支持所有现代浏览器**：覆盖最广，但浏览器越多，兼容性问题和测试工作越多。
- **只提供 Electron 应用**：不承诺支持任何浏览器，要求用户下载应用；内部仍然运行 Web 技术，但浏览器版本和行为由应用控制。
- **同时支持 Electron 与某个浏览器**：例如过去的 Slack 视频通话可选择 Chrome，或在 PC 上使用 Electron 应用。

面对不支持或不愿支持的浏览器，还可以直接忽略它们并提示用户更换浏览器。这在 Safari 尚未支持 WebRTC 的年代很常见，现在仍是一种产品选择，只是会把转换成本交给用户。

历史上还存在两条补救路线：在 Internet Explorer 等浏览器中安装 WebRTC 插件，包括 Temasys 的商业插件和一些开源方案；或在没有 WebRTC 时降级到 Flash。课程明确把二者都视为已经走到尽头的路线，不建议继续采用。

如果不想直接使用 Electron，也可考虑其他浏览器封装或桌面容器。课程列举了 Windows 上的 WebView2，以及 CEF、OpenFin 等方案，并指出 Electron 是其中最受欢迎的选择。最后一种决策当然是判定 WebRTC 不适合当前产品，转而采用其他技术；支持 WebRTC 本身并不是必须完成的目标。

## 移动端的三种基本方式

移动端可以沿三条基本路线使用 WebRTC：

1. 在支持 WebRTC 的移动浏览器中运行 Web 应用。
2. 在封闭的应用中运行，包括原生应用或应用内 WebView。
3. 不提供 WebRTC 支持，保持现状。

### Android

Android 上的 Chrome、Firefox 及其他一些浏览器支持 WebRTC，应用内 WebView 也可使用。因此可以选择：

- 直接在支持的浏览器中运行 Web 应用，并针对目标浏览器测试；
- 把 Web 应用放入 WebView，避免为媒体部分编写完整的原生实现；
- 开发原生应用，直接使用 WebRTC 库。

### iOS

按课程录制时的说明，Safari 自 iOS 11 起支持 WebRTC，WebView 的可用支持则在 iOS 14/15 所代表的阶段逐步补齐。其他 iOS 浏览器同样受到 WebKit 基础的影响。

“已经支持”并不表示没有工程风险。课程特别强调当时仍存在不少严重缺陷，尤其集中在音频栈，以及切换 Bluetooth、AirPods 等音频设备时。开发者需要处理大量边缘情况，或者明确接受某些情况不在支持范围内。

### 为什么仍要支持移动浏览器

既然原生应用可控性更强，为什么不完全放弃移动 Web？原因是用户确实会在移动浏览器或应用打开的网页中完成部分活动。如果目标用户的使用过程包含移动 Web，就应考虑支持它。

一次性或低频交互尤其能体现这一点。例如，在医疗场景中，患者只需要与医生进行一次通话。要求患者在通话前强制安装应用，往往会增加不必要的阻力；移动浏览器可以提供更直接的入口。是否开发原生应用，应由使用频率和产品需求决定，而不是由“WebRTC 可以在浏览器里运行”这一点单独决定。

## 原生移动应用中的 WebRTC

原生开发最常见的基础仍是 Google WebRTC 项目提供的 libwebrtc。课程以 Android 为例说明两种组织方式。

### 使用 JNI 绑定

一种方式是使用库自带的 JNI 绑定，在其上用 Java 或 Kotlin 编写应用逻辑，信令也位于这一层。

如果采用 SIP 方案，则可能使用 PJSIP。课程描述的结构是把 PJSIP 实现在 JNI 绑定之下，直接连接 WebRTC 库；上层应用仍通过 JNI 使用 Java 或 Kotlin。此时信令主要位于 C/C++ 一侧，而应用逻辑位于 Java/Kotlin 一侧。这个例子说明，WebRTC 库、信令栈和应用层可以分别选择，不必全部使用同一种语言或框架。

### 使用 WebView

另一种方式是用 HTML5 和 Web 开发技术构建跨平台移动应用，通过操作系统的 WebView 访问 WebRTC。应用可以把大部分功能都放在 WebView 中，也可以只让 WebRTC 部分运行于 WebView，其余部分保持原生实现。

### 获取 WebRTC SDK 的途径

课程列出了几种来源：

- 从 webrtc.org 获取代码，自行构建和移植。
- 请第三方协助移植。
- 购买第三方 SDK 的商业许可；课程指出这类供应商数量正在减少。
- 使用 libwebrtc 以外的开源 SDK，例如以 Go 语言实现的 Pion。
- 使用 WebRTC 平台型服务提供的整体方案。SDK 只是其中一部分，中间的媒体服务器、TURN 服务器和信令等也可由同一供应商提供。

选择 SDK 时，不能只比较客户端接口：是否同时获得服务器、信令和运维能力，会改变整个系统的责任边界。

## 移动端架构的组合选择

课程并未把某一种移动路线定为所有产品的答案，而是给出多种可组合策略：

- **分别开发 Android 与 iOS 原生应用**：对于追求高端、精致体验的移动产品，课程将其视为最佳实践；WebRTC 只是整个应用的一部分。
- **使用跨平台框架**：可在 Xamarin、PhoneGap 等方案之上开发，再通过框架接入 WebRTC。
- **只在一端使用原生应用**：例如为 iOS 构建原生应用，而 Android 继续使用 Chrome。这样可绕开课程所述的 Safari WebRTC 缺陷，是一种常见取舍。
- **两端采用不同的 Web 容器策略**：Android 应用中使用 WebView，而 iOS 不采用 WebView，原因同样可能是希望绕开 iOS 浏览器侧的问题。
- **只支持移动浏览器**：Android 上支持 Chrome，iOS 上支持 Safari，不再提供原生应用。
- **原生与 Web 混合**：使用 React Native 等跨平台方案，让应用的一部分保持原生，另一部分采用 Web 技术，同时覆盖 Android 和 iOS。

这些策略的共同点是按平台问题分配工程投入，而不是强求两个平台使用完全相同的内部实现。

## 嵌入式设备

“嵌入式”并不只指一种硬件。课程列举的范围包括 PC 应用、机顶盒、IP 摄像头、无人机、汽车、Raspberry Pi，以及需要运行 WebRTC 的其他设备和芯片组。这类环境往往没有现成浏览器支持，开发者需要承担更多移植工作，但并非无法实现。

主要有三种方式：

1. **移植 libwebrtc**：把主库适配到目标设备或系统。
2. **采用其他实现或第三方方案**：例如 Pion，或适合目标平台的其他 SDK。
3. **通过媒体服务器做网关**：使用 Janus 等媒体服务器，以不同协议连接服务或设备，再把这些通信网关到 WebRTC。

网关路线说明，设备并不一定要自己完整实现浏览器式 WebRTC 栈；有时把协议转换放在媒体服务器侧更符合系统结构。

## 小结

现代 Chrome、Firefox、Edge 和 Safari 已让 WebRTC 覆盖 Windows、macOS、Linux、Android 和 iOS 等主要环境，libwebrtc、Pion 及其他 SDK 又把能力扩展到原生和嵌入式设备。但架构选择不能只问“是否支持”，还要问支持成本由谁承担。

浏览器优先能减少用户安装步骤；Electron 和 WebView 能复用 Web 代码并提高部分可控性；分别开发原生应用有利于打造完整体验，却需要更多平台投入；嵌入式设备则可能需要移植或网关。课程强调 Safari、iOS 音频和设备切换等实际差异，正是在提醒开发者：覆盖范围必须与测试范围、边缘情况和产品使用方式一起决定。
