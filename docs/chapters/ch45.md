# 第 45 章 信令替代方案

WebRTC 不提供完整的信令系统。它能够生成会话描述协议（SDP）等需要交换的信息，但由应用程序决定把这些信息发送到哪里、使用什么方式发送，以及如何处理。本章比较两类选择：开源自建信令，以及信令即服务。所提到的项目维护状态、产品能力和课程推荐均保留录制时的语境，不作为后续产品现状的更新。

## 开源自建信令的起点

### 为什么经常看到 Node.js

准备自行编写信令服务器时，Node.js 是最常见的起点之一。课程给出三个原因：

- 它使用 JavaScript，与浏览器客户端常用的开发语言一致；
- 它天然偏向异步处理，适合大量消息和连接事件；
- 它较为流行，开发者通常更容易找到相关经验。

用 Node.js 很快搭出一个信令服务器并不困难，但“能够交换 SDP”与“可以支撑生产服务”之间仍有很大距离。

### GitHub 项目不能直接等同于生产方案

另一种常见做法是在 GitHub 搜索 WebRTC 信令项目，下载并运行，遇到问题后再抱怨项目不可用。这种方式忽略了从概念验证到生产服务之间的缺口：示例可能只覆盖最理想的呼叫流程，而没有解决规模、状态、异常和长期维护。

完全从零编写所有生产机制成本很高，但找到一个恰好适合自身需求的现成项目也不容易。因此，选型时必须区分学习代码、演示代码和可运营服务。

## 课程讨论的开源项目

### AppRTC

AppRTC 是 Google 的“Hello World”式演示应用。可以在线看到它运行，也可以取得开放源代码，自行下载、安装和运行。它采用宽松许可证，课程指出它过去维护较为积极，录制时已不如从前。

主要问题是控制和修改并不容易，尤其是在尝试支持移动端时。课程的明确建议是不把它作为实际项目的基础，而不是因为它的演示无法运行，而是因为从演示走向定制产品的代价较高。

### OpenEasyRTC

EasyRTC 最初由 Priologic 创建，后来被分叉出 OpenEasyRTC，并曾相当流行。它采用 BSD 许可证，比较贴近一对一会话，即一个人与另一个人通信。

如果需要在此基础上实现群组通话和组信令，修改会比较困难。分叉的背景也与原项目维护不足有关，原维护方后来退出了相关市场。综合维护状态和适用场景，课程同样不建议选用它。

### SimpleWebRTC

SimpleWebRTC 采用 MIT 许可证，功能不算十分丰富，但结构简单，容易理解和使用。它曾是相关服务内部信令能力的一部分。

课程指出，随着对应服务转向付费模式，SimpleWebRTC 的维护减少，团队不再积极把新功能持续加入这个免费开源项目。因此，即使它曾经流行，课程录制时仍不建议采用。

### PeerJS

PeerJS 同样采用 MIT 许可证，设计目标是尽量简单。课程讲师过去会直接建议不要使用，但在看到 2019 年左右维护有所增加、出现较活跃的开发或支持后，态度有所缓和。

不过，这种缓和并不等于首推。课程仍表示，如果存在其他合适选择，不会优先推荐 PeerJS。它说明维护状态会变化，选型应核实项目当下的实际活动，而不能只记住项目过去的流行程度。

### SimplePeer

SimplePeer 由 WebTorrent 项目的维护者 Feross 编写，而 WebTorrent 本身也使用 WebRTC。课程认为 SimplePeer 维护良好，并且为开发者提供的结构优于前面几个简单方案。

如果需求确实非常简单，课程在录制时的建议是优先考虑 SimplePeer，而不是 AppRTC、OpenEasyRTC、SimpleWebRTC 或 PeerJS。这里的推荐有明确边界：它针对简单需求，并不意味着可以不做生产化工作。

### WebRTC Missing Codelab

WebRTC Missing Codelab 是 Philipp Hancke 编写的 GitHub 项目，也是 WebRTC Codelab 课程的一部分。它对各部分代码作出解释，说明为什么这样写、背后的理由是什么，并附带练习，便于理解代码。

该项目代码量很小，基本部分质量较好，维护也得到课程肯定，但**并不适合直接投入生产**，仍有许多工作要做。课程把它推荐为自行构建时的学习起点，而不是完整信令产品。讲师也说明自己对此存在一定偏向。

### Matrix

课程还推荐关注 Matrix（matrix.org）。它最初由 Amdocs 创建并资助，后来独立发展，相关公司为 Element，在开放通信领域可看作 Slack 的一类开源竞争方案。

按课程的归纳，Matrix 可作为信令服务器，采用 Apache 许可证，具有开放、去中心化和联邦式特征，并开箱提供丰富的消息能力。如果需求复杂、需要大量现成消息功能，可以研究 Matrix，而不是只盯着极简 WebRTC 演示项目。

课程还提到其 Python 实现，以及当时正在构建、旨在提供更高性能的另一个实现。这里的重点是功能丰富度与架构路线，具体版本状态不作额外延伸。

## 从概念验证到规模化生产的困难

一对一直接音视频通话看起来很简单：注册用户从浏览器相互呼叫，不需要会议功能，似乎只需交换信令即可。课程认为，许多服务对这种简单浏览器间通话的支持也只是浅层的，自行搭建一个演示确实不难，难点在于生产化。

### 连接规模与跨服务器路由

课程用 WebSocket 数量说明扩展问题：一台机器需要维持 1 万个用户连接时，就要处理 1 万个 WebSocket；当连接数增长到 10 万，单机很可能不再足够，需要扩展到多台机器。

多机之后问题不只是“增加容量”。如果用户 A 要呼叫用户 B，而 B 连接在另一台信令服务器上，系统必须解决：

- A 如何找到 B 所在的位置；
- 两台服务器如何交换或转发信令；
- 整个路由过程如何随服务规模增长而持续工作。

因此，信令扩展不仅是服务器数量问题，还涉及用户定位、跨节点通信和系统状态设计。

### 状态与异常场景

生产服务还必须维护连接和会话状态。例如，用户关闭浏览器标签页或按 F5 刷新页面时，原有连接、在线状态和正在建立的呼叫应如何处理？这些边缘场景在最小示例中往往不存在，却会直接影响真实用户体验。

再叠加审计日志、故障排查、无法连接的原因分析、全球地理分布和持续维护，信令就不再是简单的消息转发。选择自建，就意味着愿意承担这些隐性复杂性。

## 为什么采用信令即服务

WebRTC 已进入零售银行、游戏、监狱探视、广播、健身、约会、视频直播、远程医疗等许多垂直场景。对这些企业而言，通信是产品能力之一，却未必是核心业务。

课程以远程兽医服务为例：企业真正关注的是让宠物主人远程获得兽医服务，而不是亲自开发和维护一套信令基础设施。它可以选择完整 CPaaS，也可以只把信令交给服务商，自己保留其他部分。

采用信令即服务的主要理由包括：

- 获得服务可扩展性和可维护性；
- 减少自建全球地理分布的工作；
- 借助平台处理审计日志和故障定位；
- 避免亲自维护所有连接、扩展和异常机制；
- 让团队把精力放回核心业务。

这并不是说托管服务消除了所有问题，而是把一部分基础设施责任转移给供应商。

## 信令即服务的选择

### 通用或专用消息服务

课程首先提到 Google Firebase。如果应用已经使用 Firebase，可以继续在其上增加信令组件。

此外，还有多家消息即服务供应商：

- **PubNub**：课程称其为这一领域较知名的公司，可以用其消息能力传输 SDP 和其他信令消息。
- **Pusher**：作为同类消息服务选择。
- **Ably**：课程讲师特别偏好的方案。
- **Scaledrone**：课程列举的另一项选择。

按录制时的观点，如果在这些供应商中开始调研，课程会先考察 Ably。testRTC 在构建非常简单的 WebRTC 示例时通常也使用 Ably，而不自行开发信令服务。这样可以采用无服务器方式，甚至不需要另外安装并运行 Node.js 服务器。

这里的“无服务器”是指应用团队不必自行运行信令服务器，并不表示底层不存在服务器。它适合简化示例和减轻运营工作，但仍需核对自身完整需求。

### IP 消息与 CPaaS 平台

一些 IP 消息或 CPaaS 供应商也提供可复用的聊天能力，用于承载信令。课程列举了：

- Twilio 的可编程聊天服务；
- Azure Communication Services 的丰富聊天能力；
- Vonage Conversation API，可处理信令部分并保存历史记录。

这类方案适合已经使用相应通信平台，或除了实时媒体信令外还需要消息、历史记录等能力的应用。它们与纯消息服务的边界并不只由名称决定，而要看实际需要的能力和已有平台依赖。

## 服务连续性与供应商风险

托管信令减少了运营工作，却引入供应商连续性风险。课程以 Parse 为例：Parse 被 Facebook 收购后退出相关市场，原先依赖它进行信令的用户便无法继续按原方式使用。

PubNub、Pusher、Ably 等公司也可能在未来发生收购或战略变化。课程讲师推测，如果收购看重的是客户基础和开发者服务，而非单纯技术，服务可能继续存在；但这只是课程中的判断，不能替代对服务连续性和迁移成本的评估。

因此，采用托管服务时应同时考虑：如果供应商改变产品方向，自己的信令消息、状态逻辑和客户端集成是否容易迁移？不要因为免去了服务器维护，就忽略对供应商的长期依赖。

## 三类路线的取舍

| 路线 | 主要优势 | 需要承担或接受的事项 |
| --- | --- | --- |
| 基于开源项目改造或从零自建 | 控制力强，可按自身需求设计 | 从示例到生产的缺口、扩展、状态、异常、维护和全球分布 |
| 使用 Firebase、PubNub、Pusher、Ably 等消息服务 | 减少信令服务器运营，便于聚焦业务 | 供应商依赖、服务连续性，以及应用侧信令逻辑和集成 |
| 使用 IP 消息／CPaaS 平台 | 可结合聊天、历史记录及平台中的其他通信能力 | 对平台 API 和能力边界的依赖，需确认是否贴合整体架构 |

选型不应只比较“能否发送 SDP”。还要明确应用是一对一还是群组、需要多丰富的消息能力、预期规模多大、是否要求全球部署、团队是否愿意长期运营，以及通信是否属于核心竞争力。

## 小结

WebRTC 把信令留给应用，是为了让应用自行决定交换 SDP 和其他消息的方式，但这也把生产化责任交给了开发者。开源项目适合提供不同复杂度的起点，其中 SimplePeer 被课程用于简单需求，WebRTC Missing Codelab 更偏学习，Matrix 面向丰富消息和复杂需求；它们都不能在未核对需求的情况下直接等同于生产系统。

信令即服务可以把扩展、维护、日志和地理分布等工作部分交给供应商，代价是引入平台依赖和连续性风险。最终选择应围绕业务重点、规模、功能丰富度、运营责任和迁移成本，而不是仅依据项目流行度或搭建演示的速度。
