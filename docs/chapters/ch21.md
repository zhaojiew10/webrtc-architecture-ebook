# 第 21 章 WebRTC 安全

WebRTC 的媒体传输默认加密，但“WebRTC 本身安全”并不等于“基于 WebRTC 的应用天然安全”。浏览器、信令、原生客户端、TURN 服务器和媒体服务器分别承担不同的安全责任。本章从常见误解出发，讨论外设权限、SRTP 密钥交换、服务器防护、本地 IP 地址与 mDNS、端到端加密，以及漏洞和升级治理。

## 安全设计与常见误解

WebRTC 的媒体栈使用 DTLS 和 SRTP，媒体始终加密，应用不能选择发送未加密的 WebRTC 媒体。信令则不属于 WebRTC 的标准范围，需要由应用自行实现；浏览器厂商强烈推动信令和网页使用加密通道，但这部分最终仍是开发者的责任。

浏览器是 WebRTC 安全模型中的一项重要优势：

- 浏览器厂商负责其 WebRTC 实现。`libwebrtc` 由 Google 发起并维护，同一实现也进入 Chrome；发现的漏洞会由厂商修复并发布。
- 浏览器通常自动更新，安全补丁能够迅速到达用户，而不必等待每个应用分别升级。课程引用的 Firefox 和 Chrome 发布数据表明，新浏览器版本通常能在几天内覆盖超过 80% 的部署量。
- 浏览器沙箱把许多底层风险隔离在应用之外，相当于将一部分安全工作委托给浏览器厂商。

这种优势不能自动覆盖整个系统。原生应用需要自行决定何时更新代码和修复漏洞；TURN 服务器、媒体服务器的软件与配置需要自行维护；信令逻辑、身份识别和会话策略也都由应用负责。WebRTC 是不规定信令的媒体引擎，而不是一套完整、开箱即用的安全通信产品。

围绕 WebRTC 的 Fear、Uncertainty and Doubt（FUD，恐惧、不确定与怀疑）常把不同问题混在一起。应当分别判断：

- **IP 地址泄露**：这是实际讨论过的问题，后续引入的 mDNS 机制用于减少本地 IP 暴露，不能简单推导为“必须使用 VPN”。
- **互操作性**：早期争论常围绕 Internet Explorer。课程录制时，主流浏览器均已支持 WebRTC，但不同实现仍可能有少量功能差异和互操作性问题。
- **缺少固定信令机制**：这是设计选择，让应用能够采用适合自己的协议，而不是遗漏了一项必备功能。
- **容易遭受中间人攻击**：风险往往来自应用的信令和身份机制，而不是 SRTP 媒体加密本身。应用仍需设计可靠的身份与信令保护。
- **只支持点对点通信**：加入 SFU、MCU 等媒体服务器后，WebRTC 同样能够支持多人通话。

WebRTC 运行在浏览器中，因此会遇到其他 VoIP 产品没有的浏览器特定攻击；它的广泛应用也使研究者与攻击者更愿意寻找其实现漏洞。不过，许多应用层风险并非 WebRTC 独有。

课程以 Zoom 在 2019 年的安全事件说明这一点。为了方便再次启动应用，Zoom 曾在 Mac 上安装本地 Web 服务器，该组件的缺陷可能让网站劫持摄像头。Zoom 修复后，Apple 又通过静默更新移除了这个本地服务器。这个例子并不意味着 WebRTC 能自动解决所有类似问题，也不意味着某个产品永远不安全；它说明安全很复杂，而采用由浏览器持续维护的媒体引擎，可以减少其中一部分风险。

## 麦克风、摄像头与屏幕权限

访问外设既是功能问题，也是用户隐私问题。

### `getUserMedia` 与 HTTPS

调用 `getUserMedia` 是为了访问麦克风或摄像头。课程要求使用 WebRTC 的网页及信令采用 HTTPS：使用 HTTP 时，一些浏览器不允许调用该 API，另一些浏览器虽然允许，却可能在每次调用时重新请求权限。以 Chrome 为例，通过 HTTPS 提供页面后，浏览器可以按域名记住用户允许或拒绝摄像头、麦克风访问的决定，减少重复询问。

HTTPS 本身并不保证整个应用安全，但它是必须完成的基础措施。如果业务以微件形式嵌入第三方网站，而承载页面仍使用 HTTP，外设访问可能无法按预期工作。课程给出的补救方式是从主页面打开独立弹出窗口，让实际功能运行在满足要求的页面中。

### 屏幕共享权限不能按普通外设处理

屏幕共享每次都由浏览器请求用户许可，不能记住一次选择后永久复用，也不能在普通网页中绕过。权限窗口以及“共享什么”的选择界面属于浏览器安全模型，网页不能重新设计其外观或删除这个步骤。Electron 等受控应用环境可以减少或移除这类弹窗，但那是应用运行方式的变化，而不是网页取得了绕过权限的能力。

浏览器提供细粒度的共享范围，包括整个屏幕、设备上的某个应用窗口，或特定浏览器标签页。应用需要把这些限制纳入交互设计，而不是把它们当作可以随意关闭的阻碍。

## SRTP 的密钥交换

SRTP（Secure Real-time Transport Protocol，安全实时传输协议）负责加密媒体数据，但它需要通信双方拥有共享秘密。以 Alice 和 Bob 为例，双方都必须得到密钥，而窃听者 Eve 不能得到；如果双方此前从未通信，关键问题就是如何安全地完成密钥交换。

### 为什么 WebRTC 不使用 SDES

SIP 中常见的一种方式是会话描述协议安全描述（SDP Security Descriptions，SDES）。SDES 把一方提供的 SRTP 共享秘密直接放入 SDP。SIP 再通过 TLS 发送 SDP，因此网络传输过程看似受到保护。

问题在于，WebRTC 的 SDP 和信令逻辑会进入浏览器中的 JavaScript 环境。开发者工具、已安装的扩展以及其他恶意代码都可能接触其中的信息。即使 SDP 在 HTTPS 连接中加密传输，共享秘密仍可能暴露在浏览器内运行的代码面前。因此，WebRTC 不采用 SDES；课程也指出这种方式已经过时，仍在使用它的系统应当重新评估。

### DTLS-SRTP

WebRTC 使用 DTLS-SRTP。DTLS 在 UDP 上完成安全会话握手，媒体平面由此获得共享秘密，再将其用于 SRTP 数据包。也就是说，密码学密钥交换复用在媒体通道上，而不是把媒体密钥作为明文 SDP 参数交给 JavaScript。

对大多数 WebRTC 应用开发者而言，理解这一信任边界比推导握手的每个细节更重要；只有自行实现 WebRTC 协议栈时，才需要进一步研究标准中的完整过程。

## TURN 与媒体服务器的防护

### TURN 凭据与配置

TURN 通过服务器转发媒体，运营者需要支付带宽和服务器 CPU 成本。如果没有访问控制，第三方就可能把这套中继资源当作免费基础设施，因此 TURN 必须配置凭据。

直接把长期 TURN 密码交给浏览器也有暴露风险：创建 `RTCPeerConnection` 时需要提供 ICE 服务器及其认证信息，这些值会进入客户端环境。课程建议改用临时、短生命周期的密码，在浏览器范围之外完成协商，由服务端为特定会话生成凭据，再交给客户端使用。Twilio、Xirsys 等服务以令牌形式提供访问凭据；自建 coturn 也可以建立类似的临时凭据机制。

密码并不能解决全部问题。TURN 软件漏洞和错误配置同样危险。课程引用 Slack 的 coturn 配置事件：其中继服务器曾被滥用以访问同一网络中的内部服务。这说明部署时既要更新软件，也要限制中继能够访问的网络目标，不能把“配置了密码”视为完成全部安全工作。

### 媒体服务器的网络暴露面

媒体服务器需要让客户端访问其媒体端口。应开放服务器实际使用的 UDP 临时端口范围，否则媒体可能退回 TCP，损害实时媒体质量。与此同时，不应把整个主机无差别暴露给公网：

- 关闭不需要的 UDP 端口；媒体面不要为了省事而依赖 TCP 或 TLS。
- TCP 端口默认关闭，只开放运行确实需要的端口。
- 对协商、控制等端口，尽量只允许应用服务器或信令服务器的特定地址访问。

由应用或信令服务器统一负责实际会话协商，可以形成系统的单一事实来源，集中掌握会话状态并执行策略，也能减少媒体服务器被滥用的机会。媒体连通性和控制面最小授权需要同时设计，而不是相互替代。

## 本地 IP 地址与 mDNS

ICE 候选主要包括主机候选、服务器反射候选和中继候选。主机候选使用本地 IP 地址；无法直连时，可以通过 STUN 得到服务器反射地址，使用公网映射地址；仍然失败时，可以通过 TURN 中继。

主机候选有实际价值。如果双方位于同一局域网，本地地址可以让媒体不经过 NAT 或 TURN，降低延迟，也避免把媒体送到外部网络。但是，把类似 `10.0.0.1` 的本地地址通过 SDP 暴露给网站，又会泄露本不希望公开的网络信息。课程以 Chrome 77 与 Chrome 78 之间的变化说明：过去网页能够利用 JavaScript 显示这类地址，后来浏览器借助 mDNS 缩小了这个泄露口。

mDNS 即多播 DNS（Multicast DNS），本身并不是 WebRTC 专有技术。它依赖 UDP 多播：设备在本地网络中查询某个名称，多播消息不会发送到局域网之外；拥有该名称的设备作出响应，其他设备也能获得并缓存名称与 IP 地址的对应关系。

WebRTC 为用户生成随机的 mDNS 名称，并在 SDP 中传递这个随机名称，而不是直接传递本地 IP：

- 对不在同一局域网的接收者，这个随机值没有可用意义，也无法据此取得本地地址。
- 对同一局域网中的通信方，可以通过 mDNS 解析并访问对应设备，从而保留本地直连的优势。

课程还描述了当时的浏览器行为：未调用 `getUserMedia`、没有获得麦克风或摄像头权限时，WebRTC 将连接视为仅接收场景，不共享本地 IP；对于 ICE TCP 候选，也使用 mDNS 名称替代本地 IP。具体在哪些场景隐藏地址由浏览器实现决定，后续实现还可能扩大 mDNS 的使用范围。

## 可插入流与端到端加密

需要区分“传输加密”和“应用端到端加密”。

两个浏览器直接交换媒体时，DTLS-SRTP 可以保护浏览器之间的媒体。通过 TURN 中继时，TURN 只转发数据，没有客户端的共享秘密，无法查看媒体内容，因此仍能维持通信端点之间的加密。

使用 SFU 或 MCU 后，信任关系发生变化。媒体服务器需要路由或混合媒体，会作为每条传输连接的端点，与每个客户端分别协商密钥。服务器因而能够访问媒体内容，也有能力录制或转发它。SRTP 仍然保护每个网络区段，但不再保证媒体内容对媒体服务器保密。

可插入流（Insertable Streams）通过在 SRTP 之内再增加一层应用加密解决这一问题：

1. 密钥管理系统或服务（KMS）帮助通信端点建立新的共享秘密，这层密钥交换在 WebRTC 媒体服务器之外完成。
2. 摄像头或麦克风数据先被采集和编码，编码后的缓冲区在发送端进入应用的发送转换。
3. 应用先加密编码帧，随后正常的 SRTP 过程再加密一次并发送。
4. SFU 只能解开外层 SRTP，以完成接收和转发，不能解开应用内层加密。
5. 接收端完成 SRTP 解密后，在接收转换中解开应用层加密，再交给解码器播放。

课程把这套技术描述为一个分层栈：WebRTC 之上是可插入流，其上是规定加密方式的 SFrame，再向上是 KMS。SFrame 处理发送转换取得的帧，增加一个小的 4 字节头部和认证标签，对内容进行认证并加密帧。头部保持可读，使 SFU 仍能获得路由媒体所需的信息，而真正需要保护的帧内容保持加密。课程录制时已经有开源的 JavaScript SFrame 实现。

真正的难点通常落在 KMS：由谁运行和实现，谁可以访问密钥，密钥如何分发，都是端到端加密系统必须回答的问题。课程指出，当时存在多种专有答案，IETF 的标准化工作也仍处于早期。只加入帧加密而不解决密钥管理，并不能自动得到完整的端到端安全方案。

## 漏洞、攻击面与升级策略

课程以模糊测试和漏洞治理作为最后一个安全主题。WebRTC 与其他软件一样会有缺陷；随着它进入浏览器、操作系统和大量通信产品，攻击者寻找并利用这些缺陷的动机也会增强。课程记录的历史数据是：2019 年大约修复了 26 个 WebRTC 漏洞，其中一部分被明确标为安全问题。它们大多仍是具有安全后果的普通软件缺陷，而不是某种 WebRTC 独有的神秘弱點。

广泛部署的库尤其有吸引力。课程提到 WhatsApp 曾出现只需拨入电话、目标不必接听就可能受攻击的案例，说明媒体处理路径可能在用户明确交互之前就成为攻击入口。漏洞交易市场也为常用移动技术中的零日漏洞提供回报，而 `libwebrtc` 同时存在于多种高使用率产品中，进一步提高了研究价值。

应用可以采取以下措施缩小攻击面：

- 如果不需要 `libwebrtc` 的某项能力，可以在信令层过滤相关协商内容，避免开放该路径。
- 对原生应用，可以调整 `libwebrtc` 的构建，移除不需要的代码或不把它们编译进实际库。
- 不要在没有用户动作时建立连接。快速呼出或接听体验不能以绕过用户参与为代价。
- 特别注意被叫方的 `setLocalDescription(answer)`：设置本地 answer 后，WebRTC 就会启动 ICE 协商并开始打开连接。即使应用暂不发送 SDP 或 ICE 候选，也不能把连接启动推迟到以后。因此，被叫方不应在用户点击接受或接听前执行该步骤。主叫方则仍需按正常流程先设置本地 offer，再将其发送给被叫。

原生实现还需要长期维护自己的 WebRTC 源代码树。跟随上游并不容易：构建系统复杂，需要评估 Chrome 上游变更、测试测试版、验证性能与破坏性变化，规划新版本发布方式，并维护自己在 WebRTC 之上的补丁。

升级节奏也应有明确策略。不必追逐每一个约 4～8 周的 WebRTC 发布周期；可以每隔 3～4 个上游发布版本升级一次，约每 4～6 个月一次，并强调每年不要少于 2 次，以便获得安全修复、缺陷修复以及影响移动端与浏览器互通的变化。同时，常规版本之外还必须有处理紧急安全问题的机制，能够把上游安全补丁整合进当前发布版本。

## 小结

WebRTC 强制媒体加密，浏览器又提供沙箱、自动更新和及时补丁，这些能力构成了良好的安全起点，而非应用安全的终点。完整方案还需要保护信令与身份、遵循外设权限模型、使用临时 TURN 凭据、最小化服务器暴露面、理解 mDNS 的隐私作用，并在 SFU/MCU 架构中区分区段加密与真正的端到端加密。最后，原生实现必须把缩小攻击面、控制连接启动时机和持续升级纳入日常工程流程。
