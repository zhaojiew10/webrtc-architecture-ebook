# 第 32 章 AV1

AV1 是课程录制时最新一代、面向免版税生态的视频编解码器。它汇集了多个开放编解码项目的成果，并由开放媒体联盟（Alliance for Open Media，AOM）推动。AV1 的压缩能力很有吸引力，但较高的计算要求、仍在成熟的实现以及不均衡的终端支持，决定了它更适合从特定场景和实验开始，而不是直接替换所有 WebRTC 视频链路。

## 从多个开放项目到 AV1

在 H.264、VP8 之后，HEVC 与 VP9 分别代表需版税和免版税两条演进路线。VP9 之后，多家公司又分别推进新的开放编码技术：

- Google 在 VP8、VP9 的基础上继续研究 VP10。
- Mozilla 推动 Daala。
- Cisco 推动 Thor。

这些项目中的开放工具，以及公司愿意放入共同专利池的相关技术，最终被整合到开放媒体联盟的工作中，形成了 AV1。因此，AV1 内部可以看到 VP9、VP10、Daala 和 Thor 等项目的部分成果，而不是某一家公司的单线升级。

同一时期还有 HEVC 的后继者 VVC（H.266）。课程指出，按录制时的情况，VVC 与 WebRTC 尚无实际交集；讨论 WebRTC 的未来视频编码时，产业注意力主要集中在 AV1。

## 开放媒体联盟与免版税生态

开放媒体联盟最初由七家公司发起，课程录制时已列出十二个创始成员。Microsoft、Mozilla 和 Google 从一开始就参与其中，使 Chrome、Edge 和 Firefox 背后的厂商进入同一协作体系。Apple 后来也加入，兼具设备、硬件和浏览器厂商身份。

联盟及生态中的代表性成员还包括：

- 芯片厂商 Intel、NVIDIA，以及以推广成员身份参与的 AMD、Arm；
- 互联网公司 Amazon、Meta、Netflix；
- 长期从事视频通信、拥有 Webex 的 Cisco；
- Samsung 和 Tencent；
- Adobe、Agora、Zoom 等众多其他厂商。

Cisco 至少在 2022 年就已开始试验 AV1，研究它在 Webex 中的适用位置。成员名单会变化，具体名单应以联盟网站为准，但这些参与者说明了 AV1 同时得到浏览器、芯片、内容平台和通信厂商的关注。

AV1 的设计目标包含三个相互关联的方面：

1. **免版税许可。** 联盟公司向希望使用 AV1 的一方提供免版税许可，并将与 AV1 相关的专利贡献到共同体系中，避免成员再向其他 AV1 使用者主张这些专利。
2. **专利审查与法律防御基金。** 联盟不仅汇集技术，也建立专利审查流程和防御机制，为面对外部专利主张的使用者提供支持。
3. **协作式开源环境。** 编解码器有开放实现，产业可以共同优化，而不必各自封闭重复建设。

这里的“免版税”不等于数学意义上的零诉讼风险。课程后文将其解释为：没有使用者必须前往缴费的专利池，通常按无需支付版税处理，但理论上仍可能遇到外部权利人的主张。

## 压缩率、功耗与“代际”的真实关系

一种简化的比较方法，是用横轴表示压缩率、纵轴表示压缩所需功耗或 CPU。越向右，达到相同质量所需码率越低；越向上，编码计算成本越高。

在这种粗略模型中，HEVC 相比 H.264 可获得更高压缩率，同时也需要更多计算；VP8 到 VP9 也呈类似趋势。VP 系列与对应的 H.26x 编解码器位置接近，只是倾向于用稍低的压缩能力换取稍低的计算开销。AV1 则像是进入了另一个区间。

课程在与实际编解码器设计者讨论后，对这个模型作了更接近工程现实的修正：

- VP8 与 H.264 大体处于相近水平；
- VP9 的综合表现不如 HEVC；
- 在特定条件和用例下，AV1 的压缩表现可以优于 HEVC，同时功耗更低；
- 但 AV1 相对开发者更熟悉的旧编解码器，仍然有很高的 CPU 消耗。

因此，所谓“代际”不是一条所有指标都严格递增的直线。AV1、HEVC 与 VP9 在某些场景中可以放在同一组比较，最终仍要结合内容、码率、实现成熟度和硬件能力判断。

## AV1 距离普及还有多远

课程录制于 2023 年，讲师用编解码器的历史时间线解释 AV1 的成熟度：

- H.261 到 H.263 相隔约七年，再到 H.264 又约八年。
- H.264 于 2003 年出现，经过约五六年才开始在部分地方普及，约十年后才可认为几乎无处不在。
- H.265/HEVC 于 2013 年出现，但到 2023 年仍未存在于大多数设备中。iPhone 等部分设备具备能力，专利问题则继续阻碍其普及。
- VP8、VP9 在课程录制时已有约十到十五年的演进历史。
- AV1 于 2018 年出现，到录制时只有约五年。

AV1 的规范和工作方式已经明确，但软件编码器仍在快速优化。课程强调，当时的改进并非每次只挤出 1% 的 CPU，而是仍能看到较大幅度的优化和质量跃升。

硬件支持也刚开始出现：iPhone 15 已带有 AV1 解码器，Intel 和 NVIDIA 的新款 GPU 也开始提供相关能力。不过，“开始可用”不等于“所有终端都已具备”，AV1 的高 CPU 要求仍是实时编码的主要约束。

因此，课程对生产采用持谨慎态度：有条件的团队应开始实验，但在当时不建议不加区分地直接投入全面生产使用。

## 适合优先尝试 AV1 的场景

### 离线或云端编码、终端只负责解码

当编码器离线运行或部署在云端，而目标设备只需解码时，AV1 可以降低网络码率和带宽需求。代价是云端 CPU 使用量上升。

这种方案还必须验证目标设备能否解码所需分辨率。只确认“支持 AV1”并不足够，还要确认其分辨率和性能是否满足播放要求。

### 原生应用中的低码率视频

在能够控制运行环境的原生应用中，可以尝试以 50、100 或 200 kbit/s 等很低码率发送视频。课程认为，当时的 CPU 已有可能承担这一级别的编码工作，而 AV1 能在低码率下带来更明显的质量收益。

码率继续升高后，编码计算压力也会上升，此时可重新比较 VP9、HEVC 或其他方案，而不是默认 AV1 始终最佳。

### 低帧率、高分辨率屏幕共享

屏幕共享中的文本编码对传统视频编解码器并不友好。AV1 编码器在这类内容上表现很好，因此低帧率、高分辨率的屏幕共享是值得优先试验的方向。

Cisco Webex 宣布首先采用 AV1 的场景也正是屏幕共享，并限定在其能够控制、支持并拥有运行环境的原生应用中。这样可以减少浏览器和设备差异带来的不确定性。

### 有明确目标的实验

如果业务涉及极低码率、离线编码或低帧率屏幕共享，AV1 尤其值得投入实验。实验应同时观察画质、码率、CPU、目标设备解码能力和实际功能边界，而不是只验证“能否编码成功”。

## 与 VP9、HEVC 的可用性和许可对比

以下描述均为课程录制时的情况，不应视为持续更新的浏览器兼容表。

| 编解码器 | 可用性与采用情况 | 许可方面的课程结论 |
| --- | --- | --- |
| VP9 | 各浏览器基本可用。Google Stadia 在关闭前曾使用；Google Meet、Jitsi Meet、Agora 等已用于生产。解码器广泛存在，编码则取决于设备能力。 | 与 VP8、AV1 一样，没有必须前往缴费的专利池，按免版税处理，但不构成永远不会被起诉的保证。 |
| HEVC | Apple 和 Intel 已表明支持，Google 及基于 Chromium 的 Edge 可能跟进。实际可用性取决于设备是否有硬件编码器和解码器。Daily 曾宣布可在其应用的 iOS 与 Mac 设备之间使用。 | 涉及 MPEG LA、HEVC Advanced、Velos Media 及独立公司等多个许可来源，费用和专利池处理都很复杂。 |
| AV1 | 课程称 Chrome 和 Safari 当时已可原生使用，Edge 与 Firefox 尚未提供相应支持。Google Duo 在移动端低码率或屏幕共享中使用，Webex 则在有限范围内用于屏幕共享。 | 以免版税生态、共同专利池、审查与法律防御机制为基础。 |

对于 H.264，课程特别区分浏览器与原生移动应用：通过浏览器使用时，Web 开发者通常不需要自行处理许可；若在自己的移动原生应用中放入 H.264 软件编码或解码实现，则可能需要就编码与解码两端分别与 MPEG LA 讨论许可。HEVC 的许可主体更多、成本更高，课程不建议在缺乏明确必要性时主动承担这份复杂性。

## 小结

AV1 汇集 VP10、Daala、Thor 等项目的成果，依托开放媒体联盟形成免版税、开放协作的编解码生态。它在压缩能力上很有潜力，但课程录制时仍处于软件快速优化、硬件逐步出现、浏览器与终端支持不均衡的阶段。

最合理的切入方式不是全面替换，而是从云端或离线编码、低码率原生应用、低帧率高分辨率屏幕共享等边界明确的场景开始。只有在真实设备上验证质量收益足以抵消 CPU、兼容性和运维成本后，才适合扩大生产使用范围。
