# 第 65 章 WebRTC 服务器端基础：服务器规格

WebRTC 的不同服务器承担不同工作，容量规划不能采用同一套机器规格。Web 与信令服务更接近常规应用后端，STUN/TURN 服务主要受中继流量影响，媒体服务器则要根据转发、混合或录制的具体方式判断瓶颈。课程的重点不是给出一组通用机器参数，而是说明各类负载究竟偏向内存、CPU、存储还是网络。

## 先按职责区分容量问题

一个 WebRTC 产品可能包含 Web 服务器、信令服务器、STUN/TURN 服务和可选媒体服务器。STUN/TURN 服务协助浏览器穿越防火墙与 NAT，使媒体尽量直接传输，必要时才通过服务器中继；媒体服务器则用于录制、多方通话等后端媒体处理。

正因为工作方式不同，这些组件通常适合部署在云环境中的不同实例类型上，而不是共享一种看似“通用”的配置。下面分别分析其资源特征。

## Web 服务器：按常规应用后端规划

Web 服务器的规格与大多数其他 Web 服务器相似，课程把它视为一个相对已知的问题。

通常需要重点关注**内存**，因为后端会处理数据库、用户以及用户如何工作、运行和位于何处等信息。CPU、存储和网络也仍然是基本资源，但没有因为使用 WebRTC 就需要一套完全不同的特殊处理。

这并不意味着 Web 层没有扩展性问题，而是其规格选择更接近普通 Web 应用；容量设计应围绕实际应用逻辑，而不是把它误当成媒体转发服务。

## 信令服务器：内存与异步消息处理

信令服务器的机器需求与 Web 服务器接近，重点仍常落在**内存**上，尤其是在许多用户同时连接到服务器时。网络管理方式会有一些额外细节，但课程指出，信令通常不会给网络带来与媒体中继同等的负载。

它与普通 Web 服务器的主要差异在于**异步性**：服务器不断接收和发送来自不同用户的消息，并以异步方式处理这些交互。

因此，信令服务除了机器规格，还涉及编程语言和运行模型的选择。课程认为 JavaScript 与 Node.js 很适合这类异步工作，并以 PHP 作为对照；当时的许多开源或其他信令项目也构建在 Node.js 之上。这里应区分两个问题：

- 使用什么语言和异步模型，影响信令服务的实现方式；
- 使用什么实例规格，影响其可承载的资源规模。

Node.js 是课程给出的实现建议，不是可以替代容量规划的参数。

## STUN/TURN 服务：为媒体中继时的网络负载做准备

STUN/TURN 服务整体上明显偏向**网络**。它通常不会消耗大量 CPU 或存储，虽然仍可能保存用户、密码等所需信息，但这些不是课程强调的主要负载。

真正的大量网络消耗发生在 **TURN 中继媒体**时，而不是所有连接期间都恒定发生：

- 能直接建立连接的会话，不需要始终把媒体流经服务器；
- 无法直连、必须由 TURN 中继的会话，会显著占用服务器网络能力。

课程以约 **5%～15% 的通话可能需要 TURN 中继**作为经验性示例。这个比例没有附带统一测量条件，不应直接当成所有产品的容量定额；它说明的是，规划时需要区分直连与中继两种负载，并特别关注中继发生时的网络需求。

## 媒体服务器不能用一种规格概括

媒体服务器虽然属于可选组件，内部却包含多种类型。选择性转发、媒体混合和录制对机器的要求差别很大，必须先明确服务器要做什么，再决定规格。

### SFU：网络密集型的媒体路由器

选择性转发单元（SFU）常用于多方视频会话或群组通话。它本质上是媒体路由器：接收各参与者的媒体，再把媒体转发给需要接收它们的人。

其资源特征是：

- **网络是主要压力**：需要同时接收和发送大量数据；
- 仍需要一定存储、CPU 和内存，但整体更偏向网络；
- 云服务商可能因为其实际网络用量明显高于普通云服务器而限制速率。

课程建议，如果云平台允许，把网络与其他资源分开计费的机器会更适合 SFU，便于围绕真实瓶颈选择资源。课程还以许多场景中 CPU 读数只有约 10%～20% 为例，说明 CPU 可能相对空闲；这一数字是课程中的经验描述，不是可用于推算 SFU 会话容量的通用指标。

在云环境中评估 SFU 时，因此不能只看实例的 CPU 核数，还要确认网络能力及服务商是否可能限流。

### MCU：CPU 与内存密集型的媒体混合器

多点控制单元（MCU）也可用于多人加入同一房间的群组通话，但它不是简单转发，而是媒体混合器。课程描述的处理流程是：

1. 接收来自各设备的媒体；
2. 解密并解码这些媒体；
3. 处理各个视频画面，把它们组合成一个视频布局；
4. 生成包含所选内容的新画面；
5. 对结果重新编码；
6. 将编码后的媒体发送给参与者。

解码、画面组合和重新编码使 MCU 需要大量 **CPU**，也会消耗很多**内存**。与 SFU 相比，它的网络压力相对较低，存储仍不是关键资源。

这种计算负担也带来扩展性取舍：在可比较的机器条件下，MCU 的扩展能力更低，单台 MCU 能容纳的参与者通常少于单台 SFU。换句话说，MCU 用更多计算工作生成统一布局，不能按 SFU 的转发模型估算其容量。

### SFU 与 MCU 的规格对比

| 对比项 | SFU | MCU |
| --- | --- | --- |
| 核心处理 | 接收媒体并按需路由、转发 | 解密、解码、组合布局、重新编码后发送 |
| 主要资源压力 | 网络 | CPU 与内存 |
| 相对网络需求 | 高 | 相比 SFU 较低 |
| 存储地位 | 需要一定存储，但不是最突出瓶颈 | 不是关键资源 |
| 相对扩展性 | 较高 | 较低，单机可容纳人数通常少于 SFU |

这里的比较针对资源倾向，不是脱离会话规模、媒体处理方式等条件的固定容量结论。

## 录制服务器：存储优先，计算需求取决于录法

录制服务器明显依赖**存储**，同时也需要一定网络能力接收媒体。CPU 和内存需求则不能一概而论，取决于具体录制什么、怎样录制。

课程对比了两种方式：

1. **取得媒体后解密并存入存储**：处理路径相对直接；
2. **把两三路不同媒体流重新组合成一个布局，只录制合成后的布局**：增加了媒体组合工作，CPU 与内存需求随之上升。

因此，不能仅凭“需要录制”就选择机器。同样的录制功能，直接保存媒体与先合成单一画面再保存，对计算资源的要求并不相同。

## 云环境中的规格选择

把上述组件放到云中时，课程给出的核心原则是**按工作负载选择不同实例**：

- Web 与应用服务器采用常规应用服务器的思路，扩展性和语言选择另行考虑；
- 信令服务关注大量并发连接下的内存与异步处理；
- STUN/TURN 服务主要受网络约束，尤其要关注 TURN 中继时的流量；
- SFU 重点核查网络容量、计费和限流条件；
- MCU 重点准备解码、合成和编码所需的 CPU 与内存；
- 录制服务器优先考虑存储，再根据是否合成画面评估 CPU 与内存。

开源、商业或其他框架可以帮助团队更快获得这些服务器能力，但框架选择与机器规格是两个不同层面的决策。

## 小结

WebRTC 服务器规格应从处理流程推导，而不是给所有组件套用相同配置。Web 和信令服务更接近普通后端，信令尤其强调异步消息模型；STUN/TURN 与 SFU 更偏网络，MCU 更偏 CPU 和内存，录制服务器则以存储为主并随合成处理增加计算需求。在云环境中，还要把网络限流、资源计费方式和不同实例类型纳入取舍。课程中的比例和 CPU 数字只用于说明资源倾向，不能替代针对自身场景的容量测算。
