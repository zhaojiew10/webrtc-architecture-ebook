# 第 66 章 WebRTC 服务器端基础：实用工具

确定需要哪些服务器、各自由什么资源支撑之后，还要决定在这些服务器上运行什么。WebRTC 部署不要求一切从零开始：现有 Web 和消息系统可以复用，信令与 NAT 穿越可以选择自建或云服务，媒体处理也有开源、商业框架及 CPaaS 可选。本章按课程列举的工具说明选择路径；产品、项目的开源或商业归类及托管服务均是课程录制时的示例，不延伸为其后续状态。

## 从服务器职责出发

前面讨论的部署包含四类服务器：

1. **Web 服务器**；
2. **信令服务器**：它与 Web 服务器经常合并，作为一个整体看待，但也可以分开；
3. **处理 NAT 穿越的 STUN/TURN 服务**：配合 ICE 建立连接；
4. **可选媒体服务器**：是否需要取决于服务要加入的媒体能力。

在这些后端之外，客户端仍需要浏览器或应用来承载实时通信。工具选择应服从这些职责，而不是先选框架，再假定它能够替代所有组件。

## Web 服务器：优先复用已有系统

课程对 Web 服务器的建议很直接：使用自己熟悉、愿意使用的工具即可。

如果已有服务器正在运行，就继续按原样使用，除非确有必要，不要为了加入 WebRTC 而修改它。如果目前还没有任何基础，则先确定信令服务器要采用什么方案，再由此推导 Web 服务器需要承担的工作。这样可以避免把 Web 层与信令层分别选定后，才发现二者难以配合。

## 信令服务器：三种实现路径

### 路径一：搭载现有消息系统

如果产品已经有用户之间的消息协议，就可以复用这套通信机制传递信令，而不必另建完全独立的消息通道。

课程以约会网站为例：网站用户原本就能互相发送消息，后来只希望增加语音和视频通话。此时，现有消息协议已经提供了类似信令服务器的基础，可以在其上传递启动语音、视频通话所需的消息。

这种方法的关键不是“约会网站”这一场景，而是识别现有系统中可复用的用户通信和消息传递能力。

### 路径二：自行构建信令服务

没有可复用消息系统时，可以自行开发信令服务器。课程当时推荐的方法是使用 Node.js，并在 GitHub 或 NPM 中搜索已经可用的相关项目或包，而不是从空白项目开始。

这里的工具用法是：

- 先确定需要怎样的信令消息流程；
- 在 GitHub 查找相关实现；
- 在 NPM 生态中查找可复用包；
- 以 Node.js 承载异步消息处理。

课程没有给出某个固定包名或配置参数，因此选择仍应回到自身信令需求。

### 路径三：使用发布/订阅云服务

第三种选择是采用支持**发布/订阅（publish/subscribe，pub/sub）**的云服务，由云平台提供消息分发能力。课程列举的当时较知名或流行的服务包括：

- Google Firebase；
- PubNub；
- Pusher；
- Layer。

这条路径把信令建立在外部云消息服务上，与复用现有消息协议、完全自建信令服务构成三种不同选择。

## STUN/TURN：自托管与托管服务

NAT 穿越组件有两条主要路径。二者都要提供 STUN/TURN 能力，区别在于由谁部署和运行。

### 自托管开源服务

希望自己运行服务器时，课程列出的两个开源项目是 **coturn** 与 **restund**。它们用于 NAT 穿越，提供 STUN 和 TURN 能力。可以从二者中选择一个，完成部署及让其正常运行所需的配置与操作，不必因为是自托管就必然购买商业方案。

自托管意味着团队自己负责服务器运行。课程在此处只给出项目和部署路径，没有提供安装命令、端口或其他参数，不应据此补写统一配置。

### 托管 NAT 穿越服务

另一种方式是让服务商代为运行 STUN/TURN 服务器。使用方需要付费，课程指出通常按进入这些服务器的流量计费。

托管方式的主要优势是**更快得到可配置、可运行的服务**。课程通常建议刚开始开发的客户先采用这种方式，再在以后需要时转向自托管，以便减少初期搭建工作。

课程列举的服务示例包括：

- Twilio 的 NAT 穿越服务，是其产品中的一个组成部分；
- Xirsys；
- Bit6。

这些名称用于说明课程当时的选择，不构成对当前功能、价格或可用性的补充声明。

### 两条路径的取舍

| 对比项 | 自托管 | 托管服务 |
| --- | --- | --- |
| 工具形态 | coturn、restund 等开源项目 | 服务商提供的 STUN/TURN 能力 |
| 运行责任 | 自己部署并运行 | 服务商代为运行 |
| 初期速度 | 需要完成部署和运行准备 | 更快开始配置与使用 |
| 费用方式 | 课程未给出统一模型 | 通常按进入服务器的流量付费 |
| 课程建议的使用位置 | 可在后续转向自行运行 | 适合开发初期快速启动 |

选择时不应只比较软件是否开源，还要把团队愿意承担的部署工作和托管流量费用一起考虑。

## 媒体服务器：按用例选框架

媒体服务器市场上的选择很多，课程没有给出统一的“最佳服务器”。首先仍要明确用例，尤其是需要怎样的后端媒体处理。

如果目标是构建 **SFU**，让媒体在参与者之间路由，课程列举的选项包括：

| 工具 | 课程中的归类 |
| --- | --- |
| Jitsi | 开源选择 |
| Kurento | 开源选择 |
| mediasoup | 开源项目 |
| SwitchRTC | 商业解决方案 |

这些项目名称本身不能替代选型分析。需要多少后端媒体处理、是否确实需要 SFU，仍取决于产品场景；课程也明确说明，除此之外还有其他选择。

## CPaaS：用现成平台与 SDK 减少底层工作

除了直接选择媒体服务器，还可以考虑**通信平台即服务（CPaaS）**。课程特别指出两类适合考虑它的情形：

- 后端需要大量媒体处理，但团队尚未完全确定后续要怎样实现；
- 需要移动端能力，却不想自己处理把 WebRTC 移植到应用中的工作，希望直接获得现成 SDK。

CPaaS 供应商提供框架，开发者可以在其上构建整个应用，也可以把供应商作为服务提供的通信能力嵌入已有应用。这样就不必处处直接处理 WebRTC 底层细节。

不过，课程同时强调，仍应理解 WebRTC 的含义和工作方式。平台与 SDK 可以减少移植和底层实现工作，却不应成为完全不了解实时通信原理的理由。

## 一套按现状选择的顺序

把课程建议串起来，可以按以下顺序确定工具：

1. **检查现有 Web 系统**：能复用就保持原样；没有现成系统时，先确定信令方案。
2. **检查现有消息协议**：能搭载信令就复用；否则在 Node.js 自建方案与 pub/sub 云服务之间选择。
3. **确定 NAT 穿越的运行方式**：需要自行运行就选择 coturn 或 restund 等开源项目；希望开发初期更快上线，可考虑托管 STUN/TURN 服务。
4. **明确媒体用例**：需要 SFU 时再比较 Jitsi、Kurento、mediasoup、SwitchRTC 等课程示例，而不是预先指定统一媒体服务器。
5. **评估平台化需求**：如果后端媒体处理复杂，或移动端需要现成 SDK、不希望自行移植 WebRTC，可进一步评估 CPaaS。

## 小结

WebRTC 服务器端工具选择应优先复用现有资产。Web 服务器可以继续使用已有系统，信令可以搭载现有消息协议、用 Node.js 自建或采用 pub/sub 云服务；STUN/TURN 可以在 coturn、restund 等自托管项目与按流量计费的托管服务之间取舍；媒体服务器必须按用例选择。对于复杂后端媒体处理或希望使用现成移动 SDK 的团队，CPaaS 提供了另一条路径，但仍需要理解 WebRTC 的基本工作原理。
