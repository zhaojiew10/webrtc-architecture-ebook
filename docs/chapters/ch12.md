# 第 12 章 VoIP 的三个层次

VoIP 的竞争焦点一直在变化。早期产品主要比拼码率、分辨率和压缩能力，而 WebRTC 普及后，基础客户端能力逐渐标准化，差异化更多转向媒体处理与网络基础设施。本章先梳理 VoIP 的三次市场转型及其技术分层，再讨论云、二线云、批发托管与运营商等部署方式，最后介绍 Anycast 在低延迟服务中的作用。

## 从“速度和规格”到用户体验

传统 VoIP 很重视“速度和规格”：希望传输得更快、效果更好、画面更大。一条路径是提高比特率，以支持 HD、1080p 乃至 4K；另一条路径是增强压缩能力，让媒体能够更高效地处理并经网络传输。围绕这些目标，市场出现了三次相互关联的转型。

### 转型一：从本地部署迁移到云

这一转型大约始于课程录制前二十年，并在随后明显加速。越来越多客户不再只使用企业内部数据中心，而是转向外部数据中心，包括批发或托管数据中心，以及 Amazon、Azure、Google Cloud 等公共云。

云化改变的不只是服务器放置位置，也改变了服务扩展和产品交付方式。不过，公共云并不是唯一选择，成本、地域覆盖和供应商依赖仍需一起权衡。

### 转型二：从工程定制系统到通用硬件，再到浏览器

早期 VoIP 方案通常建立在工程定制系统之上：先从头设计硬件，自行开发或外包硬件开发，再在这套硬件之上构建软件，并采用嵌入式操作系统。随后，方案逐渐迁移到通用硬件，操作系统也从 VxWorks 等环境转向 Linux；课程录制时，许多基于 Linux 的工作又进一步落到 Android 上。通用平台加快了开发速度，使 VoIP 产品更快进入市场。

下一阶段是浏览器。过去，通用硬件或 PC 上仍需要下载或预装应用；采用 WebRTC 后，VoIP 可以直接在浏览器中运行，无须用户另行安装软件，使用门槛因此显著降低。

### 转型三：竞争基础被重新定义

过去，尤其在视频领域，分辨率是直观的差异化指标：从 CIF 到 VGA，再到 720p、1080p 和 4K。课程以 LifeSize 早期支持 HD Ready 720p 的大屏方案为例，说明厂商曾沿这条路线持续升级。但 4K 视频会议并未因此成为普遍需求，因为更高规格不一定带来足够重要的实际价值。

这可以用“创新者的窘境”来理解。高端客户要求更高性能，低端客户初始要求较低，但其期望也会随时间提高。传统 VoIP 作为延续性技术，沿既定轨迹满足越来越高的需求；WebRTC 则具有颠覆性技术的特征，先进入要求较低的市场，再逐步具备取代传统方案的能力。课程的判断是，WebRTC 当时已走到能够替代许多其他技术的位置。

## VoIP 技术栈的分层与差异化

课程首先区分编解码器、媒体处理和信令三层技术能力，再把基础设施作为承载这些能力、形成部署差异的支撑层。为便于分析，可以将整体结构理解为：

1. **编解码器**：负责音频、视频的编码与解码。
2. **媒体处理**：在编解码器之上处理媒体，包括相关算法与质量优化。
3. **信令**：建立和控制通信会话。
4. **基础设施**：承载服务运行的网络、服务器和数据中心等。

传统 VoIP 中，编解码器、媒体处理和信令几乎都有标准可循，但厂商仍可在任意一层甚至所有层同时差异化，例如开发自有算法、采用专有的编解码器实现或专有编解码器；信令则往往直接采用已有标准。

WebRTC 改变了这套分工。它为基础客户端提供编解码器和媒体处理能力，把信令与基础设施留给应用开发者。信令本身通常难以形成持久差异，于是基础设施成为主要竞争点。与此同时，机器学习和 WebAssembly 又让厂商重新有机会在媒体处理层建立差异化。因此，WebRTC 时代的竞争并没有消失，而是更多集中于媒体处理和基础设施。

## 数据中心位置为什么直接影响质量

基础设施差异化首先体现在部署位置。课程以 Twilio 的部署为例：数年之前约有 8 个数据中心，课程录制时已有 9 个，位于 AWS 云上。即便如此，课程仍认为覆盖不足，因为中国、俄罗斯、南非、中东等许多地区缺少就近节点。

随着人们在更多地区在线工作，用户不再只集中于世界主要科技中心。只在欧洲或美国设置少量节点，难以同时满足各地用户对低延迟和高质量体验的要求。更靠近用户的部署位置通常能改善网络质量与体验。

延迟、抖动和丢包都会损害媒体质量。更好的编解码器、媒体算法和机器学习可以增强系统处理能力，但如果输入链路已经受损，优先获得更好的源流往往更有效。因此，在靠近用户的位置增加数据中心，有时比单纯优化编码或算法更能改善最终质量。

## 现代网络基础设施的部署选择

现代 VoIP 服务可以部署在单一公共云、二线云服务、批发托管或运营商环境中，也可以采用多云架构。常见选择及取舍如下。

| 部署方式 | 主要优势 | 主要限制 |
| --- | --- | --- |
| 单一公共云，如 AWS、Azure、Google Cloud | 数据中心分布较广，工具和能力丰富，开发及扩张速度快 | 成本较高，并依赖单一供应商 |
| 二线云，如 Cloudflare、DigitalOcean | 成本通常低于大型公共云 | 课程认为其全球区域数据中心数量相对有限，开发工具也未必同样完整 |
| 批发、托管与运营商 | 带宽和计算成本通常最低，可组合多个供应商扩展覆盖 | 单一供应商往往只覆盖特定地域或少量地点，开发工具最少，扩张最困难 |
| 多云或多供应商组合 | 能综合不同厂商的价格与地域优势 | 需要同时管理多个供应商及其部署环境 |

### 成本、覆盖与开发速度

从带宽和计算费用看，大型公共云通常最贵，二线服务便宜一些，批发服务最便宜。但价格越低，并不意味着整体方案越简单。

从地域覆盖看，公共云在课程录制时提供了较完整的全球化方案；二线供应商可用的区域数据中心较少；批发供应商可以通过多供应商组合扩大覆盖，但单个供应商可能只提供两三个接入地点。因此，使用批发服务支持多个地区时，通常需要多云或多供应商策略。

从开发和扩张速度看，公共云最容易使用，因为它提供最丰富的工具与能力。课程以云函数为例：大型云厂商普遍提供这类能力，二线供应商未必具备，批发环境则通常没有。这里的“高速增长”是指能以多快的速度在解决方案和数据中心中部署新机器；公共云在这方面最容易，批发环境最具挑战性。

### 两层部署：按工作负载选择平台

一些供应商采用两层策略：把应用逻辑和信令放在 AWS 等公共云上，把媒体服务器放在二线云或批发、托管环境中。这样既能利用公共云的开发速度和快速扩张能力，又能利用二线或批发服务的价格、地域覆盖优势。它不是让所有工作负载使用同一种平台，而是根据工作负载特点分配平台。

## Anycast 与低延迟服务

Anycast 是一种 IP 地址分配与路由方式。通常，应用通过 DNS 把 `google.com` 这类名称转换成 IP 地址，再把数据包发往该地址；在 Anycast 中，多台服务器可以共享同一个 IP 地址，网络根据设备位置等因素，把发往该地址的流量解析到不同机器。这些服务器可以位于同一地点，也可以分布在不同地域。

这种模型有两类值得关注的用途：

- **分散攻击流量**：攻击者向该 IP 地址发起泛洪时，不再只是攻击某一台特定服务器，而需要面对整个网络的承载与分流能力，因此可用于缓解 DDoS 攻击。
- **按地理位置降低延迟**：不只依赖 DNS 地址选择，而是通过支持 Anycast 的服务，把用户引导到合适的就近节点。课程以不再单纯依赖 Route 53、改用 Anycast 服务为例，说明其在地理定位方面的用途。

课程录制时，Anycast 已开始用于面向 WebRTC 的低延迟 TURN 服务，Cloudflare 和 Subspace 都提供这类托管 TURN 服务器。与 Anycast 相关的基础设施创新，还包括在其内部使用 Anycast 的数据包加速方案。

## 小结

VoIP 已从定制硬件和规格竞争，演进到通用平台、浏览器和云基础设施竞争。WebRTC 为基础客户端提供编解码与媒体处理能力后，基础设施成为主要差异化方向，而机器学习和 WebAssembly 也让媒体处理重新成为创新空间。

部署设计需要同时考虑成本、覆盖范围、开发速度和供应商依赖。对于实时媒体，靠近用户的数据中心和更好的源流往往比单纯提高编码指标更重要。公共云、二线云与批发托管可以按工作负载组合使用；Anycast 则为地理就近接入、TURN 服务和数据包加速提供了另一条优化路径。
