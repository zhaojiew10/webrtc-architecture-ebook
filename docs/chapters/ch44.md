# 第 44 章 WebRTC 开发策略

使用 WebRTC 构建产品，不只是选择一套媒体 API，还要决定依赖哪些供应商、基于哪套实现、由谁开发，以及由谁长期运营。本章先梳理 WebRTC 生态系统，再分析基于 libwebrtc 或独立实现时需要回答的问题，最后比较自建、外包、托管和自行运营等开发策略。文中的市场观察和供应商状态均按课程录制时的表述整理。

## 需求增长与人才供给

课程用两类公开数据观察 WebRTC 人才市场：以 GitHub 上围绕 WebRTC 构建的项目数量代表需求，以 LinkedIn 个人资料代表开发者供给。按课程的观察，相关项目自 2020 年疫情以来增长加快，而开发者资料的增长更接近线性，近年甚至有所放缓。

这一对比要说明的是，市场对有经验 WebRTC 开发者的需求增长较快，人才供给却相对不足。其直接后果是：准备开发 WebRTC 产品的团队，未必能轻松找到合适人才。后续无论是招聘内部团队还是选择外包商，都不能把“会做一般应用开发”等同于“做过 WebRTC 开发”。

## WebRTC 生态系统中的参与者

从供应商所承担的角色看，生态系统可以分为 WebRTC 核心、工具供应商、解决方案供应商、二级市场，以及对 WebRTC 组件的再利用。

### WebRTC 核心

核心参与者负责构建和维护 WebRTC API 与库，其中最主要的是浏览器厂商。

Google 是课程所说的最大核心参与者，负责维护 webrtc.org 上的开源库 **libwebrtc**。该库进入 Chrome，并通过 Chromium 进入 Edge；课程还提到 Apple 向 WebKit 的合并使其进入 Safari，以及它与 Firefox 的关系。因此，libwebrtc 的行为变化最终会影响多个现代浏览器。

Mozilla、Microsoft 和 Apple 也会加入自己的修改、完成集成并协助修复问题。课程认为其中 Microsoft 相对活跃，可能与 Microsoft Teams 和 Edge 有关。

除浏览器厂商外，还有一些企业阶段性参与核心开发：

- 课程提到，曾有厂商把 VP9 的可伸缩视频编码（SVC）贡献到 WebRTC 生态。
- Cisco 通过 OpenH264 项目开放自己的 H.264 实现、支付相关专利许可费用，并将其整合进 WebRTC，服务于 H.264 作为必须实现编解码器之一的生态需求。
- 课程录制时还提到 Intel 与 Google 围绕 AV1 实现和硬件加速的合作，使相关能力支持 Intel 硬件。

这些贡献说明，WebRTC 核心并非完全封闭，但不同企业的投入可能随自身业务重点而变化。

### 工具供应商

工具供应商为开发者提供基础设施、框架、代码和现成能力。课程指出，多数开发者不会完全直接基于 WebRTC 构建，而会使用某种开源或商业工具。

工具供应商又可细分为几类：

1. **CPaaS 供应商**：通信平台即服务（Communication Platform as a Service）提供托管基础设施、API 和支持。课程列举了 Twilio、Vonage、Agora、Daily 等。
2. **单项托管服务供应商**：只托管解决方案中的某一部分，而不是提供端到端 WebRTC 平台。例如 Xirsys、Subspace 提供托管 TURN 服务，PubNub、Ably 提供信令或消息能力。
3. **基础设施软件供应商**：提供可由客户自行安装的商业组件。课程列举了 Red5 Pro、Ant Media、AudioCodes 等，并指出这些产品通常不以开源形式提供。
4. **开源项目与外包公司**：开源项目提供可复用工具；外包公司则可直接基于 WebRTC、基于 CPaaS，或基于某个开源解决方案完成应用开发。

单项托管服务与 CPaaS 的区别尤其重要。购买托管 TURN，只解决了 NAT 穿越中的一项基础设施问题；购买信令服务，也只解决消息交换问题。它们并不自动提供完整的 WebRTC 应用或端到端媒体架构。

### 基于 WebRTC 提供产品的供应商

还有一类企业把 WebRTC 用在自己的产品和服务中。例如，云呼叫中心可以在浏览器坐席客户端中使用 WebRTC；远程医疗服务可以用它连接患者和医生。

这些企业可能直接基于 WebRTC 开发，也可能通过工具供应商开发。课程认为，后者在录制时更为常见。它们面向的是具体业务和最终用户，核心竞争力未必在通信本身。远程医疗供应商的关键资产可能是患者记录、HIPAA 合规能力或其他医疗业务，而不是实时媒体技术。

### 二级市场

“二级市场”是指一家企业采用另一家供应商的终端解决方案，同时仍把自己的竞争优势与 WebRTC 联系起来。课程用一条多层供应链说明这一点：

- 浏览器提供 WebRTC；
- Twilio 提供围绕 WebRTC 的工具，并支持 PSTN 与 WebRTC 之间的通话；
- LiveOps 基于 Twilio 构建云呼叫中心；
- Intuitive Solutions 使用 LiveOps，让坐席接听小型披萨店的订餐电话。

最上层企业并未直接开发 WebRTC，却仍会关注整套解决方案因 WebRTC 而获得的能力。与这些企业的 IT 或支持人员交流时，经常会看到这种间接参与方式。

### 对 WebRTC 组件的再利用

一些厂商并不构建标准意义上的 WebRTC 应用，而是从这个流行的开源库中抽取所需组件，把 WebRTC 当作媒体引擎使用。课程列举了 WhatsApp 和 Zoom，并提到可复用的部分可能包括 RTP/RTCP 库、回声消除代码或其他模块。

PJSIP 等开发者客户端 SDK 也体现了类似关系：PJSIP 有自己的媒体引擎，同时也可以与课程认为更好的 WebRTC 媒体引擎集成。判断这类方案时，不能只看是否出现“WebRTC”名称，还要看它实际采用了哪些组件、是否遵循完整的 WebRTC 交互方式。

## 基于 libwebrtc 构建时的决策

如果把 libwebrtc 集成到原生移动应用、桌面应用，甚至服务器端方案中，就必须主动规划升级和维护。

### 发布与更新频率

课程指出，libwebrtc 当时随 Chrome 的发布节奏每月更新。使用方未必也要每月升级，但必须明确自己的发布节奏：是每 3～4 个月，还是更长？如果一年或更久都不更新，课程认为很容易陷入困境。

更新不仅为了获得功能，也为了纳入安全补丁。随着 WebRTC 普及，相关攻击和零日漏洞利用也会增加，因此需要持续跟踪安全问题，而不能只在首次集成时编译一次库。

### 与上游源代码的距离

对 libwebrtc 本身做的每一处修改，都可能提高升级到新版的工作量。内部分支偏离上游越远，合并新版本的冲突和行为差异越多，最终还会拖慢安全修复与正常发布。

因此，在修改核心库之前，应把后续升级成本视为设计约束，而不是把一次性修改看成没有后续代价的工作。

## 采用独立 WebRTC 实现时的决策

另一种路线是采用不依赖 libwebrtc、但自行实现 WebRTC 的代码库。课程以 Go 语言实现的 Pion WebRTC 为例。这类方案提供了不同的集成选择，但需要更仔细地核对完整性和互操作性。

### 功能是否完整

首先要确认它是否包含项目所需的全部组件，而不是只看项目是否标注“支持 WebRTC”。课程特别要求检查：

- 是否包含所需编解码器，以及项目是否真的需要由该库自带编解码器；
- 是否包含带宽估算；
- 具体提供哪些带宽估算算法；
- 还缺少哪些部分，这些缺失是否影响需求；
- 对确实需要但尚未提供的功能，是否准备自行实现。

有些缺口可能直到开发后期才暴露，因此应在选型阶段按需求逐项核对。

### 更新与浏览器互操作

独立实现也需要保持足够活跃的更新。即使自身不基于 libwebrtc，仍要跟踪 libwebrtc 的变化，因为最终很可能需要与 Chrome 等浏览器中的实现通信。

所以，更新频率与互操作性必须一起评估：当浏览器端行为变化时，独立实现能否及时适配？与 libwebrtc 出现互操作问题的可能性有多大？如果无法与浏览器稳定协作，独立实现即使在自身环境中运行良好，也未必能满足应用目标。

## 开发责任与运营责任

开发策略首先有两种责任分配方式：

- **内部开发**：由自己的团队构建，也需要自己的团队长期维护，确保系统持续运行并随 WebRTC 更新。
- **外包开发**：由外部供应商完成开发，但不能把它当作交付后即结束的一次性项目，仍要明确长期维护、扩展和升级责任。

与开发责任相交的另一个选择，是由谁运营基础设施：

- **托管方案**：由其他公司在云服务中，甚至在客户本地环境中负责运营基础设施。
- **自行运营方案**：由自己的运营和 IT 团队管理整个解决方案。

因此，“外包开发”不必然等于“托管运营”，“内部开发”也不必然等于“所有基础设施都自建”。两组决策应分别说明。

## 托管方案的三种路径

### 组合多个单项服务

应用可以从不同供应商购买各个部件，再完成系统集成。例如，使用 Subspace、Twilio 或 Xirsys 等提供的托管 TURN，使用 Ably 提供信令，同时把应用开发外包。

这种方式允许逐项选择供应商，但集成边界、整体行为和跨供应商问题仍需要有人负责。每个部件被托管，并不等于整个应用已经由某一家供应商托管。

### 使用 CPaaS

更常见的托管路径是选择 Twilio、Agora、Daily、Vonage 等 CPaaS 供应商，再由内部团队或外包商在平台上开发。CPaaS 供应商负责基础设施及其运维，应用团队主要关注业务交互。

但采用 CPaaS 并不代表可以完全不懂 WebRTC。团队仍需判断需求是否可行，以及在该供应商的 API 和架构上实现需求有多困难。平台隐藏了基础设施细节，却不会消除所有实时通信约束。

### 嵌入接近成品的 SaaS 能力

如果某项 SaaS 服务已经接近需求，也可以把其中的功能作为一块整体能力嵌入自己的应用，而不是从底层媒体部件开始构建。课程以可通过 API 嵌入的视频会议方案，以及 Twilio Flex、Amazon Connect 这类云端可编程呼叫中心为例。

这条路线强调复用现成业务流程。它适合需求与现有产品足够接近的场景，但需要接受该产品已有的交互、集成边界和能力范围。

## 自行运营的部署形式

自行运营也有不同部署形式：

- 在公有云账户中部署，但账户和系统由自己管理；
- 在自己的数据中心运行；
- 在非公共云的第三方数据中心运行。

课程把公有云中由客户自己拥有并管理账户的方案也归在自行运营一侧。这里的关键区别不是机器物理上位于哪里，而是谁负责系统运营和基础设施维护。

从整体策略看，可以形成一条连续路径：自行开发、集成开源框架、采用商业 SDK 或框架、使用 SaaS、使用提供 API 平台的 CPaaS。沿这条路径向更高层服务移动时，应用团队需要直接掌握的 WebRTC 与 VoIP 细节和投入通常减少，但对平台能力和限制的理解仍然重要。

## 选择外包供应商的原则

### 核实真正的 WebRTC 经验

应选择做过 WebRTC 项目的团队，而不是只有一般开发经验的团队，尽量不要成为其第一个 WebRTC 项目。即使供应商声称团队有经验，也要确认实际投入项目的成员中有做过相关工作的开发者，而不是只有刚招聘、尚待培养的人员。

这一要求与章首的人才供需问题直接相关：供应商的品牌和团队规模不能替代具体项目成员的经验。

### 把需求写清楚

没有写明的需求，不能默认外包商会实现。需求中应明确覆盖 WebRTC 相关部分，包括业务真正需要的实时通信行为，而不是只描述一般应用功能。

### 理解供应商决策带来的架构限制

如果外包商选择第三方 CPaaS，最终架构会受到该供应商的限制；如果采用某个开源媒体框架，限制又会来自该开源平台及其架构设计。

委托方需要理解这些依赖关系，并向供应商提出具体问题。否则，即使应用按时交付，也可能在后期才发现某项关键需求受底层平台约束。

### 提前安排长期支持和维护

项目成功后仍需要持续支持、维护、扩展和升级。一种可考虑的安排，是让委托方自己的团队成员参与外包开发，使其之后能够在内部继续维护。无论采用哪种方式，都应在项目开始时明确长期责任人。

### 不削减测试与监控

不能默认测试和监控一定包含在外包交付物中。课程提醒，供应商可能对这部分额外收费，且交付前的测试有时较为表面；供应商也可能假设客户负责测试，而自己只负责后续支持和缺陷修复。因此，测试范围、监控能力和相应费用都应明确约定，而不是等到上线后再补齐。

## 小结

WebRTC 开发策略至少包含四个相互关联的选择：依赖哪类生态供应商、基于 libwebrtc 还是独立实现、由内部团队还是外包商开发，以及由平台方还是自己运营。

托管服务可以减少基础设施工作，却不会自动消除 WebRTC 需求分析和架构约束；自行开发提供更强的直接控制，也会带来升级、安全补丁和长期维护责任。无论选择哪条路线，都应把功能完整性、浏览器互操作、供应商架构限制、测试监控和长期维护纳入同一项决策。
