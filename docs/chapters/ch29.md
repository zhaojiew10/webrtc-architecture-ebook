# 第 29 章 视频编解码器基础

视频编解码器既要压缩单帧图像，也要利用连续帧之间的相关性，并在实时通信中控制延迟和丢包影响。分辨率、帧率和码率的组合会迅速改变设备需要处理的数据量，因此，理解视频编码的内部工具和实时约束，比简单记忆哪一种编解码器“压缩率最高”更重要。

## 从通用编解码器概念到视频链路

无损编解码器在压缩后再解压，可以得到完全相同的原始比特流，其行为类似 ZIP 压缩归档：文件内容不会因为压缩和解压而改变。

有损编解码器则会舍弃部分数据。对视频而言，首先去掉人眼不易察觉的变化，再大幅压缩剩余内容，所以解码结果不再与原始输入完全一致。实时通信还要求这一过程尽可能快，编码和解码都必须以低延迟完成。

视频媒体链路可以概括为：

1. 摄像头产生原始画面；
2. 编码器压缩数据；
3. 编码码流通过网络发送；
4. 接收端解码网络数据；
5. 解码结果被送往显示器，呈现远端摄像头采集的画面。

这条链路看似直接，但编码器和解码器的计算量、网络波动与显示设备能力都会影响最终体验。

## 通用特性在视频中的具体含义

语音与视频编解码器共享复杂度、延迟、韧性、许可、生态和软硬件支持等评价维度，但视频会把其中一些问题进一步放大。

| 特性 | 视频场景中的重点 |
| --- | --- |
| 复杂度 | 编码器和解码器要分别评估。编码器通常比解码器消耗更多 CPU，不同标准对两侧的复杂度分配也不同。 |
| 延迟 | 具体表现为编码一帧或解码一帧需要多少毫秒；实时会话希望这一时间尽可能短。 |
| 抗丢包能力 | 需要知道多少丢包会让视频变得不可接受。可以通过 FEC、重传等外部机制改善，但编解码器自身的韧性是更好的起点。视频编码通常并不算很有韧性。 |
| 知识产权与版税 | 实现可能涉及专利，部分专利要求支付许可费用。 |
| 普及程度与生态 | 流行方案通常更容易集成、风险更低；冷门或专有方案可能增加部署风险。 |
| 软硬件支持 | 需要确认目标平台是否有成熟实现，目标芯片是否有相应优化，而不只是“标准存在”。 |

与语音一样，视频编解码器规范主要由最终解码器的行为定义：给定码流后，解码器如何解析并还原可显示的数据。规范由此限定编码器可用的工具集合，却不唯一指定编码器的实现方式。

因此，同一个标准下的编码器仍可能在效率和复杂度上有很大差异。一个标准本身很优秀，并不代表手头实现一定优秀；最终效果取决于具体编码器及其配置。

## WebRTC 视频编解码器的基线与扩展

课程列出的 WebRTC 必须实现（MTI）媒体能力包括：

- 语音方面的 G.711 与 Opus；
- 用于电话事件、严格来说并非普通音频编解码器的 DTMF；
- 视频方面的 VP8 与 H.264。

VP8 是 Google 的开源、免版税编解码器；H.264 则涉及 MPEG LA 许可和版税。课程录制时，两者在浏览器生态中都广泛实现，是实际互通的基础，但各自仍有硬件、集成和优化方面的注意事项。

在此之外，课程还提到：

- **VP9**：Google 的另一款开源编解码器；
- **HEVC（H.265）**：H.264 的后续标准，课程当时认为其 WebRTC 可用性仍在发展；
- **AV1**：开放媒体联盟推动的下一代视频编解码器。

这些时间性描述应理解为课程录制时的生态背景，而不是永久不变的浏览器支持结论。

## 视频质量的三个基本参数

### 帧率

帧率表示每秒发送、编码和解码多少帧，单位是帧每秒（fps）。帧率越高，运动通常越流畅，对动态内容尤其重要。

### 分辨率

分辨率决定一帧图像包含多少像素。课程涉及 QVGA、VGA、HD、4K 等等级。更高分辨率可以在单帧中保留更多细节，但也增加计算、内存和码率压力。

### 比特率

比特率通常以 kbps 表示，是编码器输出并通过网络发送的数据速率。其上限可能来自网络，也可能来自设备、CPU 等因素。系统一般会先确定目标码率，再调整分辨率和帧率。

三者的核心关系是：**在固定码率下，提高帧率或分辨率，都需要在其他地方付出代价。** 提高帧率可能需要降低分辨率或接受质量下降；提高分辨率也可能需要降低帧率。工程上是在“更流畅的运动”和“单帧更多细节”之间移动平衡点。

理想目标当然可能是高分辨率和高帧率兼得，例如 **1080p60** 或写作 **1080p@60 fps**：左侧表示 1080p 分辨率，右侧表示每秒 60 帧。

## 像素数量为何使视频处理如此困难

1080p 的宽度为 1,920 像素，高度为 1,080 像素，每帧约有 200 万个像素。每个像素是画面中的一个点，课程用每像素 8～32 位、即约 1～4 字节来说明其数据表示范围。

当帧率为 60 fps 时：

- 每帧约 200 万像素；
- 每秒约 **1.244 亿像素**；
- 每个像素又可能包含 1～4 字节数据。

相比之下，VGA 为 640×480，30 fps 时每秒约 **920 万像素**。从 VGA30 切换到 1080p60，设备每秒需要处理的像素点数量会发生数量级变化。

这些原始数据还要在 CPU、GPU、I/O 和内存之间移动，占用设备总线与缓存。因此，视频压缩不仅是网络码率问题，也是内存带宽和计算架构问题；编码与解码都很困难。

### 课程涉及的常见分辨率

| 名称 | 分辨率 | 含义或定位 |
| --- | --- | --- |
| QVGA | 320×240 | Quarter VGA，即 VGA 的四分之一规格 |
| VGA | 640×480 | 课程列举的基础分辨率 |
| 720p | 1280×720 | 高清，常称 HD Ready |
| 1080p | 1920×1080 | 全高清，课程示例中的主要高分辨率 |

此外还存在接近这些规格的变体，以及 4K、8K、16K 等更高分辨率，但课程指出，多数 WebRTC 应用仍主要集中在 1080p 及以下。

## 摄像头与显示器能力并不总是匹配

课程对当时设备的观察是：普通摄像头可从 VGA、720p 到 1080p 或更高不等，智能手机摄像头通常达到 1080p 及以上；有些设备计算能力有限，却配备了很好的摄像头。

显示端也存在压力。许多手机屏幕达到或超过 1080p，笔记本屏幕可能接近或达到 4K。若编码内容是摄像头画面，可以选择适合网络和设备的采集分辨率；若编码内容是屏幕共享，高分辨率文字和细节则会直接带来更大的编码压力。

因此，不能只根据摄像头标称像素或显示器分辨率决定发送参数，还要考虑设备的实际编码能力和目标观看体验。

## 从单张图像压缩到帧间压缩

视频有损压缩可以先类比 JPEG 图像压缩：舍弃不易察觉的信息，再压缩剩余数据，使质量下降尽可能不明显。最朴素的做法，是把视频中每一帧都作为独立图片压缩并依次发送。

**MJPEG（Motion JPEG）** 就采用连续发送 JPEG 图像的思路。但现代视频编码通常不会把每帧都当作完全无关的图像，因为相邻帧往往高度相关：

- 静态演示画面可能连续几秒没有变化，不必反复发送完整图像；
- 逐句出现文字的演示中，只有部分区域改变；
- 画面淡入淡出等效果会让许多区域只发生较小变化。

编码器可以标记“没有变化”，也可以只编码帧间差异。视频压缩由“压缩一张张图片”进一步发展为“压缩图片之间的冗余”。

## 编码器管线的核心步骤

实际编码器比下面的概念模型复杂得多，但其主要思路可以分成六步。

### 1. 把帧划分为块

编码器把一帧划分为宏块或更一般的块，块尺寸可以是 4×4、8×8、16×16、8×16 等。这样就把“压缩整帧”的大问题拆成许多可以分别处理的小问题。

### 2. 进行运动估计

编码器检查当前块是否在近期帧中出现过，以及它的位置发生了什么变化。例如，一辆车从右向左移动时，与车辆相关的块也随帧移动。运动估计用运动矢量描述块从先前位置到当前位置的变化。

### 3. 计算帧间差异

得到运动矢量后，编码器比较旧块与当前块，计算两者之间的差异，也就是残差。相比重新描述整块画面，描述运动与残差通常更节省数据。

### 4. 进行 DCT 变换

离散余弦变换（Discrete Cosine Transform，DCT）把像素域数据转换为系数表示。课程用像素数值矩阵和变换后的系数矩阵说明：DCT 能重新组织数据能量，使结果更适合压缩，逆变换则用于还原近似的数据表示。

变换后的矩阵往往包含许多零或易于进一步压缩的值，这为后续处理创造条件。

### 5. 量化

编码器选择一个量化器，将 DCT 系数除以相应数值后再压缩。**量化是这一过程中真正造成信息损失的重要步骤。** 解码端按量化信息进行逆向计算时，只能得到原始系数的近似值，而不能无损恢复所有细节。

选择多强的量化，是编码器内部策略的一部分：量化越强，通常越容易降低码率，但质量损失也越明显。

### 6. 再进行无损压缩

量化后的结果还会继续经过类似 ZIP 思路的无损压缩，以进一步减少码流中的冗余。课程没有指定具体熵编码算法，因此不能把这里的“ZIP”理解为实际把视频码流打成 ZIP 文件。

## I 帧、P 帧与 B 帧

视频编码利用不同类型的帧组织参考关系：

- **I 帧（Intra Frame，帧内编码帧）**：可以把它类比为一张独立 JPEG 图像。解码该帧所需的信息都包含在自身中，不依赖其他帧，因此也是关键帧的一种典型形式。
- **P 帧（Predicted Frame，预测帧）**：依赖先前的参考帧，通过已有画面和当前差异来还原。
- **B 帧（Bi-directional Predicted Frame，双向预测帧）**：可以依赖周围多个帧，包括来自后续帧的信息。

B 帧适合离线视频编码。编码一部已完整存在的电影时，编码器已经“知道未来”，可以利用后续画面取得更好的压缩效果。实时通信则没有这样的奢侈：等待未来帧会增加延迟，接收端也不能立即得到所需参考。

这也是为什么离线流媒体的编码策略不能直接照搬到实时会议。

## 实时会议与离线流媒体的编码差异

| 设计点 | 实时会议 | 离线流媒体 |
| --- | --- | --- |
| B 帧 | 通常避免使用，因为等待未来参考会增加延迟 | 可以利用未来帧提高压缩效率 |
| 网络打包 | 希望采用便于拆分、打包并适配 UDP 传输的小块组织方式 | 更侧重文件或分片存储与连续播放 |
| I 帧数量 | 倾向减少，因为 I 帧较大、消耗带宽 | 较多 I 帧有助于拖动进度条、前后跳转和随机访问 |
| 编码遍数 | 通常采用单遍编码，避免重复处理大量数据 | 可以投入更多离线路径和处理时间 |

单遍编码强调数据只经过一次主要编码处理。高码率、高分辨率和高帧率会显著增加数据量，如果重复读取和处理，会给 CPU 缓存、总线和 I/O 带来更大压力。因此，课程指出，大多数实时编码器会采用单遍方式。

这里的目标不是宣称实时视频完全不能重传，而是说明任何恢复手段都必须受延迟预算约束。

## 不能只用压缩率评价视频编解码器

课程比较 H.261、H.263、H.264 和 H.265 时指出：若在相同质量下比较所需码率，H.265 最优；但若比较达到这一结果所需的复杂度、CPU 和能耗，H.265 也是这些方案中最高的。

因此，“H.265 压缩最好”不等于“所有系统都应选 H.265”。同样，也不能只因为 AV1 压缩效率高就直接决定采用它。必须先了解实现复杂度、设备支持、延迟和实际部署限制。

## 编解码器代际升级带来的两种收益

课程把 WebRTC 视频编解码器大致分为三代：

1. 第一代的 VP8 和 H.264，是 WebRTC 初期长期使用的组合，课程将这一阶段概括到约 2019 年；
2. 随后 VP9 和 HEVC 逐渐进入更多实现；
3. AV1 被课程作为开放媒体联盟推动的下一代方案单独讨论。

从 VP8 升级到 VP9 时，压缩效率的提升可以有两种用法：

- **保持相近质量，降低码率**：节省网络资源；
- **保持原有码率，提高质量**：在网络预算不变的情况下改善画面。

代际升级并不自动规定系统该获得哪一种收益。产品需要根据网络瓶颈或质量目标选择配置。

## 小结

视频编码在单帧有损压缩之上，通过分块、运动估计、残差计算、DCT、量化和后续无损压缩利用帧间冗余。I 帧可以独立解码，P 帧依赖先前参考，B 帧还可利用未来参考；后者更有利于离线压缩，却不适合强调即时性的会议场景。

分辨率、帧率和码率共同决定质量与资源消耗。1080p60 与 VGA30 的每秒像素处理量相差巨大，因此选择编解码器时必须同时考虑 CPU、内存、总线、延迟和网络。新标准的压缩优势可以转化为更低码率或更高质量，但最终价值仍取决于实现复杂度和部署条件。
