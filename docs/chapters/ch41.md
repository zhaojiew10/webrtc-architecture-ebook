# 第 41 章 媒体处理中的人工智能

人工智能可以用于实时音频和视频处理，但机器学习算法本身并不属于 WebRTC 的范围。WebRTC 需要解决的问题，是如何让应用程序在安全、性能可接受的位置接触媒体数据，并把训练好的模型用于实时推理。本章从媒体管道的解耦开始，比较客户端与服务器端推理，再讨论噪声抑制、丢包隐藏、背景处理等典型应用。

## 媒体管道的解耦

大约在 2019—2020 年，WebRTC 开始逐步解耦原本相对固定的处理管道。这项演进的一部分目的，正是让机器学习能够嵌入媒体处理过程。WebAssembly（Wasm）为在浏览器中运行高性能处理代码提供了重要条件；同一时期还出现了 WebCodecs、WebTransport 和 AV1 等相关技术，但本章重点关注 WebAssembly 与媒体管道的结合。

传统的发送与接收过程可以概括为：

1. 摄像头和麦克风生成媒体。
2. 应用通过 `getUserMedia` 捕获媒体。
3. 媒体进入对等连接中的编码器，编码数据随后被发送到网络。
4. 对端接收并解码媒体，最后交给显示器或扬声器播放。

解耦就是在这些环节之间开放新的应用处理入口。

### Insertable Streams：处理编码数据

Insertable Streams 将“编码后发送”和“接收后解码”的固定衔接打开。应用可以通过回调取得待发送的编码帧或已接收的编码帧，再按需要处理它们。

这一入口位于**编码数据平面**，主要用途是进一步加密，以实现端到端加密等隐私保护目标。它面对的不是可直接进行图像或声音理解的原始媒体，因此并不是本章所讨论的大多数媒体机器学习算法的理想入口。

### Breakout Box：处理原始媒体帧

Breakout Box 可理解为面向媒体轨道的可插入处理机制。它把入口放在捕获与编码之间，也可以放在解码与播放之间。应用因而能够在编码前修改捕获的原始数据，或在解码后、播放前修改接收数据。

这一位置适合媒体操控，例如更换发送前的视频背景、调整光线，或改变接收后的媒体表现。它与 Insertable Streams 的区别可以归纳为：

| 机制 | 应用接触的数据 | 主要目标 |
| --- | --- | --- |
| Insertable Streams | 编码后的数据 | 端到端加密等编码层处理 |
| Breakout Box | 编码前或解码后的原始媒体 | 修改发送或接收的媒体内容 |

WebRTC 解耦还包括用 WebTransport 增强或替代发送、接收环节，以及用 WebCodecs 增强或替代编码器、解码器等方向，本章不展开这些机制。

## WebAssembly 能承载哪些实时处理能力

课程列举的实时通信用途包括：

- **视频**：人脸检测、手势检测、自动变焦、智能取景、背景替换、背景模糊和光线校正等。
- **音频**：噪声抑制、噪声消除和丢包隐藏等。
- **传输**：借助 WebAssembly 将网络协议栈移植到浏览器中运行。

传输协议栈的移植本身不是机器学习；音频和视频类别中的许多能力则通常会使用机器学习算法。不能因为这些功能通过 WebRTC 应用呈现，就把它们误认为 WebRTC 内置算法。

## 从离线训练到实时推理

理解部署位置前，需要区分训练与推理。

训练阶段使用训练数据，由算法寻找数据中的趋势或关联并建立模型，之后还可以继续优化模型。这个过程离线完成。模型形成后，应用对新输入运行推理函数，得到去除背景、抑制噪声、物体分类或取景等结果。实时通信中需要反复执行的是推理部分。

推理可以部署在三个位置。

### 现有媒体服务器

群组通话或一对一录制等场景本来就会让媒体经过媒体服务器，因此可以在同一路径上运行推理代码，避免另建一条媒体通路。不过，大多数推理需要直接处理音频或视频，服务器通常必须先解码媒体。解码带来的成本，以及是否希望服务器获得原始媒体，都需要单独评估。

### 云端机器学习服务

应用也可以把媒体、快照或其他数据发送到云机器学习接口，由 Google、Microsoft、Amazon 等平台的此类服务执行推理。课程提到的许多概念验证采用了这一方向。

这里要注意，送交推理通常与把媒体发送给其他用户或媒体服务器**并行**发生。它不是把整条实时媒体路径简单搬进云端，而是额外建立一条用于分析的数据路径。

### 用户设备

用户设备本来就能访问自己生成的媒体，可以在媒体发往另一个客户端或媒体服务器之前直接推理。这省去了用于推理的网络往返，也不必把原始媒体交给服务器。

## 客户端与服务器端的取舍

### 速度与结果时效性

客户端推理的等待主要来自算法本身和需要处理的数据量，可视为接近即时。服务器端则必须把客户端到服务器的网络时间加到推理时间上。

如果任务与当前画面紧密相关，例如背景替换或判断用户在画面中的位置，结果晚到 100 毫秒甚至更久，就可能无法与已经变化的图像准确对应。因而，总时延不只是性能指标，也会影响结果是否仍然有效。

### 基础设施成本与设备负担

客户端方案通常不增加服务提供方的推理基础设施成本，计算由用户设备承担。服务器端方案在大规模运行时，需要承担带宽、媒体解码 CPU 和推理 CPU 等成本。

两种方案实际上是在不同主体之间转移成本：把推理放到服务器，可以减轻客户端 CPU 压力，却增加服务端开销；把推理放到客户端，可以减少服务端基础设施投入，却可能显著提高终端 CPU 使用率。大型群组通话本来就可能使客户端 CPU 紧张，这一点尤其需要纳入设计。

### 模型大小

服务器端可以利用云端存储和计算资源，模型大小所受限对较少。客户端受到设备内存、存储和应用分发方式限制；在浏览器中，模型还可能需要作为应用的一部分下载。因此，客户端模型必须考虑体积，不能为了普通的实时音频任务而无视数兆乃至更大的分发和运行代价。

### 隐私

客户端处理时，除客户端上运行的代码外，其他主体不必获得原始媒体，隐私目标相对容易实现。服务器端处理至少意味着服务器能够访问媒体，服务方需要解释这样做的必要性。若业务同时强调端到端加密，还必须说明服务器推理与这一目标如何协调。

### 知识产权保护

如果企业在算法开发或模型训练上投入较多，把代码放到浏览器客户端会增加知识产权保护难度，他人可能取得代码并用于自己的应用。服务器端实现不向外部用户暴露同样的代码和模型资产，更容易控制访问。

这些维度没有统一的优胜方案。实时性、客户端资源、服务端成本、隐私和知识产权需要一起权衡。

## 音频处理

音频机器学习可以与 WebRTC 结合，用于噪声抑制、噪声消除、丢包隐藏和情感分析，也可以探索替代回声消除器或音频增益控制等模块。课程重点讨论噪声抑制，并补充丢包隐藏的思路。

### 噪声抑制的四个运行位置

| 运行位置 | 实现特点 | 优势 | 主要挑战 |
| --- | --- | --- | --- |
| 设备驱动／操作系统层 | 独立于具体通信应用 | 应用无需自行处理 | 需要单独安装和管理，常涉及另一家供应商，增加用户使用阻力 |
| 原生应用 | 在本地设备直接实现 | 最容易实现和控制 | 能力局限于该原生应用 |
| 浏览器 | 通过 WebAssembly 在网页中运行 | 直接服务于 Web 应用 | 能力局限于网页环境 |
| 云端 | 解码音频、抑制噪声后重新编码 | 可统一不同设备和来源的体验，包括不具备本地能力或来自 PSTN 的终端 | 增加时延，运行成本高 |

云端之所以需要解码，是因为噪声抑制要处理实际音频；之所以还要重新编码，是因为后续流程需要获得已经去除噪声的媒体流。

课程按录制时的情况列举了若干实现示例：设备驱动层面有 Krisp 和 NVIDIA；原生应用包括 Teams、Amazon Chime，Dolby 也被列为相关实现者；Krisp 曾提供原生 SDK，后来转向独立应用和设备驱动层。网页侧同样可以实现，课程提到 Dolby 的相关方案。云端示例包括 Google Meet 与 SignalWire，前者把处理放在 SFU 路径中，后者把它放在 MCU 中。这些例子用于说明部署位置，而不是对产品现状作更新。

如果希望自行研究，课程建议从开源的 RNNoise 入手。它用于判断音频信号中的噪声与语音，可在此基础上继续构建适合自身需求的噪声抑制方案。

### 用预测实现丢包隐藏

课程以 Google Duo 中的 WaveNetEQ 为例说明丢包隐藏。其思路是分析已经收到的音频，根据过去的声音推断后续音频，并随着真实后续数据到达而实时微调模型。发生丢包时，再用预测结果填补缺失部分。

这一算法被放在 Google Duo 中，而不是作为 WebRTC 的现成能力提供。课程同时指出，在 WebRTC 中实现类似方案需要迂回处理，因为应用当时无法以获得此类算法所需的深度直接访问丢包信息。

## 视频处理

视频方向可结合机器学习的算法很多，课程特别提到自动变焦、背景替换和光线校正，并进一步分析背景模糊与背景替换。

### 精度与 CPU 的平衡

视频算法需要同时关注 CPU 消耗和输出质量。这里的质量包括识别与分割的准确性。更高的准确性通常需要投入更多 CPU，但 CPU 被一项处理大量占用后，又可能牺牲通话中的其他质量环节，因此必须取得平衡。

从基础能力到复杂呈现，可以形成一条渐进路径：

1. **对象分类与人物轮廓识别**：找到人物，为后续处理提供基础。
2. **自动变焦**：根据人物位置进行取景和放大。
3. **背景模糊**：对边界误差相对宽容，少量漏检不一定明显影响效果。
4. **背景替换**：需要更准确地区分人物和背景，也可以把背景换成视频等内容。
5. **人物抠像与演示模式**：把真实用户叠加在幻灯片、演示文稿等动态背景上。

### 独立应用与浏览器方案

NVIDIA Broadcast、XSplit、ChromaCam、Snap Camera 和 Mmhmm 等独立应用或设备驱动方案，可以在机器上生成虚拟摄像头，再供不同应用使用。这种方式接入较快，但应用开发者并没有真正完成媒体处理，而是把安装、配置和运行责任交给用户。

浏览器侧的课程示例包括 MediaPipe 和 BodyPix，其中 MediaPipe 在录制时更常见。课程以 Google Meet 的方案为例，说明浏览器内可以组合机器学习推理、细化和渲染。细化环节还能调整 CPU 使用量，使其适应设备可用资源：可用 CPU 较多时提高质量，较少时降低最终结果质量。

### 为什么需要更高效的处理路径

早期常见做法是把 `getUserMedia` 捕获的数据交给 HTML5 Canvas，再结合 WebGL 和 WebAssembly 处理，最后送回对等连接的编码器。捕获、Canvas、WebGL 与对等连接之间产生了过多内存复制，导致较高的 CPU 和 I/O 使用率，因此效果并不理想。

改用 Breakout Box 后，捕获数据在媒体流内部进入处理环节，处理代码可以使用支持 SIMD 的 WebAssembly 进行向量计算，再把数据交给对等连接。对后续编码发送过程而言，媒体仍按正常路径继续流动，但中间避免了旧方案的许多复制开销。这条更高效的路径使背景替换等实时处理更容易达到可用性能。

## 小结

WebRTC 的媒体管道解耦为人工智能提供了接入点：Insertable Streams 主要处理编码数据，Breakout Box 则让应用处理编码前或解码后的原始媒体。实时推理可放在客户端、媒体服务器或云机器学习服务中，选择时必须同时考虑时延、成本、模型大小、CPU、隐私和知识产权。

音频和视频算法并不随 WebRTC 自动获得。实际工作通常是从合适的开源实现出发，使其适配业务，再持续训练、微调和优化。媒体 AI 的关键不仅是找到一个模型，更是把模型放进一条时延和资源消耗都可接受的实时媒体路径。
