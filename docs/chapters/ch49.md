# 第 49 章 测试与监控

WebRTC 项目在本地演示成功，并不代表它能在真实网络中工作。常见问题包括未正确配置 TURN，上线后才发现部分用户无法连接；团队声称支持数十人的群组通话，却从未测试过接近该规模的场景。许多实现缺乏系统化测试，已有测试又主要依赖手工执行。要降低这类风险，需要把浏览器、媒体输入、网络条件、多用户流程、结果判断和运行监控作为一个整体来设计。

## 以浏览器自动化为测试基础

WebRTC 持续变化，测试对象也远不止一通简单的语音呼叫。Selenium、Puppeteer 等工具能够自动控制浏览器，因此可以把浏览器行为、应用逻辑和 WebRTC 通话纳入同一套自动化测试。

浏览器版本本身也是测试变量。课程以当时的发布节奏为例：Chrome 和 Firefox 大约每四至八周发布一个版本，平均间隔约 40～50 天；Safari 大约每六个月发布新版本；Edge 基于 Chromium，其节奏在一定程度上可能跟随 Chrome。具体间隔会变化，但架构上的结论不变：只测试当前用户正在使用的版本，无法提前发现下一次升级带来的故障。

以 Chrome 的发布渠道为例：

- **Stable（稳定版）**：客户当前主要使用的版本。
- **Beta**：预计成为下一个稳定版的版本，除非出现影响严重的缺陷，否则不会再有大的改动。
- **Dev（开发版）**：可更早发现破坏性问题，并反馈、等待修复。
- **Canary**：每日构建版本，更新频繁，也更容易出现问题。

除了稳定版，还应有针对性地测试 Beta，必要时测试 Dev，以便在服务真正受影响前识别即将发生的变化。这对 WebRTC 尤其重要，因为其中一些变化会废弃既有行为或接口。

## 为无头浏览器准备虚拟媒体源

真实 WebRTC 会话需要摄像头和麦克风，无头浏览器却通常没有这些物理输入。Chrome 的 WebRTC 实现支持虚拟媒体设备，可用文件代替真实采集：

- 视频使用未压缩的 Y4M 文件；
- 音频使用 WAV 文件。

准备素材时，可以把 MP4 等来源转换为 Y4M 和 WAV，但 Y4M 必须满足特定格式要求，不能默认任意 FFmpeg 转换结果都能直接使用。自动化的目标不只是让浏览器“拿到一段视频”，还要保证输入格式确实可被测试流程稳定消费。

## 主动构造网络问题与地理差异

真实网络会显著改变应用行为，使用媒体服务器时尤其如此。测试需要主动控制网络，而不是只在低延迟、无丢包的开发环境中运行。

### 网络损伤与防火墙

至少应覆盖以下两组情况：

1. **网络损伤**：设置比特率上限，向链路注入丢包、抖动和延迟，观察应用及媒体服务器的响应。
2. **防火墙配置**：明确阻止 UDP，验证 TURN over TCP 是否真的能够按预期工作，确认当前配置可以服务处于受限网络中的客户。

课程提到可使用 iptables，netfilter.org 提供了相关用法示例；Mac 和 Linux 上也有其他可帮助构造这些条件的开源项目。关键不在于固定使用某个工具，而在于把异常网络变成可重复的测试输入。

### 测试位置

WebRTC 对地理位置敏感，应从全球不同地点运行测试，评估位置变化对服务的影响。多地点虚拟化本身比较复杂，还要同时关注环境的稳定性和吞吐能力。总体原则是尽可能控制浏览器及其运行环境，否则测试结果中的外部变量会掩盖应用问题。

## 在浏览器之外编排多用户时序

WebRTC 测试通常不是单页面操作，而是多个用户共同完成的过程。例如：

- 主叫方与被叫方建立一对一呼叫；
- 用户连接联络中心坐席或专家；
- 两名或更多参与者进入同一房间，并可能具有不同角色；
- 一群人参加会议，或众多观众收听、观看某位主讲人的网络研讨会。

每种场景的实际流程都不同，而流程控制发生在单个浏览器之外。测试系统可能需要先让一个用户在一个浏览器中加入，再让另一个用户稍后通过临时创建的 URL 加入。只有把这种跨浏览器同步和时序编排自动化，才能验证真实的会话逻辑。

## 可视化结果，并预先定义成功标准

### 从原始转储中发现模式

`WebRTC internals` 转储包含大量数字与文本，直接阅读很难定位问题。将码率、包数量、丢包等指标绘制成曲线后，一些异常才会显现。

课程用不同 Chrome 版本中的 VP8 与 VP9 视频指标作比较：其中一条曲线明显更抖动、更不稳定，这种差异来自 WebRTC 实现本身，而不一定是外部网络造成。丢包数据也有类似情况：

- 丢包数值异常高，可能并非真实网络丢包，而是未初始化变量导致的缺陷；
- 每五秒报告的丢包数量完全相同，数据过于整齐，反而可能说明统计或报告逻辑存在错误。

因此，可视化不仅用于展示结果，也用于区分实现缺陷、网络问题和其他异常。课程提到的工具包括 TestRTC 的 AnalyzeRTC，以及 Philipp Hancke 的 Dump Importer；后者可上传 `WebRTC internals` 文件，并将转储内容可视化。

### 先设定期望，再判断通过或失败

测试运行结束并不等于测试有了结论。需要事先回答：

- 建立会话允许多长时间，超时是否判为失败？
- 会话中应出现多少条媒体通道，如何确认应连接的都已连接、也没有多余通道？
- 比特率限制是否生效，应用行为是否符合限制下的预期？

不能只看媒体服务器 CPU 尚在运行，就把测试判为通过。判断依据必须包含真实客户端的实现状态和测试期间的表现。

同时应尽可能收集完整证据，包括 `WebRTC internals` 转储、`getStats()` 调用结果、浏览器控制台日志、媒体录制、机器性能数据和网络追踪。不同故障需要不同证据，事先收集比故障发生后再猜测更有效。越早建立这些能力，后续调试和故障排除的成本越低。

## 测试与监控的五类职能

完整的质量保障不只是“自动化跑一通呼叫”，而是由五类相互补充的职能构成。

### 1. 功能测试

功能测试模拟服务的不同使用场景，覆盖应用边界情况和业务逻辑，并逐一走完整流程。还要在不同设备与浏览器上执行，确认功能并非只在单一开发环境中成立。

### 2. 非功能测试

非功能测试包括压力测试和规模测试，用于评估应用与媒体服务器容量，例如：

- 单台服务器可承载多少呼叫或用户；
- 可以通过多大带宽；
- 不同网络条件和地理位置下表现如何；
- 不稳定版本或其他浏览器会引发什么问题。

这些测试把“宣称支持的规模”转换为经过验证的容量边界。

### 3. 主动监控

主动监控要回答的是：“服务现在是否真正可用？” Datadog、Nagios 等工具中的机器性能指标只能说明 CPU 等资源的运行状态，不能代表端到端体验。有效检查需要模拟用户登录、加入通话，并确认其确实收到了媒体。

除了可用性，还要观察媒体质量是否稳定、可预测：它会随时间或一天中的特定时段下降，还是毫无规律地波动？这些问题无法仅靠服务器在线状态回答。

### 4. 被动监控

被动监控关注真实用户的实际体验，例如：

- 有多少用户能够成功连接；
- 用户分别停留多长时间；
- 服务中的平均比特率是多少；
- 有多大比例的呼叫经过 TURN 服务器。

主动监控由系统发起检查，被动监控则从真实会话中理解服务质量，两者不能互相替代。

### 5. 网络故障排查

当客户反馈无法使用时，还需要一套定位其网络问题的流程。应了解用户是否位于防火墙之后、是否配置了 VPN、是否使用 Wi-Fi，并评估支持团队能多快、多有效地协助客户。此类问题终将出现，故障排查能力本身就是服务体系的一部分。

## 课程提到的行业工具

以下描述反映课程介绍时的工具定位，其中也保留了讲师基于使用经验作出的判断。

| 工具 | 课程介绍的用途与特点 |
| --- | --- |
| TestRTC | 覆盖功能测试、非功能测试、主动与被动监控以及网络故障排查。讲师同时说明自己是 TestRTC 的联合创始人兼 CEO，因此评价可能存在偏向。 |
| Loadero | 提供覆盖 WebRTC 的功能与非功能测试，整体可靠且扩展性较好；讲师认为其不足在于，面对大型压力测试时，WebRTC 自身性能指标的收集与呈现不够便于查看。 |
| Kite | 开源工具，浏览器厂商用其开展 WebRTC 浏览器实现的互操作性和功能测试；也可部署在自己的 Selenium Grid 中，并有公司可提供定制、配置或安装服务。 |
| callstats.io | 提供被动监控，课程介绍时已成为 8×8 的一部分。 |
| RTC Canary | 课程介绍时的新产品，提供与 callstats.io 相近的工具集，主要面向初创企业。 |

## 小结

WebRTC 测试必须覆盖浏览器版本、虚拟媒体源、异常网络、地理位置和多用户同步，并用可视化与完整日志支持诊断。每次测试都要有明确的客户端侧成功标准，不能以服务器进程或 CPU 正常替代端到端判断。

上线前后还需要功能测试、非功能测试、主动监控、被动监控和网络故障排查共同配合。忽视这些工作并不会消除问题，只会把问题推迟到成本更高的真实用户环境中。
