# 第 26 章 语音编解码器基础

编解码器决定了原始媒体如何被压缩、传输和还原。对 WebRTC 而言，压缩率并不是唯一目标：编码与解码还必须足够快，并能在丢包、设备算力差异和专利许可等现实约束下工作。本章先建立通用的编解码器概念，再讨论语音编解码器的码率、采样率、声道数和频率带宽。

## 有损压缩与实时媒体链路

按解码结果是否完整保留原始信息，可以把编解码器分为两类：

- **无损编解码器**：解压后得到与压缩前完全相同的数据，不丢失任何信息。
- **有损编解码器**：主动舍弃人耳或人眼不易感知、难以区分的信息，再对剩余数据大幅压缩。音频和视频实时传输主要关注这一类，因为原始媒体数据量很大，而网络带宽有限。

有损压缩的目标不是无条件追求最高压缩率。在实时通信中，最近 20～30 毫秒产生的媒体数据需要尽快完成编码、传输和解码。如果为了获得更优压缩结果而让结果晚一两秒才可用，即使压缩效率很好，也不适合实时会话。

一条典型媒体链路如下：

1. 摄像头或麦克风产生原始数据。
2. 编码器压缩数据。
3. 编码后的码流通过网络发送。
4. 接收端把网络数据交给解码器。
5. 解码结果通过显示器或扬声器呈现给用户。

编码器与解码器共同构成通常所说的“编解码器”（codec）。

## 选择编解码器的通用维度

不同编解码器不能只按名称或压缩率比较，还要综合考察以下特性。

| 维度 | 需要回答的问题 | 对实时通信的意义 |
| --- | --- | --- |
| 复杂度 | 编码和解码分别需要多少 CPU、内存与能耗？ | 复杂度越高，设备负担通常越大；移动设备尤其需要关注能耗。 |
| 延迟 | 编码器和解码器完成工作分别需要多久？ | 延迟过高时，即使质量再好，也可能不适合实时会话。 |
| 抗丢包能力 | 收不到全部已发送数据时，输出质量如何？ | 实时网络传输必然可能遇到丢包，编码器自身的韧性很重要。 |
| 知识产权与许可 | 是否开源？是否涉及专利和版税？许可覆盖编码器还是也包括解码器？ | 影响产品成本、分发方式和可用平台；免版税方案在 WebRTC 中很受重视。 |
| 普及程度与生态 | 是否有硬件编解码、熟悉它的开发者，以及支持它的录制器和媒体服务器？ | 生态越成熟，集成和运维风险通常越低。 |
| 软硬件支持 | 是否存在多个实现？目标芯片和软件平台是否有支持？ | 单一实现或缺少硬件支持会限制部署选择。 |

这些指标相互牵制。例如，高复杂度可能换来更好的压缩效果，却同时增加延迟、CPU 占用和能耗。

## 解码器定义标准，编码器决定实现质量

编解码器规范的核心是：**给定一段码流，解码器应当怎样解释并还原它。** 规范定义码流结构和解码规则，也因此限定了编码器可以使用的工具集合，但通常不规定编码器必须采用哪一种具体实现策略。

由此产生两个重要结论：

- 遵循同一规范的解码器通常具有相似行为，否则无法互通。
- 不同编码器实现可以在复杂度、压缩效率和输出质量上差异很大。开发者需要决定何时使用哪些编码工具，以及如何分配计算资源。

离线流媒体可以投入大量时间进行高复杂度编码。例如，课程以 Netflix 的节目流为例，说明非实时场景可以为了压缩率和质量进行耗时计算。视频通话则不能照搬这种策略，因为编码器必须持续、低延迟地处理新画面或声音。因此，“同一种编解码器”并不意味着所有编码器的实际效果相同。

## WebRTC 中的编解码器版图

课程以 WebRTC 的必须实现（Mandatory To Implement，MTI）编解码器作为互通基线，并同时介绍了其他可选方案。

### 语音与电话事件

- **G.711**：用于兼容传统电话网络和老旧系统，是窄带语音方案。
- **Opus**：灵活且应用广泛的音频编解码器，支持窄带到更高质量的频带，既面向语音，也面向音乐。
- **DTMF**：用于表达电话按键等电话事件。它在协商和处理中会被当作一种“编解码器”列出，但严格来说并不是普通的音频压缩编解码器，主要服务于传统电话系统互通。

### 视频

- **VP8**：Google 的开源、免版税视频编解码器。
- **H.264**：开放标准化但涉及许可和版税的视频编解码器，不能简单等同于“完全专有、不开放”。
- **VP9**：Google 的另一款开源视频编解码器。
- **HEVC（H.265）**：H.264 的后续标准。课程录制时，其在 WebRTC 中的支持仍较有限，主要提到 Apple 和 Intel 相关生态。
- **AV1**：开放媒体联盟（Alliance for Open Media）推动的下一代视频编解码器。

上述可用性描述是课程当时的生态快照，不应把“即将普及”之类的时间判断当作永久结论。课程还特别提醒，尽管 VP8 和 H.264 属于 MTI 基线，H.264 在当时并非所有 Android 设备上都能实际使用，许可和平台集成都会造成差异。

## 语音、音频与声音

“语音”“音频”和“声音”在口语中经常混用，但语音只是音频的一个子集。音频涵盖人能听到的各种声音；语音编解码器则主要围绕人类讲话建立压缩模型，首要目标是让听者听清并理解说话内容。

这种目标差异很重要。一个适合对话的编码模型未必能很好地保留音乐细节，因此不能只用语音通话体验推断其音乐质量。Opus 的灵活性正体现在它覆盖了更广泛的语音和音乐需求。

## 语音编解码器的三个基本参数

### 比特率：每秒投入多少比特

比特率通常以千比特每秒（kbps）表示，是编码器压缩输出所趋向的目标。每种编解码器都有自己的适用码率范围：

- G.711 在网络上的典型码率是固定的 **64 kbps**。
- Opus 等动态码率方案可根据质量目标调整输出，不必固定在一个数值上。

一般来说，提高码率可以为质量提供更多空间，但也会增加网络负担。工程目标是尽量少发送比特，同时保持所需质量，而不是单纯追求最低或最高码率。

### 采样率：每秒测量多少次

采样率通常以千赫兹（kHz）表示，表示每秒对模拟声音信号进行多少次采样。可以把模拟输入理解为连续变化的声音曲线，而数字采样是在一系列时间点上测量其音量。

采样点之间的高峰和低谷不会被完整记录，因此数字表示是对原始信号的近似。提高采样率可以增加时间上的采样密度，使表示更接近原始信号，但也会带来三方面成本：

1. 需要存储和处理更多采样点。
2. 压缩这些数据需要更多计算。
3. 支持高采样率的硬件可能更昂贵。

WebRTC 使用 Opus 时的采样率为 **48 kHz**，即每秒采样 48,000 次。课程回顾，WebRTC 初期部分硬件难以直接满足这一要求，只能进行模拟或适配处理；随着硬件发展，这一限制逐渐减轻。

### 声道数：同时编码多少路声音

常见声道形式包括单声道、立体声和 5.1 声道。声道越多，需要处理的样本通常越多。空间音频编解码器还能处理声音来源方向，但这不属于课程所讨论的 WebRTC 编解码器实现范围。

## 码率、采样率与声道数的联动

音频质量可以看作由三条“凳腿”共同支撑：

- **码率**决定每秒可分配的总比特数；
- **采样率**决定每秒产生多少采样点；
- **声道数**决定需要同时表示多少路音频。

如果提高采样率却不提高码率，平均每个样本可分到的比特就会减少。类似地，从单声道改为立体声，在简化估算下可能需要接近两倍的码率；实际编码可以压缩部分声道间冗余，但更多声道仍然意味着更多数据，或者需要在其他位置牺牲质量。

因此，这三个参数不能独立优化。目标应是根据语音或音乐内容、网络条件和设备能力，在总码率约束下取得合适的质量组合。

## 人耳范围与语音频带

课程讨论的人耳听觉范围约为 **20 Hz～20,000 Hz（20 kHz）**。大象等动物可以感知次声，猫、狗和海豚等动物的听觉范围也与人类不同；语音编解码器只围绕人耳可感知范围进行取舍。

在这一范围内，课程按频率带宽区分以下类别：

| 频带类型 | 课程给出的范围或定位 | 典型体验与用途 |
| --- | --- | --- |
| 窄带（Narrowband） | 300～3,400 Hz | 传统电话信号；能听懂讲话，但音色单薄、粗糙。G.711 属于这一类。 |
| 宽带（Wideband） | 50～7,000 Hz | 对话更舒适，能保留更丰富的语音质感。 |
| 超宽带（Superwideband） | 比宽带覆盖更宽 | 更适合音乐等高质量音频。 |
| 全带（Fullband） | 覆盖课程所讨论的人耳范围 | 面向音乐和高保真场景。 |

窄带和宽带主要服务于语音通话。若用它们传输音乐，往往难以保留足够的听感；歌剧等音乐内容更需要超宽带或全带能力。

## 从众多方案回到 WebRTC 的核心选择

语音编解码器在许可方式上差异很大：有些免版税且开源，有些许可免费但不提供源代码，还有些既要求许可费用也不开源。比较时还要同时查看其码率、频带和达到某一质量所需的投资，不能只按“免费”或“高清”分类。

对课程所讨论的 WebRTC 应用，最核心的两个方案是：

- **Opus**：覆盖多种频带、质量层次和码率，是灵活的默认选择。
- **G.711**：窄带、典型码率 64 kbps，主要价值在于传统网络互通。

## 小结

编解码器规范定义码流如何解码，而编码器实现决定实际复杂度和效率。实时通信不仅需要有损压缩带来的低码率，还要求低延迟、抗丢包、合理许可以及成熟的软硬件生态。

语音质量由码率、采样率和声道数共同塑造，并受到目标频带的约束。G.711 提供传统电话互通能力，Opus 则以更宽的频带和码率适应范围成为 WebRTC 的核心音频方案。后续章节将分别展开 Opus、其他语音编解码器以及视频编解码器。
