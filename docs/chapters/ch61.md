# 第 61 章 编写 WebRTC RFP 需求

几乎所有产品都需要明确需求，WebRTC 产品还要额外处理实时语音、视频通信带来的复杂性，不能完全套用普通网站或 Web 应用的需求写法。WebRTC 往往只是整个产品中的一个子模块，可能外包给第三方，也可能交给专门负责实时通信的开发团队。此时，一份具体、可实施的 RFP 需求文档，就是产品目标与工程交付之间的共同依据。

## 为什么要把需求写清楚

### 让外部团队能够直接实施

如果要把全部或部分开发工作外包，仅口头描述“增加视频通话”远远不够。需求必须记录得足够具体、详细，使承接方可以据此设计、估算和实施，而不必反复猜测产品意图。

### 借写作发现产品本身的问题

记录需求也是向自己澄清目标的过程。课程讲师与客户共同编写需求时，常常会发现此前没有注意到的用户界面、操作方式、业务流程和功能问题，尤其包括：

- 今天必须具备什么，未来又需要什么；
- 哪些是强制功能，哪些只是“有了更好”；
- 每项功能大约要付出多少开发成本。

例如，一项非必需功能如果要耗费三到四个月，而整个开发周期只有五到六个月，就可能应当放弃它。需求文档因此不仅描述要做什么，也帮助团队作出范围与成本之间的取舍。

### 建立团队共同语言

实际项目通常不只有一名开发者，还涉及测试人员、产品经理、开发人员和 DevOps 人员。把需求明确写下来，可以减少不同角色对功能、运行方式和验收目标的不同理解，使团队更容易协作。

## 从目录和 TBD 占位开始

课程采用的基本文档结构是：

1. 概述；
2. 架构；
3. 功能性需求；
4. 非功能性需求；
5. 其他问题或未决事项。

写作不必严格从第一页顺序进行到最后一页。可以先建立所有标题，在尚未确定的位置标记 **TBD（待定）**，再逐步填充内容。例如，先写概述，转到功能部分时发现一项设备支持要求，就立即补入非功能部分；暂时无法确定的内容保留 TBD，之后通过搜索这些标记逐项补全。这样可以让文档各部分并行成熟，也降低遗漏重要主题的概率。

## 概述：先说明要建成什么

概述首先用简洁语言说明产品目标，再补充会显著影响架构的关键规模和交互方式。课程以 BlogGeekMe 的网络研讨会服务为例：该服务以视频为基础，最多四位发言者可以加入，并向大量参与者分享会议内容；发言者还能通过聊天消息、投票和提问与参与者互动。

这段概述同时表达了几类重要信息：服务类型、主动发言者数量、受众规模，以及发言者与参与者之间的互动方式。它们为后续架构和详细需求设定了背景，而不是只写一句“建设一个视频会议系统”。

## 架构：定义实体、能力与通信关系

架构部分可以先画出目标系统。使用 Visio、PowerPoint 或白板都可以；课程讲师更偏好白板，因为它通常更快，也便于边画边思考。关键不在绘图工具，而在于把系统中的实体及其关系说清楚。

网络研讨会示例包含四类实体：

- **发言者（speaker）**；
- **观众（viewer）**；
- **网络研讨会（webinar）实体**；
- **存储（storage）系统**。

文档应为每个实体写一到两段，说明它在系统中的含义、能做什么，再明确实体之间需要怎样的通信：

- 发言者向网络研讨会实体发送音频和视频，同时接收其他发言者的媒体，因此媒体是双向的；
- 观众只接收音频和视频；
- 存储系统也接收音频和视频，这意味着平台需要录制能力。

先列实体，再列各实体的功能，最后明确通信方向和媒体类型，可以把“实时通信究竟发生在哪里”落实到架构需求中。

## 功能性需求：用户能做什么

功能性需求描述产品内部的功能，即用户能够执行的操作或达到的目标。以下问题应逐项回答，而不是留给开发者自行假设。

### 会话与媒体形式

- 服务是一对一通话，还是多人、群组通话？
- 需要音频、视频，还是两者都需要？
- 是否存在只使用视频的特殊要求？
- 是否允许用户仅以音频方式加入视频会话？

### 协作与内容共享

- 是否需要屏幕共享？
- 是否需要共同浏览、文件发送或文件共享等协作能力？

### 消息与聊天

- 是否需要消息和聊天？
- 消息只包含文本，还是还要支持图片或其他内容？
- 消息是否必须经过服务器？
- 是否需要把消息保存为网络研讨会的一部分？
- 消息只发生在会话内，还是会话前也可以发生？它是否参与会话的创建过程？

### 授权与身份验证

- 用户拿到 URL 是否就足以加入？
- URL 是否是面向特定用户的个性化地址？
- 加入前是否必须登录？
- 服务是否必须知道加入者的真实身份？

这些问题既影响服务流程，也会影响安全设计和身份验证方式。

### 会话内控制

- 用户能否将自己静音，能否将他人静音？
- 用户能否进行演示，能否把演示权限授予他人？
- 能否改变画面布局、放大画面或执行类似操作？

这些控制直接决定实时通信服务如何被主持人和参与者使用。

### 状态指示与录制提示

- 某人被静音时，是否向其本人显示状态？是否也向同一会话中的其他人显示？
- 会话正在录制时，参与者是否必须知情？
- 录制通知是在开始时播放提示，还是在屏幕上持续显示？
- 是否还需要其他状态指示器？

最后，应明确是否需要录制能力；如果需要，就将其作为独立功能记录，并继续检查是否遗漏了其他重要功能。

### 标明阶段和优先级

无论功能写在功能部分还是非功能部分，都应同时标明：

- 第一阶段或最小可行产品（MVP）立即需要什么；
- 哪些内容留待后续阶段；
- 哪些是强制要求，哪些是可选项。

内部或外部开发者只有了解这些优先级，才能判断各项工作的耗时，并在必要时与产品方协商调整范围。

## 非功能性需求：服务怎样、在哪里运行

课程把与服务具体功能无直接关系、但决定服务如何使用和在哪里使用的要求归入非功能部分。

### 设备与运行环境

需要明确是否支持浏览器，以及是否要求支持所有浏览器。对于不支持 WebRTC 的浏览器，是否还要通过插件或 Flash 提供支持？除浏览器外，是否还需要 PC 应用、移动设备或专门的嵌入式设备？

对于移动端，还应写明支持哪些系统版本，以及 iOS、Android 需要向前兼容到什么范围。不能只写“支持手机”或“支持主流浏览器”而不给出版本边界。

### NAT 穿越

NAT 穿越应单独成节，因为它经常在项目中被忽略。一些项目只使用 Google 的 STUN 服务器，直到通话无法连接时才发现方案不足。

课程建议把以下要求明确写入文档：

- 同时需要 STUN 和 TURN；
- TURN 需要支持 UDP、TCP，并支持 TLS；
- TURN 服务器密码应是临时密码。

尤其是与外部开发者合作时，没有写明的要求很可能不会实现；内部团队若准备简化其中某项，也应当让产品方明确知道，而不是默默省略。

### 可扩展性

可扩展性至少有两个维度：

1. **单个会话的规模**：多人服务中允许多少活跃用户？网络研讨会示例中的主动发言者为四人；观众可能是 10、100、1000，甚至一百万。观众加入时能够接受多大的延迟，也应说明。
2. **并发会话数量**：平台能够同时承载多少场网络研讨会或其他会话？

还可以进一步讨论单机扩展能力，以及采用横向扩展还是纵向扩展。不过，这些指标更难在需求阶段准确给出，通常要等到开发过程中进行容量估算后才能细化，不宜随意填写缺乏依据的数字。

### 安全

安全部分应说明哪些资产和服务器需要保护，并再次明确 TURN 服务器及其临时密码等要求。还要列出哪些服务器允许从互联网连接，以及连接边界在哪里。

即使是云服务，也不意味着所有服务器都应直接暴露在公共网络。课程给出的思路是把媒体服务器尽量放在内部，把应用服务器放在更接近公共网络的位置，构建受保护的网络，并在不同部分之间进行隔离。

### DevOps 与运行维护

DevOps 需求同样容易被遗漏。文档应说明：

- 需要哪些监控能力；
- 收集哪些指标，是否只需要实时指标；
- 指标来自服务器、客户端，还是两者；
- 后台需要展示什么信息；
- IT 或 DevOps 团队需要哪些操作选项，才能在服务运行期间维护它。

## 其他问题与交付约束

最后一节用于集中放置尚未解决、需要反馈的问题，以及与开发和运营方式有关的要求。

开源组件是大公司和初创公司都可能面对的敏感问题。需求方应说明哪些组件或许可方式可以接受、哪些不可接受，并要求承包商和开发者列出最终使用的开源组件。商业产品也应采用类似的清单方式，避免交付后才发现组件选择不符合要求。

技术偏好也应明确。例如，可以指定希望使用 Node.js；其他团队也可能要求 .NET、Java 或自己熟悉的技术栈。偏好若不写下来，就无法假定承接方会主动遵循。

## 小结

一份可执行的 WebRTC RFP 需求，应按“概述—架构—功能—非功能—未决事项”组织，并通过 TBD 占位迭代补全。概述说明目标，架构定义实体和通信关系，功能部分覆盖媒体、协作、消息、身份验证、会话控制、指示和录制，非功能部分则明确设备、NAT 穿越、扩展性、安全与 DevOps。为每项要求标注阶段、优先级和强制程度，再记录组件与技术栈约束，才能让需求真正用于估算、分工和交付。
