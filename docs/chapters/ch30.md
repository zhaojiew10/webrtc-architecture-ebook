# 第 30 章 VP8 与 H.264

VP8 和 H.264 是 WebRTC 必须实现的两种视频编解码器。就课程讨论的实时场景而言，它们在相同码率下可以提供大致可比的质量，CPU 使用量也大体接近；真正的差异更多来自版税、硬件支持、浏览器集成、时间可扩展性以及既有系统。选择哪一种，往往是系统架构决策，而不只是图像质量比较。

## 早期质量对比不能直接指导现在的选择

课程引用了一篇 2010 年的早期文章，其中详细比较 VP8 与 H.264，并认为 H.264 在若干图像区域具有更好的压缩表现。但这份数据早于 WebRTC，也早于 VP8 后续的大量优化。

因此，不能从这篇历史对比直接推导出当前实时实现的固定优劣。课程给出的现实判断是：两者在今天的比较中已相当接近，肉眼未必能看出明确差异。真正需要解释的是，既然质量和 CPU 大致可比，为何选择仍如此重要。

第一层原因是成本：VP8 免版税，而 H.264 涉及许可和版税。但许可并不是唯一因素，硬件加速和媒体服务器能力也可能改变最终决策。

## VP8 与 H.264 的生态差异

| 比较维度 | VP8 | H.264 |
| --- | --- | --- |
| 许可 | 开源、免版税，可自由使用 | 开放标准，但使用涉及 MPEG LA 等许可与版税问题 |
| WebRTC 中的地位 | 长期广泛应用，是课程建议的默认方案 | 课程称自 2016 年起在 WebRTC 中可用；通常在有明确需求时采用 |
| WebRTC 之外的生态 | 可以使用，但并不常见，主要存在于 WebRTC 生态内 | 在 WebRTC 之外也广泛使用，既有部署很多 |
| 硬件支持 | 相对有限，很多设备最终使用软件编码器和解码器 | 多数硬件芯片提供支持，但浏览器或 WebRTC 未必总能调用 |
| 计算开销 | 软件实现较多，可能带来更高 CPU 使用 | 硬件加速可降低设备负担，但可用性和质量需要实测 |
| WebRTC 集成 | 课程认为支持路径更成熟、优化投入更多 | 课程观察到部分实现路径问题更多、优化较少 |
| 时间可扩展性 | 支持较明确 | 课程录制时支持不完整，编码端与解码端能力并不一致 |

这些描述是课程对当时实现的观察，不应被理解为所有浏览器、所有版本都永久如此。尤其是 H.264，芯片“支持”与 WebRTC“能使用”是两个不同层次。

## VP8 为什么常成为 WebRTC 默认方案

VP8 免版税，并在 WebRTC 中得到了广泛应用。课程认为，如果一个实现没有使用 VP8，通常应当能找到具体场景下的理由，而不是因为 VP8 缺乏基本可用性。

在 H.264 于课程所称的 2016 年进入 WebRTC 之前，VP8 已是主要方案。此后，许多新实现仍倾向默认使用 VP8，只有存在既有 H.264 系统、硬件或其他明确需求时才转向 H.264。

课程还把 VP8 的集成优势与 Google 的实际投入联系起来：Google 在 Google Meet 等服务中使用 VP8，因此围绕 VP8 的 WebRTC 集成和优化投入较多。相较之下，H.264 路径在其观察中更容易遇到缺陷或较少优化。这不是“不要使用 H.264”的结论，而是提醒部署者不能只检查协商是否成功，还要验证实际媒体路径。

## H.264 硬件支持为何不等于实际可用

H.264 的一个突出优势是硬件生态。多数硬件芯片支持 H.264，这为编码和解码加速提供了基础。然而，硬件能力需要经过设备驱动、操作系统和浏览器或应用的多层集成，才能被 WebRTC 使用。

课程以某些 Android 设备为例：

1. 设备本身具有 H.264 硬件能力；
2. 厂商加入的驱动没有正确接入 Android 操作系统提供的相关路径；
3. 浏览器中的 WebRTC 因而无法访问这套硬件编解码器。

此时，即使规格表写着“支持 H.264”，也不代表浏览器通话能获得硬件加速。课程还指出，Google 在部分此类设备上没有为 Chrome 补充 H.264 软件编码器，原因之一是这样做会引入版税成本。

服务器和嵌入式设备也不能默认直接复用浏览器方案。自行编译、集成本地 WebRTC 时，需要明确处理 H.264 的代码来源、硬件接入和专利许可问题。

## Cisco OpenH264 与浏览器动态下载机制

Cisco 将其 OpenH264 实现贡献给 WebRTC 生态，与其自身 Webex 产品需求密切相关。Webex 及会议室硬件系统已经广泛使用 H.264；如果 WebRTC 接入后只能使用 VP8，就必须把大量会议室系统的 H.264 视频转码为 VP8，计算成本很高。

Cisco 希望保持 H.264 端到端，因此贡献了已有代码及相关专利安排，以缓解 WebRTC 使用 H.264 的障碍。课程描述的部署方式是：

1. 浏览器安装并首次运行；
2. 浏览器从 Cisco CDN 动态下载相应的 H.264 库；
3. 该库作为 H.264 实现的一部分参与媒体处理。

这种动态方式有助于浏览器厂商处理专利和许可问题，但也意味着本地编译 WebRTC 的开发者不能假设同样的组件和许可安排会自动出现在自己的应用中。

另一种路径是不采用这套动态库，而是接入设备的 H.264 硬件编码器。这需要额外集成工作，并且不是所有设备、服务器或嵌入式平台都能直接支持。

## 时间可扩展性为什么影响大型会议

时间可扩展性允许视频流在时间上具有可选择层次，接收端或转发系统可以根据条件保留不同帧率层级。课程将在后续媒体处理模块详细展开，这里重点是两种编解码器的实现差异：

- VP8 的时间可扩展性支持较明确；
- H.264 在课程所述 WebRTC 实现中处于“不完整”的状态，有些设备或路径只涉及解码器能力，编码器虽然存在，却没有在 WebRTC 中实现相应支持。

这会影响大型 SFU 群组通话的灵活性。SFU 不只是判断能否转发 H.264，还要考虑能否利用时间可扩展性适应不同接收端。课程因此更偏好在大型群组通话中使用 VP8。

至于这一差异对具体产品是否构成严重问题，需要结合会议规模、媒体服务器能力和接收端适配策略判断，而不是脱离架构单独比较编解码器名称。

## 如何在 VP8 与 H.264 之间做决策

### 1. 尽量避免视频转码

视频转码需要解码再编码，会消耗大量 CPU 和内存。若后台需要同时处理多种视频编码并频繁转码，容量成本会很高。

如果应用的其他部分已经大量使用 H.264，通常更愿意端到端保持 H.264，而不是仅在 WebRTC 段转成 VP8。既有系统的边界成本，可能高于单独追求 VP8 默认方案的收益。

### 2. 全新系统优先考虑 VP8

如果没有大型 H.264 既有部署，而且可以自行决定端到端技术栈，课程建议选择 VP8 作为全新实现的默认方案。这样可以利用其免版税、WebRTC 集成和时间可扩展性方面的优势。

### 3. 大型 SFU 群组通话重点评估 VP8

课程在大型 SFU 场景下偏好 VP8，主要理由仍是时间可扩展性。选择媒体服务器时，还要确认它是否真正支持所需编解码器及其配套工具和优化，而不是只看功能清单中的编解码器名称。

### 4. 移动端同时检查 H.264 可用性与 VP8 CPU 占用

移动端不能只看“VP8 免费”或“H.264 有硬件”：

- 检查 H.264 硬件能力是否能被目标浏览器或应用调用；
- 测量 VP8 软件编解码的实际 CPU 使用；
- 注意新设备通常更能承受 VP8 的计算开销，旧设备可能压力较大。

### 5. 实测编码器质量与边界条件

并非所有编码器实现都有相同质量，硬件实现尤其需要验证。课程曾遇到一些硬件编码器或解码器在低分辨率、低码率下崩溃或只显示黑屏的情况。

因此，部署前应覆盖目标分辨率、码率、设备型号和驱动组合，检查画面质量、稳定性以及异常表现，不能只用一段高码率样本测试。

### 6. 允许同一产品使用多种视频编解码器

选择不必永远只有一种。课程以 Google Meet 为例：条件允许时使用 VP9，不可用时回退到 VP8，并根据可用 CPU 等因素继续决策。关键是让回退策略与设备、网络和服务器能力相匹配，而不是把多编解码器支持变成无规则的实时切换。

## 浏览器可用性的最终核对

课程给出的基线是，VP8 和 H.264 在当时的现代浏览器中均可用，包括 Chrome、Edge、Firefox 和 Safari。VP8 覆盖广，但多数情况下缺少硬件加速；H.264 常具有硬件加速基础，却并非总能访问，也并非每个硬件实现都理想。

VP8 和 H.264 属于 WebRTC 必须实现的编解码器，VP9、HEVC 等其他方案则属于可选能力。MTI 提供的是互通起点，不会替代对设备驱动、动态组件、媒体服务器和时间可扩展性的验证。

## 小结

VP8 与 H.264 在课程讨论的实时质量和 CPU 维度上大体可比，但部署特征明显不同。VP8 免版税、WebRTC 集成和时间可扩展性支持较好，却更依赖软件编解码；H.264 拥有广泛的外部生态和硬件支持，却受到许可、驱动接入和 WebRTC 实现差异的影响。

已有 H.264 系统通常应优先评估端到端 H.264，以避免昂贵的视频转码；全新系统和大型 SFU 群组通话则更适合把 VP8 作为默认候选。无论选择哪一种，都必须在目标设备上实测可用性、CPU、质量和边界条件，而不能只根据标准名称或早期压缩对比作决定。
