# 第 27 章 Opus

Opus 是 WebRTC 的默认音频编解码器，也是其必须实现的编解码器之一。它的核心价值不是某一个固定码率或频带，而是把低码率语音、高保真音乐、单声道与立体声、丢包纠错等能力组合在同一套灵活机制中。理解 Opus，需要同时理解其质量优势、混合结构和部署成本。

## 如何理解 Opus 的质量与码率优势

课程用一张编解码器比较图说明三个问题：使用什么码率、获得什么质量，以及采用什么许可方式。图的横轴是比特率，纵轴是质量，因此越靠近左上方，越表示“以更低码率获得更高质量”。

图中的编解码器按许可大致分为三类：

- 需要许可费用且不开源，例如 AMR 系列、AAC 和 MP3 等；
- 许可免费但不开源，例如 G.722.1C 和 G.719；
- 免费且开源的方案。

G.711 位于高码率、低质量的区域。在课程的比较语境中，它几乎不进行面向码率削减的压缩，典型码率为 64 kbps。Opus 则覆盖很宽的码率和质量范围，在许多码率下都能提供有竞争力的质量。

不过，这张图来自 Opus 网站，课程明确提醒读者对“Opus 在每个码率上都优于所有其他编解码器”的展示保持审慎。更稳妥的结论是：Opus 被广泛认为是一款非常优秀的编解码器，但并非没有代价——它需要相当的处理能力才能有效运行。

## SILK 与 CELT：一套编解码器中的两种技术

Opus 与许多传统语音编解码器的主要区别，是它内部结合了两种编码技术：

- **SILK** 最初由 Skype 开发，主要面向低码率语音，也就是人与人对话中的讲话内容。
- **CELT** 主要面向音乐和高保真音频。

因此，可以把 Opus 概括理解为“SILK + CELT”：SILK 擅长语音，CELT 擅长音乐。通常，窄带和宽带编码更倾向使用 SILK，全带等高质量音频更倾向使用 CELT，但这种分工不是固定不变的。

Opus 还支持**混合模式**：同一音频帧的不同部分可以分别由 SILK 和 CELT 编码。课程将模式选择描述为通过小型 RNN 算法分析音频：更像语音时倾向 SILK，非语音内容倾向 CELT，两者兼有时则采用混合编码。这样，Opus 不必把整个通话永久锁定在单一模式中。

### 版本演进带来的边界扩展

课程以当时已出现的 Opus 1.4 为背景，回顾了此前版本的改进：

- Opus 1.2 改善了 CELT 在较低码率下的表现，并增强 SILK，使其在较低码率下也能支持全带。
- Opus 1.3 后期进一步扩展低码率能力：SILK 可在 **9 kbps** 下支持宽带，并将窄带能力延伸到约 **5 kbps**。

这些变化说明，SILK 与 CELT 的适用边界会随着实现优化而变化，不能把早期频带分工当成不可改变的限制。类似地，libopus 从 1.0 到 1.1 的优化重点之一，就是减少 CPU 和内存消耗。

## Opus 的主要能力与 WebRTC 用法

| 能力 | Opus 本身 | 课程所述 WebRTC 用法 |
| --- | --- | --- |
| 许可 | BSD 许可证、免版税，允许商业使用 | 可直接作为 WebRTC 的核心音频方案 |
| 采样率 | 8～48 kHz | 使用 48 kHz |
| 比特率 | 支持动态调整 | 课程所述实现采用相对固定的码率设置 |
| 帧长 | 支持多种毫秒级帧长 | 通常每 20 毫秒发送一次 |
| 声道与内容 | 支持单声道、立体声，支持语音和音乐 | 可在受实现支持的范围内使用 |
| 模式切换 | 可在不同能力之间无缝切换 | 是否真正启用各项动态能力取决于具体实现 |

需要区分“标准具备某项能力”和“WebRTC 实现会动态使用这项能力”。例如，Opus 本身支持动态码率，并不意味着每个 WebRTC 实现都会在通话中自动利用所有码率和模式组合。

## 内置 FEC 与带内控制

Opus 成为 WebRTC 默认方案的另一个原因，是 SILK 中内置了前向纠错（Forward Error Correction，FEC）。网络状况恶化时，可以通过增加用于恢复语音的冗余信息提高抗丢包能力。课程将其概括为加入重复数据以进行纠错；这里的关键不是简单重发整个 RTP 包，而是编码器提供冗余，帮助接收端应对丢失。

这套 FEC 不一定是最强的纠错实现，但它已经内置、无需另付许可成本，并可在实现支持时自动发挥作用，从而改善宽带语音在丢包环境下的韧性。

Opus 还把许多控制放在编解码器带内完成。例如，是否使用 FEC、如何采用混合模式等，不必全部转化为额外的会话信令。这样可以降低信令平面的复杂度，使编码器能根据媒体内容更灵活地工作。

## 为什么通常优先选择 Opus 而不是 G.711

课程给出的实践建议很直接：在 WebRTC 中如果可以在 Opus 和 G.711 之间选择，通常先选 Opus；若要换用其他方案，应当有明确理由。

### 1. 保留宽带语音质量

假设传统电话侧使用宽带编解码器 G.722.1，电话通过会话边界控制器（SBC）或专用交换机（PBX）接入 WebRTC 浏览器。浏览器侧不能直接沿用该编解码器时，需要在 Opus 和 G.711 之间选择：

- 选 G.711，会把原来的宽带语音降为窄带；
- 选 Opus，可以在 WebRTC 一侧继续保持宽带能力和较高质量。

因此，即使边界必须转码，Opus 也能避免不必要地把整段通话都限制在传统电话音质上。

### 2. 提高抗丢包能力

即使传统电话另一端本来就是窄带，WebRTC 一侧仍有理由使用 Opus。Opus 的抗丢包能力优于 G.711，在不稳定网络中可以更好地维持可懂度和通话体验。这一收益与是否扩展到宽带无关。

### 3. 降低带宽需求

课程给出的示例是：Opus 可以用 **8、10、15 或 16 kbps** 等码率发送语音，而 G.711 的典型码率仍为 **64 kbps**。在可比的窄带质量目标下，Opus 能用更低码率传输，因而更容易适应受限或质量不稳定的网络。

所以，Opus 的价值不能被简化为“把窄带升级成宽带”。即使最终仍是窄带端到端通话，带宽和韧性收益也足以支持选择 Opus。

## 部署 Opus 前需要回答的问题

### 是否必须在某处切换到其他音频编解码器

如果系统只包含 WebRTC 端点，端到端使用 Opus 最简单。如果还要连接传统电话网或其他媒体网络，就必须先确认那些网络使用的编解码器，以及是否需要进行转码。

转码是把一种编码码流转换为另一种编码码流，通常需要先解码，再重新编码。它不是无成本的格式改名。

### 转码应该放在哪里

候选位置包括后端服务、SBC 或专门的媒体服务器。位置选择会影响媒体路径、系统边界、容量规划和运维责任，不能只根据某个设备“支持转码”就决定。

### 转码的计算成本是多少

编码和解码都需要计算资源。转码把两者串在一起，因此成本较高。部署时应评估并发路数对 CPU 和内存的影响，而不是只检查功能是否可用。

### 转码目标是窄带还是宽带

如果 WebRTC 宽带音频最终必须转成窄带，可以让宽带编码侧也相应降低质量或处理能力目标，避免为最终会被丢弃的细节继续消耗 CPU 和内存。关键是让编码策略与真实端到端能力匹配。

### 客户端是否有理由使用其他编解码器

浏览器场景通常仍应优先 Opus。但原生实现或特定的 WebAssembly 方案可能有特殊需求，需要评估其他编解码器是否真的更合适，以及为此付出的集成成本是否值得。

### 能否端到端使用 Opus

如果可以，课程建议尽量全链路使用 Opus。这样可以减少转码、质量损失、信令适配和编解码差异带来的问题，是降低系统复杂度的有效方式。

## 小结

Opus 通过 SILK 与 CELT 的组合覆盖低码率语音和高保真音乐，并能采用混合模式处理同一帧中的不同内容。它支持 8～48 kHz 采样、单声道和立体声、动态码率与多种帧长；WebRTC 则采用其中一组具体配置，典型采样率为 48 kHz、发送间隔为 20 毫秒。

相比 G.711，Opus 同时提供更高的语音质量、更好的抗丢包能力和更低的带宽需求。实际部署的重点往往不是“浏览器是否支持 Opus”，而是传统网络能否端到端使用它、必须在哪里转码，以及转码的 CPU 与内存成本。没有特殊约束时，Opus 应作为默认选择。
