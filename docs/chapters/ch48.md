# 第 48 章 VoIP 框架

VoIP 早于 WebRTC，而 WebRTC 本身也属于 VoIP 技术体系。二者的重要差别在于使用方式：传统 VoIP 往往用于替代电话通信，WebRTC 则让更多产品能够把实时沟通作为一项功能嵌入其中，而不必把沟通本身做成完整服务。本章聚焦开源组件，并以 SIP 为主线说明 VoIP 客户端、服务器及其与 WebRTC 的结合方式。

## SIP 与 WebRTC 并不能天然互通

SIP 是用于 IP 语音通信的信令协议，也可以从架构、网络和规范的角度理解它。如今，大量基于 IP 的语音通话都使用 SIP。WebRTC 可以使用 SIP 信令，但这并不意味着任意 SIP 产品都能与 WebRTC 产品直接互通。

| 技术环节 | WebRTC 一侧 | 传统 SIP 产品中的常见情况 | 互通问题 |
| --- | --- | --- | --- |
| 音频编解码器 | 使用 Opus 和 G.711，课程建议尽可能采用 Opus | 课程所讨论的产品中，许多尚不支持 Opus | 双方需要具备可共同使用的编解码能力 |
| SIP 传输 | 浏览器中的 SIP 必须通过 WebSocket 传输 | 通常使用 TCP、UDP 和 TLS | 普通 SIP 电话不支持 WebSocket，浏览器不能直接与其建立 SIP 呼叫 |
| 媒体加密 | 强制使用 SRTP | SRTP 并非强制，且不少产品未实现 | 加密能力与配置可能无法对齐 |
| SRTP 密钥交换 | 使用 DTLS-SRTP | 实现 SRTP 时通常采用 SDES 或 ZRTP | 即使都支持 SRTP，共享主密钥的方式仍可能不同 |
| RTP 组织方式 | BUNDLE 与复用几乎是默认能力 | 在许多 SIP 产品中很少见 | 媒体协商与传输方式需要适配 |
| ICE 候选地址收集 | 实现 Trickle ICE | 通常只有 ICE，不支持 Trickle ICE | 连接建立过程需要兼容处理 |

SRTP 密钥交换的目的，是让通信两端安全地共享用于媒体加密的主密钥。一端用 SRTP 加密数据包后，另一端必须持有相应秘密才能解密。因此，“双方都支持 SRTP”还不够，密钥交换机制也必须一致，或者由中间组件完成转换。

这些差异说明，把 SIP 用作 WebRTC 的信令协议只是第一步。现有 SIP 产品通常还要进行适配和修改，才能处理浏览器传输、媒体安全、RTP 复用和 ICE 等要求。

## 与 WebRTC 相关的 SIP 实体

SIP 体系包含许多实体，IMS 等基于 SIP 的体系还会增加更多抽象和网络分解层次。对 WebRTC 架构而言，重点是以下几类实际承担终端、路由、媒体处理或边界连接职责的组件。

### 用户代理

用户代理（User Agent，UA）是参与交互的端点，可以是一台设备、一个客户端或一个浏览器。它是实际接收媒体的终端。在 SIP 交互中，通信两端的用户代理就是会话参与者。

### 代理与 B2BUA

SIP 代理只处理信令。它接收一侧的 SIP 消息，再将其转发到另一侧；同一路径上可以存在多个代理。每个代理都可以增加或修改消息内容，并基于这些消息实现服务。

背靠背用户代理（Back-to-Back User Agent，B2BUA）在信令面把一通呼叫拆成两段：一段位于用户代理与中间组件之间，另一段位于中间组件与对端用户代理之间。B2BUA 在两侧分别终止并重建 SIP 对话。是否同时锚定和处理媒体取决于具体产品及其配套媒体组件，并不是 B2BUA 这一角色的必然定义。

应用服务器可以构建各种应用和服务，通常建立在代理或 B2BUA 之上。IP PBX 则可承担电话交换、路由和相关通信服务；具体产品所覆盖的信令与媒体职责，需要结合其形态判断。

### 会话边界控制器

会话边界控制器（Session Border Controller，SBC）通常部署在 DMZ 中，也就是同时面向公共网络和私有网络的暴露区域，常见于企业或数据中心边界。它有两个主要作用：

1. **保障安全。** 这是首要原因。可以把 SBC 理解为 VoIP 呼叫的防火墙，用它控制进入内部网络的通信。
2. **处理互操作性。** SIP 虽是统一协议，不同产品和厂商的实现却存在细微差异。SBC 可以在信令面充当 B2BUA，并可在媒体面执行锚定、互通处理或转码，以屏蔽这些差异。

一些 SBC 能把 WebRTC 作为进入网络的另一条连接支路。它们仍主要使用 SIP 信令，同时处理 WebRTC 与传统 SIP 实现之间的其他差异，例如 RTP 的 BUNDLE 与复用、SRTP、DTLS 和密钥交换。代理与 B2BUA 也会在各自负责的层次上处理部分差异。

### 网关

网关用于连接两个不同的网络。在本章语境中，它连接 SIP 网络与 WebRTC 网络。与仅在同类组件之间转发消息相比，网关的核心职责是跨越两个技术域建立连接。

## 客户端框架

SIP 客户端在用户代理一侧运行。按运行环境，可分为浏览器客户端和面向移动或嵌入式系统的应用客户端。

### 浏览器：JsSIP 与 SIP.js

浏览器环境采用 SIP over WebSocket。课程重点推荐 JsSIP 和 SIP.js，也提到了 SIPML，但不建议采用后者。选择前两个库时，可以根据项目适配程度决定。

基本使用方式是把 JavaScript 包引入网页，再调用其 API 发送 SIP 信令。库还会处理 WebRTC 内部所需的工作，其中包括 SDP 处理。因此，应用并非只获得一个独立的消息发送器，而是获得 SIP 信令与浏览器实时媒体之间的衔接能力。

### 移动与嵌入式应用：PJSIP、Linphone 和 baresip

这一类框架主要以 C 语言编写。课程列出的选择包括 PJSIP、Linphone 和 baresip：

- **PJSIP 与 Linphone**：都是功能完整的客户端，包含媒体、信令及其上的应用部分，可运行于 Android 和 iOS，有些情况下也支持其他操作系统。按课程介绍，两者采用 GPL，并提供双重许可方式，需要商业许可时可以付费获得。
- **baresip**：开源许可证更宽松，但只提供基础的 SIP 实现。开发者需要自行完成 iOS、Android 适配，并在其上构建用户界面。

因此，许可条件只是选择因素之一。完整客户端能够减少集成工作，基础实现则把更多平台适配和应用层工作留给开发团队。

## 服务器框架

开源 SIP 服务器很多，本章重点讨论 Asterisk、FreeSWITCH 和 Kamailio，其他选择还包括 OpenSIPS 和 FreePBX。前三者的角色并不相同，不能仅按“是否支持 SIP”来比较。

### Asterisk：以语音为中心的 IP PBX

Asterisk 是支持 SIP 和 WebRTC 的 IP PBX。使用它意味着进入 SIP 与 PBX 的工作方式：开始时需要掌握一些 SIP 基础，但主要工作是配置 Asterisk，并在其上建立集成点。信令和媒体都由它处理。

Asterisk 内置会议桥和交互式语音应答（IVR），可以实现多方呼叫、内部呼叫路由，并结合双音多频（DTMF）输入与预录消息组织呼叫流程。

课程建议把 Asterisk 用于语音场景。它虽然支持视频，但不建议用 Asterisk 或其他 SIP 产品承担视频处理。课程录制时还提到，Digium 当时才正式为 Asterisk 加入 Opus 支持，此前则因知识产权方面的顾虑而未支持。这一时间背景也说明，评估具体产品时需要核实其编解码能力，而不能根据协议名称推断互通性。

### FreeSWITCH：能力相近，但生态与视频判断不同

FreeSWITCH 与 Asterisk 的能力和产品定位相近，两者各自拥有稳定的支持者。利用 FreeSWITCH，可以构建与 Asterisk 类似的产品，功能集也大体相当。

课程特别指出，FreeSWITCH 的开发者社区和受众相对较小，因此寻找熟悉它的开发人员可能更困难。其视频功能是在课程录制前一两年才开始加入的，讲师认为当时还不够完善或稳定；如果项目以视频为主，他更倾向于采用纯粹的 WebRTC 技术路线，而不是依赖 FreeSWITCH 的视频实现。

### Kamailio：只处理信令的 SIP 代理

Kamailio 是 SIP 代理，不处理媒体，主要负责呼叫路由和直接呼叫。它通常与 FreeSWITCH 或 Asterisk 配合，把更适合代理由完成的特定功能从 PBX 中分离出来。由此形成的分工是：Kamailio 处理 SIP 消息与路由，Asterisk 或 FreeSWITCH 承担需要 PBX 和媒体能力的部分。

## 小结

把 SIP 引入 WebRTC 架构时，不能只检查信令协议是否一致，还要逐项核对编解码器、WebSocket 传输、SRTP 与密钥交换、RTP 复用以及 Trickle ICE。SBC、B2BUA 和网关可在不同层次弥合这些差异。

客户端选型需要同时考虑运行平台、功能完整度与许可证；服务器选型则要先分清代理、PBX 和媒体处理职责。对于课程所讨论的方案，Asterisk 与 FreeSWITCH 更适合以语音为中心的通信产品，Kamailio 负责信令代理，而视频处理不应仅因某个 SIP 产品宣称支持视频就默认采用。
