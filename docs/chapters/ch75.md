# 第 75 章 WebRTC 视频质量

视频质量并不只是“分辨率高不高”。采集设备、编码器、CPU、可用带宽、丢包恢复、接收端展示尺寸以及媒体拓扑都会改变用户最终看到的画面，甚至还会间接影响音频。本章沿用课程嘉宾 Philipp Hancke 的分析路径：先界定质量问题，再说明如何测量，随后拆解带宽估计，最后比较全网格与基于选择性转发单元（SFU）的联播方案。

课程讨论涉及当时的浏览器实现和算法状态。理解这些内容时，应重点掌握测量方法和推理过程，而不是把某个版本的实现细节当作永久不变的规则。

## 视频质量问题有哪些表现

生产环境中的用户反馈通常集中在以下几类：

- 分辨率低、画面像素化或模糊；
- 视频经常冻结；
- 帧率太低，屏幕共享等对动态更新有要求的场景尤其明显；
- CPU 占用过高，甚至能明显听到设备风扇持续转动。

最容易被忽视的问题，是视频会连带损害音频。会议中如果音频不断中断，体验会非常糟糕；原因却可能是视频正在占用过多带宽或处理资源。在这类情况下，让用户暂时关闭视频往往能带来改善，这也说明不能只看视频轨道本身来诊断“视频质量”。

## 从采集到编码：质量在哪里下降

### 采集分辨率不等于发送分辨率

摄像头可能支持 VGA、720p、全高清，部分设备甚至支持 4K。但选择采集规格时，既要考虑使用场景，也要考虑用户的网络连接，不能简单追求设备支持的最高值。

按课程录制时的浏览器能力，调用 `getUserMedia` 之前无法直接查询摄像头支持的全部分辨率。因此，应用能做的是向浏览器表达目标分辨率，同时允许浏览器在必要时返回较低规格。

拿到某个分辨率的视频流，只说明采集已经完成，并不代表：

1. 网络足以发送这一分辨率；
2. 编码器能按当前期望的速率编码；
3. 接收端确实需要这么大的画面。

CPU 不足时，浏览器可能主动缩小图像。例如，摄像头采集的是 720p，实际发送的画面仍可能被降低。这属于基于 CPU 的自适应；课程指出，可以在 Chrome 的 `webrtc-internals` 页面中观察这类 CPU adaptation。

### 编码器如何适应带宽

带宽估计会驱动编码器适应连接的可用带宽。课程讨论了两条路径：

- **降低空间分辨率。** 宽和高都减半后，像素数量只剩原来的 25%。编码器需要处理的数据显著减少，课堂估算中带宽需求也约降到原来的四分之一。
- **丢弃部分帧。** 这相当于降低时间分辨率。按讲师当时的说明，浏览器中的 WebRTC 实现并不采用这种浏览器端降帧策略，但服务器可以执行类似处理。

这两种适应分别改变清晰度和流畅度，因此“码率降低了”并不足以解释用户到底会看到模糊画面，还是会看到低帧率画面。

### 编解码器选择首先是资源问题

讲师不认为 VP8 与 H.264 在主观画质上存在大多数用户都能明显察觉的差异，并提出可以让用户参与实验、收集反馈来验证，而不是预设某一种一定更好。

更实际的选择依据有两点：

1. **编码复杂度。** VP9 通常消耗更多 CPU，选用时必须把这部分成本计入整体预算。
2. **硬件加速。** 如果某个平台能为一种编解码器提供硬件编码器或解码器，而另一种只能使用软件处理，前者通常会明显降低 CPU 压力，为应用其他部分留下资源。课程以 iOS 上通常优先选择 H.264 为例，原因就在于其硬件编码能力。

因此，编解码器对比不能脱离设备、硬件路径和应用负载，只比较一张静态图像的细腻程度。

## 第一层测量：视频元素与实际展示

从 HTML 应用入手，最直接的测量对象是 `HTMLVideoElement`，更一般地说是 HTML 媒体元素。可以读取视频的 `videoWidth` 和 `videoHeight`，再与视频在页面中实际显示的宽、高进行比较；`resize` 相关事件则能帮助发现视频尺寸变化。

这些观察可以回答几个很实际的问题：

- 视频是否频繁改变分辨率？如果频繁发生，可能说明远端带宽不足或连接不稳定。
- 是否长时间把很小的视频图像放大到很大的视频元素中？即使播放没有停止，用户也不会满意。
- 使用联播时，SFU 是否过于频繁地切换发给接收端的流？发送端会向 SFU 提供多路编码流，而 SFU 每次选择一路转发；不合理的选择会造成接收画面反复改变分辨率。

### 发送端应与接收端的展示需求匹配

质量分析不能只关注“网络上发送了什么”和“本机编码、解码消耗多少 CPU 和内存”，还必须问：对方真正需要看到多大的画面？

课程用移动应用中的图片作类比：为了显示一个图标或缩略图，却发送一张千万像素、占用数兆字节的图片，显然浪费。WebRTC 视频也会出现同类问题——发送端传得很多，接收端却只把它显示为一个小窗口。

因此，接收端实际需要的宽度和高度应成为发送上限的重要依据。FaceTime 的分析也提供了类似启发：它会与另一端协商发送分辨率，讲师推测这与目标设备的宽度和像素数量有关。

反过来，展示或解码尺寸如果频繁变化，也说明网络或处理媒体的 CPU 存在过多波动。展示层因此既是体验指标，也是诊断信号。

## 第二层测量：正确使用 `getStats`

`getStats` API 能揭示浏览器媒体引擎内部正在发生什么。课程录制时，Chrome 同时存在旧版与符合规范的新统计接口：

- 旧接口基于回调，`webrtc-internals` 当时仍在使用；
- Chrome 58 带来的新接口基于 Promise，返回 JavaScript `Map`，输出结构经过重写，也更容易遍历。

这一版本背景本身会过时，但接下来的统计模型和指标之间的关系仍然具有分析价值。

### 先理解采样模型，再计算速率

应用可以随时调用 `getStats`，API 无法预知两次调用之间会隔多久。因此，对“当前连接速度是多少”这类问题，不能简单把某一次快照中的累计值当作速率。

典型做法是测量两次：

1. 在第一个时刻读取累计接收字节数；
2. 在第二个时刻再次读取同一计数；
3. 用两次计数之差除以两次调用的时间间隔，得到该区间内的平均值。

也就是说，常见模式是“测量、再测量、用增量除以时间”。瞬时统计并非完全没有，但相对少见。计算比特率时还要注意把字节换算为比特，并确保时间单位与目标单位一致。

### 轨道报告：接收、解码和丢弃是否一致

轨道报告描述音频或视频媒体流轨道，可以区分本地与远程来源，各自具有不同属性。不知道远程轨道 ID 时，课程建议检查 `remoteSource` 是否为真。

与视频质量直接相关的内容包括：

- `frameWidth` 与 `frameHeight`：了解媒体帧本身的尺寸。不过，`getStats` 不知道页面把视频显示得多大，展示尺寸仍应在视频元素上测量。
- 接收帧数：可理解为解码器之前的计数。讲师提到它与 VP8 picture ID 的关系，但这是实现层面的说明。
- 解码帧数：反映解码器之后实际完成了多少帧。如果它明显少于接收帧数，说明解码器无法处理所有输入，正在丢弃图像，通常不是好兆头。简单的本地浏览器测试未必会暴露这种情况，真实服务中却可能发生。
- 丢弃帧数：可揭示抖动缓冲区因帧到达太晚而将其丢弃的情况——既然已经来不及展示，就不再保留。这类现象在高延迟连接上更常见。

把这三个阶段放在一起比较，比只看一个“帧率”数字更容易判断问题发生在接收、解码还是调度展示之前。

### RTP 报告：码率、丢包与恢复请求

入站 RTP 和出站 RTP 报告描述相应的 RTP 数据包流。首先关注的是累计字节数，例如接收端的 `bytesReceived`，它可用于按上述采样模型计算码率。码率是影响视频质量的核心因素；稳定且足够高的码率与持续低码率带来的体验显然不同。课程以稳定达到约 2 Mbit/s 作为一种令人满意的视频状态示例，而不是把它规定为所有场景的固定目标。

丢包分析可以结合以下数据：

- 丢包数量与接收包数量：用两个时刻的增量计算某一测量区间内的丢包比例。
- `fractionLost`：它来自较底层的 RTCP 控制消息，是瞬时性质的数据，并不对应应用自行定义的测量区间，因此对应用分析往往不如自行计算区间丢包率有用。
- NACK 数量：NACK 是否定确认，用于请求重传。持续丢包时通常会看到很多 NACK，媒体引擎正在尝试恢复。看到 NACK 本身并不等于故障，关键要看其规模及恢复是否成功。
- PLI 计数：PLI 即图像丢失指示（Picture Loss Indication），基本含义是“需要发送新的关键帧”。大量、尤其是连续出现的 PLI 表明问题较严重；解码器可能已经处于没有新关键帧就无法继续显示视频的状态，新关键帧也会显著拉低质量。

### 候选对报告：找到真正使用的路径

RTP 报告中虽然定义了往返时间（RTT），但按课程录制时的状态尚未得到支持。旧版统计里看似存在的 RTT，讲师向 Google 相关人员确认后得知，实际来自另一层，并不是可靠的真实测量。

课程建议改从候选对报告入手：

1. 找出当前正在使用的 ICE 候选对；
2. 读取 `currentRoundTripTime`；如需平均 RTT，则用累计的 `totalRoundTripTime ÷ responsesReceived` 计算；
3. 同时查看输出方向可用比特率等带宽估计信息；
4. 检查候选对是否表明正在使用 relay，并经由 TURN TCP 传输媒体。

RTT 是质量的重要影响因素。课程参照 ITU E-model 等质量指标指出，RTT 超过 300 ms 会非常糟糕，因此值得重点监控。这个阈值应针对当前 RTT 或换算后的平均 RTT，而不是不断累积的 `totalRoundTripTime` 总值。TURN over TCP 则意味着媒体通过 TCP 中继，通常也不是理想路径。把传输路径与码率、丢包和 RTT 放在一起，才能解释相同的编码参数为何在不同网络下产生不同结果。

## 带宽估计为什么会影响画质

### 固定码率不能替代动态估计

WebRTC 运行在公共互联网上，没有端到端的服务质量保证，必须处理丢包和带宽波动。应用不能只在设置页问用户“你的连接能发送多少数据”，随后整个通话都固定使用这个码率。用户可能只参加一次会议，而且即使同一次会议中，可用带宽也会变化。

固定码率并非在任何场景都绝对不能使用，但应先利用统计信息估算其影响，再明确作出取舍；讲师总体上不推荐依赖固定视频码率。

### 区分突发丢包与持续丢包

课程把丢包大致分成两种形态：

- **短时间剧烈丢包。** 例如在一秒或两三秒内丢失约 800 个包。这通常会对会话造成灾难性影响，视频冻结，之后才可能恢复。
- **持续性丢包。** 会看到大量 NACK 和数据包重传，并希望重传包仍能及时到达并显示。前向纠错（FEC）等技术可以稍微缓解，课程也提到 Opus 音频中的相关讨论。

二者在用户侧都可能表现为“质量差”，但恢复机制和统计曲线并不相同。

### 通过试错探测可用带宽

估计可用带宽的基本方法只有试错：逐渐增加视频发送量，直到观察到丢包，再降低发送量。之后再次上升，于是统计曲线常出现锯齿状变化。课程建议参考 Mozilla 的 Randell Jesup 以及 Gustavo García 对相关算法的技术分析。

课堂描述的算法逻辑是：

- 丢包率低于 2% 时继续增加发送量，增幅约为 8%；
- 丢包率超过 10% 时，按丢包率的一半降低带宽；例如丢包率为 10%，流量降低 5%，丢包率达到 100% 时则降低 50%。

通话开始阶段还希望快速提高码率。初始没有可靠估计，如果花两分钟才升到全高清，用户早已感受到长时间低质量。因此，快速初始升速与避免过冲之间需要不断平衡。

### REMB 与 transport-cc 的决策位置

课程讨论了两种带宽适应思路：

- **REMB（Receiver Estimated Maximum Bitrate，接收端估计最大比特率）。** 按讲师当时的介绍，Chrome、Firefox 和 Edge 均已实现。它虽然仍是 IETF 草案，且当时已有三年没有更新，但实际上构成了当时通行的做法。
- **transport-cc。** 它把可用带宽的决策移到发送端，也称发送端带宽估计。其反馈格式让接收端报告在何时收到了多少数据包，发送端再据此判断可以使用多少带宽。

这一区分的关键不是背缩写，而是明确“谁观察、谁反馈、谁决定发送速率”。

### 视频拥塞也会伤害音频

共享连接上的适应有一个重要副作用：视频丢包时，音频也可能同时丢包。在低带宽网络上，如果已经出现约 10% 的丢包，音频质量往往也会恶化。因此，关闭视频能够释放带宽并改善音频，并不是与视频无关的权宜之计。

### 从一段码率曲线诊断恢复问题

课程分析了一次通话的码率变化，过程如下：

1. 码率从约 100 kbit/s 起步，用 25～30 秒升至约 600 kbit/s；
2. 在高档位维持约 70 秒，随后跌回约 100 kbit/s，视频很可能已经冻结；
3. 第二次升速耗时约 60 秒，在 600 kbit/s 附近仅保持约 10 秒便再次崩溃；
4. 接着再次升速，短暂下跌，但这次恢复更快，并稳定了数分钟；
5. 后续仍出现下跌和恢复。

初始带宽估计逐步改善，并不等于通话中的恢复问题已经解决。一次短暂故障后，如果仍需一分钟才能恢复，用户会持续抱怨，甚至刷新页面。讲师把“短暂下跌后是否应该、以及如何更快恢复”列为这一领域仍很困难的问题之一。

## 全网格中的带宽竞争

全网格（full mesh）中，每个参与者都直接向其他参与者发送媒体。它不需要 SFU 或混音服务器来集中处理媒体，但并不意味着不需要 TURN；NAT 穿越失败时仍可能需要中继。

### 一个发送端面对多个不同估计

每条点对点连接都会得到自己的带宽估计。同一个发送端可能面对一个约 1 Mbit/s 的参与者，同时面对另一个只有约 500 kbit/s 的参与者，却无法简单地让单一编码输出同时精确匹配两者。

一种做法是向较低估计靠拢，例如都降到约 512 kbit/s，但这会牺牲条件较好的接收端。讨论中还提出，可把估计归为三类，让编码侧输出三档分辨率，以更有结构地作出决策，而不是把最低档当作唯一答案。

### 多条连接会互相“抢带宽”

带宽估计通过逐步升速、发现丢包后回退来工作。在全网格里，一条连接升速可能导致另一条连接丢包；后者降速后再升速，又可能反过来影响前者。多条连接轮流抢占资源，形成不稳定的循环。

课程介绍的应对措施是主动限制带宽：

1. 根据参与者数量调整可用带宽；
2. 同时限制发送分辨率；
3. 带宽越低，发送的分辨率越低；
4. 借此同时减少编码和解码带来的 CPU 消耗。

讲师表示，采用这种限制后，八人全网格通话可以运行；如果不加限制，系统会试图耗尽所有可用带宽，CPU 很可能在达到八人之前就已不堪重负。

### 全网格是否值得使用

这里没有脱离场景的统一答案：

- 大量通话本来就是一对一，而且不希望为其部署媒体服务器时，全网格很合适；
- 三人左右的通话通常也可能工作良好；
- 如果拓扑、网络和终端机器都可控，多方全网格的问题更容易处理；
- 如果参与者、网络和设备都高度开放，试图用全网格支撑多方通话会非常困难。

因此，多方场景通常转向服务器，尤其是 SFU，但这只是改变了问题的位置，并没有让带宽估计消失。

## SFU、最低共同能力与联播

### 单流 SFU 仍可能拖累整场会议

SFU 让发送端只向服务器发送一次，再由服务器服务多个接收者。如果发送端只提供一路流，应该使用多大码率？

假设接收者中有人只有 512 kbit/s，另有人约有 2 Mbit/s，发送端就需要照顾最低共同能力。否则，低带宽接收者会收到超过其承受能力的流量，报告丢包，发送端随后仍会整体降速。

早期许多视频桥正是这样工作的，而且自动适应机制本身有效。问题在于：一个网络状况很差的参与者可能把整场会议的质量都拉低，这通常不是产品希望看到的结果。

### 空间可扩展性：联播提供多档分辨率

联播（simulcast）的做法是向服务器发送三种不同的空间分辨率，为 SFU 提供三个带宽等级。课程给出的示例档位是：

- 约 150 kbit/s；
- 约 500 kbit/s；
- 最高约 2.5 Mbit/s。

Chrome 中还存在对应的分辨率、带宽需求和目标码率表。这里的数字是课堂示例，重点是 SFU 可以按每个接收者的条件选择流，而不再让所有人共同降到最低档。

### 时间可扩展性：在空间档位内继续细调

课程指出，Chrome 的联播实现还结合时间可扩展性。视频流被编码为一系列图像，其中一部分可以被丢弃，从而降低帧率。

例如，一个接收者只有约 90 kbit/s，即使选择了约 150 kbit/s 的空间档，也仍可能需要进一步调整。如果它只是以缩略图显示，把帧率从 30 fps 降到 15 fps 往往是合理选择，没有必要强求全帧率。

时间可扩展性因此带来更细粒度的自适应码率控制。讲师估计，空间与时间档位组合后总共可形成约九种带宽类别，使系统能够为不同参与者分别选择合适的码率、分辨率和帧率。其核心目标不是提供越多档越好，而是避免“一个差连接决定所有人质量”，同时减少无效发送。

## 音频、视频与数据通道如何分配带宽

课程最后的问答还提出：音频、视频和数据通道之间由谁决定带宽分配，尤其是数据通道出现突发流量时谁优先？

按讲师当时的理解，并不存在一个同时覆盖 RTP 媒体与 SCTP 数据通道的统一带宽分配器；RTP 与 SCTP 各自拥有拥塞控制，但两者并未合并。因此，分析这类问题时，不能假设已经有一个全局仲裁者会自动保证音频永远优先，相关实现仍需分别研究。

## 小结

排查 WebRTC 视频质量，应把以下线索串成完整链路：

1. 采集分辨率、CPU 自适应和编解码器决定了进入网络前的画面与资源成本；
2. 视频元素揭示实际展示尺寸及频繁切换，`getStats` 则揭示接收、解码、丢包、恢复请求、RTT 和中继路径；
3. 速率应由两次统计的增量与时间间隔计算，不能把累计计数误当瞬时速率；
4. 带宽估计通过升速、丢包和回退动态工作，突发下降后的恢复速度与初始升速同样重要；
5. 全网格会受到多连接不同估计和相互竞争的影响，单流 SFU 又可能受最低能力接收者牵制；
6. 联播与时间可扩展性让 SFU 能按接收者分别选择空间、时间档位，从而同时管理画质、帧率、码率和 CPU 成本。

最终目标不是让所有连接始终发送最高分辨率，而是在实际网络和终端能力下，持续发送接收端真正需要、且能够稳定处理的画面。
