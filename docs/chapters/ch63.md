# 第 63 章 媒体算法

实时媒体通话并不是把音频、视频编码后简单发出去。音频与视频需要在接收端重新对齐，扬声器回传的声音需要消除，发送码率需要跟随可用带宽变化，接收端还要处理丢包、乱序和到达间隔不均。本章按照课程顺序讨论唇同步、声学回声消除、带宽估计和抖动缓冲区，并补充噪声抑制、舒适噪声生成、语音活动检测和增益控制等语音算法。

这些算法可以按作用位置理解为几类：

| 类别 | 代表算法或机制 | 主要处理的问题 |
| --- | --- | --- |
| 音视频协同 | 唇同步（lip synchronization） | 让分别传输、处理的音频与视频在播放时重新对齐 |
| 声学与语音处理 | AEC、噪声抑制、CNG、VAD、AGC | 处理回声、环境噪声、静默、语音活动和音量变化 |
| 网络与码率适应 | 带宽估计 | 判断当前可以发送多少媒体数据，避免过多数据造成丢失或延迟 |
| 接收与播放控制 | 抖动缓冲区（jitter buffer） | 用一定缓冲时间处理抖动、乱序、丢包，并配合唇同步 |

它们不是彼此孤立的模块。例如，唇同步所需的播放等待常由抖动缓冲区配合完成；带宽估计又会影响视频质量、丢包和恢复速度。

## 唇同步：重新对齐独立的音频与视频

### 为什么音频和视频要分开处理

在课程所讨论的 VoIP 系统中，音频和视频通过两个独立的流传输，至少也会被当作两个独立流处理。它们分别进入音频编解码器和视频编解码器。

WMV、AVI 或 MP4 文件可以把二者放在同一个文件中，但这种文件本质上是**容器**：内部仍分别保存经过编码的音频和视频。网络传输也是类似的，每个流单独编码后再发送；是否进一步复用，则是另一个问题。

分开处理带来了很大的灵活性：

- 音频和视频可以独立选择、升级编解码器。例如，音频改用 Opus，或视频采用 VP9，而不必同时改变另一种媒体的处理方式。
- 可以只发送音频或只发送视频，不必强制二者同时存在。
- 立体声、5.1 或高保真音频等需求，会使音频与视频的流组织不一定保持一一对应。
- 屏幕共享时，一个参与者可能同时发送两路视频：一路是共享屏幕，另一路是摄像头中的发言者。
- 多方通话可以按接收需求选择媒体，而不是把每一路流原样送给所有人。

课程用五位参与者的 SFU 模型说明最后一点：每位参与者贡献自己的媒体，并接收其余四位的媒体；若每人都包含音频和视频，接收方就要面对来自四位其他参与者的多路音频、视频流。

如果应用只想听见部分人，例如只保留声音较大的发言者，课程示例中的 SFU 可以检查音频是否静默，并决定不把静默流继续转发给其他人，甚至调整所转发的内容。也可以不转发某路视频而保留其音频。正是这些独立选择和组合能力，使音频、视频分离成为必要的架构基础。

### 为什么会失去同步

分离带来灵活性，也产生了唇同步问题。课程给出两个主要原因。

**第一，编码和解码耗时不同。** 视频帧的编码、解码通常比音频帧花费更多时间。即使音频和视频在发送端同时开始处理，视频也可能更晚完成编码或解码，播放时因此出现偏差。

**第二，网络不会平等对待两个流。** 网络存在抖动、延迟和丢包。一个音频包与一个视频包同时发出，并不保证它们按原有顺序到达，也不保证二者仍保持发送时的时间间隔。音频通常更早准备好播放，进一步加大了重新对齐的必要性。

### 用采集时间戳驱动播放

唇同步不是简单地把两个流“同时开始播放”，而是沿着采集、编码、传输、解码和播放流程保存时间关系：

1. 从麦克风、摄像头或显示器取得帧时，先记录时间戳，标明这一帧何时产生。
2. 将带有采集时间依据的数据送入相应编码器。
3. 编码后的音频、视频分别经过网络发送。
4. 接收端取得数据并进行解码。
5. 到准备播放时，根据发送端记录的原始时间戳决定还要等待多久，以及按怎样的时间关系播放。

音频流与视频流的时间戳数值本身可以不同，重点也不是某个时间戳的绝对数值，而是同一媒体中时间戳如何随时间递增，以及两个流之间的时间差如何变化。接收端据此对齐来自麦克风和摄像头的帧。

多数情况下，音频会更早到达并准备好，因此接收端往往要**延迟音频，等待对应视频到达并可播放**。这个等待不能无限增加，否则唇同步会以过大的交互延迟为代价。

### 同步算法必须作出的取舍

当媒体没有按计划同时准备好时，算法需要回答一组具体问题：

- 是否应让音频继续等待视频？如果音频本身已经太晚，是否还应等待？
- 同步偏差过大时，是否应丢弃部分媒体？
- 等待超时后，如果没有视频帧，是仍播放音频、接受暂时失同步，还是连音频也不播放？
- 如果音频已经播放，晚些才到的视频还要不要播放，还是直接丢弃？
- 为恢复同步，是否应加快后续播放？是否应跳过一些帧，让画面以一次跳跃追上音频？

这些选择体现了质量与延迟之间的权衡：等待更多数据可能改善同步和连续性，却会增加延迟；丢帧或加快播放可以追回时间，却会让用户感知到跳跃。课程指出，其中许多决策由抖动缓冲区处理。

### 排查唇同步问题的三个方向

课程列出了三类成因：

1. **浏览器实现缺陷。** 课程讲师回忆，在此前约两年的某个时期，Linux 上的 Chrome 曾在其设备上持续出现这类问题，后来得到修复。这是课程中的历史案例，不代表其他时期或平台的固定状态。
2. **采集和播放设备。** 设备采集、播放媒体的方式及其自身耗时，也会影响同步计算。
3. **中间媒体服务器。** SFU、MCU、录制引擎或其他路由设备可能处理时间戳、延迟发送或改变传输中的媒体。这些操作都可能影响唇同步，也是部署自有媒体服务器时需要重点检查的部分。

## 声学回声消除与相关语音算法

### 声学回声是怎样形成的

这里讨论的是**声学回声消除（Acoustic Echo Cancellation，AEC）**。它主要处理开放扬声器和麦克风共同使用时形成的声音回路，而不是耳机已经把声音输出与麦克风清楚隔开的情况。

一个典型过程如下：

1. 远端用户说话，其音频经网络到达本地浏览器。
2. 本地扬声器把远端声音播放到房间中。
3. 扬声器播放的声音在房间内传播、反射，再次被本地麦克风采集。
4. 麦克风同时采集本地用户声音和这段远端声音，本地浏览器把混合后的音频编码并发回远端。
5. 远端用户因此再次听到自己刚说过的话，形成回声。

所以，**听到回声的人通常不是制造回声的一端**。如果某位参与者报告自己听到回声，问题往往来自通话中另一位使用开放麦克风和扬声器的参与者，而不是报告者本人。

声学环境也会改变回声严重程度。玻璃窗，甚至玻璃门、玻璃墙较多的房间会产生更强反射和混响，使回声条件更差。

### 硬件与软件 AEC

WebRTC 中的 AEC 可以有两类实现：

- **硬件实现**：例如课程提到的 iOS 或 iPhone 设备自带 AEC，WebRTC 最终会使用设备提供的能力。
- **软件实现**：由软件算法完成回声消除，并需要适应设备和运行环境的差异。

课程回顾，在此前约两三年的某个版本中，Google 曾更新、改进甚至替换 WebRTC 的 AEC 算法，使其更动态，并能适应 Android 的实时处理特点。这里同样应作为课程中的历史描述理解。

Android 带来的第一个难点是实时性。设备驱动以及通过 Java 代码访问麦克风、扬声器的过程，距离 AEC 所依赖的实时分析和实时假设较远。AEC 需要根据声音采集与播放的时间关系工作，因此课程所述的重新实现必须把这种运行环境考虑进去。

第二个难点是设备差异。AEC 与麦克风、扬声器之间的位置关系有关，可以针对特定设备进行设计；但 Android 设备种类繁多，硬件、设备驱动、芯片组和软件差异很大，难以用一套固定的设备假设覆盖所有情况。

因此，算法需要动态调整参数，适应它判断出的实际场景。课程给出的体验示例是：通话最初两三秒可能听到一些回声，随后回声自行减弱或消失，这可以对应算法逐步调整的过程。

### 其他语音处理算法

除 AEC 外，课程还列出了几种常见语音算法：

| 算法 | 作用 |
| --- | --- |
| 噪声抑制（noise suppression） | 抑制房间或周围环境中的噪声，使其不那么容易被听见 |
| 舒适噪声生成（Comfort Noise Generation，CNG） | 没有人说话时填充适度舒适噪声，避免线路听起来像已经中断；其作用几乎与单纯消除一切声音相反 |
| 语音活动检测（Voice Activity Detection，VAD） | 检测语音活动，课程指出它主要被 IVR 系统使用 |
| 增益控制（AGC） | 尽量补偿人与麦克风之间距离的变化，使距离改变后仍能维持相近的听感音量 |

这些算法说明，语音质量并不只取决于编码器。采集后的声音是否含有回声、噪声，静默是否自然，以及说话者移动后的音量是否稳定，都需要相应处理。

## 带宽估计：让发送码率适应动态网络

### 要估计的不是标称带宽，而是当前可发送量

可以把设备之间的网络想象成一根虚拟管道。管道当前可用于传输数据的空间，对应可用带宽或能够发送的码率。实时媒体必须回答：每秒可以发送多少比特、千比特或兆比特，而不因发送过量造成数据丢失或延迟？

文件传输可以把数据排队，等待其最终到达另一端；实时对话却不能无限等待，因为语音和视频必须及时发生。如果媒体数据已经超过管道可容纳的量，就不能继续按原码率硬塞进去。

标称速率也不能直接替代估计。课程举例说，家中 ADSL 标称下载速率可以达到 100 Mb/s，这个数字听起来很好，但不代表每次测量、每个时刻都能实际得到同样速率。带宽具有动态性，发送方需要不断估计当前情况。

### 带宽为什么会变化

课程把原因分为本地因素、信号或接收条件，以及外部因素。

**本地因素**来自同一连接上的其他活动：

- Google Drive、Dropbox 等云存储服务会自动上传或下载文件；
- Android 手机使用 Google Photos 时，照片可能在连上家中 Wi-Fi 后自动上传；
- 同一网络中的其他设备可能正在播放 YouTube 视频、同步电子邮件或浏览 Facebook。

这些活动都会消耗有限带宽。即使通话设备本身没有改变，只要同一互联网连接上出现其他流量，可用于通话的码率就可能波动。

**信号和接收条件**也会改变线路质量。Wi-Fi 信号、以太网网线问题等都可能影响带宽；设备远离 Wi-Fi 接入点，就是一个会降低码率并增加延迟的例子。

**外部因素**包括服务器拥塞、服务器负载过高，以及媒体路径上的流量拥塞。服务器负载过高时，可能无法按发送方期望的速度接收数据。即使本地连接很好，从所在区域到目的地的某段共享线路发生拥塞，也仍会限制实际传输能力。

### 最基本的丢包驱动估计流程

课程先用一种简单、朴素的方法说明码率调节：

1. 按当前码率发送媒体数据。
2. 检查是否出现丢包。丢包可能表明发送量已经超过网络当前承受能力。
3. 如果出现丢包，就降低发送码率。
4. 以较低码率继续运行几秒，再检查网络状况。
5. 如果不再出现丢包，可以尝试重新提高码率。
6. 重复这一过程，让发送码率随网络状况上下调整。

这一流程容易理解，却有明显缺陷：**如果一直等到丢包才开始调整，损害已经发生。** 对视频而言，丢失一个关键数据包后，恢复可能需要较长时间。课程指出，旧系统中的丢包会造成持续数秒的视频故障或停顿；新系统也可能出现类似现象。因此，理想目标不是把丢包当作正常调节依据，而是尽量避免走到丢包这一步，或至少不只依赖丢包进行估计。

### 改进方向：调节速度与估计位置

课程从两个角度讨论更好的估计。

一是**更快地降低和提升码率**。遇到丢包时，更快回到网络实际可承受的码率；网络恢复后，也更快提升发送码率。提升速度直接影响视频多快能从较低质量恢复到较高质量。

二是**选择估计在哪一侧完成**。课程所述时期，多数带宽估计算法采用接收端估计：

- 发送端发出数据；
- 接收端根据自己实际收到的数据判断丢包等情况并进行估计；
- 接收端把结果告知发送端，发送端再改变码率。

这种方式要求通话双方能够配合：要么了解或使用相同的算法，要么至少具备传递码率变化信息的能力。

与之相对的是发送侧的本地估计。其特点是估计过程不必依赖对端实现同一种算法，因而可以独立运行。课程提到，当时的 WebRTC 在近期版本中开始采用这种方式，讲师记忆中的起始版本为 57。该版本信息应作为课程录制时的说明，而不是对后续实现的持续描述。

### 两组码率爬升示例

课程用测量结果说明，最终稳定码率并不是唯一值得观察的指标，**达到稳定码率花了多长时间**同样重要。

第一组是课程展示的 Chrome 通话测量，讲师同样将版本回忆为 57。发送码率从零上升，超过 2 Mb/s，并在大约两秒后稳定在 2.5 Mb/s 左右。也就是说，示例中的 WebRTC 用一两秒判断出至少可以使用约 2 Mb/s，并按这一能力发送数据。如果要发送高清、高质量视频，这种爬升速度很重要，否则通话开始后的较长时间内都只能保持较低质量。

第二组是课程使用 testRTC 测试的一台媒体服务器。其码率最终相当稳定，达到约 1.3 Mb/s 附近，但缓慢爬升耗费了约 30～35 秒。与最终数字相比，这段长时间的爬升过程更容易解释用户为什么在通话初期迟迟得不到理想质量。

因此，检查媒体服务器时，不应只看稳态码率，还要观察：

- 码率上升和下降有多快；
- 使用了怎样的带宽估计机制；
- 视频质量需要多久才能随网络恢复。

## 抖动缓冲区：用受控延迟换取可播放性

### 网络中的四类问题

抖动缓冲区面对的是混乱、不可预测的网络，课程在回顾 RTP、RTCP 时列出了四类典型问题，在 UDP 传输中尤其值得关注：

1. **丢包**：某个包没有到达。例如编号为 2 的包丢失。
2. **重复**：同一个包被接收两次。课程示例中，2 号包只发送了一次，却被收到两次。
3. **乱序**：包没有按发送顺序到达。例如 4 号包先于 3 号和 2 号包到达，3 号包又先于 2 号包到达；播放前必须重新确定顺序。
4. **抖动**：发送端大约每 20 ms 发出一个包，但接收端看到的包间隔不再稳定保持 20 ms，到达节奏变得不均匀。

丢包、重复、乱序和抖动是不同问题，不能只用“网络慢”概括。抖动缓冲区尤其需要根据到达时间和播放时间处理其中的乱序、丢失与间隔变化。

### 从网络延迟到缓冲区延迟

可以把路径分为三段：

**发送端 → 网络 → 接收端 → 抖动缓冲区 → 播放。**

其中有两种不同延迟：

- **网络延迟**：数据包从发送到接收所花的时间。抖动缓冲区无法消除这段已经发生的延迟；只能在某些情况下通过优化服务器、部署位置和网络路由等后台条件改善路径。
- **抖动缓冲区延迟**：包已经到达接收端后，到真正播放之前再等待的一段时间。

第二段延迟是主动加入的。它首先可以配合唇同步，其次为处理抖动、丢包和乱序留下时间。没有这段时间，接收端只能按混乱的到达节奏立即播放；等待过多又会损害实时性。因此，缓冲区的核心不是“越大越好”，而是用可接受的额外延迟换取更连续、有序的播放。

### 课程示例中的处理过程

课程用一串存在抖动、乱序和丢失的数据包说明播放决策：

1. 第一个包到达后，并不立刻播放，而是在缓冲区等待一段时间，由此建立初始播放余量。
2. 后续包可以使用不同的缓冲等待时间，补偿到达间隔的变化，使播放节奏重新趋于连续。
3. 对在网络中交换了顺序的包，在播放前恢复正确顺序。
4. 遇到已经丢失、无法及时补齐的包时，播放过程需要以某种方式跳过它，不能永远停下等待。
5. 如果那个包后来终于到达，但其应播放的时刻已经过去，接收端无法回到过去重新播放，只能继续向前。此时即使已经收到该包，抖动缓冲区也会因它到达太晚而将其丢弃。

最后一个决策尤其重要：**晚到的数据不等于仍然有用的数据。** 实时媒体有明确的播放时点，错过时点的包可能只能被舍弃。缓冲区通过排序、等待、跳过和丢弃，把不稳定的包到达过程转换成可以继续向前的播放过程。

### 自适应抖动缓冲区

网络状况会在通话期间变化，固定的初始延迟无法始终合适。**自适应抖动缓冲区**会根据实际接收到的数据和网络状况，在通话过程中动态调整延迟：

- 网络状况允许时，可以降低缓冲延迟，减少等待；
- 抖动等问题需要更多处理余量时，可以增加缓冲延迟。

这里仍然存在同一个权衡：较低延迟有利于交互，较高延迟则为应对网络变化留下更多空间。自适应的意义，是让这一选择随实际状况变化，而不是在通话开始前固定下来。

## 小结

WebRTC 的媒体质量由多组算法共同维持。音频、视频独立编码和传输带来流选择与组合的自由，也要求接收端依据采集时间戳完成唇同步；AEC 处理扬声器声音被麦克风再次采集形成的回声，并需要适应实时性和设备差异；带宽估计根据动态网络调整码率，评估时既要看稳态码率，也要看升降速度；抖动缓冲区则用主动、可调整的播放延迟处理乱序、丢包和抖动，过晚到达的包仍会被丢弃。

这些机制共同体现了实时媒体中的基本取舍：等待可以提高同步与连续性，却增加延迟；提高码率可以改善质量，却不能超过当前网络能力；丢帧、跳过或丢弃迟到数据会损失部分内容，却能让播放继续向前。理解这些流程，才能更准确地定位浏览器、设备、媒体服务器和网络分别对通话质量造成了什么影响。
