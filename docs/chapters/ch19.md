# 第 19 章 实时 Web 与 XMPP

实时 Web 的核心，是把浏览器变成一个能够双向通信、且延迟足够低的应用端点。Jack Moffitt 在本章的课程中以 XMPP 和 JavaScript 库 Strophe.js 为主线，说明如何在仍以 HTTP 为主的浏览器环境中建立有状态连接、交换协议消息，并构建协作应用。内容从 XMPP 的网络模型和 XML 消息结构开始，一直延伸到 BOSH、长轮询、事件处理、插件、身份验证以及实际部署。

本章保留课程所描述的技术背景。其中若干产品、浏览器限制和未来规划都属于演讲当时的情况，阅读重点应放在协议结构、工程取舍和实现方法上。

## 实时 Web 为什么需要新的通信方式

### HTTP 轮询的困境

HTTP API 和 REST API 能完成大量工作，但普通轮询并不适合低延迟交互。假设页面希望尽快显示最新动态，就只能反复询问服务器：“有新消息吗？”多数时候答案是否定的，课程用“约 95% 的请求没有新内容”来形容这种浪费。

如果降低轮询频率，新消息到达后就要等待更久才能被客户端发现；如果提高频率，又会产生大量空请求。对于聊天、协作或快节奏游戏，客户端需要接近对话式的响应速度，单纯不断拉取数据很难同时兼顾低延迟与效率。

XMPP 提供了另一种模型。HTTP 请求通常是无状态的，而 XMPP 在底层维持长期的 TCP 连接，并在此之上保留会话状态。服务器不必等客户端再次询问才知道它需要数据，连接建立后即可按照协议语义双向传递消息。接下来的问题便是：浏览器没有直接暴露这种任意长期 TCP 会话时，怎样继续使用 XMPP？BOSH 和 Strophe.js 正是课程给出的答案。

### XMPP 不只用于即时消息

XMPP 的全称是可扩展消息与在线状态协议（Extensible Messaging and Presence Protocol）。它于 1999 年由 Jeremie Miller 等人开始开发，早期目标是挑战 AOL、Yahoo 等封闭的即时通信系统。课程还特别提到，当时的 Gmail/Google Talk 用户实际上已经在使用 XMPP，即使他们并未意识到自己接触了这个协议。

即时消息只是 XMPP 的起点。通过扩展，它可以表达：

- 发布—订阅（PubSub）；
- 临时命令（ad hoc commands）；
- XML-RPC；
- 多人聊天、服务发现；
- 文件传输和多媒体会话等更复杂的功能。

因此，不能把 XMPP 简化成“聊天文本协议”。讲师开发的大多数 XMPP 应用甚至与传统即时消息无关；真正有价值的是一套有状态连接、可路由消息、在线状态和可扩展协议语义的组合。

## XMPP 的联邦网络与地址

### 客户端到服务器、服务器到服务器

XMPP 网络以开放方式联邦，整体形态类似电子邮件，但消息路径更直接。

- 客户端通过**客户端到服务器协议**连接自己的 XMPP 服务器。
- 大量客户端可以同时连接同一台服务器。
- 两台服务器通过略有不同的**服务器到服务器协议**互联。
- 多台服务器可以继续组成联邦，每台服务器都服务自己的客户端群体。

如果服务器 A 上的用户向服务器 B 上的用户发送消息，A 会把消息转发给 B，再由 B 交给目标用户。与电子邮件不同，这里不需要经过一连串中间转发节点：发送方服务器直接连接对端服务器。

课程还强调了这种模型的来源约束。服务器可以伪造自己域内的本地用户，但不能据此任意伪造其他服务器上的用户；收到来自某台服务器的消息时，接收方能够确认其服务器来源。这一机制减少了 SMTP 式伪造来源所带来的一类问题，但并不意味着本地服务器本身永远可信。

### JID、bare JID 与 full JID

XMPP 地址称为 JID（Jabber ID），外形与电子邮件地址相似，可以有三种典型粒度：

| 地址形态 | 作用 |
| --- | --- |
| `domain` | 最简单的地址，通常表示服务器或服务所在域 |
| `user@domain` | **bare JID**，标识域中的一个用户 |
| `user@domain/resource` | **full JID**，在裸地址后增加资源，标识该用户的一条具体连接 |

资源用于区分同一账号的多条连接。例如，家庭环境中的连接可以使用 `home`，工作环境使用 `work`。某些服务会生成看似随机的资源字符串；资源具体叫什么并不重要，关键是它能唯一地区分连接。

消息可以发送到 full JID，也可以发送到 bare JID、域或其他由扩展定义的实体。这个地址体系使用户、设备连接、服务器和扩展服务都能进入同一套路由模型。

## XML 流与三类 stanza

### XML 流不是一次性发送完整文档

XMPP 基于 XML，但它不是每发一条消息就单独传输一份完整 XML 文档，而是使用 **XML 流**。

连接建立时，双方分别打开根元素。之后，消息作为根元素的第一层子元素持续写入。连接结束时，再关闭根元素。因此：

- 从整个连接的生命周期看，两个方向各自形成一份完整、有效的 XML 文档；
- 在连接进行期间，应用实际处理的是一个个第一层子元素，即 **XML stanza**。

可以把 stanza 理解为协议的基本消息单元。XMPP 主要有 `message`、`presence` 和 `iq` 三类。

### `message`：聊天文本与任意数据

`message` 是最直观的一类 stanza。普通聊天消息通常包含：

- `from`：发送者。一般用户消息使用 full JID，服务器消息等情形可能不同；
- `to`：接收地址，可以是 bare JID、full JID、域等；
- `type`：消息类型，私聊常用 `chat`，群聊使用 `groupchat`，还有 `headline` 等类型；
- `body`：聊天正文。

`body` 并不是所有 `message` 都必须具备的内容。非聊天应用可以携带完全不同的结构化数据。因此，同一类 stanza 既能承载聊天，也能承载棋步、协作事件或自定义业务消息。

### `presence`：在线状态与订阅关系

`presence` 用来表达在线、离开、忙碌、勿扰等状态。课程把它形容为一种小型发布—订阅系统：状态不是只写在个人资料里，而会传播给订阅了该状态的联系人。

阅读状态时要区分两个概念：

- `show` 的取值有限，用来提示客户端应怎样展示状态，例如离开或勿扰；
- `status` 是自由文本，可放类似社交网站状态更新的说明。

未声明特殊类型时，基本语义是可用。课程示例用离开状态说明这些字段，不应把自由文本与预定义的展示状态混为一谈。

查看他人状态之前通常需要建立订阅。若要把某人加入自己的联系人列表（roster），一方先发送在线状态订阅请求，对方可以接受或拒绝。订阅关系具有方向性：

- A 可以订阅 B，而 B 不订阅 A；
- 双方也可以互相订阅；
- 是否能看到状态，取决于相应订阅是否得到允许。

这与单向关注的社交关系很相似，而不是强制对称的好友关系。

### `iq`：带请求—响应约束的信息查询

IQ 表示 Info/Query，语义接近 HTTP 的请求—响应操作：

| `type` | 语义 |
| --- | --- |
| `get` | 查询信息，类似 HTTP GET |
| `set` | 设置或修改数据，更接近 HTTP POST |
| `result` | 成功响应 |
| `error` | 错误响应 |

每个 IQ 请求都必须带有在当前流中唯一的 `id`。响应必须复用同一个 `id`，客户端据此把响应与原请求配对。三类主要 stanza 中，IQ 是明确要求响应的一类。

许多 XMPP 扩展在 IQ 内放置 `query` 子元素，并用 XML 命名空间说明正在使用哪一种扩展协议。课程中的服务发现示例就通过这种方式请求实体的信息；响应会返回该实体的身份（identity）和能力特性（feature）列表。XMPP 服务器可能支持很多特性，因此响应列表可以很长。网络上的不同对象也可以对服务发现查询给出不同答案。

课程为演示简化过部分命名空间文本，重点应放在 `id` 配对、`get`/`result`/`error` 流程和命名空间选择扩展协议这三个机制上。

## 浏览器中的 XMPP：BOSH 与长轮询

### 已经在使用这类模型的应用

课程列举了若干当时的实时网站，以说明 XMPP 并不局限于桌面聊天客户端：

- **ChessPark**：讲师团队开发的在线国际象棋网站；
- **Drop.io**：每个协作空间对应一个多人聊天室，把文件拖入浏览器分享时，系统向房间发送 XMPP 消息，空间内所有人都会收到文件事件；
- **Presently 与 Yammer**：利用这种实时更新机制保持站点首页动态。

这些应用的共同点不是界面相似，而是浏览器需要持续接收服务器事件，并且事件类型会随着业务扩展。

### 普通轮询与长轮询的区别

普通轮询的过程是：

1. 客户端发送请求：“有新消息吗？”
2. 服务器立即回答：“没有。”
3. 客户端等待一段时间，例如一分钟。
4. 客户端再次发起请求，如此反复。

长轮询把服务器的即时空响应改成有等待的响应：

1. 客户端仍然发出询问。
2. 如果暂时没有新数据，服务器不立即结束请求，而是尽量保留它。
3. 一旦新数据到达，服务器立刻用该请求返回数据。
4. 如果等待一段时间仍无数据，服务器返回空响应；客户端随即重新发起等待请求。

这样，请求会在服务器端保持较长时间，但新事件出现时不必等下一次轮询。它是在 HTTP 约束下实现低延迟双向通信的一种办法。

客户端仍要主动管理请求。例如，一个请求正在等待服务器数据时，客户端可能突然需要发送自己的数据。课程描述的机制会在客户端发出新请求时释放旧请求。由于当时多数浏览器可用请求数量通常只有两个，实现需要在它们之间交替使用，既保留接收通道，又能发送数据。

### BOSH 的作用

BOSH 的全称是 Bidirectional-streams Over Synchronous HTTP，即“基于同步 HTTP 的双向流”。课程把它概括为长轮询的一种正式协议化形式：浏览器通过 HTTP 请求交换数据，BOSH 层再把这些请求映射到有状态的 XMPP 通信。

BOSH 与 Comet 都属于当时实现浏览器双向低延迟通信的技术路线。也有团队自行编写长轮询和自定义协议，而不采用 Comet 或 BOSH；课程提到 CouchDB 团队当时就在进行类似工作。它们解决了相近的传输问题，但上层协议语义并不相同，后文还会比较。

## Strophe.js：把长轮询隐藏在有状态 API 之后

### 两个演示揭示的实时性

课程首先展示了一个群聊应用。用户输入内容后，文本并不是只在本地直接显示，而是要等服务器把刚输入的消息发回来再显示在屏幕上。输入能够立即出现，说明整个“发送到服务器—服务器分发—客户端收到”的回路延迟很低。界面同时还能显示自己的在线状态和房间中的其他成员。

ChessPark 的要求更严格。该服务当时最受欢迎的对局速度，是双方各自在一分钟内完成全部棋步，因此消息延迟必须足够低。它的初始页面本身就是一个完整的 XMPP 客户端：

- 左侧显示 roster；
- 私聊和群聊位于另一侧；
- 中间列出正在寻找对手的对局；
- 对局开始后，相应条目会立即从列表消失；
- 用户还可以观看正在进行的游戏。

这些动态界面直接使用 JavaScript 中的 XMPP API 构造并发送协议消息。开发者不需要处理每一次长轮询，看到的仍是一个类似桌面客户端的真实有状态 XMPP 连接。BOSH 的传输细节被库隐藏了。

### Strophe.js 的设计目标

Strophe.js 是讲师为在浏览器中使用 XMPP 而编写的 JavaScript 库，主要用于实现 XMPP 客户端。通过浏览器和 BOSH 编写 XMPP 服务器并不是它的目标，协议本身也不适合这种用法。

库的主体使用纯 JavaScript。课程当时还讨论了借助不可见的 Flash 组件和相应的 XHR 方案实现跨域，这是特定时代浏览器能力下的选择，不应与核心 XMPP 协议混为一谈。

Strophe.js 强调完整文档和边界情况处理。这里的“高度优化”并不只是追求最快的 XHR，而是处理大量 XML HTTP 请求时容易忽略的失败模式：

- XHR 能识别 404、500 等 HTTP 状态；
- 如果代理服务器丢弃请求、始终没有返回数据，普通错误码不足以描述问题；
- 如果服务器也始终不回应，客户端必须主动检测“本应收到数据却没有收到”的状态；
- 不设置合理超时，可能让请求等待代理自身的长时间超时，课程以约九分钟为例，期间用户无法继续正常交互。

因此，库中大量复杂工作都用于 XHR 错误处理，而不是单纯构造聊天消息。只有正确处理无响应、超时和连接状态，长轮询才能维持低延迟体验。

课程还列举了当时的实际验证和使用情况：ChessPark 已使用约三年半，库能在 Wii 和 iPhone 上运行，也有人把它用于 Adobe AIR 应用。除 ChessPark 外，实时搜索项目 Stanzic（后来称为 Collecta）、群聊应用 Speek，以及在 Neuros OSD 字幕区域加入聊天功能的应用都使用过它。这些例子说明同一个协议栈可以服务游戏、搜索、协作和嵌入式界面。

## 用 Strophe.js 管理连接

### 创建 BOSH 连接

每个 XMPP 客户端首先需要连接对象。课程给出的核心调用形式是：

```javascript
var connection = new Strophe.Connection(boshUrl);
connection.connect(jid, password, onConnect);
```

`boshUrl` 是 BOSH 连接管理器的地址，可以由服务提供者给出，也可以由开发者自行部署。`connect` 接收用户名、密码和连接状态回调；每当连接、认证或错误状态发生变化，回调都会被触发。

如果只提供 `user@domain`，服务器会为连接分配资源，从而形成 full JID。客户端也可以显式传入希望使用的资源。

库还支持 SASL ANONYMOUS 匿名认证。匿名连接不要求普通的用户名和密码，服务器为访客提供可与服务交互的会话。Speek 的示例流程是：用户首次访问时先匿名登录，无须注册即可使用服务；用户后来决定注册时，再把连接升级为经过认证的连接。这让“立即试用”和“正式身份”可以处在同一套实时协议中。

### 连接成功后做什么

状态回调最重要的任务之一是等待已连接状态。连接成功后，典型初始化动作包括：

1. 向服务器发送初始 `presence`，表明客户端已经在线；
2. 查询 roster；
3. 根据应用需要注册消息和 IQ 处理器；
4. 查询服务或执行其他初始化操作。

发送数据使用 `connection.send()`。课程强调发送结构化 XML/DOM 对象，而不是让调用者随意手工拼接字符串。如果忘记转义特殊字符，产生无效 XML，XMPP 连接可能直接被断开。让库接收规范的 DOM 结构，可以把这类格式问题限制在发送之前。

结束连接则调用 `connection.disconnect()`。连接、发送、断开本身并不复杂，应用的主要逻辑集中在事件和 stanza 处理上。

## 事件驱动的编程模型

XMPP 应用与多数 UI 程序一样，是事件驱动的。课程区分了三类事件：

- **交互事件**：例如用户点击发送按钮，可以用 jQuery 或其他 UI 库捕获，随后构造并发送 stanza；
- **定时事件**：Strophe.js 当时提供了对 `setTimeout` 的一致包装，也可以使用 jQuery 或其他工具；
- **stanza 事件**：连接收到符合条件的 XML stanza 时，触发相应回调。

定时包装有历史原因：Strophe.js 最初编写时 jQuery 尚未出现，因此库自己保留了一些后来可以交给通用工具完成的辅助功能。

### 用 `addHandler` 匹配消息

处理器通过 `connection.addHandler()` 注册，并指定希望匹配的 stanza 类型和条件。例如，只处理 `type` 为 `chat` 的 `message`。每当连接检测到匹配项，就调用类似 `onMessage` 的回调。

回调收到的是消息对应的 DOM 元素，应用可以提取 `body`、读取属性，再把内容显示在界面上。回调的返回值决定处理器生命周期：

- 返回 `true`：保留处理器，以后继续接收匹配消息；
- 返回 `false`：移除处理器；
- 返回 `null`：在课程的一次性 IQ 示例中，也起到类似 `false` 的效果。

持续聊天处理器应当保留；只等待一次特定响应的处理器则应在完成后移除。

### 处理 IQ 的两个方向

收到别人发来的 IQ 请求时，客户端必须按协议返回结果或错误。例如，对 `jabber:iq:version` 的 `get` 查询是在询问客户端软件版本。应用可以注册对应 IQ 处理器，构造响应并返回。

自己发送 IQ 时，则要等待对方的响应。通常步骤是：

1. 创建流内唯一的 IQ `id`；
2. 发送 IQ；
3. 注册能匹配该 `id` 的处理器；
4. 在响应到达时处理 `result` 或 `error`。

监听响应时不能只假设成功，因为响应类型可能是 `result`，也可能是 `error`。可以为两种情况分别注册更精确的处理器，也可以在同一处理器内分支处理。讲师更倾向于让匹配条件尽可能具体，以避免无关消息进入同一套逻辑。

## 使用 Strophe.Builder 构造 stanza

直接操作 DOM API 比较繁琐，因此 Strophe.js 提供了受 jQuery 启发的 `Strophe.Builder`。它的大多数方法都返回构建器自身，从而支持链式调用。

### 基本构造操作

可以从 `new Strophe.Builder()` 创建 stanza 根元素并传入属性，再使用以下操作：

| 操作 | 用途 |
| --- | --- |
| `c()` | 添加带名称和可选属性的子元素 |
| `t()` | 添加文本节点 |
| `cnode()` | 插入一个已经存在的 DOM 子节点，例如复用收到消息中的某部分 |
| `attrs()` | 修改属性，适合在已有基础 stanza 上补充 `to` 等信息 |
| `up()` | 回到树的上一层，以便继续创建兄弟节点 |

链式构造会沿子节点向下移动。例如，创建 `message` 后调用 `c("body")`，再调用 `t("Hello World")`，就形成带正文的聊天消息。若还要在 `message` 下添加另一个与 `body` 同级的扩展子元素，必须先 `up()` 返回上层。

课程的复杂示例正是这样构造 XHTML-IM 内容：先建立普通正文，再返回上层，添加遵循 XHTML-IM 的 `html` 子树，并在其中建立相应的 `body`、`p` 等节点。这使同一条 XMPP 消息既能保留标准文本正文，也能携带富文本表示。

### 便捷函数与终止链式调用的操作

反复书写 `new Strophe.Builder` 很长，因此库提供：

- `$msg()`：构造 `message`；
- `$iq()`：构造 IQ；
- `$pres()`：构造 `presence`。

这些函数可以同时设置基本属性。`$pres()` 本身就能形成课程所说的最短有效 presence stanza。

并非所有构建器方法都适合继续链式调用：

- `toString()` 把 DOM 序列化为字符串，便于查看或记录；
- `tree()` 类似 jQuery 的取值操作，返回实际的顶层 DOM 树。

理解“构建器”“字符串”和“DOM 树”三种返回形态，可以避免在链式调用中误用结果。

## 完整示例：查询服务器的服务发现信息

课程用一个完整小应用把上述内容串起来。用户输入服务器地址并点击连接后，页面连接 XMPP 服务器、查询它支持的功能，然后把身份和特性输出到页面。演示连接的是本机的 ejabberd 服务器，返回结果包含不少 PubSub 特性。

### 连接与协议日志

界面用 jQuery UI 组织标签页，并把连接按钮绑定到处理函数。处理函数先阻止表单默认提交行为，再创建 `Strophe.Connection`。

连接对象设置了 `rawInput` 和 `rawOutput` 原始输入、输出日志回调。Strophe.js 每当通过连接接收或发送数据时都会调用它们，因此可以直接用于协议调试。演示日志依次显示：

1. 建立连接的初始 BOSH 数据；
2. 认证相关内容；
3. 发往 localhost、`disco#info` 服务发现查询的 IQ `get`；
4. 服务器返回的 IQ；
5. 客户端处理结果后断开连接的状态。

因为这里使用匿名连接，所以密码参数为空。服务器地址则从表单字段读取。

### 状态回调与一次性 IQ 处理器

连接状态回调只处理已连接和已断开两种情况：断开时输出信息；连接时注册等待服务发现结果的处理器，构造 IQ 并发送。

该处理器主要依据之前生成的唯一 IQ `id` 来识别响应。演示只匹配 `result`，没有处理 `error`，因此若服务器返回错误，页面不会执行成功结果逻辑。课程特别指出，实际应用可以增加单独的错误处理器，或在一个处理器中同时处理两种响应。

结果回调收到 DOM 对象后，使用 jQuery 提取数据：

- 找出所有 `identity` 节点，生成身份表格；
- 找出所有 `feature` 元素，生成特性列表；
- 把结果写入指定区域；
- 调用 `connection.disconnect()`。

这个 IQ 处理器只使用一次，完成后返回 `null`，使其自动移除。由于新的 IQ 必须使用新的唯一 `id`，同一个响应也不会再次合理匹配该处理器。

真实应用会同时保留很多处理器。ChessPark 就分别处理私聊、群聊、收到棋步、自己发出棋步等不同事件。服务发现示例虽然短，却已经包含真实客户端的基本骨架：连接状态、消息匹配、请求—响应关联、DOM 解析和连接释放。

## 通过命名空间与插件扩展协议

### 自定义业务 stanza

XMPP 的可扩展性允许应用在消息中插入新的命名空间内容。ChessPark 要传输棋步时，不需要修改基础 `message` 的定义，只需为棋步 stanza 建立专用命名空间，再把相应元素放入消息。

当时已经有数百个 XMPP 扩展，覆盖范围很广：

- 多人聊天和服务发现被广泛使用；
- SOAP over XMPP 等扩展使用者很少；
- Jingle 用于多媒体会话；
- 还有大量面向其他特定场景的协议。

扩展生态的价值不只是“已有功能可以直接调用”。面对复杂应用场景，开发者可能仍需编写实现代码，却不必独立设计协议并穷举所有边界情况。协议设计和互操作讨论已经由社区完成，实现协议通常比重新设计一套协议容易得多。

### Strophe.js 插件结构

Strophe.js 核心 API 很小，因此需要插件承载扩展的高级操作。例如：

- SOAP 插件可以提供类似 `soapSend` 的简单函数；
- PubSub 插件可以直接提供 `subscribe`；
- 调用者不必每次手工构造订阅 IQ，也不必在所有业务代码里重复处理错误分支。

插件基础设施主要提供两种能力：

1. **添加命名空间**：每个扩展使用自己的命名空间。插件注册后，构建消息时不必反复书写完整字符串，例如 XHTML-IM 的命名空间可以集中管理。
2. **添加连接插件**：通过 `addConnectionPlugin` 提供插件名称和实现对象。连接初始化时，插件也被初始化，并成为连接对象上的一个新属性。`subscribe` 等高级方法便可以封装在这个对象中。

由此，核心库继续负责连接和 stanza，扩展协议则以插件形式附着到每条连接上。

## identi.ca 扩展示例：从机器人消息到可点击内容

课程还演示了一个简单的 identi.ca 客户端。identi.ca 当时提供 XMPP 机器人，可以把微博消息发送给用户，类似 Twitter 曾经提供、后来取消的机器人能力。

演示使用 Gmail 凭据登录，因为 identi.ca 消息都被转发到该账号。连接建立后，客户端发送初始 presence，注册传入消息处理器，并进入等待消息状态。登录过程中还能看到 roster 中各联系人发来的能力信息，例如对方是否有音乐信息可以分享。

当 identi.ca 消息到达时，处理器把消息加入页面列表。发送操作则由按钮交互事件触发：构造 stanza，再调用 `connection.send()`。整个流程与服务发现示例相同，只是这里保持连接持续接收消息，而不是查询一次后断开。

演示中的消息使用 XHTML-IM，因而正文里能包含指向个人资料页面的可点击链接。接收端用 jQuery 找到目标区域，提取消息中的 HTML 表示并插入页面。这个例子同时说明了三点：

- 扩展可以带来富文本，而不必替换普通消息框架；
- 机器人与真实用户使用同一消息通道；
- 一个处理器负责持续事件，交互事件负责主动发送，两者共享同一连接。

## 身份验证与当时规划的改进

### SASL 认证方式

课程当时列举的认证能力包括：

- SASL ANONYMOUS；
- DIGEST-MD5；
- PLAIN；
- 某些服务器支持的 SASL EXTERNAL。

SASL EXTERNAL 可以接入 Kerberos 等外部认证机制；Google 当时也把相关机制用于自己的即时通信令牌认证。重点是 Strophe.js 所在的 XMPP 栈能接纳不同 SASL 机制，而不是把所有服务都限定为同一种用户名密码流程。这些选项是演讲时期的能力说明，并非对现代部署安全性的排名或建议。

### 更精确的 XPath 匹配

讲师当时希望为 Strophe.js 增加 XPath 匹配。原有 `addHandler` 需要四到五个匹配参数，约束方式有限；若可以直接写 XPath，就能精确指定 stanza 条件，例如同时限定来源域和 `type='chat'`。

这种写法不仅更简洁，也能减少误匹配：无关消息不会先进入宽泛处理器，再由业务代码逐一过滤。实现难点在于，普通 DOM XPath 功能不能直接用于尚未挂入完整文档树的部分 DOM 元素，而流式接收的 stanza 正具有这种特点。因此，课程把它列为仍在开发的方向，而不是已经完成的特性。

### 多标签页与多会话同步

如果一个标签页已经建立 XMPP 连接，用户又打开新标签页，浏览器中就可能出现两条连接。应用需要让它们保持一致状态，否则消息、在线状态和 UI 状态可能彼此脱节。

课程当时计划扩展 BOSH 来处理多会话问题，使各标签页能够共享一致状态，而不必依赖复杂且脆弱的黑客技巧。这里的关键问题不是“能否再连一次”，而是多个浏览器上下文如何表达同一会话的协调关系。

## 问答一：XMPP 与 Comet 怎样选择

按讲师在问答中的划分，Comet 主要提供发布—订阅语义：客户端订阅某个路径，随后接收该路径上的事件。XMPP 的 PubSub 可以完成这类工作，presence 也具有类似的订阅传播特征。

两者的传输目标相近，都是双向、低延迟通信；差别主要在上层已经定义了多少协议语义。除 PubSub 外，XMPP 扩展还覆盖 I/O 数据交互、文件传输等能力。若在 Comet 上实现同等功能，往往需要自己在发布—订阅语义之上继续设计新协议。

因此，课程给出的判断是：

- 需求非常简单、确实只需要 PubSub 时，Comet 是合适选择；
- 如果应用很快会增加文件传输或更复杂的交互，从已有协议扩展出发可能更省力；
- 真正困难的工作通常不是写协议解析代码，而是设计完整语义并处理边界情况。

关于扩展规模，问答提到当时美国职业棒球大联盟聊天系统由 ejabberd XMPP 服务器支撑，具有数百万并发用户；Google Talk 也以 XMPP 支撑数百万并发用户。它们被用来说明协议和服务模型可以扩展，而不是作为任何部署都能直接复现的性能承诺。

## 问答二：BOSH 服务器怎样转发数据

### BOSH 连接管理器是有状态代理

BOSH 服务不是必须购买的商业服务，可以自行部署。它类似面向 XMPP 的 Web 代理：

1. 浏览器的 HTTP 请求到达 BOSH 连接管理器；
2. 连接管理器与 XMPP 服务器建立并保持一条双向 TCP 连接；
3. 它在 HTTP 长轮询与 TCP 上的 stanza 流之间转换；
4. XMPP 数据返回时，管理器利用正在等待的 HTTP 请求把数据送回浏览器。

在线路上，BOSH 使用 `<body>` 元素作为包装。连接管理器收到 XML 后，会检查包装中的安全和会话信息，防止连接被任意伪造；随后取出 `<body>` 内的 stanza，通过 TCP 连接转发给 XMPP 服务器。反方向则把服务器返回的数据放入 BOSH 响应。

因此，`<body>` 只是 BOSH 信封，业务协议仍然位于信封内部。浏览器不必直接管理 XMPP TCP 流，服务器也不必把每个 HTTP 请求都理解成独立无状态会话。

### “Synchronous”不等于同步 AJAX API

有人根据 BOSH 名称中的 Synchronous，询问 XHR 是否变成同步请求。答案是否定的：浏览器仍使用异步 AJAX。

长轮询在“请求保持打开、等待服务器响应”这一层面上带有同步等待的外观，但 Strophe.js 把整个过程包装成完全异步的 API。开发者注册 stanza 事件处理器，匹配的消息到达后触发回调，无须用阻塞式代码等待每个响应。

## 问答三：同源、反向代理与本地开发

### 为什么通常需要反向代理

受浏览器同源策略限制，通常要把 BOSH 连接管理器反向代理到应用自身的 URL 之下，也就是与 `index.html` 或应用页面相同的站点来源。

课程中的部署方式是由 Nginx 提供静态内容，同时把相应路径反向代理到 BOSH 服务。ChessPark 还有 Django 应用，因此静态服务、应用后端和 BOSH 路径需要共同纳入站点配置。

当时也可以借助基于 Flash 的跨域 XHR 方案，在保留类似 XMLHttpRequest API 的同时使用 Flash 的跨域能力。这属于课程时代解决跨域限制的一种补充方式。

Comet 有类似部署需求。CometD 的角色可类比 BOSH 连接管理器：把浏览器传入的 HTTP 数据转换为服务器端更有状态的通信。

### 本地不必运行完整 XMPP 服务器

如果使用独立于 XMPP 服务器的连接管理器，本地开发时不一定还要启动一台 XMPP 服务器。独立管理器能够连接远程 XMPP 服务，课程中的演示就从本机连接到了 Gmail。

讲师的本地工具会：

- 通过 HTTP 提供当前目录中的应用文件；
- 读取一个小型文本配置；
- 根据配置设置反向代理及 BOSH 路径；
- 在开发期间启动一个短期本地 HTTP 服务。

生产部署通常再由 Nginx 反向代理 BOSH 并提供静态文件；ChessPark 则同时运行 Django 应用。课程团队使用的独立 BOSH 服务器名为 **Punjab**，与 Strophe.js、开源的 Speek 示例一样，当时都公开了源码。

这套分离方式让前端开发、BOSH 接入和实际 XMPP 服务可以位于不同机器，同时保留清晰的调试路径。

## 问答四：内置 BOSH 与独立 BOSH 的取舍

课程指出，当时多数 Jabber/XMPP 服务器都带有自己的 BOSH 服务。选择内置还是独立连接管理器，需要权衡序列化开销和连接范围。

### XMPP 服务器内置 BOSH

优点是少一层序列化。XML 进入服务器后，可以在服务器内部传递，直到返回浏览器时再序列化，不需要先经过一个独立管理器再转为另一段 TCP 数据。

代价是连接范围通常受限于这台服务器。把 BOSH URL 切换到某台 ejabberd 服务器后，客户端可以连接该服务器，却不能因此任意连接 Gmail 等远程 XMPP 服务。

### 独立 BOSH 连接管理器

独立管理器多了一步转换：数据先序列化到 BOSH 连接，再由管理器序列化到通往 XMPP 服务器的 TCP 连接。因此开销更高。

但它能够连接不同的 XMPP 服务器，更适合需要开放联邦用户登录的应用。Speek 就属于这种情况：它希望用户使用 Gmail 凭据登录并访问自己的 Google Talk 内容，而不是被迫注册一个 Speek 专用账号。

相反，Drop.io、Yammer 这类服务可以使用匿名 XMPP 连接，再在应用层完成自己的身份认证，不一定需要让用户连接任意外部 XMPP 账号。应采用哪种方式，取决于是否需要联邦身份，而不只是取决于哪条数据路径少一次序列化。

## 问答五：stanza 粒度与批量发送

BOSH 虽然异步传输，却不会把半个 stanza 当成完整消息交给应用：

- 可以在一次通信中包含多个 stanza；
- 只能发送完整 stanza；
- BOSH 连接管理器也只向客户端交付完整 stanza，不交付 stanza 的局部片段。

Strophe.js 还提供发送排队能力。连接启动时，多个初始化代码片段可能同时产生大量数据。客户端可以先暂停实际发送，把这些 stanza 排队，待初始化阶段结束后恢复发送，把它们合并在一次请求中。这样既保留各模块独立生成消息的方式，也减少启动阶段的请求数量。

因此，“流式 XMPP”并不意味着浏览器 API 必须处理任意 XML 字符碎片。BOSH 在传输边界上保持了 stanza 的完整性，Strophe.js 又在事件层面把完整消息交给应用。

## XML 与 JSON：课程中的扩展性比较

问答最后讨论了能否改用 JSON。讲师的观点并不是 JSON 完全不能扩展，而是 XML 命名空间为 XMPP 提供了非常直接的增量扩展方式：

- 可以给属性增加命名空间；
- 可以在任意元素下加入带命名空间的子元素；
- 原有 `body` 等标准元素仍保持原义；
- 不理解扩展的服务器可以忽略其语义，只把数据转发给最终客户端。

例如，标准聊天正文可以继续使用不带扩展命名空间的 `body`；棋步则使用 `move` 元素，并配上类似 `chesspark/move` 的专用命名空间。棋步内部可以放业务需要的数据，中间服务器即使不理解棋步，也无须阻止消息通过。

若用 JSON 达到同等通用扩展能力，就需要设计更复杂、统一的扩展格式。讲师特别指出，JSON 数组不像 XML 元素那样能通过带命名空间的子节点就地扩展；实现时可能必须更多使用对象而减少字面量，才能在各层保留扩展位置。这样会损失 JSON 一部分简单性。课程由此解释为什么 XMPP 虽然冗长，却仍选择 XML：命名空间不仅改变语法，还决定了不同组织能够在不破坏基础协议的情况下增加语义。

这一比较应放在 XMPP 的联邦路由和扩展生态中理解。它并不意味着所有实时应用都必须选择 XML，而是提醒设计者：替换消息格式时，还要同时替换扩展约束、版本协商和中间节点处理方式。

## 小结

本章从实时 Web 的双向低延迟需求出发，完整走通了一条浏览器 XMPP 技术路线。

XMPP 通过客户端—服务器和服务器—服务器协议形成联邦，以 JID 区分用户和连接，并在两个持续生成的 XML 文档流中交换 `message`、`presence` 与 `iq`。其中，消息承载文本或任意业务数据，presence 形成有方向的状态订阅，IQ 通过唯一 `id` 配对请求与成功、错误响应。

浏览器无法直接照搬桌面 TCP 客户端，因此 BOSH 用长轮询和连接管理器把 HTTP 请求映射到有状态 XMPP 会话。Strophe.js 隐藏了请求轮换和大量 XHR 错误处理，向开发者提供连接回调、DOM stanza、事件处理器和链式构建器。服务发现、ChessPark、PubSub 插件与 identi.ca 示例进一步展示了从连接建立到业务扩展的完整实现方式。

部署时还必须考虑同源反向代理、本地开发、内置与独立 BOSH 的序列化和联邦取舍、完整 stanza 交付以及启动批量发送。Comet、XML 与 JSON 的比较则说明，实时通信方案的选择不能只看传输是否低延迟，还要看上层协议已经定义了多少语义、能否扩展，以及中间节点如何处理不理解的数据。
