# 第 72 章 testingRTC 简介

testingRTC 是 testRTC 面向 WebRTC 测试与验证提供的浏览器自动化工具。它通过真实浏览器、地理位置和网络配置模拟用户活动，并将测试结果与 WebRTC 指标集中展示，适用于功能验证、性能评估、容量规划和后端基础设施检查。

## WebRTC 测试的主要挑战

### 浏览器与技术栈持续变化

WebRTC 应用运行于浏览器之上，开发者并不完全控制整个技术栈。新浏览器、新功能、接口弃用和破坏性变化都可能影响应用，因此需要持续而充分地验证，而不是只在某个版本中测试一次。

### 测试本身消耗大量资源

WebRTC 测试需要较多 CPU、内存和网络资源。分配测试机器与服务器时，必须把这些消耗纳入容量考虑，否则测试环境自身就可能影响结果。

### 媒体质量对网络敏感

丢包、比特率、时延和抖动的变化都可能影响用户媒体质量，因此测试需要覆盖不同网络条件，不能只验证理想网络中的功能是否可用。

### 多参与者需要动态同步

一次 WebRTC 会话通常需要两个或更多参与者。自动化测试不仅要控制多个浏览器，还要同步它们何时加入会话，并在测试过程中动态交换数据，例如测试所用的 URL。这些都是普通单页面自动化不会自然解决的问题。

## 适用问题与测试类型

课程列出的典型问题包括：

- 新的 Chrome 版本支持某种编解码器或功能后，如何验证它在自有应用中的表现；
- 不同地理位置的用户能否获得良好体验，是否会被引导到错误的服务器；
- 呼叫中心来电者多于坐席时，用户是否能在队列中得到正确处理；
- 同一会话能否容纳 500 个并发用户，并维持所需质量；
- 这些负载能否运行在同一批服务器上，容量应如何规划。

为回答这些问题，testingRTC 使用真实地理位置、真实浏览器和真实网络配置来模拟用户行为。课程提到的测试用途包括功能测试、负载测试、压力测试、规模测试、持续集成和性能测试，并支持桌面与移动网络。

## 测试配置与执行流程

### 以探针组织浏览器

testingRTC 用“探针”（probe）表示一个自动化浏览器。课程示例使用两个探针，让两个浏览器加入同一个 AppRTC 会话。测试既可以并行运行多个会话，也可以组织成一个较大的会话。

脚本控制面板中可设置被测服务 URL，并可使用 Webhook 收集数据，此外还有相应运行选项。配置完成后，平台分配机器、执行测试并收集结果。

### 使用 Nightwatch.js 编写自动化脚本

课程示例采用 Nightwatch.js，在 Selenium 之上进行浏览器自动化。Nightwatch.js 使用 JavaScript，是开源的浏览器自动化方案。testRTC 在此基础上加入了自己的命令，例如：

- `rtcSetTestExpectation`：检查特定指标是否符合预期；
- `rtcSetSessionValue`：在同一测试的浏览器之间发送消息和数据；
- `rtcWaitForSessionValue`：等待并读取另一浏览器在会话中共享的值，例如房间 URL。

这些扩展把浏览器操作、参与者同步和 WebRTC 指标断言放进同一个测试流程。

### 一个跨地区测试示例

演示选择美国西部和美国东部两个地点的 Chrome Stable，并为两端使用不同媒体文件。运行后，testingRTC 负责分配测试机器、启动浏览器、执行脚本，最后汇总结果。这个过程对应的是跨地区的双浏览器会话，而不是在同一台机器上模拟两个页面。

## 测试结果与分析能力

### 从总体指标到单个探针

结果页首先提供高层摘要，并可通过图表查看整个测试的视频平均比特率。视图可以切换到音频，例如检查抖动，也可以回到视频并按探针查看平均比特率。

测试人员能够继续深入到任意用户。课程强调，同样的查看方式也适用于包含一千个浏览器的大规模测试，不因探针数量增加而改变分析路径。

单个探针的视图包含该浏览器在整个测试中的平均指标，并提供以下信息：

- 通知；
- 测试期间截取的屏幕截图；
- 测试机器的性能指标；
- 收集到的日志。

### 媒体与网络图表

展开结果后，还可以查看更详细的比特率、数据包、丢包、抖动和往返时间信息；视频测试还包括帧率。测试人员因此可以把质量变化与具体探针及其运行环境联系起来。

### 高级 WebRTC 分析

需要更深入的数据时，可进入高级 WebRTC 分析。课程展示的信息范围包括：

- 从 `getUserMedia` 到对等连接配置的细节；
- 状态机；
- ICE 候选对，其中实际选中的候选对以绿色标记；
- 记录 API 调用的事件日志；
- 其他可展开并用于深入分析的指标。

这一层用于回答“连接具体怎样建立、调用了哪些 API、最终选择了哪条候选路径”等问题，而不仅是给出一个平均质量分数。

## 适用场景

testingRTC 适合需要可重复浏览器自动化流程的 WebRTC 团队：既可以在新版本浏览器或新功能出现时验证应用，也可以通过多探针、多会话和大规模测试检查性能、容量与后端架构。其价值不只在于自动点击页面，还在于同步真实浏览器参与者，并把脚本预期、机器日志和 WebRTC 深度指标放在同一套结果中。

## 小结

testingRTC 针对 WebRTC 的浏览器变化、资源消耗、网络敏感性和多方同步难题，提供基于真实浏览器与地理位置的自动化测试。测试由 Nightwatch.js 脚本和 testRTC 扩展命令驱动，结果既可按探针查看摘要、日志和媒体质量，也可深入 ICE 候选对、API 调用与连接配置，尤其适合性能、容量和后端基础设施验证。
